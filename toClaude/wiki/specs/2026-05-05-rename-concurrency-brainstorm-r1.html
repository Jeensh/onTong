1. 현황 분석 (코드에서 확인한 사실)

참조 그래프는 4 개 레이어가 동시에 존재. 현재 rename / move 가 각각을 어떻게 처리하는지 정리.

레이어위치rename 시move 시folder move 시
L1. Frontmatter supersedes / superseded_by / related[] YAML 헤더 부분 raw.replace(old, new) 부분 동일 없음
L2. Body wikilink [[stem]] 본문 없음 stem 변경 → 깨짐 우연히 OK stem 으로 resolve 우연히 OK
L3. Body markdown link [t](path.md) 본문 없음 추출 자체 안 함 없음 없음
L4. Image ref ![alt](assets/x.png) 본문 ImageRegistry 가 filename 기반으로 ref count 만 추적 (path 무관)
L5. ChromaDB chunk metadata file_path 벡터 DB 신규 path 로 BG 재인덱스되지만, 다른 문서의 chunk 본문에 박힌 old path 는 그대로

핵심 코드 위치:

  • backend/application/wiki/wiki_service.py:627-685 — move_file + _update_references (naive raw.replace)
  • backend/application/wiki/wiki_service.py:697-718 — move_folder (인바운드 참조 업데이트 0 줄, 전체 재인덱싱만)
  • backend/application/wiki/wiki_search.py:31-55 — wikilink 는 stem 기반 backlink 만 빌드 (재작성 로직 없음)
  • backend/application/lock_service.py — TTL 락 서비스. 편집 보호용이고, rename/move 는 락 안 걸음
  • backend/api/wiki.py:222-228 — PATCH /file/{path} 핸들러. ACL require_write 만 체크, 락 검사 없음
  • backend/application/metadata/metadata_index.py:36-37 — threading.Lock + 인메모리 캐시 _data → 멀티 워커 시 stale
  • backend/infrastructure/events/event_bus.py — SSE 단일 프로세스 broadcast (워커 간 fan-out 없음)

배포 가정: HANDOFF.md 기준으로 현재는 단일 uvicorn (포트 8001, --reload off). 100K+ 문서 가정은 메모리에 명시.

2. 발견된 문제 가설 (16 건)
치명: 데이터/링크 손실, 보안 중요: 사용자 체감 버그, 성능 일반: UX, 운영성
  • H1Body wikilink 부패 (rename)
    파일명 (stem) 이 바뀌면 모든 문서의 [[old-stem]] 가 깨진 링크가 됨. 현재 코드는 본문을 건드리지 않음.
  • H2Body markdown link 부패 (rename + move)
    [보기](docs/foo.md) 형식은 추출조차 안 됨. rename/move 둘 다 → 404.
  • H3Wikilink stem 충돌
    stem-only resolve 라 서로 다른 폴더의 동일 stem 이 있으면 backlink 가 잘못된 문서를 가리킬 수 있음.
  • H4Folder move = inbound 참조 0 업데이트
    move_folder는 _update_references 호출 없음. 폴더 이름 바꾸면 모든 inbound 참조가 깨짐. 전체 reindex 도 본문 링크는 안 고침.
  • H5Naive string replace 오작동
    raw.replace("a/b.md", "c/d.md") 가 frontmatter 외 본문/주석/예제 코드 블록까지 건드림. 또 "a/b.md"가 "a/b.md.backup"의 부분 문자열이면 의도치 않은 매칭.
  • H6Race A — rename + 동시 편집
    User A: PUT /file/old (저장), User B: PATCH /file/old → new (rename). 결과: 저장이 old 에 떨어진 뒤 rename 이 빈 파일을 옮길 수도, 또는 저장이 새 파일을 덮어쓸 수도 있음.
  • H7Race B — 동일 target 충돌
    A: X→Y, B: Z→Y 동시. Path.rename() 자체는 atomic 이지만 앱 레이어에 uniqueness 사전 체크가 없음 → 마지막 승자가 덮어씀.
  • H8Race C — 인덱싱 중 rename
    Save → BG _bg_index(old_path) 시작 → 사용자가 rename. BG 작업이 old_path 로 chunk upsert 후, rename 핸들러가 old 를 지움 → ghost chunk 잔존 또는 부분 인덱스.
  • H9Race D — inbound 업데이트 비원자성
    filesystem rename 성공 후 _update_references 진행 중 크래시 / 타임아웃 → 일부 inbound 만 업데이트, 일부는 stale. 재시도 큐 / 로그 없음.
  • H10멀티 워커 캐시 드리프트
    gunicorn workers ≥ 2 가정 시 BM25 in-memory, MetadataIndex._data, FileHashStore, IndexStatus._pending 모두 워커별 사본. SSE 도 워커 간 fan-out 안 됨 → 일부 사용자만 신규 트리.
  • H11감사 / 복원 흔적 없음
    누가 언제 어떤 문서를 어디로 옮겼는지 기록이 없어 잘못된 rename 후 추적/복원이 어려움.
  • H12Dry-run / undo 부재
    rename 직전 영향도 (몇 개 inbound, 어떤 사용자 락) 미리보기 / 직후 undo 가 없음.
  • H13Hot doc 성능
    100K 코퍼스에서 인기 문서가 1만 inbound 가지면 sequential write × 1만 = 분 단위. 그 동안 다른 작업 블록 / 락 만료 / 재시도 폭주.
  • H14ACL 변경창 누출
    private 폴더 → public 폴더로 move 시 chunk metadata 의 access_read 가 reindex 완료 전까지 stale. 이 사이 검색에 노출.
  • H15락은 있지만 rename 이 무시
    B 가 편집 락 보유 중인 문서를 A 가 rename 가능. 편집자 입장에서 갑자기 파일이 사라짐.
  • H16레이트 제한 / 쓰로틀 없음
    짧은 시간에 rename 폭증 → 인덱싱 / SSE / 재참조 쓰기 쓰나미. 데모 중 누가 실수로 폴더 5번 이동하면 분 단위 멈춤 가능.
