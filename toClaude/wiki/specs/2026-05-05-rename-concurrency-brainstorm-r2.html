⚡ 함의 — 위 답변 조합이 강제하는 것

"수만 동시사용자 × 멀티 호스트 × 100K 문서 × pessimistic 락" 의 조합은 사실상 v2 인프라 재배치를 요구합니다. 현재 코드의 다음 부분이 외부화되어야 정합성 유지 가능:

  • 락 — InMemoryLockBackend 폐기, Redis 락만 사용 (이미 RedisLockBackend 존재 → 활성화)
  • SSE 이벤트 fan-out — event_bus 단일 프로세스 → Redis Pub/Sub 으로 호스트 간 broadcast
  • MetadataIndex — .ontong/metadata_index.json 파일 캐시 → Redis hash + invalidation
  • FileHashStore / IndexStatus — Redis 또는 외부 KV
  • BM25 — in-memory → 외부 검색엔진 (Elasticsearch / Meilisearch / OpenSearch) 또는 Postgres FTS
  • 파일 저장소 — POSIX rename 은 단일 호스트만 atomic. 멀티 호스트면 공유 FS (NFS) 또는 객체 스토리지 (S3 + 메타데이터 DB) 로 이동
  • 백그라운드 작업 — asyncio.create_task → 외부 큐 (Arq/Celery/Dramatiq)
  • 스냅샷 — 신규 컴포넌트, 객체 스토리지나 Postgres LOB

Phase 0 (인프라 재배치) 가 다른 모든 작업의 선행 조건이 됩니다. 결정 D 의 phase 그래프에 반영함.

결정 1 · 참조 패치 정확도

rename 시 본문/메타의 참조를 어떻게 정확히 찾고 바꿀까?

현재의 raw.replace(old, new) 는 부분 매칭 / 코드블록 / 우연 매칭 위험. 정확도 모델을 골라야 모든 후속 단계가 안전.

결정 2 · 분산 락 모델

수만 동시사용자에서 rename 의 락 fan-out 을 어떻게 안전하면서 빠르게?

pessimistic 락이지만, 인기 문서 1 개에 inbound 1 만이면 1 만 락을 쥐는 건 비현실. 어떻게 작은 단위로 쪼갤까?

결정 3 · 저장 시 충돌 + 스냅샷

load 한 버전과 저장 직전 버전이 다르면 어떻게? 스냅샷 형태는?

라운드 1 추가 요구. 자동 저장이 없으니 사용자가 "저장" 누를 때까지 임의로 길어질 수 있음.

결정 4 · 인프라 스택

멀티 호스트 / 수만 사용자를 위한 스택 — 어디까지 도입?

기존 Redis 옵션 코드는 이미 있음. 추가 도입 항목을 묶어서 결정.

결정 5 · 작업 순서 (Phase 의존성)

"전부 다 충돌 안 나게" — 추천 순서. 동의 / 수정 표시.

화살표(→) = 의존. 병렬 = 같은 단계 내 병렬 가능. 각 phase 끝에 데모 가능 산출물.

Phase 0 인프라 재배치 선행 0
  • Redis 락/Pub-Sub 활성화 + InMemoryLockBackend 폐기 경로
  • EventBus → Redis Pub/Sub adapter (워커 간 SSE fan-out)
  • MetadataIndex/FileHashStore/IndexStatus → Redis hash 백엔드
  • Arq 워커 도입 + Postgres 스키마 (refs, snapshots, versions, audit)
Phase 1 정확한 참조 추출 + ReferenceIndex 선행 P0
  • ReferenceExtractor — frontmatter YAML + body markdown AST → {target_path, kind, offset}
  • Postgres references 테이블 + 정/역방향 쿼리 API
  • 저장 핫패스에 추출기 wiring + 마이그레이션 (전체 코퍼스 1 회 추출)
  • Broken-link 리포트 (Q8 답) — 같은 인덱스 재활용
Phase 2 OCC + 스냅샷 선행 P0 (P1 과 병렬 가능) 병렬
  • WikiFile 에 version 필드 + load 응답에 ETag 헤더
  • If-Match 검사 → 409 + 3-way diff 페이로드
  • 스냅샷 스토어 (Postgres LOB 시작) + 슬라이딩 N=20
  • 프론트 3-way diff UI
Phase 3 단일 파일 rename/move (정합성 핵심) 선행 P1 + P2
  • 새 RenameOrchestrator — Plan / Execute / Reconcile 3 단계
  • source 락 + collision check + Phase-2-Phase 인바운드 배치 락
  • 본문 정확 패치 (P1 ReferenceIndex 사용) + frontmatter 갱신
  • ChromaDB 본문 path 갱신 (L5) — 영향 chunk 재인덱싱
  • SSE 진행률 + 영향도 미리보기 API
  • 실패 항목 → Arq 재시도 큐 + audit 로그
Phase 4 폴더 / bulk 선행 P3
  • 서브트리 enumeration → P3 의 단일 rename 을 N 회 큐잉
  • 전체 작업 = parent 그룹 단위 정렬, 청크 50
  • 아토믹 dryrun: "이 폴더 이동 시 X 개 inbound 영향, 추정 Y 초"
Phase 5 UX 마감 선행 P3 (P4 와 일부 병렬) 병렬
  • 영향도 미리보기 다이얼로그 + 임계값 confirm
  • 편집 중 rename 경고/차단 (lock_service 통합)
  • 진행률 토스트 + undo 버튼 (5 분 윈도우, 스냅샷 활용)
  • Broken-link 리포트 페이지
Phase 6 스케일 검증 선행 P3~P5
  • 100K 시드 + 동시 50 사용자 시뮬레이션 부하 테스트
  • 성능 회귀 가드 (rename SLA: inbound 100 까지 ≤ 2s, 1000 까지 ≤ 30s)
  • ACL 누출 윈도우 측정 (H14)
