Section 1
위키
자정 작용 가능한 전사 지식 시스템

전사 개인이 로컬(메모장·옵시디언 등)에 따로 쌓아 두던 암묵지를 한 시스템 안으로 통합한다.

같은 목적의 중복 문서들 중 대표 문서를 지정하고, 안 쓰는 문서는 deprecated 처리해 자동으로 정리되는 — 자정 작용 가능한 파일 시스템.

여기에 AI 에이전트를 결합해 문서 접근·관리를 쉽게 한다. 대표 문서 외 필요한 개인 참고 메모도 외부 툴에 흩뿌리지 말고 이 시스템 안에서 처리.
  • 중복 문서 자동 탐지 — 유사도 스캔 + LLM 의미 분석
  • 충돌 해결 4 액션 — 무시 / 버전체인화(대표 지정) / 범위 구분 / 병합
  • 대표 지정 & deprecated 체인 — 순환·자기참조 자동 차단
  • AI 에이전트 문서 관리 — 읽기·검색·편집·작성·충돌 감지·자동 태깅
  • 개인 작업 공간 — 외부 툴 흩뿌림 방지
  • 이미지 내 텍스트 검색 — 설비 명판·도면 + 문의 메일·메신저 대화 캡처 OCR
  • 이미지 중복 자동 통합
  • 통합 검색 — 키워드 + 의미 + 한국어 자연어 조건
  • 권한 제어 — 사용자/그룹별
  • 문서 관계 그래프 — 참조·계보 시각화
 발표 기준 개발 완료. 현재 상태를 최종 상태로 본다.
  • 중복 판정 임계값 튜닝 — 점수만으로는 한계가 있어 LLM 의미 분석을 더해 보완
  • 자정 작용 아이디어 도출 자체 — 선례가 없고, 실 도입 전이라 놓친 부분이 남아 있을 수 있음
  • 다용도 위키의 UI/UX 편의성 설계
  • 문서가 많아져도 사용자 체감 속도를 유지하는 처리 방법 고민
  • 에이전트가 적절히 검색·답변하는 RAG 구조 설계
Section 2
모델링
코드 기반 온톨로지 빌더 툴

Section 3의 세 가지 기능이 동작하려면 코드의 구조·의미·관계를 담은 온톨로지가 먼저 있어야 한다. 문서로 완벽히 관리되지 않고, 여러 개발자가 오랜 기간 손대면서 표준화되기 어려운 Java/Spring 코드베이스에서 이 온톨로지를 사람이 손으로 전부 만들 수는 없다.

Section 2는 이 온톨로지를 자동 추출 + 사람 검증·보완으로 쌓아 갈 수 있게 하는 빌더 툴을 만든다.

초기엔 업무처리기준서(매뉴얼)를 1차 소스로 두고 LLM이 온톨로지로 변환하는 방향을 시도했는데, 검토 결과 "정확한 현행 내용은 코드에 있고, 매뉴얼은 이미 코드와 어긋나 있더라" 가 확인돼 코드를 1차 소스로 두는 방향으로 전환. 지금은 이 방향 위에서 빌더 툴을 만들고 있다.
  • 코드 → 온톨로지 자동 추출 엔진
    • Java/Spring 파서
    • Spring 특수 패턴 7종 분석기
    • 동적 매핑 라이브러리 3종 추적
    • 영향도 그래프 탐색 코어
단, 백엔드 테스트 수준에서 동작하는 단계. 외부 API 노출 전이며, 프론트엔드는 아직 이전 매뉴얼 빌더 UI 상태.
  • 자동 추출 엔진의 API 노출 + 빌더 UI 재설계
  • 자동 추출 결과를 사람이 검증·보완하는 UX
  • 실제 코드베이스 샘플로 E2E 검증
  • Section 3 연구 결과에 맞춘 온톨로지 스키마 보강
  • 방향 자체를 찾는 어려움 — 매뉴얼 1차 빌더로 가 본 뒤에야 "이게 팀 목적이 아니다"가 드러남. 이전에 쌓은 UI/API 상당 부분을 버리고 새로 쌓아야 함
  • Spring 코드는 정적 분석만으로 안 잡히는 패턴이 많음 (의존성 주입·AOP·Reflection·JPA 메서드 파생·이벤트·스케줄러·프로파일) → 각각 전용 분석기를 따로 만듦
  • 동적 매핑 라이브러리 3종 (MapStruct · BeanUtils · SQL) 추적 — 자동 추출 신뢰도 설계가 까다로움
  • 코드 하나가 여러 비즈니스 개념에 걸쳐 있음 — 1:N 매핑 모델 재설계 필요
  • 자동 추출 결과를 사람이 검증·보완하는 UI 설계 (아직 구상 단계)
  • 근본 난제 — 실제 소스로부터 Section 3의 3대 기능을 제대로 동작시킬 온톨로지 구조 자체를 설계하는 것. 지금도 풀어 나가는 중.
Section 3
시뮬레이션
온톨로지 기반 3대 기능 에이전트

Section 2에서 만든 코드 기반 온톨로지를 활용해, 코드를 쉽게 이해하고 안전하게 바꿀 수 있게 돕는 세 가지 기능을 제공한다.

  1. 비즈니스 용어로 대상 코드 탐색 + 영향도 분석"'폭가변 계산 로직' 건드리려는데 어느 코드인지, 이 변경이 어디까지 영향 가는지" 한 번에 풀기
  2. 코드 수정 후 시뮬레이션수정된 로직이 전체 흐름에서 어떻게 동작하는지 실제로 돌려 봄
  3. 테스트 데이터 자동 생성그 변경을 검증할 입력값·기대값을 자동으로 만듦
 현재 완성된 구성물 없음. 현 Slab 도메인 에이전트 샘플은 목표 기능의 구현체가 아니라, "어떤 온톨로지 구조가 있어야 에이전트가 제대로 동작할까?" 를 역으로 탐색하기 위한 연구 도구.
  1. 각 기능의 에이전트 아키텍처 설계
  2. 각 기능의 UI/UX 설계

연구 단계 난제 상당 부분은 Section 2와 공유 — 역방향 설계, 빌더와의 양방향 검토 등은 두 섹션이 함께 풀어 나가는 중.

Section 3 고유의 어려움 — 온톨로지가 준비됐다고 쳐도 3가지 기능을 UI/UX로 어떻게 풀지:

  • 탐색 + 영향도 — 어느 코드인지 + 어디까지 영향 가는지를 한 화면에 어떻게 담아 사용자가 빠르게 판단할 수 있게 할지
  • 시뮬레이션 — 결과를 어떤 형태로 보여줘야 사용자가 실제 결정에 쓸 수 있는지
  • 테스트 데이터 생성 — 어떻게 제공해야 현장에서 신뢰하고 쓸 수 있는지

Section 1 — 위키 기술 상세

핵심 구성 기술

  • 하이브리드 검색 : BM25 + 벡터 임베딩 + Cross-encoder 재정렬
  • 이미지 OCR : EasyOCR (한국어+영어), 비동기 백필 + 재인덱싱
  • 벡터 DB : ChromaDB (access_scope 메타데이터로 ACL 사전 필터)
  • 이미지 중복 제거 : SHA-256 해시 + 문서별 ref counting
  • 중복 문서 감지 : 유사도 임계값 스캔 → LLM 의미 분석(ConflictCheckSkill / /api/conflict/analyze-pair)
  • 대표 지정·deprecated : supersedes / superseded_by 체인 + lineage_validator 로 순환·자기참조 차단
  • 에이전트 스킬 : wiki_read · wiki_search · wiki_edit · wiki_write · conflict_check · auto_tag
Section 2 — 모델링(빌더 툴) 기술 상세

방향 전환 배경

  • 이전 : 매뉴얼 1차 빌더 — 기준서를 LLM으로 YAML 온톨로지화
  • 현재 : 코드 1차 빌더 — 기준서는 검증 파트너로 강등, 코드가 1차 소스
  • 이전 시도 산출물 중 매뉴얼 빌더 UI·관련 API는 deprecated 처리 예정. 코드 분석 인프라는 복원·확장하여 재사용.

자동 추출 엔진 구성 요소

  • 파서 플러그인 프로토콜 (EntityKind 17 / RelationKind 18)
  • java_parser + graph_writer
  • Spring 특수 패턴 7 분석기 — DI · AOP · HTTP · Events · Scheduled · Profile · Reflection (JPA는 차후)
  • 동적 매핑 3 분석기 — MapStruct · BeanUtils · NativeSQL + CrossFileEnricher
  • Reflection Literal Resolver + Runtime Collector Protocol
  • 영향도 BFS 엔진 + 3-mode 필터 (SAFE · OBSERVED · POTENTIAL) + 자율 축소 + 타임아웃
  • 역매핑 스텁 (direction=outgoing)

남은 공사

  • REST API 노출 (신규 엔진)
  • 빌더 UI 재설계 (매뉴얼 빌더 UI 치환)
  • 사람 검증·보완 UX (미착수)
  • 실 코드베이스 sample repo 수령 후 E2E
  • 비즈니스 개념 브릿지(Round 2) · 기준서 갭 탐지(Round 3)
