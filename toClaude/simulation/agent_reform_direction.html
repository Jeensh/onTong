멀티턴 agent 개혁 방향 — 어떻게 진짜 유용해질까?

4 페르소나 실사용 + 데이터 vs agent 활용 감사 + Phase 12 Activation 경험을 종합한 architecture 방향 제안. "재배선" 으로 50% 해결, 나머지 50% 는 agent 형태 자체 의 변화 필요.

CORE THESIS
검색-실행 챗봇  →  근거 기반 대화형 워크스페이스
  • 현 agent = 자연어 → 후보 → 선택 → 시뮬/영향 의 선형 파이프. 사용자의 모호한·점진적 사용과 맞지 않음.
  • 진짜 유용 agent = 도구 카탈로그 에서 적절한 tool 을 골라 답하고, 모든 응답에 근거 (rule + code + anchor) 를 노출하며, 모호하면 역질문 으로 좁힌다.
  • ontology 그래프는 이미 풍부 — 새 데이터 0, agent 형태 만 바꾸면 됨.
목차: 진단 5 원칙 새 아키텍처 도구 카탈로그 9 페르소나 시연 Phase 13~15 결정

1. 진단 — 현 agent 의 3 본질적 한계

한계 현 동작 왜 본질적 문제인가
L1. 좁은 intent simulate / impact / ambiguous 3 종 강제. 운영 현실의 자연어 의도 (어디서? 뭐함? X면 Y? 비슷한 것? 둘러보기) 가 5+종 — 3종으론 못 담음. ambiguous 가 사실상 "포기" 응답.
L2. 선형 흐름 turn 1 stub → turn 2 cand → turn 3 bundle → turn 4 exec. 매 단계 분기. 사용자는 탐색적: 후보 보고 "이거 다른 거랑 비교", "이 메서드의 caller 보고싶다", "관련 룰?" 같이 옆으로 가고 싶음. 선형 파이프에선 항상 새 session.
L3. 단일 표현 Gate I 카드 = candidates 5 행 + Gate II = Java/Python/fixture + Gate III = sim 결과 or affected_methods. 김PM 은 한글 룰 + 비즈니스 효과를, 신입은 코드 본문 + caller 를, 시니어는 영향 표를 원함. 같은 query 에 4 페르소나 4 표현 필요한데 1 형태로 강요.

2. 다섯 가지 원칙 — 어떤 가치로 reform 하나

P1

Evidence-first — 모든 응답이 근거에 묶임

주장만 하는 응답 금지. "X 가 Y" 라고 답할 때 code line + business_rule + anchor_binding 셋 중 최소 하나가 동시에 surface. Q5 비전 ("확실한 근거 / 빠진 대로") 의 운영 강화.

SQLite: business_rules.statement + code_methods.body_text + anchor_bindings.target_slot 데이터 활용. 데이터 이미 적재됨.
P2

Active dialog — ambiguous 는 시작점, 끝점 아님

모호한 입력 시 dead-end 422 대신 역질문: "두께 룰을 보고 싶으세요, 영향을 알고 싶으세요, 시뮬해 보고 싶으세요?". 0-cand 시 동의어 추천. 잘못 고른 후보도 같은 session 내 복구.

State machine: ambiguous + 같은 session 으로 재분류 path 신설. follow-up suggestion 버튼 surface.
P3

Tool-use ReAct — gate fixed → tools flexible

intent 3 종 → 도구 9 종 의 카탈로그. LLM 이 intent 분류 대신 적절한 tool 선택. 같은 자연어가 query 안의 동사 / 명사 / 의문문 형태에 따라 다른 tool 로 라우팅.

LLM prompt: "user 의도에 맞는 tool 골라 + 인자 채워" function-call 패턴. 결과 → tool 실행 → 응답 합성.
P4

Multi-modal output — 페르소나에 맞는 표현

도메인 자연어 (PM) / 코드 본문 (신입) / 영향 표 (시니어) / boundary verdict (QA). 같은 데이터, 다른 view. 사용자 페르소나 선택 또는 query 패턴 자동 인식.

응답 schema = base evidence + view-specific rendering. frontend 가 tab/toggle 로 view 전환.
P5

Session memory — 누적 컨텍스트

같은 session 안에서 이전 결정 / 후보 / 룰 검색 결과를 누적. "그 메서드의 caller 도 보여줘" 같은 후속이 같은 컨텍스트로 동작. Phase 11 Session History 가 인프라 — 활용만 안 되고 있음.

section3_decision_log 이미 누적 저장 중. ReAct loop 가 이전 turn 의 payload 를 LLM 컨텍스트로 주입.

6. 로드맵 — Phase 13 → 14 → 15

완료된 Phase 12 Activation 위에 쌓는 3 phase. 각 phase 1 묶음이고 사이에 사용자 체감 검증 가능.

Phase 13

ReAct + Tool catalog 인프라

intent classifier 3종 → tool selector 9종 으로 LLM 역할 전환. 가장 큰 변화이자 가장 큰 임팩트.
  • LLM prompt 재설계 — "intent 분류" → "tool 선택 + arg 채움" (OpenAI function call 또는 structured output)
  • 9 tool wrapper 구현 — locate / explain / hypothesis / search_term / search_rule / browse_domain / compare_diff 신설 (simulate / impact 는 기존)
  • tool 결과 → Provenance 통합 응답 schema 신설 (현재 GateTarget / GateBundle / GateExecutedSimulation / GateExecutedImpact 4 종을 단일 ToolResult 로 통합 또는 union 확장)
  • state machine 단순화 — 3 게이트 fixed → "tool call → result → 사용자 후속 / 종료"
  • Ambiguous 복구 — 같은 session 내 follow-up 질문 가능 + tool 선택 후보 button surface
예상 비용: backend 5~7 파일 (intent.py / gate_*.py 통째 재설계 / tool wrapper 신규) · frontend 3~5 컴포넌트 (Multi-tool 응답 카드 / follow-up button). 2 phase 분량.
Phase 14

Evidence grounding — anchor + rule 자동 inject

모든 응답에 근거 자동 첨부. Q5 "확실한 근거" 의 운영 완성.
  • anchor_bindings 163 행 활용 — synthesize_fixtures 에 anchor 의 atomic slot 별 boundary value 자동 inject (QA 페르소나 핵심 use case)
  • business_rules 자연어 statement → 모든 응답 evidence 에 (Phase 12 가 Gate I 만, 이걸 모든 tool 응답에 확장)
  • caller graph match_kind / strength 시각화 (5단계 색상 + min_strength slider 노출)
  • code_method.body_text 의 한글 주석 추출 → 검색 score boost + display
예상 비용: backend 4 파일 (synthesize_fixtures / evidence composer) · frontend 2 컴포넌트 (evidence side panel). 1 phase 분량.
Phase 15

Active dialog + Multi-modal view

사용자 페르소나 / query 패턴에 맞는 표현 + 적극 역질문 시스템.
  • 0-cand 시 동의어 추천 (KoreanTermResolver score 활용) + "이 키워드도 시도해보세요" UI
  • Ambiguous 시 LLM 이 명시적 역질문 ("두께 룰을 보고싶으세요, 영향을 알고싶으세요, 시뮬해보고 싶으세요?")
  • 응답 카드에 view 토글 (Domain / Code / Impact / Verdict) — 같은 데이터 다른 표현
  • Session memory — 이전 turn 의 후보 / 결과를 LLM 컨텍스트 + UI breadcrumb 으로 노출
  • "이 메서드의 caller 도 보여줘" 같은 후속 query 가 같은 컨텍스트로 처리
예상 비용: backend 3 파일 (LLM 보조 질문 생성 + memory 컨텍스트) · frontend 4 컴포넌트 (view 토글 / follow-up UI / breadcrumb / suggestion chips). 1.5 phase 분량.

7. 결정 — 어디부터?

가장 큰 임팩트 = Phase 13 ReAct + Tool catalog. 가장 빠른 PoC = locate / explain tool 만 먼저 신설 (intent 3 종은 유지하면서 locate/explain 만 추가).

방안 A — 가장 빠른 PoC (1~2 일)

intent 3 종 그대로 + LLM prompt 에 "if 'where' / 'what is' / '뭐함' → locate/explain" 케이스만 추가. 새 tool 응답 schema 1 종 신설. 박주니어 페르소나 즉시 해결.

방안 B — Phase 13 풀 ReAct (2 phase)

intent classifier → tool selector 전체 전환. 9 tool 카탈로그. 응답 schema 통합. 4 페르소나 모두 동시 개선이지만 backend 통째 재설계.

방안 C — 점진적 (Phase 13a → 13b → 13c)

먼저 locate/explain 만 (방안 A) → 사용자 검증 → search_term/search_rule 추가 → hypothesis 추가. 각 단계 사용자 체감 후 다음. 리스크 최소, 진행 안정.
