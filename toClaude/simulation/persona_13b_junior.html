2. 평가 (박주니어 입장)

이전보다 도움이 되는가? — Yes, 부분적으로

  • 이전엔 "validateOrder 어디 있어?" 풀 문장을 BM25 토큰화 → "어디"/"있어" 노이즈가 점수 흔들었음. 지금은 LLM이 validateOrder만 깔끔하게 뽑아 ontology 검색에 넘김 → provenance도 깔끔.
  • intent 라벨 (locate/explain/impact) 이 정확히 분기됨 → 박주니어가 "이 응답이 위치 답인지 영향도 답인지" 헷갈리지 않음.
  • Q1 turn 3에서 body_text + file_path + linked_term 풀 surface → "이 코드 안 열어봐도 IDE 열듯 본문이 보임".

영문 → 도메인 다리 (suggestion) 가 보이나? — No

  • Q2 checkInventory는 0-cand인데 suggestions []. 코드는 정상 동작 — slab-design repo aliases에 "check"/"Inventory"가 안 들어있어서 매칭 안 됨.
  • 즉 도메인이 정말 모르는 영문 식별자일수록 다리가 안 생긴다. "엣징" 같이 한국어로 물으면 alias hit이 나오겠지만, 박주니어는 한국어 도메인어 자체를 모름 → bridge가 catch-22.

3. 남은 마찰

  • sim_v2 fallback 품질: validateOrder/OrderService ontology miss 시 sim_v2가 무관한 SdFinalLengthRange/Width/FirstWeight를 동률 score 29로 surface. 근거가 명시 안 됨 → 박주니어는 왜 추천됐는지 모름.
  • confidence 신호 부재: ontology=0, sim_v2=0.9인데 5개 후보 confidence 표면이 없어 "이건 그냥 그럴듯한 추측" 인지 알 수 없음.
  • suggestions 의 영문 fallback: 0-cand + alias 매칭 실패 시 "혹시 이런 영문 식별자?" 류 fuzzy 제안 (FQN substring, method name similarity) 없음 — Phase 13b 의 진짜 빈자리.
결론 — 영문 식별자 분류·추출은 크게 개선. 도메인 무지 신입을 위한 영문→한국어 다리는 repo 어휘에 의존해서 진짜 모르는 식별자엔 도움 못 줌. 다음 단계로 (a) sim_v2 fallback 후보에 confidence cap + reason 노출, (b) suggestions에 method-name fuzzy 후보 보강을 제안.
