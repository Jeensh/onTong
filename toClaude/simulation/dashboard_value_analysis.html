1. 현재 상태 — 짧게 짚고 가기

Section 3 의 "대시보드" 탭은 이미 존재합니다. 다만 보여주는 건 ontology 통계 (노드 / 관계 카운트) 뿐이라 실질적으로는 landing page 에 가깝습니다. Multiturn Chat 이 primary 플로우이고, session 누적 뷰는 없습니다.

현재 활성 UI
Multiturn Chat · Orientation 대시보드
backend 누적 데이터
session + decision_log (SQLite)
in-memory 전용
token, idiom, verification, proposal
Phase 7~10
finalize 완료 (619 PASS)

즉, 데이터가 일부는 이미 SQLite 에 쌓이고 있고, 일부는 저장조차 안 됩니다. 옵션별로 이 차이가 비용을 가릅니다.

2. 5 가지 옵션 — 토글하면서 보세요

AOrientation Dashboard (현재 것)

유지 이유

  • multiturn chat 으로 바로 들어가면 "이 시스템이 뭘 보는지" 가 안 보이는 문제 방지.

  • 대부분의 경우 해당 없음.

BSession History Browser ★ 강추

과거 multiturn 세션 목록 / 검색 / 클릭 시 replay 진입.

┌─ 최근 세션 ─────────────────────────────────┐ │ 🔍 검색: [ ] │ │ │ │ ● 2026-05-18 14:32 ✓ done │ │ "UC36 capstone 검증" │ │ Gate III sim · 4 turns · slab-v2 │ │ ─────────────────────────────────────────── │ │ ● 2026-05-18 11:08 ⚠ stale │ │ "VAT 변경 영향도" │ │ Gate III impact · 3 turns · slab-v2 │ │ ─────────────────────────────────────────── │ │ ● 2026-05-17 22:01 ✓ done │ │ "ProductCategory term merge" │ │ Gate II → III sim · 4 turns │ │ │ │ ▶ 클릭 → /session/{sid}/replay │ └──────────────────────────────────────────────┘
데이터 가용성
section3_session + decision_log SQLite 이미 쌓임
구현 비용
저 — 1 endpoint + 1 React 컴포넌트 (~ 0.5 phase)
주요 수혜자
3 인 팀 · 운영 / 데모 둘 다
왜 도입해야 하는가
  • 실제 페인 포인트: 3 인 팀이 동시에 다수 세션을 띄우면 "내가 어제 한 그 분석" 을 다시 못 찾음. 현재는 sid 를 손으로 보관해야 함.
  • 데이터가 이미 있음: SQLite 에 session UUID + status + 결정 로그 다 들어 있음. 단지 surfacing 만 하면 됨.
  • replay 인프라가 이미 있음: Phase 1 에서 /session/{sid}/replay 가 만들어졌으나 클릭 진입점이 없음 → 매몰 자산.
  • 데모 효과: "Section 3 가 그동안 N 회 검증을 돌렸다" 가 maturity signal 로 변환됨. 단발 chat 데모보다 system 운영감을 줌.
  • 디버깅 가치: Gate 실패 사후 분석 시 sid 가 손에 있어도 다른 세션과 비교할 방법이 없음.
보류해도 되는 경우
  • 1 인이 단발성으로만 시뮬레이션을 쓸 때. (현실: 3 인 팀이라 해당 안 됨)
  • 이 옵션을 빼면 매몰 자산 (replay endpoint) 이 유저에게 영영 안 닿음.

주요 수혜자
엔진 개발자 · 발표 청중 (capstone story)
도입해야 하는 강력한 이유 (있다면)
  • UC36 0 remaining findings 가 invisible: 메모리 기준 framework 최대 실증인데, 데모에서 청중이 인지할 채널이 없음.
  • Regression 감시: 누군가 idiom_rewriter 를 깨면 UC36 이 다시 비어버리는 걸 dashboard 가 알려줘야 함.
  • 발표 가치: "8 차원 verification 이 살아 있다" 를 1 컷 캡처로 증빙 가능.
보류 이유 (현 시점)
  • 저장층이 통째로 없음: OracleResult / HealthReport 가 in-memory 종료 → DB schema 부터 설계해야 함.
  • CI hook 결합 필요: capstone snapshot 누적 = pytest run 마다 DB 에 적재해야 함. 즉 한 phase 으로 안 끝남.
  • 당장 안 보여도 시스템은 계속 돈다: pytest 619 PASS 가 단일 진실 — dashboard 는 "더 잘 보여주는 것" 이지 동작 차이 없음.
  • 풀 데모 시연 시 multiturn chat + history browser 가 이미 검증 자체를 라이브로 보여줌.

  • 실 사용 흐름이 누적되기 전에 만들면 "왜 만들었지?" 의 빈 dashboard 가 됨.

  • "필요해지면" 만드는 게 합리적. 지금 만들면 빈 차트.
