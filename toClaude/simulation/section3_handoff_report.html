2 시드 JSON 출처 — 솔직한 해명

사용자가 의심한 backend/modeling/ontology/data/*.json 7개 파일의 출처를 git 결과에 근거해 보고합니다.

2.1 사실 — 추적 결과

  • 해당 7개 JSON 은 단 한 커밋 78827ae (2026-05-12, 작성자 Jiyoon Bae) 에서 일괄 추가됨.
  • 그 커밋 메시지는 "chore(modeling): origin/main 의 backend/modeling/ 전체 동기화" 라고 적혀 있음.
  • 그러나 git ls-tree -r origin/main backend/modeling/ontology/ 결과는 비어 있음 — origin/main 에는 ontology 폴더 자체가 존재한 적이 없음.
  • 모든 브랜치 (jyu, section4-handoff-clean, authoring-phase-c3) 를 검색해도 tables.json 을 포함한 브랜치는 section3-integration 하나뿐.

2.2 결론 — 커밋 메시지가 사실과 다름

78827ae 커밋의 "origin/main 동기화" 라는 메시지는 부정확합니다. origin/main 에는 그 파일들이 존재한 적이 없습니다. 출처로 가능한 시나리오는 두 가지:

  • 그 시점에 origin/main 이 다른 상태였다가 누군가 force-push 로 되돌려 흔적이 사라짐 (검증 불가)
  • 이전 세션에서 손으로 작성됐고 메시지에 잘못 적힘 (현재 세션에서는 절대 작성 안 함 — 진입 시 이미 디스크에 존재)

2.3 "온톨로지 API 응답만 써라" 지시 위반 여부

  • Section 3 코드는 JSON 을 직접 안 읽음 — grep "ontology/data" backend/section3/ 결과 0건. Section 3 는 POST /api/modeling/ontology/query 등 HTTP API 만 호출. → 사용자 지시는 지켜졌음.
  • JSON 시드는 backend/modeling/ontology/builders/{layer1,layer2,layer3,bridges}.py 가 ontology 그래프(SQLite data/ontology.db) 를 빌드할 때만 사용. 부팅 시점엔 호출되지 않음 (main.py 어디서도 builder import/호출 0건).

builders 가 부팅 경로에 있지 않으므로 시뮬레이션 동작에는 영향 없음. ontology 그래프 (data/ontology.db) 가 이미 빌드되어 있어 API 응답 계속 가능. 다만 ontology.db 를 재빌드하려면 시드를 다시 정의해야 함 (이 작업은 Section 2 영역).

5.3 결론

chat 자체는 작동합니다. 단 sim_v2 자산은 두 경우에만 활용됩니다:

  1. 사용자가 action FQN 을 정확히 입력 (Sprint 1 경로)

6 개발 예정 — agent 재설계 (사용자 피드백 루프)

현재 chat 은 단발성 stream 응답입니다. 이를 Section 2 의 Authoring agent 패턴처럼 사용자에게 확인받고 피드백 받아 다음 단계로 진행하는 멀티턴 agent 로 재설계합니다. LLM 이 온톨로지를 반복 호출하며 단계마다 사용자 승인을 받습니다.

6.1 목표 흐름 — 6단계 멀티턴 agent

1
의도 파악 + 온톨로지 1차 조회
사용자 자연어 → LLM 이 intent 분류 + 온톨로지에 keyword/term 검색 → 후보 action 2~4개 제시 + ★ 추천
2
사용자 확인 게이트 — "이게 맞나요?"
사용자가 후보 중 선택 / "다른 거 보여줘" / 자유서술 보정. 승인 전까지 다음 단계 진행 안 함 (pending_action 으로 상태 보존)
3
온톨로지 응답 기반 Java 코드 핵심 부분 추출
선택된 action 의 code_method_fqn + 의존 method/table/column 을 온톨로지에서 가져와 Java body 의 핵심 부분만 surface. 사용자가 "이 부분 시뮬?" 확인
4
Python 코드 변환 + 사용자 확인
sim_v2 W75 (Java idiom rewrite) + Section3Translator 로 Python 변환 → 사용자에게 변환 결과 보여주고 "이 코드로 돌릴까요?" 게이트
5
Input (Order 데이터) 합성 — 온톨로지 응답 기반
사용자가 입력값을 직접 안 주어도 OK. Order 엔티티의 스키마를 온톨로지에서 가져와 fixture 자동 합성 (W71) → 사용자가 표 형태로 확인 + 수정 가능
6
실행 + 결과 확인
sandbox 실행 → 결과(invariant_status, output, diff) 표시 → 사용자가 "OK / 다시 / 다른 케이스 시도" 결정. 결과를 baseline 으로 저장 옵션 제공

6.2 상태 머신 — DecisionKind

Section 2 의 authoring_decision_log 처럼 각 단계 결정을 DB 에 영구 저장 → 세션 끊겨도 resume 가능.

candidates_proposed   → 후보 카드 surface 직후
target_selected       → 사용자가 action 1개 선택 후
code_extracted        → Java 핵심 부분 추출 후 (확인 대기)
python_generated      → Python 변환 후 (확인 대기)
fixtures_synthesized  → Order 데이터 합성 후 (확인 대기)
sandbox_executed      → 실행 완료 (결과 게이트)

6.3 사용자 확인 게이트 — Section 2 패턴 차용

  • pending_action 보존 — backend/core/session.py 의 add_pending_action / resolve_action (UUID 추적). Section 3 도 동일하게 각 게이트를 pending_action 으로 DB 저장. 사용자 새 메시지를 그 UUID 에 대한 응답으로 해석.
  • discriminated union — 단계마다 다른 payload (candidates / extracted_code / python / fixtures / result). FastAPI Pydantic discriminator="kind" 로 schema 표현 (Authoring 의 Hypothesis union 참조).
  • resumable replay — Section 2 의 build_resume_state 처럼 decision_log 를 (turn_no, kind) 순으로 replay → 끊긴 세션 복구.

6.4 LLM 의 온톨로지 반복 호출 패턴

각 게이트 통과 후 LLM 이 다음 게이트로 가기 위해 필요한 온톨로지 호출을 직접 결정. tool-use 패턴.

LLM tool catalog (Section 2 의 OntologyClient 와 동일):
- ontology.search_action_by_keyword(q)
- ontology.get_action_detail(action_id)            # code_method_fqn, deps
- ontology.get_method_body(code_method_fqn)        # Java source
- ontology.get_entity_schema(entity_name)          # Order, ProductLine 등 → fixture
- ontology.list_baseline_for(method_fqn)           # 기존 baseline 있는지
- sim_v2.find_action_candidates(q)                 # 한국어 검색 (W77)
- sim_v2.quick_diagnose_action(action_id)          # invariant 진단

LLM 이 매 게이트에서 위 tool 들을 호출 → 결과를 사용자 확인 카드로 변환 → 사용자 응답 받고 다음 tool 호출.

6.5 Order 데이터 자동 합성 — 핵심 신규 흐름

현재 fixture 는 sim_v2 W71 이 method signature 기준으로 합성. 신규: Order 같은 도메인 엔티티는 온톨로지의 엔티티 스키마로부터 합성.

  1. LLM 이 ontology.get_entity_schema("Order") 호출 — column 목록 + 타입 + constraint + 예시 값
  2. 해당 스키마 기반으로 LLM 이 plausible Order fixture 1~5건 합성 (정상 케이스 + 경계 + 에러)
  3. 사용자에게 표로 surface → "이 데이터로 실행할까요?" 게이트
  4. 사용자가 수정 또는 승인 → sandbox 입력으로 흘림

이미 sim_v2 의 synthesize_fixtures 가 있고, ontology API 는 POST /api/modeling/ontology/query 로 엔티티 스키마 가져올 수 있습니다. 두 자산을 연결하는 LLM tool 만 정의하면 됩니다.
