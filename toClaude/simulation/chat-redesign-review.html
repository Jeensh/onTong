3 · 4 sub-agent 검토 결과 정보

spec 을 검토하라고 4 sub-agent 를 병렬로 launch 했고, 각자가 실제 코드까지 읽고 보고했습니다. 핵심만 정리:

Agent 1 · 아키텍처

  • 지적 1: spec §5 (DB-resident decision_log) 와 §6 (in-memory _pending dict) 가 모순. 세션 재개 약속과 in-memory 가 양립 불가.
  • 지적 2: "다시" 분기를 LLM 에 맡기는 게 spec 에 적힘 — state machine 이 아니라 free-form ReAct loop 가 됨.
  • 지적 3: GateSandbox 가 PASS/FAIL/ERROR 를 한 schema 로 강제 — variant 폭발.
  • 강점: Gate 3/4/5 분리는 옳음 (Java 추출/변환/fixture 가 독립적으로 실패 가능). per-gate tool allowlist 는 진짜 safety property.
우선 surface 할 위험: persistence 기반 (DB vs in-memory) 모순. 둘 다 쓰면 결합 불가.

Agent 2 · 엔지니어링 실행 가능성

  • Blocker 1: ApprovalAction Union 은 wiki only. Section 3 가 그대로 쓰려면 Union 확장 또는 새 store 작성. spec 의 "신규 구현 0" 약속 깨짐.
  • Blocker 2: authoring 은 alembic 안 씀 (Base.metadata.create_all 패턴). spec 의 "마이그레이션 같이 진행" 가정 부정확.
  • Blocker 3: get_entity_schema 의 sim_v2 fallback 실제 함수 없음 — 새로 작성 필요.
  • Blocker 4: repo_id 현재 hardcoded constant — 세션 state 로 옮겨야.
  • Blocker 5: sim_v2 tool 은 sync, SSE handler 는 async — 매 호출 asyncio.to_thread 래핑 필요.
  • 강점: 9 sim_v2 tool 다 존재함 (실측 확인). Hypothesis union 패턴 진짜 있음. SSE infra 도 frontend 에 있음.
사용자 결정 필요: pending-action store — core Union 확장 vs 새 Section3PendingStore 작성

Agent 3 · 위험 / 누락

  • omitted 1: replay 의미 모호 — re-execute (live, 분기 가능) vs hydrate (historical) ?
  • omitted 2: 테스트 전략 0 언급.
  • omitted 3: auth/세션 ownership 없음 — UUID guess 로 남의 세션 진입 가능.
  • omitted 4: frontend toggle 두 store / SSE 상태 충돌.
  • omitted 5: LLM budget 소진 시 recovery 없음.
  • treated too brief: LLM cost / concurrency / Section 2 dependency — 모두 TODO 수준, 구체 mitigation 없음.
  • 제안: MVP demo = Gate 1+2+6 만 (3/4/5 hardcode).
단 1개의 must-decide: decision_log = source-of-truth (hydrate) 인가 audit log (re-execute) 인가?

Agent 4 · 더 단순한 대안

  • Alt A: 3 gates 로 압축 (1+2 / 3+4+5 / 6). 약 50% 코드 감소.
  • Alt B: 6 gates 유지하되 LLM auto-confirm 이 default. UX win, 코드 무게 동일.
  • Alt C: Section 2 의 authoring_decision_log 를 section 컬럼으로 공유. 결합도 ↑.
  • Alt D: 1 endpoint + SSE tool loop. 75% API 표면 감소.
  • Alt E: 3 데모 시나리오 하드코딩 (regret-debt).
  • 추천: Alt D + Alt A 결합 — 1 endpoint + 3 gates. 진정한 50% cost path.
  • 추가: section3_decision_log table 을 drop 가능 (Section 2 협업 #3 dependency 해소).
관찰: Spec 은 Section 2 authoring 의 1,227 LOC 패턴을 미러링 — Section 3 chat 의 단순한 happy path 에 비해 over-engineered.

4 · ⚠ False premise 발견 (3 agent 공통 지적) 중대

Spec §6 은 잘못된 패턴 차용에 기반

spec 의 §6 ("Pending Action Gate") 는 다음과 같이 약속합니다:

Section 2 의 backend/core/session.py:70-87 (add_pending_action / resolve_action) 그대로 재사용.
장점: core 모듈이라 신규 구현 0, 그대로 차용.

그러나 실제 코드는:

  • backend/core/session.py:70-87 의 add_pending_action 은 wiki 전용. ApprovalAction = WikiWriteAction | WikiEditAction | WikiDeleteAction 만 받음.
  • Section 2 의 authoring 은 이걸 안 씀. 직접 REST POST /sessions/{id}/confirm + add_decision() 패턴 사용.
  • 즉 spec 작성자가 wiki 패턴을 Section 2 패턴으로 오인.

결과적으로 발생할 문제:

  • in-memory _pending dict 가 server restart 마다 날아감 → spec §5 의 "세션 resume" 약속과 정면 충돌
  • wiki ApprovalAction Union 에 6 gate 변형 끼워넣어야 — wiki schema 오염
  • wiki 의 JSONL side-channel (data/sessions/{id}.jsonl) 과 신규 section3_decision_log 가 같은 state 를 두 곳에서 관리

→ 이 부분은 어차피 재설계 필요. 이 김에 어느 방향으로 갈지 결정해야 함.

✓ 한 줄 요약

Alt A (6 → 3 gates) + §6 false premise 수정 + section3_decision_log 유지 (alembic 없이 ORM bootstrap)

구조

  • 3 gates:
    • Gate I — 의도 + 후보 + 선택 (spec Gate 1+2 합침)
    • Gate II — 코드 / Python / fixtures bundle (spec Gate 3+4+5 합침, edit-in-place)
    • Gate III — 실행 + 진단 (spec Gate 6)
  • 각 gate: LLM + tool 호출 → 카드 surface → 사용자 승인 → 다음 gate. 핵심 UX 유지.

§6 수정 — Section 2 authoring 의 실제 패턴 사용

  • wiki 의 add_pending_action 폐기
  • 대신: POST /api/section3/multiturn/confirm/{session_id}/{turn_no} → section3_decision_log row 에 user_response_json 채움 → 다음 gate
  • 장점: DB-only 단일 source-of-truth, server restart 후도 resume 가능

Persistence — section3_decision_log 유지 (alembic 없이)

  • authoring 패턴: Base.metadata.create_all() 로 bootstrap 시 자동 생성. alembic 없음.
  • Section 2 협업 요청 #3 (alembic) 자체가 불필요 — Section 2 도 안 쓰는 패턴이라.
  • replay 의미: source-of-truth (hydrate). payload self-contained. re-execute 안 함.

부수 결정 (내 default)

  • LLM client: 기존 backend/section3/llm/openai_client.py 유지 (Section 2 의 Anthropic llm_router 로 swap 비용 큼)
  • async: sim_v2 tool 호출은 asyncio.to_thread 래핑 (Agent 2 Blocker 5)
  • repo_id: 세션 state 에 저장, per-request 아님 (Agent 2 Blocker 4)
  • test: LLM mock + replay-based regression (decision_log 가 source-of-truth 면 자연스러움)
  • get_entity_schema mock: sim_v2 의 synthesize_fixtures 내부 schema 추출 로직을 helper 함수로 추출 후 노출

왜 이 조합?

  • Alt A 가 spec 의 핵심 UX ("사용자가 각 단계 결과 보고 승인") 를 보존하면서 코드 50% 감소. Gate 3/4 분리 명분 (Java 추출 vs 번역 독립 실패) 은 실제로 약함 — sim_v2 W75 는 Java→Python 한 호출.
  • §6 수정 은 안 할 수 없음 (false premise). 어차피 재설계 → authoring 의 진짜 패턴 단일화.
  • table 유지 는 demo 의 "어제 세션 resume" 가능성 확보. alembic 없으니 협업 #3 부담 0.
