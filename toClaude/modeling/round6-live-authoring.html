★ 답: 그게 정확히 C-1 의 가치. 자동 처리됨.

매핑 row 가 (atomic + codeType + codeField) 3개 키로 unique 하므로, CustomerStdJpo.PRODUCT_NAME_CD 와 OtherJpo.PRODUCT_NAME_CD 가 같은 컬럼명이어도 다른 row. 각자 다른 atomic 가리킬 수 있음. 코드 맥락이 그대로 살아있음.

역방향 — atomic 입장에서 보면?

term.scm.shared.product_kind  ← (PARTIAL TR 4 row)
  ├─ CustomerStdJpo.productNameCd
  ├─ SdProductivityStdJpo.prodKindCd
  ├─ HrSpecJpo.productTypeCd
  └─ ... (다른 6 std 도 추가 가능)

term.scm.something.else  ← (PARTIAL TR 1 row, 가상)
  └─ OtherJpo.productNameCd  ★ 같은 컬럼명이지만 다른 atomic

즉 ontology 가 보장하는 건 "이 컬럼 ↔ 이 atomic" 쌍의 명시적 등록. "PRODUCT_NAME_CD 라는 컬럼명이면 자동으로 품종" 같은 추측은 없음. 매핑은 항상 코드 위치 단위.

★ Q7a 풀이 — default 0.95 의 운영 vs 데모

  • 변천: 2017 0.90 → 2019 0.92 → 2021 0.95 (3~5년에 1회 코드 patch 로 갱신)

  • TODO OPS-2199: std 미비 시 운영자 슬랙 알림 — 미진행 (운영 사각지대)

  • ProductivityStd 테이블 비어있음 (실제 DB 없음 — 정적 코드만)

                                         String confirmedPlantCd,
                                         String gradeCd, String prodKindCd, String customerCd) {
    if (confirmedPlantCd == null || confirmedPlantCd.length() < 8) {
        return DEFAULT_PRODUCTIVITY;
    }
    BigDecimal product = BigDecimal.ONE;
    for (int i = 0; i < 8; i++) {
        if (confirmedPlantCd.charAt(i) == ' ') continue;
        BigDecimal p = lookupOrDefault(
            cmpCd, orgCd, PROC_CODES[i], gradeCd, prodKindCd, customerCd);
        product = product.multiply(p);
    }
    return product;
}
