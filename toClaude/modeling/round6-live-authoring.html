Q4 추가 의문에 답 — alias 가 다른 atomic 에서도 중복 사용되면?

사용자 인용
"alias도 여기저기에 중복으로 사용될 수 있잖아. 맥락에 따라서. 예를들어 A의 alias가 q, w, e 라면 C의 alias가 q, r, b 일 수 있는거잖아? 코드 맥락안에서는 그걸 판단 가능하지만 우리 지금 작성하는 것도 그게 고려되는거지?"
★ 답: 그게 정확히 C-1 의 가치. 자동 처리됨.

alias 를 atomic 자체의 속성 으로 박으면 (= C-3 옵션) → "q" 가 어떤 atomic 인지 모호 → 충돌.

대신 C-1 은 매핑 단위 = (atomic, codeType, codeField) 3-tuple. 같은 컬럼명도 entity 별로 독립 매핑 가능.

구체 예시 — PRODUCT_NAME_CD 컬럼이 4 entity 에 다 있다고 가정

코드 위치매핑되는 atomicTR scope의미
CustomerStdJpo.PRODUCT_NAME_CDterm.scm.shared.product_kindPARTIAL품종 (= 같은 의미)
SdProductivityStdJpo.PROD_KIND_CDterm.scm.shared.product_kindPARTIAL품종 (다른 컬럼명, 같은 의미)
HrSpecJpo.PRODUCT_TYPE_CDterm.scm.shared.product_kindPARTIAL품종 (또 다른 컬럼명, 같은 의미)
★ 가상의 케이스 — OtherJpo.PRODUCT_NAME_CDterm.scm.something.else (다른 atomic)PARTIAL같은 컬럼명, 다른 의미 — 충돌 X

매핑 row 가 (atomic + codeType + codeField) 3개 키로 unique 하므로, CustomerStdJpo.PRODUCT_NAME_CD 와 OtherJpo.PRODUCT_NAME_CD 가 같은 컬럼명이어도 다른 row. 각자 다른 atomic 가리킬 수 있음. 코드 맥락이 그대로 살아있음.

역방향 — atomic 입장에서 보면?

term.scm.shared.product_kind  ← (PARTIAL TR 4 row)
  ├─ CustomerStdJpo.productNameCd
  ├─ SdProductivityStdJpo.prodKindCd
  ├─ HrSpecJpo.productTypeCd
  └─ ... (다른 6 std 도 추가 가능)

term.scm.something.else  ← (PARTIAL TR 1 row, 가상)
  └─ OtherJpo.productNameCd  ★ 같은 컬럼명이지만 다른 atomic

즉 ontology 가 보장하는 건 "이 컬럼 ↔ 이 atomic" 쌍의 명시적 등록. "PRODUCT_NAME_CD 라는 컬럼명이면 자동으로 품종" 같은 추측은 없음. 매핑은 항상 코드 위치 단위.

참고: alias facet (C-3) 도 추가 가능 — atomic 에 자주 쓰이는 컬럼명 list 박아두면 검색·자동 추천 시 hint. 단 매핑의 결정권은 항상 TR 에 있음. alias 는 hint 일 뿐 ground truth 아님.

왜 composite "보강"?

큐의 자동 추천이 label + composite kind + domain 만 채움. description / parts / facets 비어있음. Customer 의 7 컬럼이 도메인 의미상 어떻게 나뉘는지 인터뷰로 채워서 confirm 가능 상태로 만들기.

parts vs facets — 핵심 구분
  • parts = composite 가 어떤 atomic 들의 묶음 인지 (도메인 정의). 다른 entity 와 공유 가능.
  • facets = entity 고유 속성 (atomic 으로 분해 안 됨, 다른 entity 에 등장 안 함).
  • 참고: 코드 위치 매핑 (어느 컬럼이 어느 atomic 인지) 은 Step 4 의 TR 에서 다룸. Step 2 는 도메인 정의만.
