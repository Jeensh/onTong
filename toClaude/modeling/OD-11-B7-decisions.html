OD-11-B7 Reflection 런타임 collector

착수 전 결정 사항 3건 — 2026-04-19 · Section 2 Modeling · Phase B
B6 가 정적 분석 라운드를 끝냈습니다 (10 analyzer + CrossFileEnricher 까지 272/272 통과). B7 은 런타임 trace 를 받아 Reflection 콜사이트를 실엣지로 승격시키는 인터페이스를 만듭니다. 아직 JVM Agent 는 붙이지 않고, 파이프라인과 Protocol 을 먼저 정의합니다.

왜 지금 이 결정이 필요한가

현재 상태

B5-8 ReflectionAnalyzer 가 정적 call-site 를 찾아서 다음과 같이 마킹해 둔 상태입니다. 아직 엣지로는 승격되지 않았습니다.

METHOD entity
  .attributes["reflection_calls"] = [
    {"api": "Class.forName",        "arg": "com.acme.FooService", "line": 42},
    {"api": "ctx.getBean",          "arg": "orderService",        "line": 58},
    {"api": "clazz.getDeclaredMethod","arg": "calculate",          "line": 71},
  ]

즉, "이 메서드 안에서 Class.forName("com.acme.FooService") 를 부른다" 라는 사실만 기록되어 있고, "그래서 실제로 어떤 클래스/메서드를 호출하느냐" 는 아직 미정입니다.

B7 이 해야 할 일

┌──────────────────────┐ ┌──────────────────────┐ │ B5-8 정적 marker │ │ B7 런타임 trace │ │ reflection_calls[] │ │ (JVM Agent 로 수집) │ └──────────┬───────────┘ └──────────┬───────────┘ │ │ └───────────┬────────────────────┘ ↓ ┌──────────────────────────┐ │ RuntimeCollector (B7) │ │ Protocol + DTO │ │ 정적·런타임 → 엣지 병합 │ └──────────┬───────────────┘ ↓ CALLS{source: static|runtime, confidence: ...} REFLECTS_AS (정적 reflection_calls → 실제 타겟)

여기서 엣지 승격 규칙(어떤 source 를 신뢰할지, confidence 는 어떻게 줄지)과 수집 경로(JVM Agent 를 이번 단계에서 붙일지) 결정이 코드 구조를 크게 좌우합니다.

PROProtocol 의 DTO 필드가 나중에 바뀌면 B9 Slab 샘플 E2E 때 파급이 크다. 미리 한 번 합의하면 그때 재작업 없음.

Q2 — 정적 marker 와 런타임 trace 가 만났을 때 엣지 병합 규칙

Q2 Design · 엣지 승격

같은 메서드에서 "정적 marker 로도 감지"되고 "런타임 trace 로도 찍힌" 경우,
그래프에 어떻게 저장할까요?

예시 시나리오 — OrderService.dispatch() 가 Class.forName(name) 를 부름:
  • static B5-8 marker : {api: "Class.forName", arg: "name", line: 42} — arg 가 변수라 실제 대상은 모름
  • runtime B7 trace : {api: "Class.forName", resolved: "com.acme.FooShipper", method: "OrderService.dispatch"} — 실제로 로드된 클래스 확인
이 둘을 그래프 엣지로 옮길 때 3가지 접근이 가능합니다.

Option A — 런타임 trace 가 정적 marker 를 교체 (Replace)

정적 marker 만 있을 때: METHOD("OrderService.dispatch") —[CALLS{source: static, target_unknown: true, confidence: 0.3}]→ <reflection-site> 런타임 trace 가 도착하면 위 엣지 삭제하고: METHOD("OrderService.dispatch") —[CALLS{source: runtime, confidence: 0.95}]→ CLASS("com.acme.FooShipper")

Option B — 정적·런타임 엣지를 공존 (Coexist)

METHOD("OrderService.dispatch") —[CALLS{source: static, confidence: 0.3}]→ <reflection-site> METHOD("OrderService.dispatch") —[CALLS{source: runtime, confidence: 0.95}]→ CLASS("com.acme.FooShipper") → Impact Analysis 쿼리 시 "source IN ('static','runtime')" 로 둘 다 타거나, 보수적으로 "source = 'runtime'" 만 타게 할 수 있음.

Option C — 단일 엣지에 confidence weight 로 반영 (Merge)

METHOD("OrderService.dispatch") —[CALLS{ sources: ["static","runtime"], confidence: 0.95, ← 런타임 도착하면 정적 0.3 을 덮어씀 static_line: 42, runtime_sample_count: 127 }]→ CLASS("com.acme.FooShipper")
AReplace — 런타임이 정적을 대체
PRO그래프가 깔끔. BFS 결과에 중복 경로 없음.
CON정적 marker 가 있었다는 사실 자체가 사라짐 (감사 추적 불가).
CON런타임에 안 찍힌 경로는 영영 안 잡힘. 정적 marker 가 남긴 "<reflection-site>" 경고 효과도 잃음.
BCoexist — 두 엣지를 source 속성으로 구분해 보존
PROImpact Analysis 에서 "런타임 확인된 것만" / "정적 포함 전체" 를 쿼리 레벨로 스위치 가능 — Q6 hops 자율 조정과 잘 맞음.
PRO정적은 많이 잡히고 런타임은 못 찍는 경로(예: 프로덕션에서만 동작하는 profile) 도 놓치지 않음.
PROconfidence 기본값이 분리되어 있어서 가중 BFS 가 단순.
CON엣지 개수가 늘어남. 시각화 시 중복 보일 수 있어 뷰어 단에서 source 필터링 필요.
CMerge — 단일 엣지에 sources 리스트 + 가중 confidence
PRO그래프 조회 시 엣지 1 개만 보면 되어 뷰어가 간단.
CONCypher MERGE 로직이 복잡 (런타임 trace 가 batch 로 계속 들어올 때 confidence·sample_count 재계산).
CON동일 source 메서드가 서로 다른 target 을 여러 개 로드하는 경우 (Class.forName with 변수) 1:N 표현이 어려움.
RATIONALE B 추천. 정적 정보는 "잠재 경로", 런타임은 "관측 경로" 로 역할이 다릅니다. 둘을 모두 그래프에 남겨두고 Impact Analysis 쿼리 파라미터로 sources=["runtime"] 같이 고를 수 있게 하는 편이 Slab 엔진 E2E 에서 "안전한 리팩토링 범위 / 전체 잠재 범위" 두 관점을 바로 뽑아낼 수 있습니다. Confidence 기본값은 static = 0.4, runtime = 0.95 정도로 제안.

Q3 — JVM Agent 임시 섹션 범위 — B7 에서 어디까지 만들지

Q3 Scope · 런타임 수집기 구현 경계

B7 에서 실제 trace 수집기를 얼마나 만들까요?

과거 합의 (Q10, 2026-04-19): JVM Agent 는 정식 Section 3 이전에 임시 섹션(toClaude/temp-runtime/, backend/temp_runtime/) 에서 실험하기로 했습니다. 하지만 "임시 섹션" 이 정확히 언제 들어오는지, B7 에서 어디까지 붙일지는 미정.

B7 작업 범위 시각화

┌───────────────────── B7 단계 경계 선택지 ─────────────────────┐ │ │ │ Protocol + DTO 로컬 trace file JVM Agent │ │ (python 쪽) 수집기 CLI (실제 bytecode) │ │ │ │ │ │ │ │◀── Option A ──▶│ │ │ │ │◀──────── Option B ───────▶│ │ │ │ │◀──────────────── Option C ──────────────▶│ │ │ │ └──────────────────────────────────────────────────────────────┘
AProtocol + DTO 만 — 실제 수집기는 B9 임시 섹션에서
PROB7 범위가 명확. Protocol (RuntimeCollector) + DTO (ReflectionTrace, CallTrace) + 합성 fixture 만으로 TDD 완성.
PROJVM Agent 는 Slab 엔진 repo 를 실제로 받은 뒤 어떤 byte-code instrumentation 포인트가 필요한지 알고 나서 만드는 편이 낭비 없음.
PROCrossFileEnricher 가 이미 관례로 자리잡은 "synthetic ParseResult" 패턴과 잘 맞음 — 런타임 trace 도 ParseResult(file_path="<runtime>") 로 들어오게 설계.
CON실제 JVM 에서 한 번도 돌려보지 않고 Protocol 을 박제하면 B9 에서 수정 가능성.
BProtocol + DTO + 로컬 trace file 수집기 CLI (JSON 읽어 ParseResult 만듦)
PRO사용자가 직접 java -javaagent:... 없이도 샘플 JSON 파일만 있으면 E2E 를 돌려볼 수 있음.
PROB8 Impact Analysis 테스트 데이터를 손으로 만들 수 있어 B9 Slab 엔진 대기 중에도 개발 진행 가능.
CONJSON schema 를 먼저 고정해야 함. 나중에 JVM Agent 가 실제로 뱉는 포맷과 다르면 재작업.
CJVM Agent 까지 한 번에 — 임시 섹션 신설 + byte-code instrumentation 프로토타입
PRO실제 Java 환경에서 trace 가 나오는지 확인 가능.
CONByteBuddy / ASM 같은 library 선정, agent manifest, shading, 배포 경로 등 완전히 새로운 스택 — B7 범위를 크게 넘어섬.
CONSlab 엔진 repo 를 아직 받지 않았는데 Agent 를 먼저 만들면 "어디에 쏠지" 를 추측으로 결정해야 함.
RATIONALE A 추천. "정보가 더 있기 전까지는 가장 적은 일을 한다" 원칙 — 지금은 Slab 엔진 sample repo 를 기다리는 중이고, Agent 구현은 그 repo 가 어떤 구조인지 알고 나서 붙이는 편이 합리적입니다. B7 에서는 Protocol + DTO + 합성 fixture 10 케이스 TDD 까지만 하고, JVM Agent 는 B9 Slab 샘플 수령 직후 임시 섹션 신설과 함께 별도 step 으로 빼는 것을 제안.
