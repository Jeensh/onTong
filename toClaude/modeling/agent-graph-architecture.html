1. 자산 inventory — 우리가 가진 것

Authoring agent 가 호출할 수 있어야 할 자산은 3-layer 로 구성된다. 현재 채워짐 상태는 다음과 같다 (백엔드 직접 확인):

L1 · Code Layer (AST graph) FULL — 100%

Java parser 가 빌드한 AST 가 ORM 으로 영속화 됨. `CodeTypeRow` / `CodeMethodRow` / `CodeFieldRow` + 7-anchor.

  • CodeType: extends · implements · extends_interfaces · fields[] · methods[] · annotations · source_file
  • CodeMethod: params · return_type · body_text · anchors[] (param/local/return/branch/literal/field/field_access)
  • CodeField: type · annotations · is_collection · element_type
  • 그래프 edge: graph endpoint 가 nodes+edges 로 노출 (확인된 edge kind: type_realization_primary 등)
L2 · Domain Layer (Ontology) PARTIAL — recommend 기반 29 terms · 36 actions

`BusinessTerm` (명사) + `Action` (동사) + facets / 도메인 계층. 아직 cold-start 상태이지만 endpoint 는 모두 살아있음 (`/api/ontology/terms`, `/api/ontology/actions`, `/api/ontology/repos/{repo_id}/perspectives`).

  • BusinessTerm: korean / english / domain / facets / inheritance
  • Action: realizations[] · code_method_fqn 포함
  • Authoring 자체가 ontology 를 채우는 도구이므로, agent 사용량이 늘수록 본인이 쓸 수 있는 graph 도 부유해진다 (positive feedback)
L3 · Mapping Layer (AnchorBinding) PARTIAL — 34 realizations

`code_method_fqn × anchor_id × business_term_id` 3-tuple 로 "이 메서드의 이 파라미터가 어떤 도메인 term 에 해당하는가" 를 기록. `/api/ontology/code-methods/{fqn}/anchor-bindings`, `/api/ontology/actions/{fqn}/anchor-bindings` 등 endpoint 가 이미 존재.

함의

인프라가 이미 거의 다 있다. agent 가 새 graph 라이브러리를 부를 필요 없음 — pydantic_ai @agent.tool 데코레이터로 기존 함수를 wrap 만 하면 된다. 실제 작업의 본질은 "어떤 tool 을 어떤 cap 에 어느 예산으로 줄 것인가" 하는 정책 설계와, "tool call 추적·비용·UI 노출" 의 운영 문제다.

2. Agent Tool Catalog — 구체적 inventory

pydantic_ai @agent.tool 패턴으로 정의될 함수 집합. 각 도구는 graph store 의 read-only 함수를 wrap 하므로 사이드 이펙트 없음.

2.1 Code Layer Tools (12개)

Tool설명Backing
code_lookup(fqn) FQN 으로 CodeType / CodeMethod / CodeField 단건 조회 code_type_store.find
code_search(q, kind?, limit?) 키워드/한글 검색 → FQN 리스트 /api/ontology/search 의 in-process
find_subclasses(type_fqn) 이 타입을 extends 하는 자식 클래스 extends 인덱스 역방향

find_callers(method_fqn) 이 메서드를 호출하는 곳 (call-site list) /api/ontology/code-methods/{fqn}/call-sites 동등
find_callees(method_fqn) 이 메서드 body 에서 호출하는 메서드들 method.extra.calls 또는 anchor
find_field_readers(field_fqn) 이 필드를 읽는 메서드 field_access anchor 역방향
find_field_writers(field_fqn) 이 필드를 쓰는 메서드 field_access anchor + mutation

get_method_anchors(fqn) 7-kind anchor list (line/snippet 포함) CodeMethodRow.anchors
find_related_jpos(jpo_fqn) 같은 PK 컬럼을 공유하는 다른 JPO field-level join
find_in_same_package(fqn, kind?) 같은 패키지의 동종 클래스 package prefix 매칭

from pydantic_ai import Agent, RunContext

# Tool registry — 모든 cap 이 공유
def register_graph_tools(agent: Agent, allowed: set[str]):
    if "code_lookup" in allowed:
        @agent.tool
        def code_lookup(ctx: RunContext, fqn: str) -> dict | None:
            """Look up a CodeType / CodeMethod / CodeField by fully-qualified name."""

        @agent.tool
        def find_callers(ctx: RunContext, method_fqn: str, limit: int = 10) -> list[dict]:
            """Find which methods call this method. Returns list of caller FQNs with line/snippet."""
            return graph_store.callers_of(method_fqn, limit=limit)

3. Per-Capability Tool Budget

각 cap 의 본질에 따라 허용 tool 집합과 최대 호출 횟수 가 다르다. 과한 권한은 비용 폭증·환각 위험; 부족한 권한은 graph 활용 가치가 죽는다.

Cap Tier 주요 tool 권한 Max calls 예상 비용
1 · extract Sonnet code_lookup, code_search, find_related_jpos, get_method_body 3–5 $0.05
2 · hypothesize Opus + find_subclasses, find_implementations, domain_search, find_terms_in_domain, find_existing_mapping 5–8 $0.30
3 · interview Sonnet term_lookup, action_lookup (질문 작성 중 갭 확인용) 2–3 $0.04
4 · absorb Sonnet (현재 P3-A 로 우회됨 — tool 불필요) 0 $0.00
5 · gaps Opus 전체 — 누락 신호 탐지에 가장 많은 graph 탐색 필요 8–12 $0.50
6 · options Opus 전체 — 대안 비교에 유사 case 검색 필요 8–10 $0.40
7 · pattern_check (예정) Opus find_terms_in_domain, find_term_realizations 4–6 $0.20
8 · naming Sonnet domain_search, find_terms_in_domain (중복 회피) 2–3 $0.04
9 · archive Sonnet (read-only summary, tool 불필요) 0 $0.02

세션 1회 (8 cap 풀 사이클) 추정 비용: 약 $1.55. 현재 raw text 방식(약 $0.40 / session) 대비 ~4배. 사람-1 세션 단가이므로 절대값으로는 미미. 100K 문서 batch 가 아닌 점에 주의.

ReAct trace (실제 LLM 이 만들 호출 시퀀스)

[Step 1] // 자바독 없고 컬럼명 모호. 같은 PK 가진 다른 JPO 부터 본다.
→ find_related_jpos("...HrPlantConstraint")
← ["HrPlant", "HrSpec", "HrPlantHist", "HrPlantConstraintHist"]

[Step 2] // HrPlant 가 가장 단순. 이게 마스터일 확률 높다.
→ code_lookup("...HrPlant")
← {javadoc: "공장 마스터", PK: hrPlantCd "공장 코드", regular: [plantName, ...]}

[Step 3] // HrPlantConstraint 가 사용되는 곳을 찾자.
→ code_search("HrPlantConstraint", kind="code_method")
← ["...PlantConstraintService.applyConstraint(slab, plant)", "...HrPlantConstraintRepository.findByPlantCd(...)"]

[Step 4] // applyConstraint body 가 핵심.
→ get_method_body("...PlantConstraintService.applyConstraint(...)")
← "if (slab.thk < constraint.minThk || slab.thk > constraint.maxThk) ..."

[Step 5] // 확정. Thk/Wid 는 thickness/width. constraintTypeCd 는 어떤 종류 enum?
→ get_method_anchors("...applyConstraint(...)")
← [literal: "HARD" / "SOFT" / "WARNING"], [branch: 3 conditions]

[Step 6] // 도메인에 이미 비슷한 term 이 있나 확인 (중복 회피).
→ domain_search("공장 제약")
← [] (없음, 신규 term 으로 추가해도 됨)

[Step 7] // 충분. 가설 작성.
→ Output: EntityHypothesis (위 우측 카드)
관전 포인트

Step 4 의 "if (slab.thk < constraint.minThk || ...)" 한 줄이 전부다. 이 한 줄이 컬럼명·PK 만 있던 raw text 와 비교해 도메인 의미를 결정한다. 그리고 이 정보는 자바독·주석 없이 body 의 코드 자체에서 나왔다. "코드가 ground truth" 라는 시뮬레이션 설계 원칙과 정확히 일치.

5. Trade-offs · 위험

차원현재 (raw text)Agentic (graph + ReAct)
비용 (per session) ~$0.40 ~$1.55 (4×)
지연 (per cap) 2–4 s 8–25 s (tool turn 당 ~1.5s)
품질 (자바독 없는 케이스) confidence 0.4 수준 confidence 0.85+
디버깅 복잡도 낮음 (1 prompt + 1 output) 중간 (tool trace 필요)
UX 부담 single spinner tool call 진행률 필요 (없으면 멈춘 듯 보임)
환각 위험 중간 (prompt 안 정보 제한) 낮음 (실제 graph 만 본다)
오답 시 사후 분석 왜 틀렸는지 불투명 tool trace 로 정확히 추적 가능
cold-start 의존성 자체 완결 ontology 가 비어있으면 ontology tool 효과 0 (code tool 만으로도 동작은 함)

5.1 위험 · 대비책

  • Tool call 폭주 — agent 가 graph 를 10+ hop 헤집고 다닐 위험 → cap 별 hard cap (max_calls), 동일 fqn 중복 호출 dedup, 세션당 총 비용 cap
  • 긴 latency 로 사용자 이탈 — SSE 로 tool call 진행 (예: "🔍 HrPlant 조회 중…") 노출. 진행률 보이면 25초도 OK
  • 잘못된 추적 → 잘못된 가설 — 모든 tool trace 를 decision log 에 기록 → cap 9 archive 가 트레이스도 함께 마크다운에 포함
  • 재실행 비용 — F3 cascading rerun 시 동일 tool call 캐시 활용 (session-level memoization)
  • Ontology 미완 cold-start — ontology tool 비활성 모드 지원 (code tool 만으로도 valuable)

6. 아키텍처 결정 사항 (사전 정렬 필요)

구현 진입 전에 사용자 결정이 필요한 항목들. 작업 단위 승인 원칙에 따라 답을 받고 들어간다.

6.1 ReAct 루프 형태

  • A · 자유 ReAct — agent 가 결심할 때까지 tool call 무제한 (max_calls 만 cap). 가장 유연하지만 latency·비용 변동성 큼.
  • B · 단계별 forced reflection — N call 마다 강제 "지금까지 알아낸 것 정리" 단계 삽입. 품질 안정적.
  • C · Plan-then-execute — agent 가 먼저 "이런 것들 조사해야 함" 계획 먼저 출력 → 사용자 승인 → 일괄 실행. 가장 투명하지만 인터랙션 늘어남.

6.2 Tool trace UX 노출

  • α · Full trace — 모든 tool call 을 진행 중 SSE 로 노출 (개발자 모드 느낌)
  • β · 요약 spinner — "🔍 관련 코드 5개 조회 중…" 처럼 현재 phase 만 노출
  • γ · 사후 expandable — 결과 카드에 "🔍 어떻게 알아냈나" 토글로 trace 펼치기

6.3 Ontology tool 활성 시점

  • S · 즉시 — recommend bulk 결과 (29 terms) 부터 활용. cold-start 라도 유용.
  • T · 임계 후 — ontology size 가 일정 이상 (예: 50 terms) 될 때까지 비활성

  • cap 당 hard cap (예: cap 5 는 max 12 calls) 만 두고 세션 cap 은 부드럽게?

6.6 새 cap (7 · pattern_checker) — agentic 으로 처음부터 설계?

cap 7 (pattern_checker) 는 아직 미구현. 처음부터 ReAct 패턴으로 설계하면 retro-fit 비용 없음. 나머지 cap 1, 2, 5, 6 도 같이 ReAct 화할지, 아니면 새 cap 부터 점진 도입할지.

핵심 의의

이 전환은 "AI 가 뭐 하는지 모르겠다" 라는 가장 큰 사용자 우려를 동시에 해결한다 — agent 가 호출하는 tool 이 그대로 "왜 이렇게 추론했는가" 의 증거 (evidence trail) 가 되기 때문. Round 5 에서 사람과 협업이 잘 됐던 이유는 "맥락을 같이 추적하는 느낌" 이었고, ReAct + tool trace 노출은 그 협업감을 product 에 그대로 옮긴다.

부수효과로, onTong 전체 가치 제안의 차별화 포인트 가 된다 — 단순 RAG agent 가 아니라 "도메인 코드 그래프 위에서 추론하는 agent" 라는 명확한 정체성.
