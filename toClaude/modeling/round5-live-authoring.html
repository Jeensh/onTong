Q4. A-a 루프 + 분할수 — 함께 만든 논리

정의

  • 예: 분할수 = 4 → slab 1개로 4 coil
왜 max → 1 로 줄여가며 시도? (사용자 + 코드 + 논리)

현재 시스템은 "slab 단중 최대화" 단일 모드 (코드 docstring + Q3 답변 명시).

  • 분할수 ↑ → 한 slab 가 더 큰 단중 (4 coil → slab 단중 = 4 × coil 단중)
  • slab 단중 ↑ → 작업 횟수 ↓ → 생산/물류 효율 ↑
  • 그래서 "가능한 최대 분할수부터" 시도. 안 되면 (제약 못 맞춤) 양보 — split-1.

"제품 단중 최대화" 모드 (현재 미구현, TODO step 14)

Q5/6. 1차 / 2차 + LOW / HIGH

  • 철강은 중량 정확 일치 불가 → 하한(LOW) / 상한(HIGH) / 목표(TARGET) 3개로 관리
  • 1차 중량 (FIRST_WGT) = forward 산정. 두께·폭·길이·비중 으로 단중 산정.
  • 2차 중량 (SECOND_WGT_LOW/HIGH) = 추가 제약·고려사항으로 단중 정밀화. 설계가능 단중 범위.

Q7. 폭/길이 FIRST → FINAL → TARGET — 함께 만든 논리

3단계 흐름 — Forward → 단중 정밀화 → Backward 역산 → 단일 목표
  1. FIRST (step 1~4): 두께 → 폭범위 → 길이범위 → 단중범위. 설비 제약 + 주문 스펙으로 *생산 가능 폭/길이 범위*. 단중도 forward 추정.
  2. SECOND_WGT (step 5~6): 단중만 정밀화 (LOW/HIGH). 폭/길이는 1차 그대로 유지.
  3. A-a 루프 (step 7~15): 분할수 + 매수 + slab 단중 수렴. "단중 우선" 으로 최적 분할 결정.
  4. FINAL (step 16~17): Backward. 확정된 단중 + 분할수 → 폭·길이 재산정 (역산).
  5. TARGET (step 18~19): range → 단일 목표값. 실제 생산에 사용할 폭·길이.

★ 핵심 통찰: 단중 (효율의 핵심 지표) 이 driver. 폭/길이는 단중을 만족하는 방향으로 최종 정해짐. Forward → Backward 라는 두 패스가 이 driver 를 중심으로 도는 이유.

Q8. 매수 / 분할수 / 한 주문 → N slab

예: 100톤 주문, 제품 단중 10톤 → 10 제품 필요. slab 분할수=2 → 5 slab 필요.

  • 설계대기량 (designPendQty) = 한 주문의 총 제품 중량 요청 (LOW/HIGH)
  • 매수 (slabCount) = 만들어야 하는 slab 개수
  • 분할수 (splitCount) = 1 slab 가 만드는 제품 개수
  • 관계: 제품수 = 매수 × 분할수, 총 제품 중량 ≈ 매수 × slab단중 × 실수율

의미slab 1개 = "물리적 slab 1장". 매수 5 → 같은 설계로 5장 만든다 → 각 장에 고유 slabNo.

② slabNo (12자리)

SLAB_RESULT row 마다 1 slabNo. 즉 매수 N → slabNo N 개. 물리 slab 1장의 식별자.

③ SLAB_DESIGN_HIST

사용자(설계자) 추적용. step 별로 어떤 값이 어떻게 변했는지 audit. 디버깅 + 사용자 행동 분석.

④ coil (제품) 의 위치 — Ontology 밖

coil = slab 압연 후 산출물. 진행관리 / MES 영역. 공정계획 (slab 설계) ontology 에는 포함하지 않음. slab 설계는 "분할수 = N coil 나올 예정" 까지만 알고, 실제 coil entity 는 다루지 않음.

⑤ 매수 vs 분할수 — 핵심 구분

용어정의위치
매수 (slabCount)한 주문 에서 만들어지는 slab 개수주문 level — slab N 장
분할수 (splitCount)한 slab 안 에서 압연 후 나올 coil 개수 (설계 값)slab level 의 설계 결정값

예: 주문 100t · 분할수 4 · slab 단중 25t → 매수 1, slab 1장 → 압연 후 coil 4개.
예: 주문 100t · 분할수 4 · slab 단중 12.5t → 매수 2, slab 2장 (각 12.5t) → 각 slab 에서 coil 4개씩 → 총 coil 8개.

⑥ designStatus = FAIL → SLAB_RESULT 미저장

FAIL 인 경우 SLAB_RESULT 에 row 안 적재. SLAB_DESIGN_HIST 에는 step 별 시도 기록 남음. errorCode (DG001~005) 는 HIST 에서 추적.

Step 6 — HrMinWgt / HrMaxWgt 도메인 사실 ✓

완료 (사실 부분) C-Q1 모델링은 재추천 진행 (다음 step)

① cell 의 진짜 의미 — "2D 구간 상한" (이게 핵심!)

cell 의 (THICKNESS, WIDTH) 는 lookup key 가 아니라 구간 상한 좌표. 이전 cell 의 좌표 ~ 이 cell 의 좌표 사이 주문이 이 cell 의 단중을 사용 → 2D step function. 

예시 (HR_MAX_WGT, 한 plant):

           폭 (가로, 좌→우 ASC)
           1000   1500   2000
        ┌───────┬───────┬───────┐
   200  │ 15000 │ 18000 │ 20000 │  ← 두께 ≤200 행
        ├───────┼───────┼───────┤
   250  │ 17000 │ 22000 │ 24000 │  ← 두께 200초과~250 행
        └───────┴───────┴───────┘
   ↑ 두께 (세로, 위→아래 ASC)

룩업: 주문 (두께=210, 폭=1200)
  → 두께 행: 200초과~250 = 두께 250 행
  → 폭 열:   1000초과~1500 = 폭 1500 열
  → cell (250, 1500) → maxWgt = 22000

코드:  WHERE THICKNESS >= 입력  AND WIDTH >= 입력
       ORDER BY THICKNESS ASC, WIDTH ASC LIMIT 1
  = "내 입력보다 크거나 같은 가장 작은 cell"

② B-Q3 — MIN/MAX 별도 테이블 이유 (중요)

B-2. 핵심 정책 — Indexing + Caching + Subgraph

정책 1 — SQLite FTS5 + 임베딩 RAG (코드 + Decision Log)
  • 코드 metadata index — class 명, table 명, PK column 등 FTS5 search
  • Decision Log — entity·step·날짜·결정자 별 색인
  • 패턴 라이브러리 — 임베딩으로 "비슷한 패턴 top-5" retrieve
  • 이미 onTong 의 5K 클래스 feedback 에서 FTS5 + pagination 정책 결정됨 — 재사용
정책 2 — 그래프는 subgraph navigation (전체 X)
  • 현재 entity + 1-hop neighbors 만 렌더 (보통 ~10~30 노드)
  • 사용자가 노드 클릭 → 다음 hop 확장
  • 이미 ontology graph UX feedback (dagre + 드래그 + 코드매핑 노출 + subgraph) 에서 결정됨 — 재사용
정책 3 — Prompt Caching layered + 운영자별 namespace
  • Layer 1 (전역): 코드 metadata, 패턴 라이브러리 — 모든 운영자 공유 cache
  • Layer 2 (branch): 본 branch 의 인터뷰 history — branch 별 cache
  • Layer 3 (turn): 직전 turn 답변 — 짧은 TTL
  • cache miss 시 fallback: index 에서 retrieve → LLM 재호출
정책 4 — 코드 추출 lazy + chunked
  • repo import 시 metadata 만 추출 (file 위치, class 이름, PK column) — 빠름
  • 인터뷰 도중 필요한 file body 만 on-demand 읽기
  • file body 도 chunk 단위 — 한 method 만 보내면 LLM context 절약
정책 5 — Merge conflict 는 entity·property 단위로 미리 hash
  • 각 entity·property 의 hash 계산 → branch 간 diff 는 hash 비교
  • 변경된 entity 만 LLM 의 "충돌 분석" 호출
  • 전수 비교 X (~10s → ~1s)

B-3. "사용자가 못 쓸 정도로 느린" 케이스

위 5 정책 적용 후 남는 진짜 위험:

  • LLM 자체의 ~3~6s — Sonnet/Opus 호출 시간. 이건 streaming 으로 체감 완화 (만족감 전략 1)
  • cache miss 시 5K 클래스 첫 retrieve — 첫 턴 ~5s, 이후 ~50ms. UI loading 표시
  • branch merge 시 100+ entity 한꺼번에 conflict — drama 시나리오. 점진적 merge UX 필요 (Risk 9.1)

캐싱 잘 된 경우 평균 turn = ~3-5s (LLM 자체 + UI render). 사용자 인식상 ChatGPT/Claude 와 유사.

위 B-1 표 + B-2 의 5 정책을 design 문서의 새 §12 로 추가. 5K 클래스 가정 / FTS5 + 임베딩 RAG / subgraph / layered cache / lazy 코드 추출 / hash diff merge 명시.

축 2 — Prompt Caching (Anthropic 지원, 자동)

맥락 5중 RAG 의 대부분은 턴마다 변하지 않음 (결정로그·패턴 라이브러리·코드 anchor). 이건 prompt 캐시에 두면:

  • 두 번째 호출부터 input token 비용 ~10% (90% 할인)
  • 지연도 단축 (캐시 hit 시 빠름)
  • 5분 내 재호출 시만 유효 — 인터뷰는 보통 빠르게 진행되므로 거의 항상 hit

효과: 입력 비용 ~10x 절감. 인터뷰 흐름이 빠르게 진행될수록 효과 큼.

축 3 — Structured Output (function calling / Pydantic)

"옵션 표 + 추천" 같은 패턴을 자유서술로 받지 않고 schema 로 받음: 

class OptionTable(BaseModel):
    options: list[Option]    # name, pros, cons, score
    recommended: str          # option name
    reasoning: str            # 짧게 한 문단

# LLM 응답이 이 schema 강제 → 형식 발명 비용 0

효과: 출력 token 절감 (마크다운 표 헤더 같은 overhead 없음). UI 렌더링 안정. JSON 파싱 안정.

축 4 — Code-not-LLM (deterministic 로직)

LLM 호출이 필요 없는 작업은 일반 코드로:

  • 표시명 ↔ id 변환 ("열연공장" ↔ HrPlant) — 매핑 테이블
  • archive 표 → markdown 직렬화 — 템플릿 함수
  • entity 그래프 차트 — dagre/d3 자동 레이아웃
  • 중복 entity 이름 검사 — DB query
  • code anchor 매칭 정확도 검사 — string match

효과: LLM 호출 횟수 자체 감소. 응답 속도 즉시 (~ms).

축 5 — Pre-baked Pattern Templates

자주 나오는 패턴은 프롬프트에 매번 만들지 말고 템플릿으로 저장:

  • Plant + Constraint Composition (Step 5 결정)
  • 2D 구간표 (CEILING_2D lookup) (Step 7 결정)
  • Asymmetric scope (Group=top / Capability=Plant) (Step 10 결정)
  • Wildcard + matchPattern (Step 5 + Step 8)

AI 가 사용자 답변을 듣고 "이건 패턴 X 다" 분류 → 템플릿 fill → 끝. Opus 가 매번 reasoning 안 함.
효과: 같은 패턴 재사용 시 비용 ~1/10. 일관성도 자동 보장.

A. "살아있는 ontology preview" 명확화 (Q2 답변)

먼저 지금 우리가 안 한 것 부터: round 5 작업 동안 archive 에 결정사항이 텍스트 로 누적됐을 뿐, onTong 의 실제 ontology DB 에는 entity 0개 들어감. 즉 결정만 있고 entity 가 만들어진 적은 없음.

측면현재 우리 작업살아있는 preview (제안)

B. Multi-Operator + 맥락 유지 (Q5 우려에 대한 답)

가장 어려운 문제. Claude Code 의 만족감은 "전체 맥락을 가진 1:1 컨설팅" 에서 옴. 멀티 운영자에서 이걸 재현하는 건 정공법 솔루션 없음 — 절충 필요. 4 가지 모델 비교:

B-1. 협업 모델 옵션

모델구조맥락 유지장단
M-1: 분담 (entity owner) 각 entity 에 담당자. 다른 사람은 read-only. 담당자 본인만 1:1 깊이 충돌 없음 / 전체 흐름 일관성 어려움
★ M-2: branch + merge (git 식) 각 운영자가 branch 작업. 합의되면 merge. branch 별로 1:1 깊이 유지 병행 가능 + 충돌 명시화 / merge UX 부담
M-3: 동시 채팅 (Google Docs 식) 한 entity 채팅에 여러 운영자 참여 한 채팅 내 다중 음성 — AI 혼란 실시간 협업 / AI 가 누구 답변인지 추적 어려움
M-4: 큐 (Linear 식 assignment) "검토 필요" 작업 큐. 누가 잡으면 1:1 진행 잡힌 사람만 1:1 비동기 / 흐름이 끊김

★ M-2 (branch+merge) 추천 이유: 각 운영자는 본인 branch 에서 Claude Code 같은 1:1 깊이 유지. 합의되면 main 에 merge. 충돌은 ontology entity 단위로 명시 (Git PR review 와 유사). onTong 이 이미 git-aware product 이라 거부감 적음.

B-2. 맥락 유지 메커니즘 (M-2 가정)

Claude Code 의 맥락 유지 = 긴 conversation + 메모리 파일. onTong 의 멀티 운영자에서 재현하려면: 

세션 시작 시 AI 에 자동 주입 (RAG 스타일):

[1] 결정 로그 (Decision Log)
    이미 합의된 모든 결정 사항. 누가 언제 어떤 옵션을 선택했고 왜.
    예: "Step 5: HrPlant + Constraint Composition 채택 (운영자 A, 2026-05-04)"

[2] In-Flight 작업 목록
    현재 다른 branch 에서 진행 중인 작업.
    예: "운영자 B 가 Customer 표준 인터뷰 중 (branch=feat/customer-std)"

[3] 패턴 라이브러리
    이전에 확정된 entity 패턴 (HrPlant, 단중표 패턴, Edging 패턴).
    AI 가 새 entity 만들 때 "비슷한 게 있나?" 비교 reference.

[4] 본 branch 의 인터뷰 history
    이 branch 에서 운영자 본인이 한 모든 대화 (긴 conversation).

[5] 코드 anchor (이미 매핑된 코드 파일)
    JPO/Service/Action 의 위치 + 이미 매핑된 entity.

이 5가지가 매 turn 마다 AI prompt 에 자동 inject. RAG with structured context.

B-3. 충돌 시나리오 + 처리

충돌예시처리
이름 중복 운영자 A 가 "HrPlant", B 도 "HrPlant" 다른 정의 merge 시 알림 + 둘 중 선택 또는 통합
패턴 불일치 같은 도메인을 A 는 entity 로, B 는 facet 로 AI 가 자동 탐지 → 합의 채팅 생성
매핑 중복 같은 코드 파일을 두 entity 가 anchor 해석 충돌. 둘 중 하나 양보 또는 분담 재정의

B-4. "Claude Code 같은 만족감" 의 정확한 정체

분석해보면 4가지 요소:

  • 전체 맥락 보유 → B-2 의 5중 RAG 로 흉내
  • 적극적 가설 (수동적 응답이 아님) → AI prompt 에 "가설부터 제시하라" 명시
  • 옵션 + trade-off 표 (지금 우리가 한 것) → UI component 로 강제
  • "세분화" 같은 사용자 요청 즉시 반영 → 인터뷰 길이·세분화 슬라이더 + 사용자 명시 명령

솔직: 현재 LLM 으로 100% 재현은 어려움. 80% 까지가 현실적 목표. 1:1 컨설팅 만족감의 본질은 LLM 이 매 턴 비싼 model (Claude Opus 등) 을 쓰고 긴 context 를 다루는 것 — onTong 도 이걸 그대로 해야 함 (비용·지연 trade-off).

Step 12 — Ontology 문법·UX·AI 매개 (Gap Inspector 보다 우선)

단순히 "용어가 많다" 가 아님. 더 근본:

  • 의사결정 깊이: 한 entity 를 만들 때 BusinessTerm? Action? key? facets? composition? lookupRule? — 6~8개 결정 동시
  • 옵션 부담: scope 가 회사·소? plant? — 매번 도메인 전문지식 + ontology 표현방식 동시 고려
  • 일관성 부담: 8 표준 표준 돌면서 패턴 통일 필요. 사람이 머리로 다 추적 불가
  • 피드백 부재: 작성한 ontology 가 "잘 된" 건지 즉시 알 수 없음

이게 정확히 Palantir 가 컨설턴트를 동반시키는 이유. 그리고 우리가 지금 인터뷰 형식으로 협업하는 이유. AI 매개가 본질적인 답. 단지 옵션이 아니라 product core.

④ Grammar 자체도 단순화 후보

AI 매개를 도입한다 해도 grammar 는 여전히 ontology 의 저장 형식 — DB 컬럼처럼 정해진 형태가 있어야 함. 우리가 발명한 부분 중 단순화 가능한 것:

현재제안효과
facetsproperties (Palantir 와 동일)친숙도 ↑
lookupRule: CEILING_2D 같은 enum"어떻게 룩업하는가" 자연어 description + 코드 함수 reference유연성 ↑, 학습부담 ↓
matchPattern: EXACT/WILDCARDrow 자체에 "match: '*'" 같이 표시 (별도 enum 없음)단순
scope: 회사·소ownedBy 관계 (없으면 top-level)명시적
tabular [(...)]별도 entity 로 분리 (기존 ER 모델대로)표준 회복. 단점: entity 수 폭증 (단중표 cell 단위처럼)

마지막 항목 (tabular vs separate entity) 은 trade-off. 우리는 의도적으로 tabular 선택 (entity 폭증 방지). 이 결정은 옳지만, 그 대신 표준에서 벗어남. AI 매개가 있다면 사용자에게 이 trade-off 안 보여도 됨.

⑤ Gap Inspector 와의 관계

둘은 사실 같은 패턴 — AI 가 사용자 멘탈 모델 ↔ 코드 사이를 매개. 차이는 매개 시점:

  • Authoring AI: ontology 를 만드는 동안 매개 (사용자 → 도메인 표현)

Step 10 — Edging 모델링 정확한 재추천 (asymmetric scope)

진행 중 Phase A.7.6 · Group=Org-level / Capability=Plant-level

★ 추천 — 옵션 D-3″ (asymmetric scope 정확 반영)

제안 — Group 은 stand-alone, Capability 는 HrPlant 산하
신규 BusinessTerm:

  ─ EdgingGroupRule (열연Edging규격그룹기준)
        scope:  회사·소 단위 (plant 무관)
        key:    (CMP_CD, ORG_CD)  → 한 회사·소 당 1 entity
        facets:
          ▸ rules: tabular [
              {priority, gradeCd, productTypeCd, customerCd,
               hrTgtWidthLow, hrTgtWidthHigh, → outputGroupCd}
            ]
          ▸ lookupRule: PRIORITY_RULE_ENGINE
              "(강종+품종+고객 일치) AND (열연목표폭 BETWEEN low~high)
               → priority 작은 것 1건 → outputGroupCd"
          ▸ errorOnMiss: failEdgingGroup

  ─ HrPlantEdgingCapability (열연Edging 능력기준)
        scope:  열연공장 단위
        key:    HrPlant 1개 (1 plant : 1 capability table)
        facets:
          ▸ capabilities: tabular [
              {edgingGroupCd, capLow, capHigh, matchPattern}
            ]
            ─ capLow/High = 깎을 수 있는 양의 LOW/HIGH 한도 (양수, mm)
            ─ matchPattern = EXACT (그룹별) 또는 WILDCARD ('*' = plant default)
          ▸ lookupRule: EXACT_THEN_WILDCARD
          ▸ errorOnMiss: IllegalStateException

관계 갱신:
  EdgingGroupRule          (top-level, 회사·소 단위)
  HrPlant ──┬── N HrPlantConstraint        (HR_SPEC)
            ├── 1 압연MAX단중기준           (HR_MAX_WGT)
            ├── 1 압연MIN단중기준           (HR_MIN_WGT)
            └── 1 HrPlantEdgingCapability  (EDGING_SPEC, plant 별)

협력 흐름 (런타임):
  주문 → EdgingGroupRule.lookup(주문) → groupCd
       → 주문의 confirmedPlantCd[열연위치] 로 HrPlant 찾기
       → HrPlant.edgingCapability.lookup(groupCd) → capLow, capHigh

코드 갭 (Q2) — 이게 영향도 분석 데모의 핵심 소재

현재 코드: EDGING_SPEC.PK = (CMP_CD, ORG_CD, EDGING_GROUP_CD) — HR_PLANT_CD 누락.
의미: 같은 회사·소·그룹이라도 1열연 vs 2열연 능력이 다른데 코드는 한 row 만 저장 가능.

   "EDGING_SPEC 테이블에 HR_PLANT_CD 컬럼 추가" 변경 → 영향도 분석 → EdgingSpecPK / EdgingSpecJpo / EdgingSpecRepository / SdWidthRangeAction 의 lookup 호출 등 자동 추적

EdgingGroupRule 이 회사·소 단위라는 점에서, "Org" (회사·소) 라는 entity 를 명시적으로 만들지 여부가 영향. 다음 표준 (Customer, Productivity) 도 회사·소 단위일 가능성 큼.

Step 9 — Edging 모델링 재추천 (HrPlant 산하 구조)

진행 중 Phase A.7.5 · 단중표 패턴과 일관된 흡수

핵심 정정: 코드의 PK 가 (CMP+ORG+GROUP) 으로 보였지만, 도메인상 EDGING 은 HrPlant 의 능력. → 이전 단중표 (HR_MIN_WGT, HR_MAX_WGT) 와 동일하게 HrPlant 산하 entity 로 흡수.

★ 추천 — 옵션 D-3′: HrPlant 산하 + 단중표 패턴 일관

제안 — HrPlant 산하 신규 entity 2개 (Group rule + Capability)
BusinessTerm (이미 있음):
  - HrPlant (열연공장)
        + N HrPlantConstraint     (HR_SPEC, 품종별 폭/길이)
        + 1 압연MAX단중기준        (HR_MAX_WGT)
        + 1 압연MIN단중기준        (HR_MIN_WGT)

BusinessTerm (신규 — Step 9):
  - HrPlantEdgingGroupRule     표시명: "열연Edging규격그룹기준"
        key:    HrPlant 1개 (1 plant : 1 rule table)
        facets:
          ▸ rules: tabular [
              {priority, gradeCd, productTypeCd, customerCd,
               hrTgtWidthLow, hrTgtWidthHigh, → outputGroupCd}
            ]
            의미: 한 row = 한 룰. 매칭 조건 + 출력 그룹코드
          ▸ lookupRule: PRIORITY_RULE_ENGINE
              ─ "(강종+품종+고객 일치) AND (열연목표폭 BETWEEN low~high)
                 → priority 작은 것 1건 → outputGroupCd"
          ▸ errorOnMiss: failEdgingGroup (그룹 매칭 실패 = 데이터 결함)

  - HrPlantEdgingCapability    표시명: "열연Edging 능력기준"
        key:    HrPlant 1개 (1 plant : 1 capability table)
        facets:
          ▸ capabilities: tabular [
              {edgingGroupCd, capLow, capHigh, matchPattern}
            ]
            의미: 한 row = 그룹별 깎는 능력 한도 (양수, mm)
                  matchPattern = EXACT (특정 group) 또는 WILDCARD ('*' = plant default)
          ▸ lookupRule: EXACT_THEN_WILDCARD
              ─ "exact 매칭 → 미존재 시 '*' row → 둘 다 없으면 에러"
          ▸ errorOnMiss: IllegalStateException (plant 의 default 도 없는 데이터 결함)

관계 갱신:
HrPlant ──┬── N HrPlantConstraint         (HR_SPEC)
          ├── 1 압연MAX단중기준            (HR_MAX_WGT)
          ├── 1 압연MIN단중기준            (HR_MIN_WGT)
          ├── 1 열연Edging규격그룹기준     (EDGING_GROUP, 룰엔진 tabular)
          └── 1 열연Edging 능력기준        (EDGING_SPEC, capability tabular)

왜 이 구조인가

  • 도메인 일치: B-Q2 의 "EDGING 은 HrPlant 의 능력" 정정 반영. plant 산하로 들어감
  • 단중표 패턴 재사용: HR_MAX/MIN_WGT 와 동일하게 "1 plant : 1 tabular table" entity. ontology 어휘 일관
  • '*' 의 진짜 의미 표현: "plant 의 default capability" 라는 의미가 capability table 안의 한 row (matchPattern=WILDCARD) 로 자연스럽게 나옴
  • 영향도 분석 demo: "1열연 그룹 룰 priority 3 변경" / "2열연 default 능력 cap 100→80 변경" 같은 시나리오 자연스럽게 표현 가능
  • 코드와의 갭 표시: 현재 데모 코드 PK = (CMP, ORG, GROUP) 은 단순화. ontology 의 매핑 시 "현재 구현 단순화 — HrPlant key 누락" 같은 메모 가능 (영향도 분석 시 "여기를 plant-aware 하게 수정해야 함" 같은 demo)

데모 코드의 단순화 처리

현재 코드: EDGING_SPEC.PK = (CMP, ORG, GROUP) — HrPlant 키 없음.
ontology 매핑 시: HrPlant 매핑은 "미구현" 표시 + 데모 시 "이 코드는 plant 별로 다른 능력을 못 표현하니 수정 필요" 로 활용 가능 (영향도 분석 데모의 좋은 소재).
또는: 현재 코드 그대로 매핑하고 ontology 도 단일 EDGING entity 로 (정확도 낮음, 도메인과 어긋남) — 비추천.

Step 8 — 표준 데이터 ③ EdgingSpec + EdgingGroup (사이드 압연 능력)

진행 중 Phase A.7 · 2단 룩업 (룰엔진 → catchall fallback)

또 다른 형태: EDGING 은 "주문 → group 결정" + "group → spec(능력) 결정" 의 2단 룩업. EdgingGroup 은 priority 기반 룰엔진, EdgingSpec 은 '*' catchall fallback 패턴. HrSpec(정확매칭) / 단중표(2D 구간) 와는 또 다른 성격.

A-① EDGING 흐름 (SdWidthRangeAction 에서)
1. EDGING_GROUP 룩업 (룰엔진):

Step 7 — 단중표 모델링 C-Q1 재추천 (B-Q1 통찰 반영)

왜 재추천? 이전엔 cell 을 단순 "lookup row" 로 봤지만, B-Q1 답변으로 cell 좌표가 사실 "2D 구간의 상한" 을 의미한다는 것을 알게 됨. 이걸 모델링에 반영해야 영향도 분석·시뮬레이션 시 "이 구간을 변경" 같은 자연스러운 표현이 가능.

  - HrPlantMaxWgtTable
        표시명: "열연공장 최대단중표"
        key:    HrPlant 1개 (1 plant : 1 table)
        facets:
          ▸ axes:
              - thickness:  ASC, unit=mm  (세로축, 위→아래 오름차순)
              - width:      ASC, unit=mm  (가로축, 좌→우 오름차순)
          ▸ cells: list of {thicknessUpper, widthUpper, maxWgt}
              ─ 각 row 의미: "이전 row 좌표 초과 ~ 이 row 좌표 이하" 의 2D 구간
              ─ thicknessUpper, widthUpper = 그 구간의 상한 좌표
              ─ maxWgt = 그 구간의 단중 상한 (kg)
          ▸ lookupRule: CEILING_2D

                 thicknessUpper >= orderThickness AND widthUpper >= orderWidth
                 인 것 중 가장 작은 cell"
          ▸ defaultCell: 마지막 cell (최대 좌표) — 모든 입력 cover 의도
          ▸ errorOnMiss: ALG_HR_MAX_WGT_NOT_FOUND (DG107)
          ▸ rowCount: ~수십~백

        ⚠️ Max 와 cells 좌표가 다름 (B-Q3) — 별도 entity

관계도

HrPlant ──┬── N HrPlantConstraint    (HR_SPEC, 품종별 폭/길이 범위 — Step 5 에서 결정)
          ├── 1 HrPlantMaxWgtTable   (HR_MAX_WGT, 2D 구간표 — 신규)
          └── 1 HrPlantMinWgtTable   (HR_MIN_WGT, 2D 구간표 — 신규)

왜 이 구조인가

  • cell 의 "구간 상한" 의미를 facet 에 명시 — 단순 lookup table 이 아니라 "2D step function" 이라는 도메인 의미가 살아있음
  • 1 plant : 1 table — entity 폭증 없음 (cells 는 facet 안 tabular data). 사용자가 "1열연의 max 단중표" 하나로 navigate
  • MIN/MAX 분리 — B-Q3 의 "두 grid 가 다름" 반영
  • HrPlantConstraint 와 분리 — 단중표 PK 에 품종 없음 → constraint 와 다른 entity 가 자연
  • 영향도 분석: "1열연 max 단중표의 (200,1500) cell 22000 → 20000 변경" 시나리오 자연스럽게 표현 가능
  • 시뮬레이션: cells 통째로 swap 하거나 lookupRule 만 바꿔보기 같은 실험 가능

Step 6 — 표준 데이터 ② HrMinWgt + HrMaxWgt (단중 한도)

진행 중 Phase A.6 · 압연 단중 MIN / MAX 한도표

왜 별도 step? 코드 분석 결과 이 두 표준은 HrSpec 과 형태가 다름: PK 의 일부가 카테고리 식별자 가 아닌 좌표 값 (THICKNESS, WIDTH). 룩업도 정확매칭이 아닌 ceiling lookup (≥ 입력값 cover 하는 가장 작은 cell). 옵션 C 그대로 적용이 어색해서 모델링 옵션부터 의논.

📦 PART A — 코드에서 이미 확인한 사실

A-① 두 테이블 비교
항목HR_MIN_WGTHR_MAX_WGT
JPOHrMinWgtJpoHrMaxWgtJpo
PK (5축)CMP_CD · ORG_CD · HR_CD · THICKNESS · WIDTH (동일)
주는 값MIN_WGT (단일 숫자)MAX_WGT (단일 숫자)
호출 ActionSdSecondWgtLowAction (step 5)SdSecondWgtHighAction (step 6)
HR_CDHR_SPEC.HR_PLANT_CD 와 동일 도메인 (열연공장 1자리). 컬럼명만 다름 (레거시 비표준)
A-② 룩업 패턴 (주석에서)
주문의 (입력두께, 입력폭) 으로 룩업:
  WHERE THICKNESS >= 입력두께 AND WIDTH >= 입력폭
  ORDER BY THICKNESS ASC, WIDTH ASC LIMIT 1
= 입력값을 cover 하는 가장 작은 cell 의 MIN/MAX_WGT 반환 (ceiling lookup)

호출 시:
  hrMaxWgtService.lookup(cmpCd, orgCd, hrCd,
                          slab.slabThickness, slab.firstWidthHigh)
  → 폭은 firstWidthHigh (slab의 1차 폭상한). 2019-11-22 변경 (이전: orderWidth).
A-③ miss 처리

SdSecondWgtHighAction 에서 maxWgt == null → AlgorithmException(SdErrorCode.ALG_HR_MAX_WGT_NOT_FOUND) 명시적 던짐. HrSpec 의 NPE 와 다르게 깨끗함.
