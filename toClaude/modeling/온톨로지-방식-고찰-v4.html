1. 팔란티어 추가 발견 — Interface · Struct · Shared Property

팔란티어가 명사 측 (Object Type) 의 내부 구조를 어떻게 푸는지 — 이게 우리 BusinessTerm 의 복합 처리 설계와 직결됨.

1.1 Interface Type

"Object Type 의 shape 와 capability 를 기술하는 polymorphism 메커니즘"

  • 예: Facility interface { name, location } 을 Airport, Plant, Hangar Object Type 이 implement
  • 다중 implement 가능 / interface extension (계층) 가능
  • 한계: "aggregating by interfaces" 와 "interface link types" 는 in development (2026-05 현재)

→ 공통 shape 추상화. 우리로 치면 "여러 BusinessTerm 이 공유하는 attribute 묶음" 정도.

1.2 Shared Properties

여러 Object Type 에서 재사용되는 property 정의

  • "property 메타데이터의 중앙 관리"
  • 같은 이름의 property 가 여러 Object Type 에 등장하면 자동 매핑

→ 우리로 치면 atomic BusinessTerm 을 여러 composite 가 참조해 쓰는 패턴.

1.3 Structs (← 결정적 한계)

"schema-based properties with multiple fields" — 즉 한 property 슬롯 안에 여러 필드 묶기 (Address = {street, city, zip} 류)

제약 — 우리에게 매우 중요

  • Depth 1 — struct 안에 struct 못 넣음
  • Max 10 fields
  • 지원 필드 타입: STRING/INTEGER/TIMESTAMP/GEOPOINT 등 primitive 만. object reference 못 담음.
  • Array of struct 의 query 의미가 어색 (independent matching — 한 struct 안에서 매칭 안 함)

의미: 팔란티어조차 "주문 = 주문스펙 + 진행관리 + 품질설계 + 화학성분" 같은 깊은 복합을 struct 로 못 표현한다. Address 같은 좁은 묶음만 struct, 깊은 composite 는 linked Object Types 로 분해해야 한다.

핵심 통찰

팔란티어의 "deep composite 모델링 정답" = Object Type 분해 + Link 로 묶기 + 좁은 bundle 만 struct. 우리도 같은 패턴이 자연스럽다. 즉 BusinessTerm 을 composite/aggregate/atomic 으로 분류하고 HAS_A 류 composition 관계로 묶는다. 이게 우리가 팔란티어 한계 (struct depth 1) 를 넘는 방법: 우리는 어차피 노드·관계 그래프라 깊이 제한 없음.

2. 강약점 매트릭스 — 우리 모델 vs 팔란티어

요약 — 우리가 팔란티어보다 약한 두 곳

  1. Interface Type / polymorphism — 공통 shape 가 여러 도메인에 등장하면 추상화 부재
  2. 거버넌스 / 권한 모델 — 멀티-tenant 운영 도구 가야 한다면 보강 필요

두 약점 모두 현재 로드맵 밖. Phase 2+ 에 가서야 가치 발생. 지금 추가하면 over-engineering.

요약 — 우리가 팔란티어보다 강한 다섯 곳

  1. 코드를 ground truth 로 받기 (별도 Function 작성 불필요)
  2. 매뉴얼 fragment 통합 (3-way 매핑)
  3. 매핑 사각지대 가시화 (Unmapped Methods 패널)
  4. fragment-level Anchor binding (god-method 도 부분 매핑)
  5. VerificationLevel 진척 KPI (시뮬 신뢰도 calibration)

3. 도메인 케이스 — 주문 분해

실제 onTong 사용자가 마주칠 복합 개념. 4 가지 구성 요소로 나뉘는데, 각자가 또 내부 구조를 가진다.

주문 [aggregate] ├─ 주문번호 [atom · string] ├─ 고객 [reference → 거래처] ├─ 주문스펙 [bundle] 1:1 │ ├─ 품종 [atom · string] │ ├─ 강종 [atom · string] │ ├─ 직경 [atom · float, mm] │ └─ 길이 [atom · float, mm] ├─ 진행관리정보 [aggregate] 1:1 │ ├─ 현재공정 [atom · string] │ ├─ 목표납기 [atom · timestamp] │ └─ 마일스톤 [1:N · 마일스톤] ├─ 품질설계정보 [aggregate] 1:1 │ ├─ 인장강도목표 [atom · float, MPa, range:600~800] │ ├─ 항복강도목표 [atom · float, MPa] │ └─ 시험항목 [1:N · 시험항목] └─ 화학성분정보 [bundle · 1:N 측정시점] ├─ C [atom · float, %, range:0.10~0.25] ├─ Si [atom · float, %, range:0.15~0.40] ├─ Mn [atom · float, %, range:1.20~1.60] ├─ P [atom · float, %, max:0.025] └─ S [atom · float, %, max:0.020]

3.1 분류 — 4 종 BusinessTerm.kind 가 필요

kind의미예시composition
atomic primitive 값 (일반화 단위) C 함량 (float, %), 직경 (float, mm) parts 없음, value_type/unit/range 가짐
bundle 좁은 묶음 — primitive 들의 dataclass 화학성분(C/Si/Mn/P/S), 좌표(x/y), 주소 parts 가 atomic 만 (depth 1, ≤ ~10) — 팔란티어 struct 정합
aggregate 깊은 composite — sub-term 트리 주문, 주문스펙, 품질설계정보, 진행관리정보 parts 가 bundle/aggregate/reference/atomic 무엇이든, 깊이 제한 없음
reference 독립 엔티티 (다른 곳에서도 참조) 거래처, 품목, 작업장 스스로 aggregate 일 수 있음, 다른 term 이 ref 로 가리킴 (link)

3.2 매핑 패턴 — 같은 도메인이 코드 측에서 어떻게 보일까

// Java 도메인 객체 (전형적인 SCM 코드)
class Order {
    String orderNo;
    Counterparty customer;
    OrderSpec spec;              // → BusinessTerm "주문스펙" (aggregate)
    ProgressInfo progress;        // → "진행관리정보" (aggregate)
    QualityDesign quality;        // → "품질설계정보" (aggregate)
    List<ChemComposition> comps;  // → "화학성분정보" (bundle, 1:N)
}

class ChemComposition {  // bundle (= Palantir struct depth 1)
    Instant measuredAt;
    double C, Si, Mn, P, S;
}

// 시뮬 대상 메서드
class QualityValidator {
    ValidationResult validate(Order order) {       // ← Action "주문_품질검증"
        ChemComposition latest = order.comps.get(order.comps.size()-1);
        if (latest.C < 0.10 || latest.C > 0.25) {  // ← Anchor: literal 0.10, 0.25
            return fail("C 함량 범위 위반");
        }
        if (latest.Mn < 1.20) ...
    }
}

이 코드의 anchor 들이 composite term 의 깊은 슬롯을 가리켜야 함:

  • literal 0.10 → 주문.화학성분정보.C.range[0]
  • literal 0.25 → 주문.화학성분정보.C.range[1]
  • field_access order.comps → 주문.화학성분정보 (1:N)
  • local latest → 주문.화학성분정보 [최신 1건] (selector 표현 필요)

4. 모델 보강 — Composite BusinessTerm + 경로 표기

4.1 BusinessTerm 확장

class BusinessTerm:
    qualified_name: str              # "term.scm.order"
    canonical_label: str             # "주문"
    aliases: list[str]
    domain: str
    description: str
    kind: TermKind                   # atomic / bundle / aggregate / reference
    confirmed: bool

    # — atomic 일 때만
    value_type: ValueType | None     # int/float/string/bool/timestamp
    unit: str | None
    range: list[float] | None
    enum_values: list[str] | None    # for string enum

class TermComposition:               # 노드가 아닌 엣지
    parent_fqn: str
    child_fqn: str
    role_name: str                   # "spec" / "composition" / "quality"
    cardinality: Literal["1:1", "0:1", "1:N", "0:N"]
    required: bool
    description: str = ""

4.2 경로 표기 — 통일된 dotted path

같은 syntax 가 graph traversal (link) 과 struct field access 양쪽에 동작:

# 모든 슬롯 path 는 동일한 형식
"params[0].spec.diameter"          # 주문 → 주문스펙(aggregate) → 직경(atomic)
"params[0].composition[-1].C"      # 주문 → 화학성분정보(bundle, 1:N) → 마지막 → C
"params[0].progress.milestones[*].name"  # 1:N traversal with wildcard
"effects[0].target_term=주문.품질설계정보.인장강도목표"
"preconditions[2]"                 # Action 슬롯 직접

parser 는 segment 별로 traversal 종류 결정:

  • .<name> = 1:1 또는 0:1 traversal (단일 sub-term) 또는 atomic field
  • [i], [-1], [*] = 1:N collection 접근 (index / 마지막 / 전체)
  • 마지막 segment 가 atomic 이면 leaf, aggregate/bundle 이면 sub-tree

4.3 모델 invariant (composite 추가)

  1. kind=atomic 은 TermComposition 의 parent 로 등장 금지 (parts 없음)
  2. kind=bundle 의 children 은 모두 atomic (depth 1 정합)
  3. kind=aggregate 의 children 은 무엇이든 (depth 무제한)
  4. TermComposition graph 는 DAG (사이클 금지) — 기존 PARENT_PROCESS 사이클 검출 패턴 재사용
  5. kind=reference 인 term 은 다른 aggregate 에서 link 로만 가리킴, 직접 part 가 되지 않음 (독립 lifecycle)

7. 결정 질문 4 개 — Composite 모델링
