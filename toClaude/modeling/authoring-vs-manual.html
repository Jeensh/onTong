§1. onTong 의 ontology 작성 3 path

① 자동 Recommend

기존 · 작동 중
코드 import 후 POST /api/ontology/repos/{repo}/recommend 로 자동 후보 생성. heuristic + LLM 으로 BusinessTerm + Action + Realization 한꺼번에 generate.
  • 입력: 코드 (CodeType, CodeMethod)
  • 출력: 후보 entity 들 (큐에 적재)
  • 인간 개입: 거의 없음 (자동 generate)

② 큐 confirm / reject

기존 · 작동 중
좌측 📥큐 탭에 ① recommend 가 만든 후보 list. 사용자가 한 행 클릭 → confirm 또는 reject.
  • 입력: 자동 후보 + 사용자 판단
  • 출력: confirmed BusinessTerm / Action
  • 인간 개입: per-entity 1 클릭 (yes/no)

③ Authoring AI 인터뷰 (우리)

신규 · R2 진행 중
코드 → 가설 → Q&A → 옵션 → 명명 → archive → confirm. Round 5 의 협업 패턴 그대로.
  • 입력: 코드 + 도메인 인터뷰
  • 출력: 정확한 BusinessTerm (with composition)
  • 인간 개입: 매 turn 답변 + 옵션 선택
발견한 사실 — frontend grep 결과: "신규 Term", "BusinessTermForm", "ActionForm" 등 매칭 0건.
→ onTong 에 완전 수동 form (빈 페이지부터 BusinessTerm 직접 작성) 은 없음. 자동 recommend 가 만든 것을 큐에서 confirm / reject 하는 게 유일한 manual path.

§2. 3 path 의 적합 시나리오

시나리오 최적 path 이유
repo 처음 import — 100+ class 한꺼번에 채워야 ① + ② recommend 가 1회 generate → 큐에서 빠르게 confirm/reject. quality 낮아도 양 우선.
핵심 entity (HrPlant 같은) 깊이 있게 만들기 ③ Authoring 도메인 인터뷰로 의미·composition·옵션 trade-off 까지. 비용 ↑ 이지만 quality ↑↑.
recommend 결과 잘못 — 이름·구조 다르게 ② reject + ③ 다시 큐에서 reject 후 Authoring 으로 새로 — 가장 reliable.
Action 작성 ① 만 가능 Authoring 은 아직 BusinessTerm 만 다룸. Action 은 recommend 가 method 분석으로 만들고 큐에서 confirm.
"빈 페이지부터 BusinessTerm 만들기" (코드 없이) 없음 onTong 디자인은 코드가 source of truth. 코드 없이 entity 직접 만드는 path 는 의도적으로 빠짐. (reverse engineering tool 컨셉)

§3. 현재 onTong 의 ontology 작성 흐름 — 사용자 입장에서

[코드 import 직후 — recommend 안 돌렸을 때] ↓ 좌측 코드 트리: 클래스 보임 큐 탭: 비어있음 Detail mode: Action 미선택 (빈 화면) ✏️ Authoring: 사용 가능 ✓ ──────────────────────────────────────────────────────────── [recommend 1회 실행 후 — 일반 onTong 사용 흐름] ↓ 좌측 코드 트리: 클래스 + ★ (term 있음 표시) 큐 탭: 후보 N개 list Detail mode: Action FQN 선택하면 detail 보임 ✓ ✏️ Authoring: 사용 가능 (대안 또는 reject 후 깊게)
사용자 혼란의 원인: 우리는 recommend 안 돌리고 Authoring 만 진행 중. 그래서 큐도 비어있고 Detail/Split 도 빈 화면. 즉 onTong 의 default 흐름 (recommend → 큐 → confirm) 이 안 작동하는 상태.

§4. 권장 흐름 (이상적)

단계 경로 현재 진행도
1. 코드 import 자동 ✅ 완료 (slab-design-real 123 class)
2. 자동 recommend 실행 📥 큐 → bulk 후보 generate 🔴 안 돌렸음 (Authoring 만 사용)
3. 핵심 entity 깊게 (HrPlant 류) ✏️ Authoring 인터뷰 🟡 R2 진행
4. 나머지 entity bulk confirm 📥 큐에서 confirm/reject 🔴 큐 비어있음
5. Action 작성 (큐 confirm) 📥 큐 confirm/reject 🔴 큐 비어있음
6. AnchorBinding (Detail/Split) Detail/Split mode 🔴 Action 데이터 없어서 빈 화면
실용적 다음 행동 후보:
  1. recommend 1회 돌려서 큐 채우기 — 그럼 Detail/Split 도 작동, 현재 빈 화면 해소
  2. Authoring 으로 핵심 entity (HrPlant) 만 깊게 — recommend 가 못 만드는 quality
  3. Authoring + recommend 하이브리드 — recommend 로 채운 후 잘못된 것만 Authoring 으로 재작성

Round 5 의 우리 협업처럼 "정확한 quality" 가 목표면 ② Authoring 단독으로도 OK. 양적 채움이 필요하면 ① + ② 조합.

§6. Clipboard 복사 fix (이번 HTML 부터 적용)

이전 HTML 답변 복사 실패 원인: file:// protocol 은 secure context 가 아니어서 navigator.clipboard.writeText() 가 거부당함. 폴백 코드 추가. 
// 이 HTML 의 copy 버튼은 다음 fallback chain 사용:
async function copyText(text) {
  try {
    if (navigator.clipboard && window.isSecureContext) {
      await navigator.clipboard.writeText(text);
      return "modern";
    }
  } catch {}
  // file:// fallback — temp textarea + execCommand
  const ta = document.createElement("textarea");
  ta.value = text;
  ta.style.cssText = "position:fixed;opacity:0;left:-9999px";
  document.body.appendChild(ta);
  ta.select();
  const ok = document.execCommand("copy");
  document.body.removeChild(ta);
  return ok ? "fallback" : "failed";
}

성공 시 버튼이 "✓ 복사됨 (modern)" 또는 "✓ 복사됨 (fallback)" 으로 표시. 둘 다 실패하면 "✕ 복사 실패 — 미리보기에서 직접 선택" + 미리보기 영역이 자동 select 가능.
