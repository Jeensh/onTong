📋 Phase 1 — 무결점 지식 동기화 (Continuous Ontology Integration)

🎯 이상향
git commit → CI 파이프라인 → Joern CPG + 런타임 로그 자동 분석 → 그래프 DB 갱신. 파괴적 변경 감지 시 build fail + "매핑 재설정 요망" 알럿.
✅ 현재 가진 것
  • 15 analyzer 풀 파싱 (`parse_repo`)
  • P29-3 qualifier-aware call resolver
  • P29-2 MyBatis XML/Annotation
  • P30-1/2 AOP fan-out + event chain
  • .analyzed/entities.json + repo-meta 디스크 캐시
❌ 결정적 결손
  • git push 자동 트리거 없음 — 사용자가 「재등록」 버튼 눌러야 함
  • Stale binding 감지 없음 — confirmed binding 의 code_fqn 이 사라져도 그대로 confirmed
  • 차단 게이트 없음 — gap_engine 은 후행 알림만, PR 막는 hook 없음
  • 변경 영향 추적 없음 — "이 commit 이 어떤 binding 을 깨뜨렸나" 답 못함

현재 시스템 체크포인트 답

"자바 코드가 오늘 배포되었을 때 매핑 데이터가 구버전으로 전락하는 것을 시스템 레벨에서 즉각 감지하고 차단할 수 있는가?"

답: 못 한다. 사용자가 직접 「Repository → 재등록」 버튼을 눌러야 새 분석 결과로 갱신되며, 갱신 후에도 stale binding 은 「proposed → confirmed」 상태 그대로 보존되어 사라진 코드를 가리킬 수 있다. CI 차단 게이트는 존재하지 않는다.

제안: 우회 가능한 공학적 대안 (Joern 도입 없이도)

개입 지점구체적 액션구현 난이도
S7-A. Git webhook GitHub/GitLab webhook → POST /repos/{id}/reindex 백엔드 엔드포인트 신규. 또는 git pull + 변경 파일 추적 데몬 (slab-design-real 같은 로컬 repo 도 가능). 낮음 (1일)
S7-B. Stale binding sweeper 매 재파싱 후 ConceptBindingProposal 전수 점검: code_fqn 이 새 entity index 에 없으면 status를 stale 로 자동 전환 + 사용자 알림. 새 후보 자동 매칭 시도 (alias 일치). 낮음 (반나절)
S7-C. Diff-driven 알림 이전 entities snapshot 과 신규 비교 → "삭제된 method/field 가 어떤 confirmed binding 을 갖고 있었나" 리포트 + 「재매핑 큐」 자동 생성. 중 (1~2일)
S7-D. PR check (선택) GitHub Actions step: onTong CLI --check-bindings 실행 → exit 1 if breaking. 사용자가 GitHub PR 사용 시만 의미. 중 (1~2일, 외부 환경 의존)

📋 Phase 2 — 시맨틱 API 계층화 (Decoupled Semantic Hooks)

🎯 이상향
수동 매핑 결과는 단순 선이 아니라 Mutate({Domain.SafetyStock}, {StockService.reduceStock.param[1]}) 같은 정형화된 메타데이터. 에이전트는 자바 코드 안 보고 "조작 가능한 변수 카탈로그" 만 봄.
✅ 현재 가진 것
  • ConceptBinding: term_fqn ↔ code_fqn (필드/메서드 단위)
  • MethodAnchor: param[base], return[@line:6], literal[70@line:6] 등 정밀 좌표
  • ChangeSpec.kind: anchor_value / method_body 로 변경 타입 분류
  • P14 mutation_extractor: tree-sitter 로 메서드 내 변수 mutation 추적
❌ 결정적 결손
  • 3 부품이 서로 모름 — ConceptBinding 은 anchor 까지 못 들어감, ChangeSpec 은 binding 모름
  • "조작 가능 카탈로그" 부재 — 에이전트가 "이 term 으로 무엇을 mutate 할 수 있나" 질의 불가
  • 역할 메타 없음 — binding 이 "param[1] 인지 return 인지 field-write 인지" 구분 X
  • Python generator 가 raw Java 봄 — "블랙박스 시맨틱 훅" 정확히 반대 방향

현재 시스템 체크포인트 답

"운영자가 수동 매핑을 완료했을 때, 그 결과물이 '단순한 관계망'인가, 아니면 시뮬레이터가 즉시 변수를 인젝션할 수 있는 '실행 가능한 API 명세서'인가?"

답: 단순한 관계망에 가깝다. ConceptBinding 의 정보는 (term_fqn, code_fqn, scope, confidence) 4-tuple 이며, 이걸로 "어떤 위치를 mutate 할 수 있는지" 자동 추론 불가능. ChangeSpec 의 anchor_value 는 직접 anchor_locator 를 사용자가 입력해야 함 (binding 과 join 안 됨).

제안: SemanticHook DTO 도입 — 가장 큰 한 방

class SemanticHook(BaseModel):
    """ConceptBinding × MethodAnchor 결합 — 에이전트가 보는 '실행 가능 카탈로그' 한 줄."""
    term_fqn: str                # "term.안전재고"
    method_fqn: str              # "com.x.StockService.reduceStock"
    anchor_locator: str          # "param[stock]" or "return[@line:42]" or "field_write:this.stock"
    operation: Literal["read", "write", "mutate", "constrain"]
    declared_type: str           # "long" / "BigDecimal" / "List<Slab>"
    valid_range: dict | None     # {"min": 0, "max": 999999} (BusinessRule 에서 추출)
    confidence: float
    source: str                  # "manual" | "alias_match" | "llm_anchor_suggester"
개입 지점구체적 액션구현 난이도
S8-A. SemanticHook 모델 + 자동 derive 기존 (ConceptBinding × MethodAnchor) 조합으로 자동 derive. anchor_binding_suggester 결과를 SemanticHook 으로 승격. 중 (2~3일)
S8-B. GET /semantic-hooks?term_fqn=... "term.안전재고로 무엇을 할 수 있나" 질의 → SemanticHook 리스트 반환. Python generator 가 이걸 받아서 hook 단위로 코드 조립. 중 (1~2일)
S8-C. PythonGenerator 재설계 현재: Java 본문 → LLM → Python (hallucination 발생). 변경 후: SemanticHook 호출 trace → Python 템플릿 (LLM 은 hook 선택만 담당). 결정론 + 검증 가능. 높음 (3~5일, 핵심 변경)
S8-D. ChangeSpec ↔ Hook ChangeSpec 생성 시 SemanticHook 카탈로그에서 선택 (드롭다운). anchor_locator/operation 자동 fill. 사용자는 "안전재고 mutate" 정도만 선택. 중 (2일)

📋 Phase 3 — 결정론적 샌드박스 시뮬레이션

🎯 이상향
가상 메모리 state machine + CFG 따라가며 매 노드마다 SHACL/OWL reasoner 가 "현재 상태가 도메인 룰 102 위반?" 질의. 위반 시 LLM 이 지어내지 않고 reasoner traceback 그대로 보고.
✅ 현재 가진 것
  • RestrictedPython sandbox (network/memory cap)
  • SyntheticInputGenerator (입력 자동 생성)
  • DiffReporter — before/after mutation diff + 영향 rule 매칭
  • method_mutation_extractor — 변수 단위 mutation 추적
❌ 결정적 결손
  • Python 변환을 LLM 이 함 — Java body → Claude → 한국어 Python. 결정론 X
  • SHACL/OWL 미사용 — BusinessRule.statement 는 자연어 텍스트, 기계 검증 불가
  • Step-by-step 검증 없음 — Python 다 돌리고 최종 mutation diff 만 봄
  • Traceback 형식 위반 보고 없음 — DiffReporter 가 "rule X 영향" 만, "어느 줄에서 어떻게 깨졌는지" 답 X

현재 시스템 체크포인트 답

"파이썬 시뮬 스크립트가 실행되는 도중, 매 스텝마다 온톨로지 추론기 (Reasoner) 의 하드 팩트 검증을 통과하도록 설계되어 있는가?"

답: 그렇지 않다. 실행은 RestrictedPython 한 번 끝까지, 검증은 종료 후 mutation diff 와 BusinessRule.statement 의 휴리스틱 매칭. SHACL/OWL reasoner 는 도입 안 됨. "rule 102 위반" 같은 결정론적 traceback 불가능.

제안: SHACL 도입은 과하다 — 경량 ConstraintEvaluator 로 우회

개입 지점구체적 액션구현 난이도
S9-A. BusinessRule 머신화 지금: statement: str. 추가: predicate: str (Python eval 가능, 예: slab.lengthHigh >= slab.lengthLow) + 변수 binding (term_fqn → 가상 변수). LLM 이 자연어 statement → predicate 변환 (1회 / 사용자 검증). 높음 (3~5일, BusinessRule 모델 확장)
S9-B. Step-by-step ConstraintEvaluator Python sandbox 가 mutation 발생할 때마다 hook 발동 → 적용 가능한 BusinessRule.predicate 평가 → False 면 즉시 traceback (line, rule_fqn, expected vs actual). 중 (2~3일)
S9-C. PythonGenerator 결정론화 S8-C 와 함께. SemanticHook 기반 템플릿 + LLM 은 hook 선택만. hallucination 영역 제거. 높음 (S8-C 와 묶음)
S9-D. SHACL/OWL 옵션 완전한 reasoner 가 정말 필요한가? slab demo 의 룰들 (max/min/range) 은 대부분 단순 술어. 완전 SHACL 도입은 ROI 낮음. predicate-eval 충분. X (지금 단계 비추천)

📋 Phase 4 — 지식의 자가 증식 (Knowledge Feedback Loop)

🎯 이상향
시뮬 결과의 "위험 파급 경로"나 "새로 발견된 제약"이 휘발 없이 온톨로지에 새 edge / rule 로 자동 write-back. 시간 지나면 에이전트 성능이 인간 개입 없이 고도화.
✅ 현재 가진 것
  • ChangeSpec.simulation_result (diff + 영향 rule) DB 영속
  • history UI (Workbench R 「📋 시뮬레이션 기록」)
  • cache hit re-run
❌ 결정적 결손
  • Critical path 자동 추출 X — diff 패턴 분석 안 됨
  • 새 BusinessRule 제안 X — "이 mutation 이 항상 X 결과로 이어진다" 학습 안 함
  • Confidence 자동 갱신 X — 시뮬 통과한 binding 의 confidence 안 올라감
  • Cross-spec 패턴 인식 X — 비슷한 ChangeSpec 끼리 묶기 안 됨

현재 시스템 체크포인트 답

"시뮬레이션이 성공적으로 끝난 후, 그 결과 (파급 효과 패턴) 가 다음 시뮬레이션을 더 똑똑하게 만들기 위해 온톨로지 시스템의 지식으로 저장 (피드백) 되는가?"

답: 안 된다. ChangeSpec.simulation_result 는 그 spec 안에 갇힌다. 다른 spec 이나 BusinessRule 큐로 흘러들지 않는다. "안전 바닥 제거 = lengthLow 100% 변동" 같은 발견이 새 BusinessRule 후보로 자동 등록되지 않는다.

제안: 가장 ROI 낮은 단계 — 1, 2, 3 끝나기 전엔 손대지 말 것

개입 지점구체적 액션구현 난이도
S10-A. Sim 결과 → BusinessRule 후보 spec.simulation_result 에서 "differs > 50%" 같은 큰 변동 패턴 추출 → "anchor X 변경 시 anchor Y 도 함께 변함" rule 후보 자동 등록 (proposed 상태, 사용자 confirm 필요). 중 (2일)
S10-B. Spec 패턴 클러스터링 비슷한 anchor 변경 패턴 spec 끼리 묶어서 "이 패턴은 항상 X 영향" 발견 → ImpactPropagator 의 학습 가중치로. 높음 (4~7일, 데이터 충분 후)

🩺 외부 의견의 병목 진단 — 반박 + 보강

외부 의견 예측 실제 진단
"가장 먼저 파열음 — Phase 1 (코드↔매핑 비동기화)" 적중. stale binding 검출 0%. 사용자가 직접 재등록 안 누르면 무한히 구버전 그대로. 1순위 작업.
"또는 Phase 2 (운영자 매핑의 해상도 부족)" 적중. ConceptBinding 이 필드 단위에서 멈춤. param/return/literal 단위 anchor 와 분리되어 "실행 가능"하지 않음. 2순위 작업.
"이 단계는 도저히 자동화 안 보인다고 느껴지는 병목 지목" 병목 1 — Phase 3 의 LLM 의존성. Java body → Python 변환에 Claude 가 끼어 있는 한 결정론 불가능. 우회: SemanticHook 템플릿 기반 코드 조립 (LLM 은 hook 선택만).

병목 2 — BusinessRule 자연어 statement. 기계 검증 불가능. 우회: predicate: str 필드 추가 + LLM 일회성 변환 + 사용자 검증.

병목 3 — SHACL/OWL 풀 도입. ROI 매우 낮음. 우회: 경량 Python eval 기반 ConstraintEvaluator. 우리 도메인 (slab range / chemical composition / process matching) 은 대부분 단순 술어로 표현 가능.

🌟 외부 프레임워크가 안 짚은 우리의 강점
  • BusinessTerm 한국어 alias 사슬 — 외부는 영어 시맨틱 가정. 우리는 한국어 도메인 (품종코드/Slab 단중) 4-stage chain (exact/alias/embedding/LLM) 매칭 — 외부 의견은 이 layer 가 없음.
  • 도메인 맵 Top-down 진입점 (S6) — Joern CPG 도 평면 그래프임. 우리는 LLM 으로 비즈니스 흐름 카테고리 (주문→화학성분→Slab사양→공정매칭) 자동 추출 — 외부에는 없는 사용성 레이어.
  • 매뉴얼 ↔ Rule auto-link — 외부는 "도메인 룰" 운영자 입력 가정. 우리는 PDF/MD/DOCX 인제스트 + 임베딩 ↔ rule 자동 연결 (auto_linker) — 운영자 부담 ↓
  • Multi-Layer ImpactPropagator — anchor 단위까지 BFS. 외부의 "위험 파급 경로" 의 backbone 이 이미 있음.
🎯 이걸 다 합치면
한국어 도메인 + LLM 카테고리 + 매뉴얼 자동 인제스트 = "운영자 진입 비용 최소화" 가 우리만의 무기. 여기에 외부 프레임워크의 Phase 1/2/3 자동화를 얹으면, 단순 모방이 아닌 "한국 제조 현장에 진짜 들어갈 수 있는 솔루션" 이 됨.
