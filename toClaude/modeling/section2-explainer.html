1. 최종 목적 — 우리가 만들려는 것

공장의 암묵지를 기계가 추론 가능한 온톨로지로 바꾼다.

SOP, 표준, 절차서, 품질 기준. 모두 사람이 읽는 마크다운으로만 존재한다. 안전재고 계산이 어떻게 되는지, 가열 공정 파라미터가 어떤 기준으로 결정되는지, 누가 책임자인지. 전부 PDF나 위키 어딘가에 흩어져 있다.

이걸 AI가 "What-if", "Why", "어디에 영향?"을 대답할 수 있는 구조화된 지식으로 바꾼다.

1매뉴얼 (마크다운)
SOP, 표준, 절차서 — 자연어
→
2Ontology YAML
Primary Layer — 검증된 구조
→
3Neo4j 그래프
:OntNode — 연결된 지식
→
4AI 에이전트
What-if / Why / Diagnostic
핵심 가치: "안전재고를 10% 올리면 생산 일정에 무슨 영향?" — 지금은 사람이 엑셀 뒤지고 담당자 찾아서 전화해야 답 나온다. 이걸 AI가 1초에 답하게 만드는 게 최종 목적.

2. 전체 아키텍처 — 3층 모델

✅ LAYER 1 — PRIMARY (현재 구현 완료)

매뉴얼 기반 온톨로지. 코드 없이도 이해 가능한 자체 완결 구조.

  • ontologies/*.yaml 파일로 영구 저장
  • Process · Entity · Role · Relation · Term · Formula · Rule
  • Pydantic strict 검증 (extra="forbid") + 3단계 그래프 검증
  • Sub-DSL로 공식(formula)과 룰(rule) 표현 — AST 화이트리스트 파싱
⏳ LAYER 2 — EXECUTION (Section 3, 예정)

시뮬레이션 엔진. 공식과 룰을 실제로 실행.

  • Sub-DSL AST를 Python 함수로 변환해 실행
  • 입력값 주입 → 공식 계산 → 룰 적용 → 출력
  • What-if 시뮬레이션 엔진의 기반
⏳ LAYER 3 — AGENTS (Section 3, 예정)

3개 추론 에이전트. Primary + Execution 위에서 동작.

  • WhatIf Agent — "X를 바꾸면 어떻게 될까?" → 공식 재계산
  • WhyTrace Agent — "이 값이 왜 이렇게 나왔나?" → 의존성 역추적
  • Diagnostic Agent — "이 이상 징후의 원인은?" → 룰 위반 탐지
지금 우리가 보는 화면 (매뉴얼 빌더 + 도메인 온톨로지)은 Layer 1만 담당한다. 실행 엔진과 에이전트는 Section 3로 이관되어 현재 UI에는 없다.

3. 매뉴얼 빌더 (Manual Builder)

역할: 마크다운 SOP 하나 → 검증된 Ontology YAML 한 개.

사용 흐름: 좌측에 매뉴얼을 붙여넣거나 드롭다운에서 불러온다. "LLM 드래프트" 버튼 클릭. 우측에 YAML이 생성된다. 자동 검증이 돌고, 통과하면 "저장" 버튼으로 ontologies/*.yaml에 영구 저장.

내부 동작 4단계

1마크다운 로드
ontologies/manuals/*.md에서 선택하거나 직접 붙여넣기
→
2LLM 드래프트
pydantic_ai Agent가 마크다운 → raw YAML 문자열 변환 (code fence 자동 제거)
→
33단 검증
parse → schema → graph. 실패 시 구조화된 에러 반환
→
4저장
/api/modeling/ontology/save → 파일로 영구화

3단 검증의 의미

단계무엇을 검증하나실패 예시
① parse yaml.safe_load() — YAML 문법 자체 들여쓰기 오류, 콜론 빠짐
② schema Pydantic strict (extra="forbid") — 필드명/타입/enum 일치 오타 필드 formular, 알 수 없는 action_type: "alert"
③ graph id 중복, depends_on 순환, refers_to 경로 유효성, Sub-DSL AST 파싱 A→B→A 순환, term.refers_to: "FakeProc.outputs.x", 공식 안의 eval(user_input)

Sub-DSL 화이트리스트

공식(formula)과 룰(rule)은 수학/불리언 식만 허용한다. 함수 호출과 임의 코드 실행 차단.

산술 연산자 
+  -  *  /  **  //  %
단항: +x, -x
비교 연산자 
<  <=  >  >=  ==  !=
불리언 연산자 
AND  OR  NOT
(대소문자 무관)
허용된 함수 (6개만) 
sqrt   # 제곱근
abs    # 절댓값
min    # 최솟값
max    # 최댓값
norminv # 표준정규 역함수
round  # 반올림
차단되는 것: eval, exec, import, 함수 정의, 어트리뷰트 접근, 리스트 컴프리헨션, lambda.

실제 YAML 예시 — safety_stock_v1.yaml

ontology:
  id: safety-stock-v1
  source_document: assets/manuals/inventory-planning.md
  scope: v1-inventory
  version: "1.0"

processes:
  - id: SafetyStockCalculation
    name: 안전재고 계산
    inputs:
      - id: demand_variability    # 수요 표준편차
        type: float
      - id: lead_time_days
        type: int
        range: [1, 365]
      - id: service_level
        type: float
        range: [0.8, 0.999]
    outputs:
      - id: safety_stock_level
        type: float
    formula:
      expression: z * demand_variability * sqrt(lead_time_days)
      derived_params:
        z: norminv(service_level)
    rules:
      - id: SSR-002
        condition: lead_time_days > 30
        action_type: assign
        target: safety_stock_level
        expression: safety_stock_level * 1.15
      - id: SSR-003
        condition: demand_variability > 100 AND lead_time_days > 14
        action_type: warning
        action_message: 고변동 + 롱리드타임 — 재고 계획 재검토 필요
왜 이게 중요한가: 이 YAML 하나만 있으면 — ① 사람이 공식을 읽고 이해할 수 있고, ② 기계가 AST로 파싱해 실행할 수 있고, ③ "lead_time_days > 30일 때 왜 1.15배를 곱하는지" 같은 설명 가능성이 확보된다.

4. 도메인 온톨로지 (Domain Ontology)

역할: 회사 전체 제조/SCM의 표준 참조 계층을 한눈에 본다. SCOR + ISA-95 하이브리드.

사용 흐름: 좌측에 Process / Entity / Role 트리. 상단 "템플릿 불러오기" 버튼으로 SCOR+ISA-95 초기 트리 생성 (26 process + 7 entity + 5 role + 16 relation). 노드 클릭 → 우측 상세 패널. "+ 노드 추가" 버튼으로 새 노드 등록.

2개의 표준을 합친 이유

SCOR (수평축)

공급망 프로세스 분류. "무슨 일을 하는가".

  • Plan — 수요 예측, S&OP
  • Source — 구매, 입고
  • Make — 생산, 조립
  • Deliver — 출하, 배송
  • Return — 반품 처리

ISA-95 (수직축)

자동화 레벨 계층. "어느 층위에서 일어나나".

  • L4 — ERP (사업계획)
  • L3 — MES (운영관리)
  • L2 — SCADA (감시제어)
  • L1 — PLC (센서/액추에이터)
  • L0 — 물리 공정

둘을 합치면 2차원 격자가 된다. "안전재고 계산"은 Plan × L4, "가열 공정 온도 제어"는 Make × L2. 새 프로세스를 추가할 때 이 격자 어디에 속하는지만 정하면 된다.

데이터 모델 — Neo4j :OntNode

OD-6 마이그레이션으로 단일 레이블 통합했다. 이전에는 :DomainNode, :Process, :Entity 등이 분리되어 있어 쿼리가 복잡했다. 지금은 kind 속성으로만 구분한다.

// Process 노드
(:OntNode {id: "SafetyStockCalculation", kind: "process", name: "안전재고 계산"})

// Entity 노드
(:OntNode {id: "SafetyStock", kind: "entity", name: "안전재고"})

// Role 노드
(:OntNode {id: "Planner", kind: "role", name: "계획담당자"})

// Relation (4종 edge)
(a)-[:RELATION {kind: "part_of"}]->(b)         // 하위-상위 포함 관계
(a)-[:RELATION {kind: "uses"}]->(b)            // 프로세스가 엔티티 사용
(a)-[:RELATION {kind: "produces"}]->(b)        // 프로세스가 엔티티 생산
(a)-[:RELATION {kind: "responsible_for"}]->(b) // 역할이 프로세스 담당

트리 예시 (템플릿 로드 시)

Plan (L4) ├─ DemandPlanning ←[responsible_for]── Planner │ └─ uses → DemandForecast (entity) ├─ SafetyStockPlanning │ ├─ uses → SafetyStock (entity) │ └─ produces → ReorderPoint (entity) └─ SupplyPlanning Source (L3-L4) ├─ PurchaseOrderManagement ←[responsible_for]── Buyer │ └─ produces → PurchaseOrder (entity) └─ Receiving Make (L2-L3) ├─ ProductionScheduling ├─ ShopFloorExecution ←[responsible_for]── Operator └─ QualityInspection ←[responsible_for]── QualityEngineer Deliver · Return ...

5. 둘의 관계와 최종 목적 기여

매뉴얼 빌더와 도메인 온톨로지는 같은 온톨로지 그래프에 기여하는 두 가지 입력 경로다.

🔍 매뉴얼 빌더 = 수직 (깊이)

하나의 프로세스에 대한 세부 지식. 공식, 룰, 입출력 포트, 용어까지 상세하게.

예: SafetyStockCalculation 안에 z * σ * √L 공식과 3개 룰.

🗺️ 도메인 온톨로지 = 수평 (넓이)

전사 프로세스들의 관계와 위치. 어디 속하나, 누가 책임지나, 무엇과 연결되나.

예: SafetyStockCalculation이 Plan 카테고리, Planner 담당, PurchaseOrderManagement와 연결.

최종 목적에 기여하는 방식

┌──────────────────────────────────────────────────────────────┐ │ "안전재고를 10% 올리면 어떻게 될까?" │ └──────────────────────────────────────────────────────────────┘ ↓ ┌────────────────┴─────────────────┐ │ │ [도메인 온톨로지] [매뉴얼 빌더 산출물] SafetyStock 엔티티 관계 SafetyStockCalculation 영향 받는 프로세스 탐색 공식 재계산 · PurchaseOrderMgmt · z * σ * √L · ProductionScheduling · 룰 재평가 · DemandPlanning (SSR-002: L>30일 +15%) │ │ └────────────────┬─────────────────┘ ↓ [3개 에이전트 종합] · WhatIf: 수치 재계산 · WhyTrace: 영향 경로 설명 · Diagnostic: 경고/위험 감지
둘 다 필요하다. 공식만 있고 관계가 없으면 "무엇에 영향?"을 답할 수 없다. 관계만 있고 공식이 없으면 "얼마나 영향?"을 답할 수 없다.

6. 현재 한계

솔직하게. 지금 구현된 Layer 1은 입력 도구의 절반이다. 아직 안 되는 것들.

6-1. Builder ↔ Tree 단절 Critical

매뉴얼 빌더로 safety_stock_v1.yaml을 저장해도, 도메인 온톨로지 트리(Neo4j)에는 자동으로 반영되지 않는다. 두 경로가 같은 DB에 써야 하는데 지금은 각자 따로 쓴다.

결과: 사용자가 빌더에서 만든 SafetyStockCalculation은 트리에서 안 보이고, 트리에 만든 Process는 빌더 YAML과 연결 안 된다. 의도된 기여 구조가 아직 이어지지 않았다.

6-2. 실행 엔진 없음 Section 3

Sub-DSL로 공식을 썼지만 실제로 실행할 수 없다. 파싱만 하고 계산은 못 한다. What-if 시뮬레이션의 기반이 빠져 있다.

6-3. 3개 에이전트 미구현 Section 3

WhatIf, WhyTrace, Diagnostic. 이게 있어야 Layer 1이 최종 목적에 닿는다. 현재는 "입력 도구만 있고 소비자가 없는" 상태.

6-4. LLM 드래프트 품질 의존 OD-9

LLM이 마크다운에서 Ontology를 잘 뽑아내면 3단 검증 통과. 못 뽑으면 구조화 에러가 줄줄 나고 사용자가 수동으로 고쳐야 한다.

  • 복잡한 공식은 놓치거나 잘못 번역할 수 있음
  • 용어 정규화(canonical/aliases)가 일관되지 않을 수 있음
  • 한국어 매뉴얼 → 영어 id 변환 품질이 매뉴얼마다 다름

6-5. 기존 YAML 편집 모드 없음 OD-9

ontologies/safety_stock_v1.yaml을 이미 저장했는데, 수정하려면 다시 새로 드래프트해야 한다. 기존 YAML 로드 → 편집 → 저장 플로우가 없다.

6-6. Syntax Highlighting 없음 OD-9

YAML 에디터가 그냥 <textarea>다. Monaco나 CodeMirror가 없어서 들여쓰기 실수가 많다.

6-7. Relation 수동 편집 UI 부재 OD-9

도메인 온톨로지에서 노드는 추가되는데, 노드 간 관계(relation)를 끌어서 만드는 UI가 없다. 지금은 템플릿에서 자동 생성된 16개만 있다.

6-8. 충돌 감지 없음 확장

여러 YAML이 같은 process.id를 가지면? 다른 팀이 같은 엔티티를 다르게 정의하면? 지금은 탐지 안 된다.

6-9. 버저닝/히스토리 없음 확장

safety_stock_v1.yaml에서 v2로 올릴 때 변경 이력이 추적 안 된다. git이 해 주긴 하지만, 도메인 관점(예: "이 룰이 언제 왜 추가됐나")으로는 볼 수 없다.

7. 로드맵

🔜 OD-9 — UX 개선 다음 스프린트

  • Monaco/CodeMirror YAML 하이라이팅
  • 기존 ontologies/*.yaml 불러와 편집
  • "Format" 버튼 (YAML 재정렬/정돈)
  • LLM 재드래프트 (기존 YAML + 수정사항 주면 개선)

🔗 Builder-Tree 연결 미정

  • 빌더 저장 시 YAML의 Process/Entity/Role을 Neo4j :OntNode로 자동 등록
  • 트리에서 노드 클릭 → 연결된 YAML 파일 열기

🚀 Section 3 — 엔진 + 에이전트 이후

  • Sub-DSL AST → Python 함수 컴파일러 (Execution Layer)
  • 시뮬레이션 런너: 입력 주입 → 공식 실행 → 룰 적용 → 결과
  • WhatIf Agent — 수치 재계산
  • WhyTrace Agent — 의존성 역추적
  • Diagnostic Agent — 룰 위반/이상 탐지
