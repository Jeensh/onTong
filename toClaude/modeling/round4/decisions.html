안건 1 — dagre → ELK 마이그레이션 spike

결정됨 → C (spike 후 결정) 관련: 차용 후보 #2 (compound expand-in-place), 사용자 피드백 6번

무엇이 안건

현재 layout 은 @dagrejs/dagre. ELK.js (Eclipse Layout Kernel) 는 compound node (패키지 box 안에 클래스 노드 중첩) 를 1급 지원. dagre 는 사실상 못 함.

Compound expand-in-place 패턴 (Stage 3 차용 후보 #2): 패키지 box 클릭 → 그 자리에서 안의 클래스만 펼침. 현재 cluster mode 통째 전환 대비 drill-down 단절 없음. 사용자 피드백 6번 (패키지 hierarchy 가시화) 정답에 가장 가까움.

Option 비교

A. dagre 유지 B. ELK 풀 마이그 C. ELK spike + 결정
Compound expand-in-place ❌ 포기 ✅ ✅ if proven
Bundle size 증가 +0 +250~300 KB +0 (spike 후 결정)
5K class layout 시간 알려진 빠름 불확실 — 측정 필요 측정 결과 보고 결정
코드 변경량 0 OntologyGraph 절반 PoC 1 페이지
학습 cost 0 medium (async API + ELK options) low
Backout 가능성 n/a hard (의존 깊음) easy
일정 risk 0 중–high low
내 추천
C — ELK spike 먼저, 결과로 풀 마이그 결정. 이유:
  • ELK 가 compound 의 정답이지만, 5K class 에서 layout 시간이 unacceptable 가능성. ELK 는 일반적으로 dagre 보다 2–5배 느림 (hierarchical algorithm 비용).
  • spike 산출 = 작은 page 에 ELK 로 117 노드 + 가공된 5K 노드 layout 측정. < 2s 면 마이그, > 5s 면 hybrid (dagre default + ELK on-demand).
  • 컨텍스트 비용 작고 evidence-driven 결정.
결정 영향
  • C 선택 → 안건 2/3/4 진행 (모두 ELK 결과와 무관). compound 만 ELK 결과 본 후 commit.
  • A 선택 → 안건 6 (5K verification) 결과 보고 cluster mode UX 개선 (smooth zoom, in-cluster breadcrumb) 으로 우회.
  • B 선택 → 일정 risk 큰 대신 가장 빠른 결과. 데모 시기 압박 시 가능.
미해결 의문: xyflow 의 ELK 통합 사례 (공식 예시 있으나 유지보수 활발도?). spike 가 답할 것.
✓ 결정: C — ELK spike + 결정

사용자 의문: ELK 가 compound 의 정답이면 성능 해결하고 B 가야 하지 않나?

답: "ELK 가 정답" 은 기능적 정답 (compound 1급 지원). 다만 5K 노드 성능은 mitigations (lazy / nested / downshift / worker) 로 풀 수 있을지 데이터 없음. C = "성능 해결 방법 찾자" + "안 풀리면 dagre fallback 보존". B = commit 후 mitigations 강행. C 가 option preserving + evidence-driven.

다음: spike PoC (xyflow + ELK 117 노드 + 가공 5K 노드 layout 측정) → 결과 따라 풀 마이그 / hybrid / dagre 유지 micro-decision.

안건 2 — Perspective 1급 노드화

결정됨 → B (Backend 1급 entity) 관련: Stage 3 차용 후보 #1 (Lens 본질 부재 해소)

무엇이 안건

Neo4j Bloom 의 Perspective = 한 그래프 위에 사용자가 만든 named view (어떤 노드 종류 보일지 / 어떤 facet 으로 색 입힐지 / 어떤 lens 적용할지 묶음). 우리도 도메인 전문가용 / PM용 / 시뮬 검증자용 다른 view 가 필요 — 이게 Stage 3 의 우리 약점 1순위.

"1급 노드화" = Perspective 를 schema 의 정식 entity 로 만들지 (backend 에 Pydantic + ORM + REST) 아니면 단순 frontend localStorage 로만 둘지.

Option 비교

A. localStorage 만 B. Backend 1급 entity C. Hybrid — backend save + URL share, local draft
한 명 사용자 use case 충분 over-eng 충분
팀 협업 (PM 이 Perspective 보내기) 불가 URL 공유 + permission URL 공유 + 본인 변경 사항만 local
데모 시나리오 (저장된 view 보여주기) brittle (브라우저 별) stable stable
구현 복잡도 frontend 만, ~0.5일 backend (table+REST+권한) + frontend ~2일 backend save+읽기 (권한 X) + frontend ~1일
버전 관리 / audit 없음 created_at/updated_at/by backend 저장된 것만
변경 비용 (잘못 선택 시) 크다 (협업 추가하려면 backend 신규) 크다 (필요 없어도 schema 박힘) 작다 (incremental 추가 가능)

Perspective 가 무엇을 담는가 (schema 미리보기)

참고 — Bloom Perspective 의 facet, 우리에 매핑:

  • Visible kinds — Term / CodeType / Action 어느 것 보일지 toggle
  • Visible edge kinds — extends/implements/composition/PRIMARY/PARTIAL/realization 토글
  • Filter — role / verification / domain / package 별 facet
  • Lens — 노드 색을 어떤 facet 으로 칠할지 (verification heat / confirmed bool / package color)
  • Layout 모드 — 이웃 / 경로 / 클러스터 + n_max
  • Saved focus — 시작 노드 + hops
  • Annotation — Perspective 설명, 사용처
내 추천
C — Hybrid (backend save + URL share, local draft). 이유:
  • 한 명 use case 도 cover (local draft 자유) + 팀 use case 도 cover (저장 시 backend, URL 로 공유).
  • schema 가 단순 — table 1개 (id, name, repo_id, created_by, perspective_json). 권한은 1차에 모두 read-only public, 다음 phase 에 ACL.
  • 변경 비용 작음. 처음에 권한 비공개로 시작 → 필요 시 공개 → 차기 ACL 도입.
  • 데모 시나리오 안정성 (사용자 브라우저 무관) — 가장 큰 가치.
결정 영향
  • C 선택 → 안건 5 (Save/share URL) 와 강하게 연결. URL routing + share token 디자인 같이 결정.
  • A 선택 → 안건 5 도 frontend 만. 데모 임박 + 일정 압박 시 합리적.
  • B 선택 → 안건 5 + 권한 모델 (ACL) 설계 같이 진행. 가장 비용 큼.
미해결 의문: Perspective 안에 "내가 저장한 focus 노드" 가 시간 지나 사라진 (re-import 후 fqn 바뀐) 경우 어떻게? graceful degrade 정책 필요. C 선택 시 backend 의 perspective load 시 invalid 노드 검사 로직 추가.
✓ 결정: B — Backend 1급 entity

Perspective 가 정식 ORM entity (table + REST CRUD + audit) 가 됨.

다음 작업 backlog: ① 새 layer view_layer/ 또는 mapping_layer 안에 Perspective Pydantic + ORM (id / name / repo_id / created_by / perspective_json) ② REST /api/ontology/repos/{id}/perspectives CRUD ③ frontend perspective 매니저 + 토글 UI ④ 안건 5 (Save/share URL) 와 합쳐서 routing 디자인. ⑤ 권한 모델은 다음 phase (1차에 read-only public).
