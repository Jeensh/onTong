AnchorBinding — 코드 fragment 와 도메인 의미를 잇다왜 이 개념이 시뮬레이션 + 영향도 분석 신뢰도의 핵심인가

레거시 코드의 한 줄 한 줄 (literal / branch / local / return / ...) 자체 를 ontology 의 도메인 의미에 직접 binding. 이게 우리 도구의 시뮬레이션이 진짜 작동하게 만드는 핵심 다리.

1. 왜 AnchorBinding 이 필요한가 "운영자는 도메인 의미로 말하고 코드는 literal/분기/loop 로 동작한다" — 둘을 잇는 다리

비유 — 운영자 vs 코드의 거리

운영자가 말하는 방식 (도메인 의미)
  • "누적 실수율은 모든 활성 공정의 곱이야"
  • "기본값은 0.95 인데 매년 평균 재계산하지"
  • "고객사 제한이 더 빡빡하면 그쪽 따라야 해"
  • "실수율은 0.5 ~ 1.0 안에 있어야 정상"
코드가 말하는 방식 (literal / branch / loop)
if (confirmedPlantCd.charAt(i) == ' ')
    continue;
BigDecimal p = lookupOrDefault(...);
product = product.multiply(p);
return DEFAULT_PRODUCTIVITY;  // 0.95
중간에 잃는 정보

"charAt(i) == ' '" 가 도메인적으로 "공정 비활성" 이라는 사실은 운영자가 지적해주기 전엔 도구가 모름. Javadoc 도 부재. 매뉴얼도 stale. 코드 자체에는 도메인 의미가 박혀있지 않음.

해결 — fragment 단위로 직접 매핑

AnchorBinding = method body 의 한 표현식 / 분기 / literal 그 자체 를 ontology 의 도메인 의미 (atomic / Action / BusinessRule) 에 직접 박는 것. 메서드 단위 매핑보다 훨씬 미세. v4 결정 Q4'=A 로 합의된 우리 차별 포인트.

4 가지 가치

가치 1 — 시뮬레이션 substitute 위치 자동 결정

ChangeSpec "0.95 → 0.92" 입력 시, 도구가 literal anchor ② 위치 (DEFAULT_PRODUCTIVITY 자리) 자동 검출. Python 코드 generation 시 그 자리에 정확히 0.92 substitute. 사람이 코드 grep 안 해도 됨.

가치 2 — 영향도 분석 정밀도

한 anchor 변경 시 영향 받는 다른 anchor / Action / 호출 chain 자동 추적. "0.95 가 어디 더 쓰이지?" 같은 질문이 자동. 사람이 코드 검색 안 해도.

가치 3 — Gap Inspector 입력

BusinessRule "0.5 ≤ p ≤ 1.0" 이 등록되면 각 method body 에 가드 분기 anchor 가 있는지 자동 검사. 없으면 갭 (코드 결함 candidate). design-gaps #13 의 핵심.

가치 4 — god-method 사각지대 흡수

500 줄짜리 god-method 라도 그 안의 핵심 anchor 만 매핑 하면 OK. 메서드 자체를 매핑할 필요 없음.

v3 + v4 의 합의 사항

4. 시뮬 흐름 — anchor 가 어떻게 활성화되나 ChangeSpec "DEFAULT_PRODUCTIVITY 0.95 → 0.92" 시나리오 단계별

5. 영향도 분석 — 한 anchor 변경의 전파 "DEFAULT_PRODUCTIVITY 0.95 변경" / "PROC_CODES 순서 변경" / "BusinessRule 가드 추가" 3 시나리오

6. 셀프 체크 — 이해도 측정 각 카드 클릭 → 답 reveal. 답 보지 말고 먼저 본인 답 생각.

Q1. 왜 메서드 단위 매핑이 아니라 fragment-level 인가?
클릭 → 답

답: 메서드 단위 매핑은 너무 거칠다. cumulativeProductivity 메서드 전체를 매핑해도 그 안의 0.95 literal 이 어디서 어떻게 쓰이는지 모름. ChangeSpec "0.95 → 0.92" 같은 미세 변경은 fragment 단위로만 정확 적용 가능.

또 500 줄짜리 god-method 의 일부분만 도메인 의미 있는 경우, 메서드 매핑은 의미 X. anchor 만 매핑하면 god-method 도 정확히 잡음 (v4 결정 Q4'=A의 근거).

Q2. literal 0.95 와 branch charAt(i) == ' ' 가 둘 다 anchor 인데, 왜 confirm 패턴이 다른가?
클릭 → 답

답: v3 Q-C 의 혼합 confirm 패턴 — formula/literal 은 명백 (값이 그대로 의미), branch 는 모호 (조건 표현이 도메인적으로 무엇을 의미하는지 추측 필요).

literal 0.95: 값 자체가 운영 평균. 의미 추측 불필요. → auto.

branch charAt(i) == ' ': 코드 표현 자체로는 "공백 문자 비교". 도메인적으로 "비활성 공정" 이라는 의미는 운영자가 알려줘야. → user_queue.

이 차이가 도구의 가치 — 명백한 건 자동으로, 모호한 건 사람 시간을 거기 집중.

Q3. 한 anchor (예: literal ②) 의 binding_target 이 metadata + rule 둘 다 가리킬 수 있는가?
클릭 → 답

답: 가능. 한 anchor 가 여러 의미 layer 가짐. 0.95 는 (a) Action 의 default 값 + (b) BusinessRule 의 fallback 값 둘 다. binding_target 이 list 또는 multi-target.

장점: ChangeSpec 시 자동으로 두 layer 다 갱신. 영향도 분석도 두 갈래로 추적.

주의: 단일 매핑 (1 anchor → 1 target) 보다 모델 복잡. design-gaps #7 (TR invariant) 와 비슷한 결정 영역.

Q4. 코드 변경 시 anchor 가 stale 되는 문제는 어떻게 처리?
클릭 → 답

답: design-gaps #2 의 미해결 영역. body_hash 변경 감지 → AST diff 분석 → 자동 fuzzy match (line range 갱신) 또는 invalidation + 사용자 큐.

현재 v3 Q-C 의 합의는 "혼합 confirm" 까지. 변경 후 흐름 명세 추가 필요.

구체:

  • signature_hash 변경 → SIGNATURE_LOCKED 해제 + 큐
  • body_hash 변경 + AST diff < 30% → 자동 fuzzy match → STALE 표시
  • body_hash 변경 + AST diff ≥ 30% → BODY_ANCHORED 해제 + LLM 재추천

이 흐름이 명세되면 운영 핵심 (5K class * 평균 10 binding = 50K binding 의 자동 관리).

Q5. BusinessRule 의 enforced_by / violated_at_call 이 anchor 와 어떤 관계?
클릭 → 답

답: BusinessRule 이 표현하는 도메인 제약사항 (예: 0.5 ≤ p ≤ 1.0) 을 코드의 어느 anchor 가 검증하는지 추적.

enforced_by: 이 rule 을 검증하는 branch anchor 들 (예: if (p < 0.5) p = 0.5;).

violated_at_call: 이 rule 을 검증해야 하는데 안 하는 method body 들 (예: cumulativeProductivity 의 가드 분기 부재).

결과: Gap Inspector 가 자동으로 enforced/violated 분류 → UI 의 🟢 / 🟡 / 🔴 배지 → 모델러가 "이 코드는 결함 있음 (방어로직 도입 필요)" 를 즉시 인식.

이것이 design-gaps #13 (사용자 통찰 — Q7d Step 3) 의 정확한 구현.

Q6. 왜 anchor 가 시뮬레이션 신뢰도의 핵심?
클릭 → 답

답: 시뮬 = 한국어 Python 코드 generation. 그러려면 PythonGenerator 가 method body 의 어느 위치를 어떤 도메인 의미로 변환할지 알아야.
