3 · sim_v2 의 새 구조 — 왜 이렇게 설계했고, 어떻게 활용 가능한가

sim_v2 는 단순히 "함수 몇 개" 가 아니라 5 가지 아키텍처 결정으로 구축된 framework 입니다. 각 결정에 ADR (Architecture Decision Record) 가 있고, 시뮬레이션 담당자의 엔진이 같은 패턴을 적용할 수 있도록 자산화되었습니다.

한 줄 요약: sim_v2 는 시스템 종속적인 모놀리식이 아니라 plugin 으로 시스템을 갈아끼울 수 있는 framework입니다. slab-design-real-v2 가 첫 번째 plugin, Banking 과 Broadleaf 가 같은 framework 의 다른 plugin. 시뮬레이션 담당자의 엔진도 같은 framework 의 plugin 으로 들어올 수 있고, 본인 엔진 안에서 같은 구조를 따라할 수도 있습니다.

A · Two-Engine Substrate (ADR-003) — Verification 과 Recommendation 분리

왜 이렇게 했는가

Verification 은 deterministic + auditable 해야 합니다 (같은 입력 → 같은 출력, 누가 보더라도 검증 가능). Recommendation 은 본질적으로 probabilistic + LLM 기반 입니다 (창의적 제안). 둘을 같은 엔진에 섞으면 신뢰성이 무너집니다. 그래서 두 engine 을 분리, Integrator 가 중간에서 proposal lifecycle 을 관장합니다.

[ Verification Engine ] # deterministic, auditable ├─ existence / idiom / param / return / behavior / trace / exception / annotation ├─ FixtureRunner Protocol (W59, W72 plug-in) └─ Oracle 4-tier (PASS / FAIL_BREAKING / FAIL_DRIFT / INCONCLUSIVE) │ ▼ proposal 검증 [ Integrator ] # 6-state lifecycle 관장 ├─ proposal 6-state (DRAFT → PROPOSED → ORACLED → REVIEWED → ACCEPTED → MERGED) ├─ axis별 pipeline (effect / structural / term) └─ revision pointer (auditable history) │ ▲ proposal 생성 [ Recommendation Engine ] # LLM-based, 4-layer defenses ├─ grounding (ontology 기반 input) ├─ validation (schema check before LLM) ├─ oracle (Verification 통과 강제) └─ review (사람 또는 auto rule 의 최종 확인)
시뮬레이션 담당자에게 의미: 본인 chat agent (LLM) 의 결과를 그대로 sandbox 에 넣지 말고, Integrator 의 proposal lifecycle 에 흘려보내면 LLM 환각을 deterministic verification (W72) 으로 걸러낸 뒤에만 사용자에게 surface 가능. UC36 의 v2 23→0 결과가 바로 이 패턴의 실증.

B · Plugin Framework (ADR-002, ADR-011) — system-agnostic

왜 이렇게 했는가

한 onTong 인스턴스가 여러 client system 을 동시에 지원해야 합니다. slab-design-real-v2, Banking, Broadleaf 가 모두 다른 도메인이지만 같은 verification framework 을 공유합니다. plugin 패턴으로 business logic 을 분리하고, framework 자체는 system-agnostic 유지.

backend/sim_v2/ ├─ core/ # framework — system-agnostic │ ├─ verification/ FixtureRunner Protocol │ ├─ synthesizer/ JavaToPythonTranslator │ └─ integrator/ Lifecycle pipelines │ └─ plugins/ # 시스템별 plug-in ├─ slab_design_real_v2/ # ★ 현재 demo 대상 │ └─ contracts (38 actions, 11 driveable) ├─ banking/ # UC2_banking_* │ └─ contracts (transactions, accounts, ...) └─ broadleaf/ # UC2_broadleaf_* └─ contracts (catalog, pricing, ...)
시뮬레이션 담당자에게 의미: Section 3 의 sandbox/composer/chat 도 같은 plugin 구조를 따라할 수 있습니다. slab-design-real-v2 의 특수 로직은 plugin 안에, framework 부분은 sim_v2 의 core 를 import. 다른 시스템 (Banking 등) 추가 시 plugin 만 새로 작성하면 됩니다.

C · 5-axis Detect→Fix Loop (UC22/UC24/UC30/UC33/UC27) — 자동 진단 + 자동 추천

왜 이렇게 했는가

한 메서드의 "결함" 은 5 가지 차원에서 발생합니다 (param 시그니처, return type, exception, annotation, term naming). 한 axis 의 결함이 다른 axis 까지 영향을 주기도 합니다 (term MERGE → return-type 자동 unblock). 5 축을 독립적으로 detect 하고, 각 axis 가 자체 remediation 후보를 emit. slab-design-real-v2 의 23 finding 이 30 MERGED proposal 로 100% reduce 된 패턴.

① Schema axis W48
params_json 의 type 정의 누락 → ADD_FIELD / RENAME_FIELD
② Param axis W55
action params ↔ Java method params 시그니처 불일치 → RENAME_PARAM
③ Return-type axis W58
declared return ↔ method body return 차이 → CHANGE / WRAP / LIFT
④ Exception axis W64
declared effects 누락 → ADD_EXCEPTION_EFFECT
⑤ Annotation axis W67
@Transactional / @PostMapping 누락 → ADD_ANNOTATION_EFFECT
시뮬레이션 담당자에게 의미: 본인 영향도 분석 panel 의 결과를 이 5 axis 의 lifecycle pipeline 에 흘려보내면 "영향 받는다" → "이렇게 고쳐라" 까지 가능. UC22/UC24/UC27/UC30/UC33 demo 가 각각의 fix 패턴 실증.

D · 6-state Proposal Lifecycle (W62/W68/W69) — LLM 환각 방어 메커니즘

왜 이렇게 했는가

LLM 이 emit 한 proposal 을 즉시 적용하면 환각 (hallucination) 이 곧장 production 으로 갑니다. 6-state lifecycle 이 그 사이를 막는 safety net: 각 state 마다 다른 검증 (schema oracle / behavioral oracle / reviewer auto-policy) 통과 후에만 다음으로. ADR-005 의 4-layer LLM defense 의 oracle layer 가 이 lifecycle 의 ORACLED → ACCEPTED 게이트.

DRAFT → PROPOSED → ORACLED → REVIEWED → ACCEPTED → MERGED

분기 가능: 어느 state 에서든 REJECTED 또는 CHANGE_REQUEST (사람 검토 필요).

각 state 의 의미 + UC36 실측 예시
  • DRAFT — LLM (또는 verifier) 가 막 생성한 raw 후보. UC36 에서 23 baseline finding 이 23 DRAFT proposal 로 시작.
  • PROPOSED — 기존 ontology 와 충돌 없는지 schema-level schema oracle 통과. 예: ADD_EXCEPTION 이 이미 등록된 exception 과 duplicate 가 아닌지.
  • ORACLED — Verification Engine (deterministic) 의 oracle 통과. 예: param rename 이 정말 시그니처 불일치를 해소하는지.
  • REVIEWED — auto reviewer policy 또는 사람 review 거침. needs_detail 인 경우 (e.g. rest_endpoint 의 path 미상) CHANGE_REQUEST 분기.
  • ACCEPTED — 최종 승인 상태, MERGE 직전.
  • MERGED — ontology DB 에 실제 반영. UC36 결과 30 MERGED proposal.
시뮬레이션 담당자에게 의미: 본인 chat 의 자연어 → fqn 변환 실패 시 [LOW] 라고만 떠 있던 부분에서, lifecycle 로 흘려보내면 사용자에게 "이 후보가 ORACLED 통과 / REVIEWED 진행 중 / DRAFT — 추가 정보 필요" 같은 진행 상태 노출 가능. UI 자체가 단순 결과 → actionable workflow 로 진화.

E · FixtureRunner Protocol — 새 verifier 가 plug-in 으로 들어오는 통로

왜 이렇게 했는가

Verification 의 핵심은 FixtureRunner 라는 단일 Python Protocol. 어느 verifier 든 이 protocol 만 구현하면 같은 oracle / engine 에 plug-in. W59 (behavioral), W72 (invariants) 가 같은 protocol 의 구현체, 같은 oracle 이 둘 모두 사용. 향후 새 verifier (e.g. fuzz-based, contract-based) 도 같은 방식으로 추가 가능.

# oracle.py 의 Protocol 정의 class FixtureRunner(Protocol): def run_fixture( self, fixture_id: str, plugin: str, apply_diffs: dict ) -> FixtureOracleResult: ... # 구현체들 (모두 동일한 인터페이스) W59 · BehaviorTwinRunner # Java baseline 과 동치 비교 W72 · TwinInvariantRunner # determinism / type / no-throw 새 verifier 추가: class FuzzVerifier(FixtureRunner): def run_fixture(...): ... # protocol 따라 구현만 하면 끝
시뮬레이션 담당자에게 의미: 본인 만든 custom verifier (e.g. slab-design-real-v2 특화 비즈니스 룰 체크) 도 FixtureRunner protocol 따라 작성하면 sim_v2 의 VerificationEngine + Oracle 인프라를 그대로 상속. 새 verification 차원 추가 시 framework 재설계 불필요.

F · W77 + W78 Hybrid Search — ontology 기존 alias 위에 4 tier 검색 (대체 ❌, 보완 ✓)

왜 이렇게 했는가

business_terms.aliases_json 컬럼이 이미 한↔영 alias 양쪽을 담는 설계 (예: ["엣징그룹코드", "edgingGroupCd"]). 그런데 modeling 의 기본 search 가 한 컬럼만 보고 있어서 "엣징" 검색 시 0 hit. 데이터는 있는데 검색이 활용 못한 것. W77 은 alias 를 대체하지 않고 같은 데이터를 4 컬럼 통합 token index 로 fully exploit. 그 위에 W78 은 사용자 query 가 alias 한쪽만 매핑되거나 (한국어 → 영문만 등록된 term), 오타 / 비표준 음역 인 경우도 close 하는 hybrid tier 를 얹음.
