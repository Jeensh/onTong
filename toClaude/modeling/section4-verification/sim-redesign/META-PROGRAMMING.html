1. 왜 meta-programming 이 twin 의 핵심 문제인가

Java 의 강력한 meta-programming 은 production 동작의 상당 부분을 source code 가 아닌 runtime 또는 compile-time 의 동적 mechanism 에 둠. Twin (Python equivalent) 이 이걸 mirror 하려면 mechanism 자체를 모방할 수 없으므로 — 의미만 capture, mechanism 무시 전략.

4 종 meta-programming

  • Polymorphic Dispatch — 어느 method 가 호출될지가 정적이 아닌 case
  • Annotation Processing — annotation 이 compile 시 추가 code 생성 (Lombok 등)
  • AOP — @Aspect 가 cross-cutting code 를 weaving
  • Bytecode Generation — CGLib / ASM 이 runtime 또는 build 시 bytecode 생성

각 종류의 twin 처리 원칙

  • Bounded (compile-time 에 set 결정) → 자동 합성
  • Static expression (pointcut, annotation rule) → 정적 매칭 후 합성
  • Bytecode-level effect (CGLib proxy 등) → Python decorator 로 의미만
  • Unbounded (runtime user input 의존) → SIGNATURE_LOCKED

5. ADR-008: AOP (Aspect-Oriented Programming) ADR-008

핵심: Aspect 를 ontology 의 별도 entity (aspects table) 로 모델. Pointcut expression 의 정적 target expansion. 합성기가 Python decorator 로 wrap.

@Around (worked example)

@Aspect @Component
public class TimingAspect {
    private static final Logger log = LoggerFactory.getLogger(TimingAspect.class);

    @Around("execution(* SdDesigner.design(..))")
    public Object around(ProceedingJoinPoint pjp) throws Throwable {
        long start = System.currentTimeMillis();
        try {
            return pjp.proceed();
        } finally {
            long elapsed = System.currentTimeMillis() - start;
            log.info("design took {}ms", elapsed);
        }
    }
}

합성기 emit: target method (SdDesigner.design) 합성 시 자동 decorator wrap

import functools
import time
import logging

log = logging.getLogger("TimingAspect")

def around_TimingAspect_around(proceed_fn):
    @functools.wraps(proceed_fn)
    def wrapper(*args, **kwargs):
        start = time.time()
        try:
            return proceed_fn(*args, **kwargs)
        finally:
            elapsed_ms = (time.time() - start) * 1000
            log.info(f"design took {elapsed_ms}ms")
    return wrapper

class SdDesigner:
    @around_TimingAspect_around   # 합성기 자동 삽입
    def design(self, order: SDOrderEntity) -> SlabDesignResult:
        # 실제 design body
        ...

핵심: Bytecode 자체는 미관찰. 효과 (생성된 method 의 의미) 만 Python 으로. 대부분은 ADR-006-008 으로 subsume.

Hibernate Lazy Loading → Python Eager (worked example)

@Entity
class Order {
    @Id private String orderNo;

    @OneToMany(fetch = FetchType.LAZY)  // Hibernate proxy
    private List<Slab> slabs;
}

// 사용:
order.getSlabs().forEach(slab -> ...);  // → SELECT * FROM slab WHERE order_no = ?

Twin 의 처리: schema_foreign_keys 가 관계 정보 보유 → LookupDataSource fixture 가 직접 채움

@dataclass
class Order:
    order_no: str
    slabs: list[Slab]  # fixture 가 직접 채움 (eager)

# Fixture loading 시 (Twin Runner):

    order_no="ORD001",

        table="slab", fk_column="order_no", fk_value="ORD001"

# 사용 시:

    ...

LAZY 의 의미는 production 의 SQL latency 최적화 — twin 의 행동 등가성에 무관.

7. Decision Tree — 사용자 코드의 meta-programming 처리

사용자 system 의 Java code 분석 → meta-programming 종류별 처리: Java code │ ├─ Polymorphic dispatch? │ ├─ single_impl → 직접 call (자동) │ ├─ instanceof → Python isinstance (자동) │ ├─ annotation → dispatch table (자동) │ ├─ factory_branch → factory function (자동) │ ├─ generic → TypeVar + ontology candidates (사용자 큐) │ ├─ strategy_map → Python dict dispatch (정적 map 분석) │ ├─ reflection_bounded → registry pattern (candidate 식별 후 user confirm) │ └─ reflection_unbounded → SIGNATURE_LOCKED + GapSurfacer │ ├─ Annotation? │ ├─ Lombok → core processor 자동 (@Getter/@Setter/@Builder/@Data 등) │ ├─ Spring DI → ADR-002 의 plugins/<sys>/stubs/spring_di.py │ ├─ JPA → ADR-002 의 LookupDataSource stub + Schema Layer │ ├─ Jackson → field 매핑 (verbatim per-field serializer) │ ├─ MapStruct → plugin/<sys>/processors/mapstruct.py │ └─ 사용자 정의 → plugin/<sys>/processors/<name>.py │ ├─ AOP? │ ├─ @Around → Python decorator (functools.wraps) │ ├─ @Before → call before target │ ├─ @After → try/finally wrap │ ├─ @AfterThrowing → except wrap │ ├─ Pointcut 일반 → 정적 매칭 → 자동 │ └─ Pointcut 복잡 → SIGNATURE_LOCKED + 사용자 큐 │ └─ Bytecode generation? ├─ Spring AOP CGLib → ADR-008 decorator (subsume) ├─ Hibernate lazy → LookupDataSource eager load ├─ Mockito (test) → Python unittest.mock (twin scope 외) ├─ JaCoCo (coverage) → 무관 (Twin 측정 안 함) └─ Custom CGLib/ASM → plugin 또는 SIGNATURE_LOCKED

8. Honest Limits — 메타 프로그래밍의 잔여 한계

9. Section 2 의 추가 작업 — meta-programming 추출

본 4 ADR 의 실현을 위해 Section 2 의 Java AST extractor 에 추가 pass 필요:

  1. CallSiteAnalyzer 실제 구현 (ADR-006) — 각 method call 의 dispatch_kind 추정. anchor_bindings.dispatch_kind 컬럼 추가
  2. Annotation processor 시뮬레이터 (ADR-007) — Lombok 등의 synthesized method 를 code_methods.is_synthetic 으로 자동 추가
  3. Aspect extractor (ADR-008) — @Aspect class 의 advice + pointcut 정적 분석. aspects 신규 table
  4. Bytecode gen detector (ADR-009) — Spring AOP / Hibernate / Mockito / custom CGLib 사용 식별. 대부분 subsume, custom 만 plugin path

이 작업들은 Section 2 의 ontology 추출 pipeline 확장 영역 — 합성기 자체와 별도. plugin/<sys>/extractors/ 에 system 별 차이 흡수.
