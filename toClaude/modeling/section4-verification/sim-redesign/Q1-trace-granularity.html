Q1 — R4 검증 단위 결정 grill-with-docs Q1

R4 ("동일 처리 과정 보장") 의 검증 단위(trace granularity) 를 어디로 둘 것인가.
실제 v2 의 SdThicknessAction 을 예시로 4가지 옵션이 어떻게 다른지 비교합니다.

이 문서의 목적 — Q1 의 4 옵션 (A/B/C/D) 을 실제 코드 + 실제 ontology 데이터로 비교해서, 사용자가 trade-off 를 손에 잡히는 형태로 평가할 수 있도록. 결정 후 ADR-001 로 기록 예정.

1. R4 가 묻는 것 — "동일 처리 과정" 의 정의

"시뮬레이션의 최고 kpi는 자바소스가 실제로 동작한 것과 동일한 input, 동일한 output이 보장되고 데이터 처리과정 또한 똑같은 형태의 코드는 아닐지언정 동일한 처리과정을 보장하는 것"
— 사용자, 2026-05-12

R3 (동일 input/output) 은 비교 단위가 명확합니다 — 최종 결과 JSON 이 비트 단위로 일치. 이미 oracle differ 가 처리 중.

R4 는 모호합니다. "처리과정 동일" 이란?

  • 같은 외부 서비스를 같은 순서로 호출 → "동일" 인가?
  • 같은 if-branch 를 같은 순서로 거침 → "동일" 인가?
  • 같은 변수를 같은 순서로 set → "동일" 인가?

이 결정이 모든 하위 설계를 분기시킵니다 — Python 코드 형태, Java instrumentation 범위, idiom card 운명, oracle differ 알고리즘.

2. 실제 예시 — SdThicknessAction.execute()

v2 의 step 1 액션. 슬랩 두께를 결정하는 가장 단순한 step (40줄). 다음을 모두 보여줍니다 — input validation, external lookup, downstream lookup, output assignment.

Java 원본 (sample-repos/slab-design-real_v2/.../action/SdThicknessAction.java:41-71)

public void execute(SDOrderEntity order, SDSlabEntity slab) {
    String confirmed = order.getConfirmedPlantCd();
    if (confirmed == null || confirmed.isEmpty()) {                // ← anchor #1
        throw fail("확정통과공장코드 미설정");                          // slot: atomic.confirmed_plant_cd.invalid_check
    }
    char smChar = confirmed.charAt(0);
    if (smChar == SdConstants.INACTIVE_PROCESS) {                       // ← anchor #2
        throw fail("제강 공장 비활성 (확통[0] = ' ')");                    // slot: atomic.confirmed_plant_cd.activation_check
    }
    String smCd = String.valueOf(smChar);

    PlantMapping mapping = plantMapping.getMapping(smCd);                // ← anchor #3
    if (mapping == null) {                                          // slot: body.service_lookup (L52)
        throw fail("PlantMapping 미정의 for smCd=" + smCd);
    }

    CastSpecEntity spec = castSpecService.lookup(                       // ← anchor #4
        order.getCmpCd(), order.getOrgCd(),                              // slot: body.service_lookup (L57)
        smCd, mapping.castCd(), mapping.machineCd(),
        order.getProductCd());
    if (spec == null) {
        throw fail("CAST_SPEC 미존재 ...");
    }
    if (spec.getSlabThickness() == null) {
        throw fail("CAST_SPEC.SLAB_THICKNESS NULL");
    }

    slab.setSlabThickness(spec.getSlabThickness());                       // ← anchor #5
}                                                                       // slot: body.set_output (L70)

각 anchor 가 "처리 과정" 의 의미 단위. 5개 anchor 가 합쳐서 1 action 의 본문 의미를 충실히 표현.

핵심 통찰 — 같은 메서드를 보는 두 단위가 모두 ontology 에 이미 존재합니다. v2 TraceCollector 는 action 단위, anchor_bindings 는 slot 단위. 둘 중 어느 단위에서 "동일 처리 과정" 을 정의할지가 Q1.

2.5. emit 의 정확한 정의 — 한 줄로

이전 섹션에서 trace.emit(...) / trace.anchor(...) 라는 표현을 썼습니다. 정확히 무슨 동작인가요?

한 줄 정의 — emit 은 "현재 코드 위치 식별자 + 변수 snapshot + status (OK/FAIL) 를 trace 리스트에 append" 하는 동작. 그 이상도 이하도 아닙니다.

현재 v2 의 Java 측 emit (이미 구현됨)

v2 의 TraceCollector.wrap() (sample-repos/.../sd/trace/TraceCollector.java:36-59) 가 action 단위 emit 의 reference 구현입니다:

public <T> T wrap(int step, String stepName, String phase, int iteration,
                  Map<String, Object> input, Supplier<T> body) {
    long t0 = System.nanoTime();
    try {
        T result = body.get();                                // ← 실제 action 실행
        double ms = (System.nanoTime() - t0) / 1_000_000.0;
        Map<String, Object> output = ...;                       // result 를 map 으로 변환
        traces.add(new StepTrace(step, stepName, phase, iteration,   // ← emit !
            input, output, TraceStatus.OK, null, null, ms));
        return result;
    } catch (AlgorithmException e) {
        traces.add(new StepTrace(step, stepName, phase, iteration,   // ← emit (FAIL)
            input, null, TraceStatus.FAIL, e.getErrorCode(), e.getMessage(), ms));
        throw e;
    }
}

핵심: traces.add(...) 가 유일한 emit 동작. action 시작 시 input snapshot 인자로 받고, 끝났을 때 output snapshot + status 와 함께 list 에 append. 옵션 B/C 의 anchor-level emit 은 정확히 이 동작을 anchor 단위에서 한 번 더 하는 것 — 새 개념이 아님.

Python 측 anchor emit 의 구체 구현 (옵션 C 의 with 문)

class TraceCollector:
    def __init__(self):
        self.entries = []      # action 단위 trace (v2 와 동일)
        self.anchors = []      # anchor 단위 trace (옵션 B/C 신규)

    @contextmanager
    def anchor(self, slot_id, **input_vars):
        # 진입 시점: input snapshot 캡처
        entry = {"slot": slot_id, "input": dict(input_vars), "line_start": ...}
        try:
            yield                                # ← with 블록 안의 Python 코드 실행
            entry["status"] = "OK"
        except AlgorithmException as e:
            entry["status"] = "FAIL"
            entry["error_code"] = e.error_code
            raise
        finally:
            self.anchors.append(entry)         # ← emit !

# 사용:
with trace.anchor("body.service_lookup", sm_char=sm_char):
    mapping = plant_mapping_service.get_mapping(sm_char)
# → trace.anchors 에 entry append 됨

즉, "emit" = "trace 리스트에 dict 1개 append". 무거운 framework 아닙니다. 단지 어디서 (slot), 무엇을 (vars), 결과는 (status) 를 기록.

2.6. Ontology 매핑이 있는데 왜 runtime trace 가 필요한가?

이 질문이 핵심입니다. ontology 에는 Action ↔ method ↔ anchor ↔ business rule ↔ source 매핑이 모두 있습니다. 그렇다면 Python 을 ontology 따라 짜기만 하면 R4 ("동일 처리 과정") 가 보장되지 않나요?

Ontology 와 runtime trace 가 각각 보장하는 것

보장하려는 속성 Static (ontology 매핑 + synthesis) Dynamic (runtime trace)
Python 코드 구조 가 Java 와 의미적으로 같음 ✓ — synthesizer 가 ontology 따라 코드 생성 —
Python 최종 출력 이 Java 와 동일 (R3) ⚠ — 구조 같으면 동일할 것이라는 추정. 검증 아님 ✓ — 실제 실행해서 출력 직접 비교
같은 input 에서 Python 이 거친 branch sequence 가 Java 와 동일 ✗ — static 코드만 보면 어느 분기가 실제로 실행됐는지 모름 ✓ — trace 에 어느 anchor 가 emit 됐는지 기록
각 anchor 시점의 중간 변수값 이 Java 와 동일 ✗ — runtime 에만 나타나는 값 ✓ — 옵션 B/C 의 anchor input/output snapshot
Python 이 refactor 됐을 때 처리 과정이 보존됨 ✗ — synthesizer 가 보장 못함 (사람이 refactor 하면 ontology 와 분리) ✓ — refactor 후 실행해도 trace 가 같으면 안전
Ontology 빈틈 (gap) 영역이 명시됨 ✓ — synthesis 시점에 # UNCLEAR 주석 삽입 가능 ⚠ — 런타임 경고 발생 가능 (옵션 C 의 anchor 부재 fallback)
핵심 답변 — "Python 이 못하는 영역"이 아니라, "static 매핑만으로 동적 동등성을 직접 확인할 수 없는 영역" 이 존재합니다:
  • 분기 실행 경로 (branch coverage) — 같은 코드라도 input 에 따라 다른 분기. 어느 분기를 거쳤는지는 실행해야 안다
  • 중간 변수값 — 외부 service 호출 결과, lookup 결과, 누적 계산값. 코드만 보면 모름
  • Synthesis 자체의 오류 — synthesizer 가 잘못 짰을 가능성 (실제로 α 의 KNOWN_DIVERGENCE 5종이 정확히 이 케이스. ontology 는 옳았는데 idiom card 작성자 + runtime 작성자가 API 형태에서 갈라짐)

α KNOWN_DIVERGENCE 5종이 이 빈틈에서 발생한 정확한 이유

Phase α 에서 ontology 는 완비 상태였습니다 (anchor 163/163 confirmed). 그런데도 미스매치 5종이 발생:

Ontology 매핑 (정상): anchor body.compute @ SdTargetLengthAction.java:25 → P01-body.compute.md (idiom card) → backend.modeling.sim_verify.runtime (Python runtime) 문제: 동일 anchor 에 대한 두 Python 산출물이 API 형태에서 갈라짐 P01 카드: BigDecimal("0.95").multiply(x) ← 클래스형 α1 runtime: bd("0.95"); bd_multiply(_, x) ← 함수형 → 카드 그대로 Python 짜면 NameError (BigDecimal 클래스 없음) → Ontology 매핑은 옳았으나, 산출물 일관성을 검증할 mechanism 부재 → 정확히 runtime trace 가 catch 했을 케이스

옵션 A (action trace) 도 이 케이스를 잡지 못합니다 (출력만 같으면 OK). 그래서 우리에게 진짜 필요한 검증 layer 가 무엇인지가 Q1 의 핵심.

3. 5가지 옵션을 동일 예시로 비교

같은 SdThicknessAction 의 Python 등가를 각 옵션이 어떻게 다르게 짜는지 보입니다.

옵션 E — Ontology synthesis + 출력만 검증 EJava 인프라: zeroPython: trace 없음 새 옵션

사용자 의문에 가장 직접 대응하는 옵션: "Ontology 매핑이 완비됐으니 Python 은 synthesis 로 짠다. Runtime trace 는 안 만든다. R3 (출력 일치) 만 검증." R4 의 "동일 처리 과정 보장" 은 synthesis 의 정확성에 의해 자동 보장된다고 가정.

R4 의 보장 mechanism — Synthesis 정확성

# Python synthesis pipeline (별도 모듈)
def synthesize_action(action_fqn: str) -> str:
    realization = ontology.get_realization(action_fqn)
    anchors = ontology.get_anchors(action_fqn)              # 5개 anchor
    java_ast = parse_java(realization.code_method_fqn)

    py_code = []
    for anchor in anchors:
        slot = anchor.target_slot                          # e.g. body.service_lookup
        idiom = idiom_registry.get(slot)                   # P01-P27 카드 매핑
        py_snippet = idiom.render(java_ast, anchor.line)
        py_code.append(py_snippet)

    return "\n".join(py_code)

비교 알고리즘 — R3 만

assert py_result.slab_results == v2_result.slabResults
assert py_result.error_code == v2_result.errorCode
# 그게 전부. 중간 trace 비교 없음.

장점

  • 가장 단순 — 새 인프라 zero, v2 변경 zero, Python boilerplate zero
  • R4 의 "코드 형태 무관" 정신과 가장 잘 맞음 — refactor 완전 자유
  • Synthesis 가 결정론적이면 결과는 재현 가능
  • α 의 카드/runtime 미스매치 같은 buug 도 R3 (5개 fixture) 에서 자동 드러남

단점

  • R4 의 "보장" 이 empirical — 5개 fixture 통과 = 동일 처리 추정. 진짜 보장 아님
  • Synthesis 가 잘못된 anchor 를 쓴 경우 (R5 의 corner case) 우연히 R3 통과하면 못 잡음 — 시나리오 #1 같은 hardcode bug
  • R2 (빈틈 자각) 은 synthesis 시점 정적 marker 만 가능 — runtime 빈틈 (예: lookup 결과가 예상과 다를 때) 은 표면화 안 됨
  • R5 (수정 전후 비교) 는 trace diff 가 아닌 code diff + output diff 만. 사람이 읽기 어려울 수 있음
E 가 가장 적합한 시나리오 — Ontology 가 완비되고 synthesizer 의 idiom card 정합성이 별도 검증된 경우. 5개 fixture 가 coverage 양호하다고 가정하면 실용적으로 충분할 수 있음. 하지만 α 의 5종 미스매치가 정확히 이 가정의 빈틈에서 발생 — 그러므로 E 채택 시 synthesizer 자체에 대한 contract test (idiom × runtime smoke 같은 것) 가 더 두꺼워야 함.

  • Refactor 자유도 제한 — anchor 순서 = 처리 순서로 강제
  • v2 (Java) 코드를 건드려야 함 — Section 2 산출물에 영향

옵션 C — 계층적 (Action default + Anchor drill-down) CJava: 점진 추가Python: emit 헬퍼 1개 추천

R3 (output) 은 항상 검증. R4 의 강도는 "action 단위 (baseline)" 와 "anchor 단위 (옵션)" 두 레벨을 모두 제공. 기본은 baseline, fidelity mode 옵션 시 drill-down.

Python 등가 (옵션 C 스타일)

def execute_thickness(order, slab, trace=None):
    def body():
        confirmed = order.confirmed_plant_cd

        with trace.anchor("atomic.confirmed_plant_cd.invalid_check"):  # 자동 emit
            if not confirmed:
                raise AlgorithmException("DG101", "...")

        sm_char = confirmed[0]
        with trace.anchor("atomic.confirmed_plant_cd.activation_check"):
            if sm_char == INACTIVE_PROCESS:
                raise AlgorithmException("DG101", "...")

        with trace.anchor("body.service_lookup", key="plant_mapping"):
            mapping = plant_mapping_service.get_mapping(sm_char)

        with trace.anchor("body.service_lookup", key="cast_spec"):
            spec = cast_spec_service.lookup(...)

        with trace.anchor("body.set_output"):
            slab.slab_thickness = spec.slab_thickness

        return {"slab.slabThickness": slab.slab_thickness}

    return trace.wrap_action(step=1, name="SLAB_THICKNESS", body=body)

Java 측은 옵션 적용

// SdThicknessAction 에 anchor emit 추가는 점진적 — fidelity mode 활성 시만 동작
// 기본 mode 에서는 trace.wrap() 하나만 → v2 변경 zero
// fidelity mode 에서는 trace.anchor(...) 호출 추가 → action 별로 개별 작업
if (trace != null && trace.isFidelityMode()) {
    trace.emitAnchor("body.service_lookup", ...);
}

비교 알고리즘 — 2단 비교

# Tier 1: action 단위 (항상 검증)
assert v2_trace[i].input == py_trace[i].input
assert v2_trace[i].output == py_trace[i].output

# Tier 2: anchor 단위 (해당 action 의 anchor 가 있고 fidelity mode 일 때만)
if v2_trace[i].anchors:
    for j, anchor in enumerate(v2_trace[i].anchors):
        assert anchor.slot == py_trace[i].anchors[j].slot
        assert anchor.vars == py_trace[i].anchors[j].vars

장점

  • R3 (output) 즉시 가용 — Phase α 그대로
  • R4 의 강한 보장이 옵션으로 제공 — 필요한 곳만 fidelity
  • R2 자연 통합: anchor 가 없는 method (Gap A 추상 메서드, Gap B 미보강) → 자동 action 단위 fallback → "이 영역은 처리 과정 보장 안 됨" 자각
  • v2 변경은 점진적 — fidelity mode 도입 액션부터 차례로

단점

  • 두 단계 비교 알고리즘 구현 — oracle differ 확장 필요
  • "기본 모드만 쓰면 옵션 A 와 같다" — fidelity mode 가 실제로 켜져야 R4 강화 효과
  • Python 작성자가 with 문 자리에서 헷갈릴 수 있음 — 가이드 필요

옵션 D — 사용자 정의 logical step DJava/Python: 양쪽 annotation

R4 검증 = "사람이 의미적으로 같다고 본 단계 (phase boundary, iteration 시작 등) 가 일치". anchor 자동 추출 무시.

Python 등가 (옵션 D 스타일)

def execute_thickness(order, slab, trace=None):
    trace.step("phase1.thickness.start")             # 사용자 정의 logical marker
    # ... validation + lookups ...
    trace.step("phase1.thickness.cast_spec_resolved")
    slab.slab_thickness = spec.slab_thickness
    trace.step("phase1.thickness.complete")

Java 측에도 동일 marker 가 필요

trace.step("phase1.thickness.start");
// ... validation + lookups ...
trace.step("phase1.thickness.cast_spec_resolved");
slab.setSlabThickness(spec.getSlabThickness());

장점

  • R4 가 "사람이 보는 처리 과정" 수준 — 직관적
  • Anchor 라는 ontology 개념을 verification 에서 분리
  • 외부 도메인 (slab-design 아닌 다른 시스템) 으로 확장 시 자유

단점

  • Ontology 와 분리 — 시뮬 검증을 위해 사람이 또 marker 를 정의해야 함. 작업 폭증
  • Marker 의 일관성 보장 X — 사람마다 다르게 찍을 가능성
  • v2 Java 에 marker 삽입 = 옵션 B 와 동일 작업량 + 무엇을 marker 로 둘지 결정 추가
  • R2 (빈틈 자각) 와 단절 — anchor 부재 신호가 marker 와 무관

4. Mismatch 시나리오별 검출력 비교

실제 Python 시뮬레이터가 만들 수 있는 3가지 미스 케이스. 각 옵션이 잡아내는지 비교.

시나리오 #1 — 우연한 동일 output, 잘못된 처리 과정

Python 작성자가 plant_mapping lookup 을 빠뜨리고 hardcode 로 채워넣었음. 우연히 S1 fixture 에서는 output 이 일치.

# 잘못 짠 Python
def execute_thickness(order, slab):
    mapping = plant_mapping_service.get_mapping(sm_char)  # 빠뜨림
    mapping = PlantMapping(cast_cd="K1", machine_cd="K")  # hardcode
    spec = cast_spec_service.lookup(...)
    slab.slab_thickness = spec.slab_thickness
옵션검출?이유
E⚠사람이 못 짠다 (Python 은 synthesizer 가 ontology 따라 생성). 만약 synthesizer 자체가 이 bug 를 일으키면 (anchor body.service_lookup 을 빠뜨림), S2/S3 의 다른 input 에서 output diff 가 catch 할 가능성 높음. 단 S1 만 통과하고 S2-S5 가 다르면 R3 통과로 false-OK 가능
A✗S1 input/output 이 일치 → action 단위만 보면 OK
B✓body.service_lookup (L52) anchor 의 input snapshot (sm_char) 은 일치하지만 출력 mapping 의 출처가 다름 — anchor 단위 비교 시 발견
C⚠Fidelity mode 켰을 때만 검출. 기본 모드에서는 A 와 동일
D✗사용자가 plant_mapping_resolved marker 를 따로 두지 않았다면 검출 못함

시나리오 #2 — Refactor (의도된 코드 형태 변경, 처리 과정 동일)

Python 작성자가 get_mapping 과 cast_spec.lookup 을 하나의 helper 로 묶음. 결과 동일, 호출 횟수도 같음.

# 의도된 refactor
def resolve_cast_spec(order, sm_char):
    mapping = plant_mapping_service.get_mapping(sm_char)
    return cast_spec_service.lookup(
        order.cmp_cd, order.org_cd, sm_char,
        mapping.cast_cd, mapping.machine_cd, order.product_cd)

def execute_thickness(order, slab):
    sm_char = ...
    spec = resolve_cast_spec(order, sm_char)  # refactor
    slab.slab_thickness = spec.slab_thickness
옵션거부?이유
EN/A"사람 refactor" 개념 자체가 없음. Python 은 synthesizer 가 매번 ontology 에서 재생성 → 같은 ontology 면 같은 Python. 사람이 refactor 한 코드는 다음 synthesis 에서 사라짐 (이게 약점일 수도)
A✓ passOutput 일치 → OK. Refactor 허용 (R4 의 "코드 형태 무관" 정신과 맞음)
B✗ failbody.service_lookup 두 anchor 가 차례로 emit 되어야 하지만 helper 안에 함께 emit → 위치/순서 mismatch 가능. 정당한 refactor 를 거부
C✓ pass기본 모드는 A 처럼 통과. Fidelity 켰어도 with 문 안에서만 anchor emit 이므로 작성자가 의식 가능 (with 문 위치만 신경 쓰면 refactor OK)
D✓ passLogical step marker 가 같으면 OK. 사람이 정한 단계만 일치하면 됨

시나리오 #3 — α의 KNOWN_DIVERGENCE 5종 같은 API 형태 차이

Python 이 BigDecimal 클래스 대신 bd() 함수형 API 사용. 결과 동일, 호출 순서 동일, 변수 흐름 동일.

# Java: thickness = spec.getSlabThickness() (BigDecimal 클래스)
# Python α2 카드 (class API 가정): BigDecimal("230.0").set_scale(0, ...)
# Python α1 runtime (실제 함수형): bd("230.0"); bd_set_scale(...)
옵션거부?이유
E✓ catch (loud)실제 발생 시: ImportError 즉시 발생 (synthesizer 가 class API 카드 + function API runtime 동시 참조 시). 출력 비교 전에 fail — silent bug 아님. 또는 synthesizer 의 contract test (Phase α E-1 smoke 같은 것) 가 합성 단계에서 catch
A✓ pass최종 thickness 값이 같으면 OK. 클래스 vs 함수형 차이는 검증 영역 밖
B✓ passAnchor 의 input/output snapshot 만 비교 — 사용한 API 형태는 무관
C✓ passA 와 동일 — API 형태는 trace 위에 보이지 않음
D✓ passLogical marker 와 무관

중요: 이 시나리오는 R4 의 "동일 처리 과정" 보다 idiom card 의 import contract 문제. Q1 (granularity) 자체로는 해결되지 않지만, 옵션 E 는 synthesizer 의 contract test 를 1급 시민으로 두므로 이런 케이스를 합성 시점에 catch. KNOWN_DIVERGENCE 는 별도 결정 (runtime API surface 결정 = Q2 이후 다룰 주제) 이지만 옵션 E 가 가장 자연스럽게 통합.

6. 추천 + 다음 결정 연결

결정의 본질 — R4 "보장" 을 어떻게 충족할 것인가:
    "By construction" (옵션 E) — Synthesizer 가 ontology 따라 정확히 합성 → R4 자동 보장
    "By verification" (옵션 C) — 런타임 trace 비교로 R4 직접 확인

이전 추천 (C 단독) 을 재검토했습니다. 사용자가 지적한 "ontology 매핑이 완비된 영역에서 Python 이 못하는 게 뭔가?" 질문에 답하면서, 옵션 E 가 equally viable 한 것이 분명해졌습니다. 둘 다 풀 시연 가능. 선택은 R4 보장 mechanism 에 대한 입장 차이.

옵션 E 가 맞는 경우

  • "Ontology 매핑이 완비되면 synthesis 만 정확하면 충분" — 사용자 의문의 자연스러운 결론
  • v2 변경 zero, Python boilerplate zero — 가장 단순
  • R4 보장 = synthesizer 정확성 + R3 fixture coverage. 둘 다 독립 테스트 가능
  • α KNOWN_DIVERGENCE 같은 케이스는 synthesizer contract test (1급 시민) 가 catch
  • 대신: synthesizer 에 무게가 실림 — ontology→Python 합성기, idiom card registry, contract test suite 를 두껍게

옵션 C 가 맞는 경우

  • "R4 보장은 런타임에서 직접 확인되어야 함" — 합성기 신뢰만으로는 부족
  • R5 (수정 전후 비교) 에서 anchor 단위 trace diff 가 사람에게 더 읽기 쉽다고 판단
  • Python 을 합성만 하지 않고 사람도 수정/확장하는 흐름 (refactor 자유 유지)
  • Fidelity mode 옵션을 통해 verification 깊이를 동적으로 조절
  • 대신: oracle differ + Java instrument + Python boilerplate 모두 점진 작업

둘 다 풀 시연 가능 — MVP 가 아님을 명시

두 옵션 모두 sample-repos/slab-design-real_v2 의 5개 시나리오를 end-to-end 로 처리합니다. E 의 "합성기에 집중" 도, C 의 "trace 에 집중" 도 부분 구현이 아닙니다.

옵션 E vs C 의 본질 차이 — "Python 어디서 오는가"

측면옵션 E (synthesis)옵션 C (hybrid)

Python 코드가 commit 되는가 예 (재생성 가능 산출물) 예 (사람 편집 보존)
"빈틈 (R2)" 표면화 시점 합성 시점 정적 (코드에 # UNCLEAR 주석) 합성 시점 + 런타임 (anchor 부재 fallback 신호)

Java 변경 (v2 → v2') 대응 ontology 갱신 → Python 재합성 ontology 갱신 → 사람이 Python 수정 (또는 합성기 도움)

옵션 E 가 채택되면 다음 결정 (Q들)

  • Q2-E: Synthesizer 의 정확성 보장 mechanism — contract test (Phase α E-1 스타일) 의 범위?
  • Q3-E: 합성 시점 # UNCLEAR 의 표면 — Python 주석 / 별도 보고서 / IDE marker?
  • Q4-E: 시뮬 에이전트 (LLM) 가 합성기인가, 별도 도구가 합성기인가
  • Q5-E: idiom card 의 운명 — synthesizer 의 internal registry 로 흡수 (사람용 markdown 삭제) vs 사람용 markdown 유지 + registry 도 별도
  • Q6-E: R5 의 surface — Python 재합성 후 git diff? Trace 도 같이? side-by-side viewer?

옵션 C 가 채택되면 다음 결정 (Q들)

  • Q2-C: Python 등가 코드의 lifecycle — long-lived / regenerated / dual
  • Q3-C: R2 빈틈 surface — 코드 주석 + 런타임 경고 둘 다? 별도 보고서?
  • Q4-C: 시뮬 에이전트 자율도 — 코드 합성 자동? 사람 보조?
  • Q5-C: idiom card 의 재정의 형태 — anchor 별 1 카드?
  • Q6-C: R5 surface — trace diff + 코드 diff?

두 옵션 모두에 공통된 위험

  • 합성기/synthesizer 의 정확성을 검증해야 함 — α 의 KNOWN_DIVERGENCE 가 정확히 합성기 정합성 문제 (카드 작성자 vs runtime 작성자 동기화 부재). 어느 옵션이든 idiom × runtime contract test 같은 cross-check 필요
  • Ontology 완비도 의존 — Gap A (2 추상), Gap C (14 type_realization 미확정) 등이 합성/trace 의 신뢰도 상한선
판단의 핵심 질문: "Python 을 사람이 손대는 것을 허용하나?"
    아니오 (합성 → 검토 → 출력) → E
    예 (합성/사람 편집 양쪽 + 검증 필요) → C
사용자가 R5 ("소스 수정 시 비교 분석") 에서 말한 "소스" 가 Java 인지 Python 인지에 따라도 달라집니다. Java 만이면 E 가 더 깔끔, 둘 다면 C 의 trace diff 가 더 유리.
