1. 4 perspective 한눈에 보기

① Automation Purist A

핵심: Synthesizer 가 translation rule + runtime selection 을 paired registry 로 own. Registry entry 는 runtime 심볼을 직접 import → runtime API 변경 시 synthesizer startup 에서 ImportError. KNOWN_DIVERGENCE by construction 방지.

강점: 합성기 단일 결정점, runtime drift 즉시 검출, R4 = compile-time property

약점: 79 distinct slot 전체 registry entry 필요, literal-translation fallback 의 brittleness

explorations/1-automation-purist.md (1988 words)

② Minimal Twin B

핵심: 결정론적 AST visitor 가 statement-by-statement 변환. Idiom card 폐기 — AST 가 이미 인코딩한 것을 재서술하는 것이라 α 의 drift 가 발생. Ontology = 사후 검증 (AnchorAuditor).

강점: 최단 코드 경로 (visitor ~1500 LOC), "코드 ground truth" 원칙과 자연 정합, idiom drift 원천 차단

약점: R1 (ontology=precondition) 위반, JPA repository interface body 없음 → special-case 필요

③ Phase α Reuse C

핵심: 27 카드 + runtime + oracle + 5 fixture + smoke test 5 가지 자산 재활용. 5 facade class (~110 LOC) 로 KNOWN_DIVERGENCE 닫고 카드를 synthesizer 의 internal registry 로 rebrand.

강점: α work (수십 시간) 보존, 카드 content 는 옳았음 (framing 만 잘못), 56 slot 중 hot 10 즉시 cover

약점: 79 slot 중 27 카드 = 34% coverage, 38 single-anchor slot 의 cross-validation 부재 (Gap F)

④ Skeptic S

핵심: A/B/C 모두 "twin 가능한 영역" 으로 시야 좁힘. 실제 v2 는 985 method × Spring DI / JPA / @Transactional / AtomicLong / LocalDateTime / Jackson 모두 사용. α 의 실패는 API typo 가 아닌 inter-agent contract 부재.

4. Skeptic 의 11 mandate — 모든 설계가 답해야 할 것

Skeptic 은 design proposal 하지 않음. 대신 A/B/C 가 답하지 못하는 빈틈을 catalog 화. 종합 설계가 이걸 모두 흡수해야 함.

M1. Twin scope 명시 — 어떤 Java 기능이 in/out? (BigDecimal/control flow IN, Spring DI/JPA/@Transactional/LocalDateTime 명시적 stub 설계)
M2. Synthesizer↔runtime API contract reify — typed Protocol, doctest per symbol, version pin. α 의 실제 실패가 이 contract 부재였음
M3. R5 diff granularity 결정 — 9k LOC text diff 는 unreadable. Semantic (per-action trace) diff 가 default 여야
M4. 947 un-anchored method 처리 — twin auto-synthesizes (B-style) / ontology 확장 / hybrid 중 선택
M5. Determinism mechanism pin — LLM 사용 시 prompt drift 발생. Pure rule-based 시 single-anchor 38 slot 대처법
M6. Gap 표면 via ontology 만 — verification_level/confidence/anchor presence 의 결정론적 함수. LLM judgment 금지 (R2 가 falsifiable 하지 않게 됨)
M7. "풀 시연" 정의 사용자 확인 — "36 actions 모두 byte-identical" vs "happy-path demo" 다른 scope
M8. LocalDateTime.now() / AtomicLong / @Transactional / JPA derived query 명시적 처리 — 각각 R3 의 silent failure 원인
M9. Git artifact volume 계획 — ~9k Python LOC regen per Java edit. version-pin / gitignore + external / content-address 중 선택
M10. Smoke-test contract 먼저 작성 — α 의 E-1 은 divergence 발견 후에 추가됨. 다음 반복은 두 번째 artifact 작성 전 smoke test 부터
M11. KNOWN_DIVERGENCE root cause = inter-agent contract 부재 — A: 부분 방지, B: 방지 못함, C: 방지 못함. 모두 explicit contract layer 필요

5. 권장 종합 설계 — "Anchored Twin Synthesizer"

One sentence: 결정론적 2-layer 합성기 + 명시적 twin scope boundary + 합성기↔runtime typed contract. 즉, A 의 paired registry + B 의 AST fallback + C 의 카드 content + Skeptic 의 contract first-class.

핵심 설계 요소 5가지

1. 2-layer Translation (A + B 통합)

  • Layer 1 — Slot-keyed Template Registry: {target_slot: (java_pattern, py_emitter, runtime_imports)}. 79 slot 모두 entry 필요. 현 27 카드 (hot 10 slot) 가 starting point — content reuse, framing reframe.
  • Layer 2 — AST-walk Literal Translator: anchor 없는 statement / un-anchored method 의 fallback. ~50 mechanical rule (B 의 table).
  • 분기: 합성 시 statement 의 line 이 anchor_binding 에 매칭되면 Layer 1, 아니면 Layer 2.

3. Synthesizer↔Runtime typed Contract (M2 + M11)

# backend/modeling/sim_verify/contracts/__init__.py
from typing import Protocol

class BigDecimal(Protocol):
    def multiply(self, other: "BigDecimal") -> "BigDecimal": ...
    def divide(self, other: "BigDecimal",
               mc: "MathContext") -> "BigDecimal": ...
    def set_scale(self, scale: int,
                  mode: "RoundingMode") -> "BigDecimal": ...
    def compare_to(self, other: "BigDecimal") -> int: ...

class AlgorithmException(Protocol):
    error_code: str
    step_no: int
    step_name: str
    message: str

class LookupDataSource(Protocol):
    def find_first(self, **keys) -> Any | None: ...
  • Synthesizer registry 는 contract 만 import. Runtime 구현은 contract 만족만 보장
  • Smoke test (확장 Phase α E-1): test_runtime_implements_all_contracts.py — 각 Protocol 의 모든 method 가 runtime 에 존재 + 시그니처 일치
  • Version pin: contract 변경 시 contracts/__version__ bump. Synthesizer 는 자신이 require 한 contract version 명시 → mismatch 시 startup fail

이게 α 실패 prevention 의 핵심. 카드/runtime drift 가 다시 발생하지 않으려면 둘이 implicit 으로 동기화되는 게 아니라 contract 가 둘 사이에 first-class artifact 로 있어야 함.

4. Gap Surface — 결정론적 (M6)

def gap_marker(action: ActionRow, anchor: AnchorRow | None,
               type_realiz: TypeRealization | None) -> str | None:
    # LLM 없음. ontology 행 상태의 pure 함수.
    if action.verification_level == "signature_locked":
        return "# UNCLEAR: SIGNATURE_LOCKED — body 추정"
    if anchor is None:
        return f"# UNCLEAR: 이 statement 는 anchor 없음 — 처리과정 보장 X"
    if anchor.confidence < 0.85:
        return f"# UNCLEAR: anchor confidence {anchor.confidence} (낮음)"
    if type_realiz and not type_realiz.confirmed:
        return (f"# UNCLEAR: type_realization {type_realiz.code_type} → "
                f"{type_realiz.term_fqn} (source={type_realiz.source}, "
                f"conf={type_realiz.confidence}, 미확인)")
    return None   # gap 없음

R2 ("빈틈 자각") 는 ontology row 의 결정론적 함수. LLM judgment 없음 → falsifiable + 재현 가능.

8. KNOWN_DIVERGENCE 5종 방지

α 의 실제 root cause = inter-agent contract 부재. 종합 설계가 contract layer 를 1급 시민으로 도입 → 5종 미스매치 mechanism 차원에서 제거:

α 미스매치종합 설계 처리
BigDecimal (class vs bd() factory)BigDecimal Protocol 정의. Facade 가 구현. Synthesizer registry 는 Protocol 만 import → runtime API 변경 시 smoke test fail
MathContext (enum vs DECIMAL64_* consts)MathContext Protocol 의 단일 형태. Facade 가 enum 으로 노출
RoundingMode (enum vs decimal.ROUND_*)RoundingMode Protocol. Facade 가 enum 으로 통일
SdConstants (namespace vs POS_SM)SdConstants namespace class facade. Synthesizer 는 namespace 형태로만 emit
ValidationResult (dataclass vs 없음)Java record ValidationResult → Python @dataclass. Java AST 의 record 인식이 Gap D-3 해결 후 자동

9. Honest weaknesses (M11 흡수)

  • Twin scope 가 ~80% 임을 인정 — @Async, 복잡한 Spring boot config, reflection 기반 코드 등은 명시적 stub 또는 SIGNATURE_LOCKED 처리. ADR-002 에서 명시
  • Registry maintenance — 79 slot 의 entry 모두 작성 필요 (현 27 카드). ~52 신규 slot 작업. 단 one-time 비용
  • Section 2 ontology 완비 의존 — Gap A 의 2 추상 action 은 Section 2 가 21 concrete realization 추가 필요. 합성기가 해결 못함
  • 합성기 자체가 새 codebase (~2000 LOC) — Layer 1 + Layer 2 + contract + gap surfacer + 5 stub. Phase α 의 ≈ 50 시간 작업과 동등 수준 추가
  • Tree-sitter 의 결정성 의존 — parser 버전 변경 시 AST 변할 수 있음. Version pin 필수
  • "풀 시연" 정의에 따라 scope 변동 — M7 (사용자 확인 필요)
