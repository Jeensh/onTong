Anchored Twin Synthesizer — 자체 검토 + 사용 시나리오 WALKTHROUGH

종합 설계안 (DESIGN-SYNTHESIS.html) 자체 비판 + 3 use case 구체 실행 예시.
사용자가 판단 가능하도록 실제 v2 코드/데이터 기반으로 흐름을 따라갑니다.

이 문서의 위치 — 종합 설계가 추상적이었을 수 있습니다. 이 문서는 (1) 설계의 약점을 honest 하게 노출하고, (2) 풀 시연 + 영향 분석 + R5 비교 세 use case 의 실제 실행 흐름을 보여줍니다. 사용자 결정: "이 설계가 진짜로 작동할 만한가?" 판단 보조.

1. Self-Critique — 종합 설계의 honest weakness 8가지

4 perspective 종합 후 떠오른 빈틈을 스스로 검토합니다. 각 빈틈 옆 HIGH/MED/LOW 는 영향도.

W1. Layer 1 ↔ Layer 2 경계의 fuzzy 영역 HIGH

문제: 단일 Java statement 가 multi-line (예: SdThicknessAction.java L57-60 의 castSpecService.lookup(...) 4 줄) 일 때, anchor 가 L57 만 가리키지만 statement 는 L57-60 까지 cover. Layer 1 emitter 가 statement 전체 처리해야 하는가, 시작 line 만 처리하는가?

완화: Layer 1 emitter 는 anchor 가 가리키는 AST 노드 전체 를 처리 (line 만이 아닌 sub-tree 단위). 합성기는 AST 노드의 line range 와 anchor.line 을 join — anchor 가 노드 시작 line 안에 들어가면 그 노드 전체가 Layer 1 으로. 미세 boundary 는 추후 ADR-003 의 dispatch table.

W2. Registry 의 52 신규 entry 누가 작성하는가 HIGH

문제: 현 27 카드 → 79 slot 의 1:1 registry 로 확장하려면 52개 신규 entry 작성 필요. 사람이 작성 시 α 의 inter-agent 문제 재발 위험.

완화: (1) Contract smoke test (E-1 확장) 가 매 entry 추가 시 강제 → 작성자가 누구든 contract 위반은 즉시 fail. (2) LLM 보조 작성 + 사람 review + smoke test 통과 후 commit (작성 자체는 빠름, 검증이 gate). (3) 38 single-anchor slot 은 cross-validation 부재 — 카드 1장 × 1 anchor 의 신뢰도 낮음을 인정하고 single-anchor 카드는 high-confidence 요구 정책.

W3. Contract version bump 비용 MED

문제: BigDecimal.multiply() Protocol 시그니처 변경 시 모든 registry entry 의 emit 코드 영향. 79 entry × 검토 = 운영 부담.

완화: backward-compatible 변경만 minor bump (Protocol 에 method 추가 OK, 기존 method 변경 X). Breaking change 는 major bump + 모든 entry migration 필수. Contract 는 SemVer 적용.

W4. Layer 2 도 contract 의존 (Layer 1 만의 책임이 아님) MED

문제: 947 un-anchored method 도 BigDecimal, AlgorithmException 등 사용. AST walker (Layer 2) 가 new BigDecimal("100") 만나면 Python 으로 BigDecimal("100") 으로 emit — contract 위반 시 똑같이 fail.

완화: Contract 는 합성기 전체의 first-class artifact 임을 명시. Layer 1 = template-based contract use, Layer 2 = AST-rule-based contract use. 둘 다 contract 통한 import. Smoke test 가 두 layer 모두 cover.

W5. Section 2 ontology transition state 미정의 MED

문제: 현 ontology 38/985 anchored. Gap A (2 abstract action) 미해결. 합성기가 이 상태에서 동작 가능한가?

완화: (1) Layer 2 fallback 으로 anchor 없는 method 도 literal Python 생성 (부분 ontology 도 동작). (2) Gap A 의 abstract action 은 NotImplementedError(SIGNATURE_LOCKED) stub + gap-report.json 명시 → orchestrator 가 호출 시 명시적 fail. (3) Section 2 의 minimum quality gate 정의 필요 — 별도 ADR-004 후속.

W6. Performance — 985 method re-synth latency LOW

문제: 매 Java edit 마다 전체 재합성? Tree-sitter parse + ontology query + render = 추정 method 당 ~5ms. 985 × 5ms ≈ 5s. R5 cycle 의 매 step 에 발생.

완화: Incremental synthesis — 변경된 Java file 만 재합성 (대부분 R5 case). 단 ontology revision change 시는 full re-synth (드물게 발생). Cache key = (java_file_hash, ontology_revision, registry_version).

W7. Stub 의 진짜 Java 동작 동등성 검증 어려움 HIGH

문제: @Transactional rollback stub 의 session journal 이 진짜 JTA 와 정확히 같은가? LocalDateTime stub 의 clock injection 이 timezone/precision 까지 동일한가? Stub 의 silent 미동등이 R3 violation 으로 직결.

완화: (1) Stub 별 behavioral parity test — Java 단순 시나리오 (트랜잭션 rollback, 시간 정확성) 를 Python stub 로도 실행해 결과 비교. (2) Golden fixture 의 stub-exercising 시나리오 추가 (현 S1-S5 는 happy path 만 — failure / time-sensitive S6-S8 추가). (3) R3 의 tolerance 정책 명시 — 100% bit-identical 이 아닌, "non-deterministic field (timestamp, sequence) 제외 + BigDecimal 은 string equality" 로 R3 의 의미 좁힘 (Skeptic E-2 인정).

W8. Impact analysis (영향 분석) 가 1급 use case 인가 HIGH

문제: 사용자가 추가한 use case ("품종 바꾸면 어디 영향?") 는 R5 의 변형 — input 변경에 따른 trace 영향 분석. 종합 설계가 이걸 지원하지만 사용자 surface (CLI / Web / Notebook) 미정. 1급 use case 면 surface design 도 spec 에 포함되어야.

완화: "Twin Runner" 의 CLI/API 가 R5 + Impact 둘 다 지원. 다음 use case 2 에서 구체화. 사용자 결정: impact analysis 가 spec 의 1급 시민인가? 종합 설계가 자연스럽게 지원하므로 yes 라고 가정하고 진행.

Q3 a 가 다른 옵션 대비 좋은 이유

  • Text diff 의 noise 회피: 9k Python LOC 의 text diff 는 1줄 변경에도 reformat noise 가능. Semantic diff 는 의미 단위 (anchor) 로 묶여서 noise 없음
  • Cascade 가시화: 단일 line 변경이 cascading 영향이 있는지 즉시 식별. 사람이 "왜 X 가 변했지?" 추적 가능
  • Action 단위 grouping: 13 action × 18 trace = 234 event 인데, action 별로 묶여서 13 cards 로 표현. 정보 밀도 적정
  • Java diff + Python diff + trace diff 3-tier: Java diff = "왜", Python diff = "synthesizer 결정성 증명", trace diff = "행동 변화". 각자 다른 질문 답

5. 합성기 자체의 self-test (M10 적용)

합성기가 옳다는 것을 어떻게 검증할까? α 의 E-1 smoke test 를 contract layer 에 확장:

# tests/verification/test_synthesizer_contract.py

def test_all_protocols_implemented_by_runtime():
    """Every Protocol method must exist in runtime with matching signature."""
    from backend.modeling.sim_verify import contracts, runtime
    for protocol_name in contracts.__all__:
        protocol = getattr(contracts, protocol_name)
        impl = getattr(runtime, protocol_name, None)
        assert impl is not None, f"{protocol_name} not in runtime"
        for method_name in dir(protocol):
            if method_name.startswith('_'): continue
            assert hasattr(impl, method_name), \
                f"{protocol_name}.{method_name} missing in runtime"
            # 시그니처 비교
            proto_sig = inspect.signature(getattr(protocol, method_name))
            impl_sig = inspect.signature(getattr(impl, method_name))
            assert proto_sig == impl_sig, f"{method_name} signature mismatch"

def test_synthesizer_idempotent():
    """Re-synthesis on unchanged inputs produces byte-identical Python."""
    out1 = synthesize("action.scm.thickness_실행", "slab-design-real-v2")
    out2 = synthesize("action.scm.thickness_실행", "slab-design-real-v2")
    assert out1 == out2

6. Honest Limitations (M11 인정)

한계대응
Reflection-based dynamic loading (Class.forName 등) v2 에는 미사용 확인. 등장 시 SIGNATURE_LOCKED + 명시 stub
@Async / Reactive (CompletableFuture) 현 v2 미사용. 미래 등장 시 단일 thread 로 폐기 (synchronous 변환)
새 Java pattern (switch expression 등) Layer 2 의 UnsupportedJavaNode error 로 fail. 사람이 visitor rule 추가
100% bit-identical R3 보장 어려운 영역 LocalDateTime.now() (injected clock 으로 fixed), AtomicLong (singleton), Java BigDecimal.equals (compare_to 만 사용 정책). R3 의 tolerance 명시
합성기 자체의 bug self-test 4종 + contract smoke. 그러나 unknown unknowns 는 fixture coverage 에 의존 — 5 fixture 외 추가 fixture 작성 권장
