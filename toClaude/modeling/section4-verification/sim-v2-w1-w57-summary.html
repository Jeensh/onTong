① 한눈에 보기

Section 4 sim_v2 는 Java→Python twin 의 production-grade 검증 인프라 완비. deterministic 한 4-차원 verification stack (존재 → param shape → primitive return → object_ref return) 위에서 실제 production 데이터 (`data/ontology.db`) 의 drift 를 surface 하고 actionable recommendation 까지 생성. framework 가 자기 결함도 측정해서 두 번의 self-improvement loop 를 자체 close out.

③ W57 예시 — Term Resolver 가 OBJECT_REF gap 을 close out

W56 이 close 시점에서 6건의 OBJECT_REF_SKIPPED 가 남아 있었음. 액션이 object_ref 출력을 선언했을 때, 해당 term 이 가리키는 실제 Java 클래스를 아직 모르기 때문. W57 은 business_terms.description 안의 「자동 추천 — <Java FQN>」 stash 형식 (W45 의 method 측 패턴과 sister) 을 파싱해 deterministic 하게 해소.

예시 1: 5/6 자동 VERIFIED — find_group

// Section 2 가 stash 한 형식
business_terms.description = "자동 추천 — com.example.slabdesign.store.sd.std.domain.entity.EdgingGroupEntity"
business_terms.aliases_json = ["EdgingGroupEntity"]

// action.output_json
{"type":"object_ref", "object_ref_term":"term.scm.edging_group"}

// 실제 Java method
EdgingService.findGroup(...).return_type = "EdgingGroupEntity"

// W57 의 resolver 작동
TermJavaResolution(
  java_fqn = "com.example.slabdesign.store.sd.std.domain.entity.EdgingGroupEntity",
  aliases  = ("EdgingGroupEntity",)
)
candidates = ("EdgingGroupEntity", "com.example...EdgingGroupEntity")

// method_return "EdgingGroupEntity" ∈ candidates → VERIFIED ✓

예시 2: 1/6 real arity drift — extract_designable_orders

액션은 단건 Order 반환을 선언했지만 실제 메서드는 List<SDOrderEntity> 반환. Section 2 의 authoring 결과와 실제 코드 사이의 의미 있는 drift — 컬렉션/단건 arity 가 어긋남. 이런 신호는 LLM 추론 없이 W57 의 deterministic 해소만으로 surface. 

// term.scm.order.order
business_terms.description = "자동 추천 — com.example.slabdesign.store.sd.working.domain.entity.SDOrderEntity"
business_terms.aliases_json = ["Order", "SDOrderEntity"]

// action.output_json
{"type":"object_ref", "object_ref_term":"term.scm.order.order"}

// 실제 Java method
SdOrderService.extractDesignableOrders(...).return_type = "List<SDOrderEntity>"

// W57 의 비교
candidates = ("SDOrderEntity", "Order", "com.example...SDOrderEntity")
method_return_simple = simple_name_of(_strip_generics("List<SDOrderEntity>")) = "List"
"List" ∉ candidates → OBJECT_REF_MISMATCH ✗

// → Section 2 의 actionable backlog 입력:
// action.scm.order.extract_designable_orders 의 output 을 list-typed term 으로 lift

④ W55/UC22 예시 — Detect→Fix Loop 의 Param 측 Close

W52 가 NAME_MISMATCH 를 감지, W55 가 그것을 구체적 fix step 으로 변환. "코드는 ground truth" 원칙으로 action declaration 측을 method 에 align.

// W52 가 surface 한 drift (slab-design-real-v2)
ParamSignatureVerification(
  action_fqn       = "action.scm.product.batch_design",
  code_method_fqn  = "com.example.slabdesign.SdDriver.batchDesign(String,String)",
  status           = "NAME_MISMATCH",
  diverging_positions = [
    (pos=3, action_name="productTypeCd", method_name="productCd"),
    (pos=4, action_name="prodKindCd",    method_name="productCd"),
  ]
)

// W55 가 변환한 RemediationStep
RemediationStep(
  kind            = "RENAME_ACTION_PARAM",
  action_fqn      = "action.scm.product.batch_design",
  code_method_fqn = "com.example.slabdesign.SdDriver.batchDesign(String,String)",
  param_position  = 3,
  current_name    = "productTypeCd",
  expected_name   = "productCd",
  recommendation  = "Rename action param at position 3: 'productTypeCd' → 'productCd'",
  rationale       = "Method signature is authoritative (code is ground truth)"
)
// 같은 형태로 #4 (prodKindCd → productCd) 도 1 step

// UC22 실행: slab-design-real-v2 → 3 RENAME_ACTION_PARAM step (모두 → productCd)

이 step 들이 Section 2 의 next-iteration backlog 의 정량 입력. 같은 패턴이 schema 측에도 적용됨 (UC18: drift → PostgreSQL DDL).

⑦ Self-Improvement Loop — Framework 가 자기 결함을 close out 한 두 번의 시연

Loop #1 (W49 → W50 → W51): bigdecimal `.add` false positive

W49 의 idiom verifier 가 production 코드에서 발견한 false positive 를 W50 가 root-cause 분석, W51 가 unambiguous method dispatch 추가로 close out. idiom coverage 100% 달성. 

before: `result.add(x)` 가 무조건 bigdecimal_arith 매칭 → 실제로는 list.add()
after:  `.add` 를 모호하므로 패턴에서 제거 + receiver type-aware dispatch 도입
        (W51 의 `_UNAMBIGUOUS_BIGDECIMAL_METHODS = {subtract, multiply, divide, remainder}`)

Loop #2 (W53 → W54): substring match + List.of() translator gap

W53 의 aggregate health rollup 이 v2 의 idiom 측 finding 두 가지를 노출: (1) try-with-resources regex 가 recordRetry( / tryStep( 까지 매칭 (substring 매치 버그), (2) List.of() 같은 collection factory 가 translator 에 매핑 누락. 

before: regex `try\s*\(` 가 `tryStep(` 매칭 (false positive)
after:  `\btry\s*\(` 의 word boundary 추가 + List.of/Set.of/Map.of → Python literal 매핑

두 loop 모두 framework 가 surface → triage → refine → re-measure 4 단계를 거쳐 자체 close out. "verification gates 가 발견한 결함은 verification gates 가 닫는다" 의 운영 가능성을 시연.
