KNOWN_DIVERGENCE 5종 — 해소 옵션 비교

α1 (runtime) 과 α2 (idiom 카드) 가 병렬로 작업하면서 만들어진 API 미스매치 5종을 어떻게 해소할지 결정합니다.
3가지 방향 (A/B/C) 의 차이를 코드 예시로 비교합니다.

1. 무엇이 문제인가

Phase α 에서 두 작업자가 병렬로 산출물을 만들었습니다:

α2 (idiom 카드 작성자) α1 (runtime 작성자) │ │ ▼ ▼ 카드 27장 작성 Python 모듈 작성 "Java처럼" 보이는 코드 함수형 API BigDecimal("100").multiply(x) bd_multiply_decimal64(bd("100"), x) .divide(y, MathContext.DECIMAL64) │ │ └──────────────┬─────────────────────┘ ▼ Section 3 (시뮬레이터 작업자) "카드 import 가 runtime 에 없네!" → ImportError / NameError 폭탄

카드가 가정한 5개 이름이 실제 runtime 에는 없습니다 (smoke 테스트 E-1 이 잡아냄):

α2 카드가 import 의도 α1 runtime 실제 결과
BigDecimal Java BigDecimal class wrapper bd() factory 함수, Python Decimal 반환 ✗ NameError
MathContext 정밀도 + rounding 묶음
(MathContext.DECIMAL64)		 DECIMAL64_PRECISION = 16, DECIMAL64_ROUNDING = ROUND_HALF_EVEN (개별 상수) ✗ NameError
RoundingMode enum (RoundingMode.FLOOR) 없음. decimal.ROUND_FLOOR 등 stdlib 상수 직접 사용 ✗ NameError
SdConstants namespace (SdConstants.POS_SM) POS_SM, POS_HR 등 module-level 직접 import ✗ NameError
ValidationResult dataclass (ValidationResult.fail(...)) 없음. Java 에는 v2 source 에 있지만 Python runtime 미구현 ✗ NameError

실제 카드 코드와 runtime 코드의 차이

P01 idiom card (body.compute — slab 무게 계산) 예시:

α2 카드가 보여주는 Python

from backend.modeling.sim_verify.runtime import (
    BigDecimal,         # ✗ 없음
    MathContext,        # ✗ 없음
    RoundingMode,       # ✗ 없음
)

INVERSE_UNIT = BigDecimal("1000000")

raw = (slab.slab_wgt_in_progress
       .multiply(INVERSE_UNIT)
       .divide(slab.target_slab_width
                  .multiply(thickness)
                  .multiply(density),
               MathContext.DECIMAL64))

floored = raw.set_scale(0, RoundingMode.FLOOR)
Section 3 가 이걸 그대로 옮기면 3개 ImportError + 메서드 체이닝 (.multiply() 등) 도 Python Decimal 에 없어 AttributeError.

α1 runtime 이 실제로 제공

from backend.modeling.sim_verify.runtime import (
    bd, bd_multiply_decimal64,
    bd_divide_decimal64, bd_set_scale,
)
from decimal import ROUND_FLOOR

INVERSE_UNIT = bd("1000000")

# multiply 2회 + divide 1회 (함수 호출)
denom = bd_multiply_decimal64(
    bd_multiply_decimal64(
        slab.target_slab_width, thickness),
    density)
numer = bd_multiply_decimal64(
    slab.slab_wgt_in_progress, INVERSE_UNIT)
raw = bd_divide_decimal64(numer, denom)

floored = bd_set_scale(raw, 0, rounding=ROUND_FLOOR)
실제로 돌아가는 코드. 하지만 Java 원본과 모양이 많이 달라 1:1 매핑이 헷갈림.

2. 해소 옵션 A — Runtime 에 facade 추가 A

α1 runtime 의 함수형 API 는 그대로 두고, 그 위에 Java-스러운 클래스 / enum / 네임스페이스를 만들어 얹습니다. 카드는 한 글자도 안 고치고 그대로 실행 가능해집니다.

Runtime 에 추가할 것 (+200줄 정도)

class BigDecimal:
    """Java BigDecimal-like wrapper around bd()."""
    def __init__(self, value):
        self._d = bd(value)

    def multiply(self, other):
        return BigDecimal(
            bd_multiply_decimal64(self._d, other._d))

    def divide(self, other, mc=None):
        return BigDecimal(
            bd_divide_decimal64(self._d, other._d))

    def set_scale(self, scale, rounding):
        return BigDecimal(
            bd_set_scale(self._d, scale, rounding=rounding))


class MathContext:
    DECIMAL64 = (DECIMAL64_PRECISION, DECIMAL64_ROUNDING)


class RoundingMode:
    FLOOR = ROUND_FLOOR
    HALF_EVEN = ROUND_HALF_EVEN
    CEILING = ROUND_CEILING


class SdConstants:
    POS_SM = POS_SM
    POS_HR = POS_HR
    # ... 8개 position 상수


@dataclass
class ValidationResult:
    is_failed: bool
    error_code: str | None
    message: str | None

    @classmethod
    def fail(cls, code, msg): ...
    @classmethod
    def ok(cls): ...

그러면 P01 카드는 한 줄도 안 고침

from backend.modeling.sim_verify.runtime import (
    BigDecimal, MathContext, RoundingMode,
)

INVERSE_UNIT = BigDecimal("1000000")

raw = (slab.slab_wgt_in_progress
       .multiply(INVERSE_UNIT)
       .divide(slab.target_slab_width.multiply(thickness).multiply(density),
               MathContext.DECIMAL64))

floored = raw.set_scale(0, RoundingMode.FLOOR)  # ✓ 그대로 작동

장단

장점 • 카드 27장 손 안 댐
• Java 원본과 거의 1:1 매핑 (slab 설계 알고리즘 자바 코드 보면서 옮기기 쉬움)
• Section 3 가 카드를 copy-paste 수준으로 사용 가능
단점 • runtime 에 약 200줄의 wrapper 코드 추가 (유지보수 부담)
• Pythonic 하지 않음 (Python 사람은 a * b 가 자연스러운데 a.multiply(b) 강제)
• wrapper 와 functional API 가 공존 → "어느 쪽을 쓸지" 혼란 가능

3. 해소 옵션 B — 카드 27장 재작성 B

runtime 은 그대로 두고, 카드 27장의 Python 예제를 모두 함수형 API + Python idiomatic 으로 다시 씁니다.

P01 카드 재작성 후

from backend.modeling.sim_verify.runtime import (
    bd, bd_multiply_decimal64, bd_divide_decimal64, bd_set_scale,
)
from decimal import ROUND_FLOOR

INVERSE_UNIT = bd("1000000")

raw = (slab.slab_wgt_in_progress
       .multiply(INVERSE_UNIT)
       .divide(slab.target_slab_width.multiply(thickness).multiply(density),
               MathContext.DECIMAL64))

denom = bd_multiply_decimal64(
    bd_multiply_decimal64(slab.target_slab_width, thickness),
    density)
numer = bd_multiply_decimal64(slab.slab_wgt_in_progress, INVERSE_UNIT)
raw = bd_divide_decimal64(numer, denom)

floored = bd_set_scale(raw, 0, rounding=ROUND_FLOOR)  # ✓

모든 카드 (27장) 가 이런 식으로 변환됨

장점 • runtime 에 새 코드 0 줄
• Python idiomatic (from decimal import …, 함수 호출, 명시적 매개변수)
• "wrapper class 와 함수, 어느 쪽?" 혼란 없음
단점 • 카드 27장 모두 재작성 — 작업량 큼
• Java 원본과 모양이 달라 1:1 매핑이 직관적이지 않음
• slab 설계 알고리즘 같이 BigDecimal 체이닝이 핵심인 코드는 가독성 떨어짐

4. 해소 옵션 C — 하이브리드 C

BigDecimal 만 facade class 로 (Java 체이닝 유지), 나머지 4종 (MathContext / RoundingMode / SdConstants / ValidationResult) 은 카드를 고쳐서 runtime 의 실제 이름을 사용하게 합니다.

Runtime 에 추가할 것 (+80줄 정도, BigDecimal 만)

class BigDecimal:
    def __init__(self, value): self._d = bd(value)
    def multiply(self, other): ...
    def divide(self, other): ...      # MathContext 인자 제거
    def set_scale(self, scale, rounding): ...

# MathContext, RoundingMode, SdConstants, ValidationResult 추가 X

P01 카드 부분 수정 (BigDecimal 체이닝은 유지, 나머지는 stdlib)

from backend.modeling.sim_verify.runtime import BigDecimal
from backend.modeling.sim_verify.runtime import MathContext, RoundingMode
from decimal import ROUND_FLOOR  # stdlib 직접

INVERSE_UNIT = BigDecimal("1000000")

raw = (slab.slab_wgt_in_progress
       .multiply(INVERSE_UNIT)
       .divide(slab.target_slab_width.multiply(thickness).multiply(density)))
       , MathContext.DECIMAL64)  # MathContext 인자 제거 — 기본 DECIMAL64 자동

floored = raw.set_scale(0, ROUND_FLOOR)  # RoundingMode.FLOOR 대신 stdlib

다른 카드 (P22) 예시 — SdConstants 부분

from backend.modeling.sim_verify.runtime import SdConstants
from backend.modeling.sim_verify.runtime import POS_SM, POS_HR, POS_HRF

if confirmed_plant_cd[SdConstants.POS_SM] != ' ':

장단

장점 • Java BigDecimal 체이닝의 가독성 유지 (slab 알고리즘의 핵심 패턴)
• runtime wrapper 코드 80줄로 최소
• 카드 수정도 단순 search & replace 수준 (MathContext.DECIMAL64 제거, RoundingMode.X → ROUND_X)
단점 • runtime 과 카드 양쪽 수정 — 일관성 없는 듯한 인상
• "BigDecimal 만 클래스, 나머지는 함수/상수" 라는 디자인 선택을 문서화 필요
• ValidationResult 는 어차피 새로 만들어야 함 (옵션 A 처럼 runtime 에 추가)

6. 결정 가이드

Section 3 가 자바 코드 보면서 옮길 때 무엇을 더 중시하는지 가 핵심 결정 기준입니다.
이런 우선순위라면 추천 옵션
Java 원본 알고리즘 (특히 BigDecimal 체이닝 + MathContext) 의 모양과 가능한 똑같이 보이도록 Python 을 짜고 싶다. Section 3 가 카드를 거의 copy-paste 로 쓸 수 있어야 한다. A Facade
onTong 의 다른 Python 코드와 같은 스타일 (함수형, 명시적, stdlib) 유지를 우선. 카드는 "이렇게 짜는 게 정석" 인 문서 역할. B 카드 재작성
BigDecimal 의 정밀도/rounding 동작은 Java 와 동일하게 보존하고 싶지만 enum/namespace 같은 사소한 wrapper 까지는 과하다. 빠르게 끝내고 Phase β 진입하고 싶다. C 하이브리드
참고: 어떤 옵션을 선택하든, tests/verification/test_idiom_runtime_contract.py 의 KNOWN_DIVERGENCE set 이 해소된 항목만큼 줄어들고, 모든 항목이 해소되면 빈 set 이 됩니다. Phase β 진입 전 빈 set 이 되어야 합니다.
