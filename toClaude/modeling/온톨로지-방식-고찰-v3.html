1. Q1 심층 — 우리는 왜 분리 안 해도 되나, 그리고 우리만의 개념

1.1 사용자 직관 검증 — "코드라는 결정론적 기반" 가설

사용자 메모: "팔란티어처럼 나눌 필요 없다는게, 우리는 코드라는 결정론적인 기반이 있으니까 매핑하는 순간 확정을 해줘서 그런건가?"

거의 정확합니다. 정확하게 짚으면 — 팔란티어가 Function 을 분리한 것은 "logic 의 재사용 (compose) 을 위해" 이고, Action 을 분리한 것은 "권한·감사·side effect 의 거버넌스 boundary" 때문입니다. 우리 환경에서는 둘 다 약하게만 필요합니다:

팔란티어 분리 이유우리 환경에서 의미
Logic 재사용 — Function 을 여러 Action 이 합성 Java 메서드 자체가 logic. private helper 도 코드에 이미 존재. 로직 단위는 코드가 ground truth(v3 결정), 재정의 불필요.
거버넌스 — Action 별 권한·승인·notification SCM 분석가 1~3명 팀 환경. 권한 모델 상세 X. PR 자동 생성 (Q-E=E2) 이 사실상 단일 거버넌스 boundary — 한 단계로 충분.
End-user mutation 안전성 우리 mutation = 시뮬레이션 (read-only) + draft PR (사람이 merge). 트랜잭션 atomicity 같은 강건성 불필요.

결론: 단일 Action 노드 + kind 필드 (pure_function/effectful/workflow → Q7 결정 후 단순화 가능) 로 충분. 단, 사용자가 던진 두 번째 질문이 더 중요합니다 →

1.2 사용자 직관 2 — "우리 문제 해결에 맞는 별도의 구성이 있는지?"

팔란티어의 Action/Function 구분은 그들의 문제 (멀티-tenant 운영 데이터 변경 거버넌스) 에서 자연스럽게 도출된 것입니다. 우리 문제는 다릅니다 — "이 시뮬레이션 결과를 사용자가 신뢰할 수 있는가?" 입니다. 여기에 맞는 우리만의 1급 개념을 제안합니다:

제안 — VerificationLevel (검증 등급)

Action 의 시뮬레이션 신뢰도를 나타내는 enum. UI 가 시뮬 결과를 표시할 때 이 등급에 따라 다르게 보여주고, 시뮬레이션 거부 여부도 등급으로 결정. 

class VerificationLevel(StrEnum):
    UNMAPPED       = "unmapped"     # 메서드 발견했으나 Action 매핑 0
    DRAFT          = "draft"        # Action 후보만 있음, 시그니처 미확정
    SIGNATURE_LOCKED = "signature_locked"  # params/output 확정, 본체 anchor 미완
    BODY_ANCHORED  = "body_anchored"  # 본체 anchor 도 모두 confirmed
    SIM_VERIFIED   = "sim_verified" # 위 + 시뮬레이션 1회 이상 통과
    PR_PROVEN      = "pr_proven"    # 위 + draft PR 까지 만들어져본 적 있음

왜 1급이어야 하나

  • 시뮬레이션 결과 화면에 등급 배지 → 사용자 신뢰 calibration ("이건 sim_verified 라 믿을 만"
    vs "이건 draft 라 추정치")
  • "몇 % 가 SIM_VERIFIED?" 같은 진척 메트릭이 자연스럽게 나옴 — 매뉴얼·코드 매핑 진척 KPI
  • Q8(=A) Strict signature lock 게이트의 정확한 정의: level >= SIGNATURE_LOCKED 이어야 시뮬 가능
  • 팔란티어 권한 모델의 "function-backed Action approval" 위치를 우리 식 (검증 진척) 으로 대체

1.3 확장성 / 고도화 관점 — 단일 vs 분리 long-term

고도화 시나리오단일 Action + VerificationLevelAction+Function 분리
AI 에이전트가 Action 을 호출해 시뮬 자동화 Action.kind 만 보면 됨 (pure 자동, effectful 신중) Function 호출은 자유, Action 만 정책 거침 — 더 유연 but 모델 복잡
복잡 도메인 (재무 / 주문 / 생산) 까지 확장 kind 분화 (pure / effectful / approval-needed / external) 로 흡수 Function library 가 커져 reusable component 화에 유리
다른 언어 (Python / Kotlin) 추가 매핑 realized_by 안에 language 필드만 추가 (이미 있음) 구조 같음, but Function-side 도 듀얼 매핑
사용자 권한·승인 워크플로우 추가 Action 에 approval_required 필드 + 정책 룰 Action 에만 박으면 됨 — 이게 분리의 원래 가치

요약: 단일 Action + VerificationLevel 이 우리 문제 (시뮬레이션 신뢰)에 더 정확히 맞고, 팔란티어식 분리는 우리가 멀티-tenant 운영 도구가 되는 시점 (현재 로드맵 밖) 에 가서야 가치가 나옵니다. Phase 후반에 필요해지면 Action 의 kind=pure_function 들을 별도 Function 노드로 강등하는 마이그레이션은 어렵지 않습니다.

2. Q2 · Q4 심층 — "코드는 있는데 우리 구성이 매핑 못 하는 경우"

사용자 메모: "가장 무서운거는 코드는 존재하는데, 우리 구성이 매핑을 제대로 할 수 없는 경우야."

이건 모델이 절대 가져선 안 되는 사각지대입니다. 시뮬레이션이 "이 변경의 영향" 을 보여줄 때 매핑 못 한 코드 영역이 있으면 결과는 partial 이고 사용자는 그걸 알 길이 없습니다. 실제 Java 코드베이스에서 매핑 곤란한 메서드는 4 가지 패턴으로 나옵니다.

2.1 매핑 곤란 4 패턴

패턴예시문제
① Helper / Util StringUtils.normalize(), private void validateOrderInternal(...) 독립된 Action 도 아니고, 어느 Action 에 속하는지도 1개로 안 정해짐. 여러 Action body 안에서 호출됨
② Composite / God-method processDailyClose() 하나가 발주 + 정산 + 알림 다 함 한 메서드 = 여러 Action 의 일부. 1:N (Q2=B) 도 안 맞음 — 메서드 내부가 조각남
③ Glue / Adapter OrderDtoMapper.toEntity(), repository 호출 wrapping 비즈니스 의미 없음. Action 후보가 아닌 인프라
④ Generic / Generic-typed <T> List<T> findByCondition(Class<T>, Spec) 다양한 도메인에서 호출. 어느 Action 의 일부인지 호출 시점에만 결정됨

2.2 처리 전략 — Q2 사용자 답변 (M:N) 이 옳은 이유 + 보강

사용자가 Q2=C (M:N) 를 고른 것은 정확합니다. 하지만 M:N 만으로는 ②, ③, ④ 가 깨끗히 안 잡힙니다. 4 가지 보강 메커니즘을 더해야 사각지대가 사라집니다.

전략 1 — Method.role 자동 분류

Java parser 단계에서 메서드를 4 종으로 자동 분류: 

class MethodRole(StrEnum):
    BUSINESS  = "business"   # Action 매핑 후보 (default — public, 비-getter, 비즈니스 의미 있는 이름)
    HELPER    = "helper"     # private util, "Internal" / "Util" 이름 패턴
    ADAPTER   = "adapter"    # repository / mapper / DTO 변환 — Action 매핑 면제
    UNKNOWN   = "unknown"    # 자동 분류 실패 — 사용자 큐

HELPER / ADAPTER 는 Action 매핑 안 된다고 경고 안 함. BUSINESS 인데 Action 0 인 경우만 "unmapped" 큐.

이미 java_parser 가 modifier (public/private/static) 를 추출하고 있으므로 base 정보는 있음. 룰 기반 + LLM 보강.

전략 2 — Composite 메서드는 kind=workflow Action 으로 흡수

② 같은 god-method 는 workflow Action 으로 만들고, 그 안에서 호출하는 sub-method 들이 각각의 atomic Action 이 됨. workflow 는 Q7 의 Scenario 와 다름: workflow Action = "이 메서드는 다른 Action 들을 호출한다" 라는 코드 사실, Scenario = "사용자가 시뮬레이션을 위해 만든 가설". 

Action(processDailyClose, kind=workflow, sub_actions=[
    Action(reconcileOrders, kind=effectful, ...),
    Action(settleAccounts, kind=effectful, ...),
    Action(sendDailyNotifications, kind=effectful, ...),
])

전략 3 — Anchor 는 fragment-level 로 자유 binding (Q4=A 보강)

한 메서드의 anchor 들이 각각 다른 Action 슬롯에 매핑되도록 허용. 즉 메서드가 Action A 의 primary 가 아니어도, 그 메서드 body 의 literal 하나는 Action A 의 params[0].range 에 binding 가능. 

class AnchorBinding:
    anchor_locator: str          # method body 안의 위치 (param idx, local name, branch path)
    method_fqn: str              # 어느 메서드의 anchor 인가
    target_action_fqn: str       # 어느 Action 의 슬롯에 매핑되는가
    target_slot: str             # "params[0].range" / "preconditions[2]" / "effects[1].target_term"
    confidence: float
    confirmed: bool

이렇게 하면 Q4=A ("Action.params/output 1급 + 별도 AnchorBinding 테이블") 가 자연스럽게 god-method / generic 메서드의 사각지대를 흡수합니다. 매핑 단위가 메서드가 아니라 anchor 라서 "메서드는 매핑 못 했지만 그 안의 literal/branch 는 Action 의 슬롯에 묶임" 가능.

전략 4 — Workbench 의 "Unmapped Methods" 패널 (사각지대 가시화)

role=BUSINESS 이면서 Action 0 인 메서드 + role=UNKNOWN 메서드를 Workbench 사이드 패널에 한 곳으로 모아 진척 KPI 로 표시. 매핑 못 했다는 사실 자체를 1급 시민으로.

시뮬레이션 시 만약 호출 chain 에 unmapped 메서드가 끼어 있으면 결과 화면에 "이 시뮬은 unmapped {N} 개 메서드를 mock_* 로 처리했음. 결과 신뢰도: 부분." 표시. VerificationLevel(§1.2) 와 정확히 연결됨.

2.3 결론 — Q2 와 Q4 답변 보강

  • Q2 (M:N) 유지 + Method.role 자동 분류 (helper/adapter 면제)
  • Q4 (params/output 1급 + 별도 AnchorBinding) 유지 + fragment-level anchor binding 허용 (메서드 매핑 없이도 anchor 만 매핑 가능)
  • Workbench 에 "Unmapped Methods" 패널 + VerificationLevel 표기 → 사각지대 가시화

3. Q7 심층 — Workflow 표현 + UI/UX

사용자 메모: "팔란티어가 잘 해놨을 것 같은데, 시뮬레이션을 잘 돌리려면 어떤 게 제일 좋아? 사용자가 눈으로 확인하는 UI/UX 에서 가장 명확하게 표현할 수 있는 방법은?"

3.1 팔란티어가 실제로 어떻게 푸나 — Scenario 패턴

조사 결과: 팔란티어는 Workflow 를 별도 노드 타입으로 두지 않습니다. 대신 Scenario 라는 첫째급 개념이 있고, 다음 특징을 가집니다 — Workshop Scenarios 공식 문서 기준 (scenarios-concepts, overview, Vertex):

  • Scenario = Ontology 의 fork/branch — 하나 이상의 Action 을 적용한 가설 분기
  • Scenario infrastructure 는 Action 위에 빌드 ("built on top of Actions")
  • 한 Scenario 는 최대 50 Actions / 30,000 edits
  • UI: Scenario Manager widget + Scenario-aware Object Table — 같은 데이터 그리드가 "어느 시나리오 보기" 로 토글
  • Vertex 도구는 "key parameter 를 override 해서 alternative Action 결과를 시각화"

핵심 통찰

팔란티어는 Action 을 atomic 으로 유지하고, compose 는 Scenario 라는 별도 모델로 빼냈습니다. 이게 우리 v2 § 6 P5 ("workflow 는 Action.kind=workflow") 보다 더 깨끗합니다 — Action 의 의미를 단일 commit 단위로 보존.

3.2 우리에게 맞는 모델 — SimulationScenario 신설

class SimulationScenario:
    id: str
    name: str                            # "리드타임 14→21 시뮬"
    description: str
    base_repo_id: str                    # ontology fork 의 base
    initial_state: dict                  # 시뮬 시작 시점 데이터 (필요 시)
    steps: list[ScenarioStep]            # ordered
    created_at, created_by

class ScenarioStep:
    order: int
    action_fqn: str                      # 호출할 Action
    inputs: dict[str, ScenarioInput]     # param_name → 값 출처

class ScenarioInput:
    kind: Literal["literal", "term_ref", "from_step"]
    value: Any | None                    # literal 일 때
    term_fqn: str | None                 # term_ref 일 때 (현 ontology 의 default)
    source_step: int | None              # from_step 일 때 — 이전 step 의 output
    source_path: str | None              # ".output.value" 같은 dotted 경로

왜 별도 모델인가 — 4가지 이유

  1. Action 은 코드 사실, Scenario 는 사용자 가설 — 두 종류의 데이터가 섞이면 마이그레이션·버전닝 다 꼬임
  2. 한 Scenario 가 여러 ChangeSpec 을 묶음 — 현 ChangeSpec 모델이 다중 변경의 batch 가 되어줌 (kind 분류 그대로 유지)
  3. Reproducibility — Scenario 는 frozen 후 share / replay 가능. P7 (signature_locked 시 새 version) 과 정합
  4. UI 분리 자연스러움 — 시뮬 drawer 가 Scenario 빌더, Ontology editor 는 Action 카드. 모드 분리가 깨끗함 (v3.1 §6 5-mode rail 정합)

단, §2.2 전략 2 의 "Action.kind=workflow" 는 그대로 유지합니다 — 그건 코드 사실 (god-method), Scenario 는 사용자 가설. 둘은 다른 계층:

Action.kind=workflowSimulationScenario
출처Java god-method 발견사용자가 시뮬을 위해 직접 만듦
변경 가능?코드 변경 시만언제든 자유
저장 단위OntologyScenario store (별도)
Trigger—"시뮬 실행" 버튼

3.3 UI/UX — 사용자가 가장 명확하게 보는 방법 3안 비교

안 1 — Step List + State Inspector (수직)

1 리드타임 변경 (set leadTime=21) → leadTime: 14→21
↓
2 안전재고_계산 → 안전재고: 100→142 (+42)
↓
3 발주수량_재산정 → 발주수량: 280→322 (+42)

장점: 5+ step 도 가독성 유지, 순서가 명확, 각 step 클릭 시 파라미터·effect 패널 확장.
단점: 분기·병렬 표현 어려움.

안 2 — Sankey / 흐름 다이어그램 (수평)

입력            Action               output
─────           ──────────            ──────
leadTime=21 ──→ 안전재고_계산 ──→ 안전재고=142
                           │
demand_stdev─→             ─→ 발주수량_재산정 ──→ 발주수량=322

장점: 분기·병렬·데이터 흐름이 시각적으로 강력.
단점: 가로 폭 한계, step 5+ 가면 빠르게 복잡, 모바일 어려움.

안 3 — Spreadsheet-Like Side-by-Side Diff (Vertex 패턴)

          | Baseline      | Scenario "리드타임 21일" | Δ
──────────┼───────────────┼──────────────────────────┼──────
leadTime  | 14            | 21                       | +7
안전재고  | 100           | 142                      | +42
발주수량  | 280           | 322                      | +42
주문비용  | ₩2,800,000    | ₩3,220,000               | +₩420k

장점: 비교가 가장 쉬움, 의사결정자에게 친숙한 표 형식. 팔란티어 Vertex 가 이걸 씀.
단점: 시간 순서·인과 흐름이 안 보임. step list 와 함께 써야 완성.

5. 갱신된 결정 질문 4 개

위 분석 결과로 Q1 / Q2 / Q4 / Q7 을 더 좁혀서 다시 묻습니다. 페이지 안 라디오 + 메모, 자동 저장, 하단 복사 버튼.

Q1' 단일 Action 모델 + VerificationLevel 신설?

§1 결론: 팔란티어식 Action/Function 분리는 우리 환경에 과함. 대신 VerificationLevel (UNMAPPED/DRAFT/SIGNATURE_LOCKED/BODY_ANCHORED/SIM_VERIFIED/PR_PROVEN) 을 1급 시민으로.

Q2' 매핑 못 하는 코드 — Method.role 자동 분류 채택?

§2 보강: Q2(M:N) 유지하되, helper/adapter 메서드는 Action 매핑 면제 + Workbench unmapped 패널로 사각지대 가시화.

Q4' Anchor fragment-level binding 허용?

§2.2 전략 3: 메서드가 Action 에 매핑 안 됐어도 그 안의 anchor 는 Action 슬롯에 직접 binding 가능. 이게 god-method / generic 메서드 사각지대를 흡수.

Q7' Workflow 표현 — SimulationScenario 별도 모델?

§3 결론: 팔란티어 Scenario 패턴 차용. Action 은 atomic 유지, compose 는 SimulationScenario 별도 모델로. UI 는 Step List(좌) + Side-by-side Diff(우) 조합.
