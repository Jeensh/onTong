1. 왜 Round 1은 '코드만'인가

10년 된 레거시에서 유일하게 안 거짓말하는 건 코드다. 기준서는 갱신이 안 돼 있고, 담당자 머릿속은 휘발성이다. 그래서 출발점은 코드.

그런데 Java 클래스 다이어그램만 보고는 "이 메서드를 바꾸면 어디에 영향이 가는가?"를 답할 수 없다. 이유는 3개:

  • Spring은 런타임 조립이 많다. @Autowired 인터페이스가 실제로 어느 구현과 바인딩되는지 AST엔 안 쓰여있다.
  • 메서드 호출이 AOP 프록시를 거쳐가면 정적 호출 그래프에선 안 보인다.
  • HTTP 요청, 배치 스케줄, 카프카 리스너, 이벤트 퍼블리셔 — 진입점이 다양하다.

그래서 Round 1은 Java AST + Spring 특화 분석기 두 레이어로 코드 그래프를 세운다. 이 그래프 위에서 결정적 BFS만 돌려도 Impact Analysis가 나오게 만드는 게 목표.

경계 선언. Round 1에서는 "비즈니스 용어 → 코드 위치" 매핑(Reverse Lookup)과 "기준서 갭 탐지"는 다루지 않는다. 각각 Round 2 / Round 3에서. 단, Round 1의 메서드 노드가 precondition/postcondition 필드를 가지는 것까지는 이번에 확정한다. Test Generation이 이 필드를 먹고 동작할 예정이라 Round 2/3에 미뤄두면 스키마 재공사가 생긴다.

3-A. 확장 설계 원칙 (Q1 / Q2 응답)

사용자 의견: "당장은 충분. 완성 후 추가 시 확장이 용이하도록."
→ 노드/엣지 kind 15종을 하드코드 enum으로 박지 않는다. 플러그인 레지스트리 패턴으로 설계.

Neo4j 층

이미 :CodeEntity{kind: "..."} 단일 레이블 + kind 속성. 새 kind 추가 시 스키마 마이그레이션 불필요. 쿼리 단에서 WHERE n.kind = 'QUARTZ_JOB' 로 필터만 추가하면 됨.

파서/분석기 층

CodeParser / SpringAnalyzer 프로토콜을 두고 각 kind를 담당하는 분석기를 register(kind, analyzer) 로 등록. 새 kind(예: FEIGN_CLIENT)를 추가할 때 기존 파일 수정 X, 새 파서 파일 1개만 추가.

API/프론트 층

Impact Analysis 응답에 kind를 문자열로 그대로 반환. 프론트는 KIND_STYLE_MAP 딕셔너리로 색/아이콘 매핑. 새 kind 아이콘/라벨만 추가하면 노출.

# backend/modeling/code_analysis/registry.py (확장 포인트)
class EntityKindRegistry:
    _kinds: dict[str, EntityKindSpec] = {}

    @classmethod
    def register(cls, kind: str, spec: EntityKindSpec):
        cls._kinds[kind] = spec

    @classmethod
    def all(cls) -> list[str]:
        return list(cls._kinds.keys())

# 기본 15 kind는 부팅 시 기본 분석기 모듈이 register.
# 신규 kind는 별도 모듈(예: plugins/feign_analyzer.py)에서 register.
운영 가능성. Neo4j 그래프 DB 특성상 새 노드/엣지 종류가 추가돼도 기존 쿼리는 망가지지 않는다(존재 안 하면 skip). 즉 하방 호환 자동. Postgres 스키마처럼 ALTER TABLE이 필요 없다. 이건 Neo4j를 고른 실질적 이유 중 하나.

4. 워킹 예시 — OrderController.place()

실제 Java/Spring 코드가 위 그래프로 어떻게 변환되는지 끝까지 따라간다.

4-1. 입력 코드

// OrderController.java
@RestController
@RequestMapping("/orders")
public class OrderController {

  private final OrderService orderService;
  private final ApplicationEventPublisher publisher;

  @Autowired
  public OrderController(OrderService s, ApplicationEventPublisher p) { ... }

  @PostMapping
  public OrderResponse place(@RequestBody OrderRequest req) {
    Order saved = orderService.place(req);
    publisher.publishEvent(new OrderPlacedEvent(saved.getId()));
    return OrderResponse.from(saved);
  }
}

// OrderService.java
public interface OrderService {
  Order place(OrderRequest req);
}

// OrderServiceImpl.java
@Service
public class OrderServiceImpl implements OrderService {

  private final OrderRepository repo;
  private final InventoryClient inventory;

  @Transactional
  @Override
  public Order place(OrderRequest req) {
    inventory.reserve(req.getItems());
    Order o = new Order(req);
    return repo.save(o);
  }
}

// OrderRepository.java
public interface OrderRepository extends JpaRepository<Order, Long> {
  List<Order> findByCustomerId(Long customerId);
}

4-2. 이 코드가 만드는 그래프 (요약)

점선 테두리의 OrderService.place는 인터페이스 메서드. 실제 런타임에 AUTOWIRES 엣지가 연결한 Bean(OrderServiceImpl)로 디스패치된다. 이 '디스패치'를 그래프에서 어떻게 만들지가 Spring 8 난제 §5.1.

핵심 포인트. 정적 AST만 쓴 일반 Java 그래프라면 OrderController.place 다음이 OrderService.place (인터페이스)에서 끝난다. 그런데 Spring 분석기가 AUTOWIRES 엣지를 놓아주면 그래프 BFS가 자연스럽게 OrderServiceImpl.place로 이어진다. 이게 우리가 Spring 전용 분석기를 따로 만드는 본질적인 이유.

5. Spring 8 난제 처리

각 난제를 "왜 안 잡히는가 / 우리 스키마가 어떻게 잡을 것인가"로.

5-1. @Autowired DI

문제

AST에는 private final OrderService service 필드만 있고, 이게 런타임에 어느 구현과 묶이는지 정보 없음.

처리

Spring 분석기가 전체 프로젝트를 1번 훑어 Bean 카탈로그를 구축. 필드 타입 + @Qualifier + @Primary 규칙으로 후보 해석. 결과를 SPRING_BEAN -AUTOWIRES-> SPRING_BEAN 엣지로 저장.

잔여

@Qualifier가 런타임 profile에 의존하거나 @ConditionalOnProperty면 후보 다수. 엣지에 condition 속성으로 저장, 쿼리 시 프로파일 필터.

5-2. AOP 프록시 (@Transactional / @Cacheable / @Around)

OrderServiceImpl.place()를 직접 호출해도 실제로는 CGLIB/JDK 프록시가 먼저 도는 것. 정적 호출 그래프엔 이게 안 보인다.

→ ASPECT 노드를 만들고, advice가 적용되는 메서드마다 ASPECT -INTERCEPTS-> METHOD 엣지. 쿼리 시 "target 메서드의 in-edges에 INTERCEPTS 있으면 그 aspect도 영향 반경"으로 계산.

@Transactional은 파생 aspect 이름을 표준(TransactionAspect)으로 고정, @Cacheable은 CacheAspect.

5-3. Reflection (Method.invoke, Class.forName) rev.2 — 런타임 계측 1차 범위 내

정적 추론 불가. 세 겹의 안전망으로 대응.

레이어처리1차 범위?
L1. 정적 표식 파서가 .invoke( / Class.forName( / BeanFactory.getBean( 호출을 감지하면 METHOD 노드에 reflection_escape: true + 쿼리 결과에 경고 표시 ✅ 포함
L2. 사람 주석 "이 invoke 대상은 이 클래스 범위"를 사람이 명시 → REFLECTS_AS 엣지로 등록 ✅ 포함
L3. 런타임 계측 JVM Java Agent 또는 APM 훅으로 실제 호출 쌍 수집 → CALLS {source: "runtime"} 엣지 추가 ✅ 스키마 + 수집기 인터페이스는 1차 포함. JVM Agent 실제 구현은 Section 2 모델링 완성 후 임시 섹션(§7-A)에서 수행.
왜 처음엔 "1차 범위 밖"이라고 했나, 왜 바꿨나.
당초 근거: JVM Java Agent 개발은 바이트코드 계측이 들어가서 구현 비용이 크고, 운영 환경에 배포해야 데이터가 들어오므로 초기 도메인 데모에는 오버킬이라고 판단. 그래서 "스키마 자리만 마련"으로 축소 제안.

반론(사용자): Reflection 누락 = Impact Analysis 신뢰성 상실. 레거시일수록 Reflection 많음. 대체 수단(사람 주석)만으론 10만 라인 레거시 전체 커버 불가.

결론: 1차에 스키마 엣지(CALLS{source}, REFLECTS_AS) + 수집기 인터페이스 + 로그 인제스트 파이프라인까지 포함. 실제 JVM Agent 구현만 플러그인 형태로 분리 (에이전트는 1 프로젝트 만들면 여러 레거시 재사용). 즉 "준비는 지금, 연결은 선택".

5-4. Spring Data JPA 메서드 파생 (findByCustomerId)

메서드 선언만 있고 쿼리 본문 없음. Spring이 메서드 이름에서 SQL을 만든다.

→ Spring Data 전용 분석기가 메서드 이름 파싱(findBy / existsBy / deleteBy / countBy + 필드 조건)으로 READS_TABLE / WRITES_TABLE 엣지를 엔티티 클래스 매핑(@Entity @Table(name=...))을 거쳐 DB_TABLE로 연결. 메서드 이름이 파싱 안되는 경우(@Query)는 native 쿼리를 SQL 파서로 추가 해석.

5-5. @Bean Configuration

classpath 스캔 기반 Bean 외에, @Configuration 클래스의 @Bean 메서드가 Bean을 만든다. 이건 "메서드 반환값 = Bean 인스턴스"라는 비일상적 의미.

→ Configuration 전용 패스가 @Bean 메서드마다 SPRING_BEAN 노드 생성 + 반환 타입을 실제 구현 클래스로 매핑 + 메서드 파라미터 → AUTOWIRES 엣지.

5-6. ApplicationEventPublisher

발행자/구독자 사이에 직접 호출이 없다. 이벤트 타입이 유일한 연결고리.

→ EVENT_TYPE 노드를 이벤트 클래스마다 생성. 호출 관계는 publisher.publishEvent(new X()) → METHOD -PUBLISHES-> EVENT_TYPE, @EventListener 메서드 → METHOD -HANDLES-> EVENT_TYPE. BFS가 PUBLISHES → EVENT_TYPE → HANDLES 로 이어진다.

5-7. @Scheduled / Kafka Listener

HTTP 엔드포인트가 아닌 진입점. HTTP_ENDPOINT만 진입점으로 모델링하면 배치/리스너에서 시작되는 호출 체인이 고아가 된다.

→ SCHEDULED_TASK / MSG_LISTENER 노드 kind로 진입점 3종을 모두 표현. Impact Analysis 출력에 "진입점 종류" 컬럼 자동 포함.

5-8. @ConditionalOnProperty / 프로파일

동일 Bean이 프로파일에 따라 다른 구현으로 바뀜. 단일 그래프로 표현 못 함.

→ Bean 엣지에 profile: ["prod", "legacy"] / condition: "order.legacy.enabled=true" 속성 저장. 쿼리 시 WHERE 'prod' IN r.profile 로 필터. Impact Analysis 호출 시 프로파일이 기본 파라미터.

6. 메서드 노드 상세 필드 (Test Generation 밑받침)

METHOD kind 노드는 가장 많은 속성을 가진다. Test Generation 엔진이 이 노드만 보고 테스트 케이스를 만들 수 있도록 미리 넉넉히 정의.

precondition선언식 (validator.py의 Sub-DSL). 예: req.items != null AND size(req.items) > 0
postcondition선언식. 예: result.status == "PENDING" AND result.id != null
input_domain파라미터별 값 범위. 예: {"req.items.size": [1, 100]}
exception_paths["OutOfStockException", "InvalidItemException"]
precondition / postcondition / input_domain 을 Round 1에 넣는 이유 (Q5 응답)

파서는 이 값들을 작성 못 한다. 사람이 Round 2/3에서 비즈니스 룰과 매핑하며 채워넣는 필드. 그런데도 스키마 자리는 Round 1에 확정해야 하는 이유 3가지:

  1. 재매핑 비용 — Round 2/3에 가서 수백~수천 METHOD 노드에 사람이 매핑 작업을 해둔 상태다. 그 후 "precondition 필드가 빠져 있었네요, 다시 채워주세요"는 워크플로우 파괴. 자리를 비워두면 null 속성만 채우면 끝.
  2. Test Generation 엔진 설계 제약 — 3대 기능 중 하나. precondition/postcondition/input_domain 없이는 테스트 케이스 생성 불가. 엔진을 나중에 붙이려면 스키마까지 재설계해야 함.
  3. Round 2/3 매핑 일체화 — 비즈니스 룰이 "A이면 B여야 한다" 형태라면 그것은 precondition(A) / postcondition(B)로 메서드에 걸린다. precondition 슬롯이 없으면 룰을 어디에 매달지 불분명. 매핑 작업이 허공에 뜸.

→ 자리만 미리 둔다. 초기 파싱 시엔 null. Round 2/3에서 채움. Test Generation은 Round 1~2 끝나고 Section 3에서 활용.

6-B. 데이터 계보 — 필드 값이 타고 흐르는 경로 (Q3 응답)

사용자 지적: "필드까지 내려가야 하고, 이런저런 필드를 타고다니면서 만들어지는 값도 존재할텐데 그런 걸 잘 추적할 수 있어야 해."

이것은 데이터 계보(Data Lineage) 문제. 예: 

OrderRequest.items           // HTTP 진입값
  → OrderServiceImpl.place()  // req.items → sum * item.price
    → Order.totalAmount        // 도메인 필드
      → repo.save()             // JPA
        → orders.total_amount   // DB 컬럼
          → SettlementJob.calc()   // 배치에서 이 컬럼 읽음
            → Settlement.netAmount
              → settlements.net_amount
              → Kafka SettlementCalculatedEvent
                → 하위 시스템 ...

"OrderRequest.items 가 잘못 들어오면 어디까지 영향이 갑니까?" 같은 질문에 답하려면 필드 단위 전파 추적이 필요하다.

6-B-1. 두 가지 표현 층

메서드 내부 계보 (메서드 속성으로 압축)

METHOD 노드에 value_flow 속성 추가. 형태:

{
  "req.items":      ["this.order.items"],
  "req.totalAmount":["this.order.totalAmount"],
  "this.order":     ["return"]
}

메서드 본문 안의 변수 대입/인자 전달을 tree-sitter로 추출. 노드/엣지 폭발 방지를 위해 노드 분리 대신 속성으로 압축.

메서드 간 계보 (엣지 + 필드 노드)

기존 READS / WRITES 엣지에 추가로 필드-간 엣지 도입:

  • DERIVES_FROM : FIELD → FIELD. "A 값은 B 값으로부터 계산됨" (CALCULATED 결과)
  • PROPAGATES_TO : FIELD/DB_COLUMN → FIELD/DB_COLUMN. "A 값이 그대로 B에 복사됨" (PASSTHROUGH)

두 엣지 모두 via_methods: [qualified_name, ...] 속성으로 어느 메서드를 경유했는지 기록.

6-B-2. 엣지 kind 추가

§3 의 15종에 2종 추가 → 엣지 총 17종:

kindsource → target의미파서 레이어
DERIVES_FROMFIELD/DB_COLUMN → FIELD/DB_COLUMN값이 변환/계산을 거쳐 나옴AST + Spring 분석기 조합
PROPAGATES_TOFIELD/DB_COLUMN → FIELD/DB_COLUMN값이 그대로 복사/전달AST + Spring 분석기 조합

6-B-3. 역추적 질의 예

"orders.total_amount 컬럼 값은 어디서 기원하는가?"

MATCH path = (src)-[:DERIVES_FROM|PROPAGATES_TO*1..]->(t:DB_COLUMN {name: "orders.total_amount"})
WHERE NOT (src)<-[:DERIVES_FROM|PROPAGATES_TO]-()  // 기원점만
RETURN src.qualified_name, path, length(path) AS hops

기대 출력: OrderRequest.items, OrderRequest.promoCode, Configuration(order.tax-rate) 등 진입점 필드.

6-B-4. 동적 매핑 3 전용 분석기 — 모두 1차 범위 포함 (Q9 응답)

데이터 계보에 구멍이 나면 Impact/Reverse Lookup 모두 허위 결과. 레거시에 흔한 3가지 동적 매핑 패턴을 전용 분석기로 1차 범위 안에 포함.

패턴문제1차 분석기 전략산출 엣지
MapStruct 소스→타겟 필드 매핑이 인터페이스 + annotation으로 선언. AST엔 쿼리 없음. @Mapper 인터페이스에 선언된 @Mapping(source=..., target=...) 파싱. 생성된 impl 클래스도 병행 확인. PROPAGATES_TO (필드→필드), DERIVES_FROM (표현식 있는 경우)
BeanUtils.copyProperties / ModelMapper / ObjectMapper 소스·타겟 타입만 인자로 넘기고 런타임에 필드명 매칭. 정적 매핑 정보 없음. 호출 발견 시 소스/타겟 클래스의 필드 교집합을 휴리스틱으로 매핑. 확실성이 낮으므로 엣지에 confidence: 0.7 속성 + 쿼리에 경고 표시. 런타임 계측(§5-3 L3)으로 보강. PROPAGATES_TO{confidence}
Native SQL / JPQL @Query, entityManager.createNativeQuery, MyBatis XML. 메서드명 파싱으로 못 잡음. SQL 본문을 sqlparse 등으로 AST 파싱 → SELECT 절 컬럼 + FROM/JOIN 테이블 + INSERT/UPDATE 컬럼을 엔티티 매핑 거쳐 DB_TABLE / DB_COLUMN 연결. READS_TABLE, WRITES_TABLE, READS / WRITES (컬럼 단위)
왜 1차에 전부 포함. 레거시 Spring 애플리케이션은 이 3개가 전부 혹은 대부분 쓰인다. 하나라도 빠지면 Impact Analysis가 "이 필드가 어디로 흘렀는지 모릅니다" 구간을 쏟아내고, 그러면 결정적 그래프 탐색의 신뢰가 무너진다. 신뢰성 > 구현 무게.

6-B-5. 한계와 복잡 케이스

  • 동적 SQL 빌더(QueryDSL / Criteria API / MyBatis <if>): 분석기가 조건부 쿼리 조각 전부 분기 열거 → 가능한 모든 컬럼 합집합을 엣지로 등록. 불확실성은 conditional: true 속성.
  • 복잡 계산 체인: a = f(b, c); d = g(a, e); 라면 d DERIVES_FROM b, c, e (a 경유). 중간 변수는 접음. 경유 메서드는 via_methods 속성으로 추적 가능.
  • String 기반 필드 접근 (obj.getProperty("name")): 정적으론 못 잡음 → reflection_escape: true 표식 → 런타임 계측으로 보강.
왜 필드-노드 + 필드-엣지 둘 다 쓰는가.
순수 노드만으로 표현하면 "변수 X, 리턴값 Y, ..." 로 그래프가 폭발한다. 순수 속성만으로 표현하면 메서드 간 계보 추적이 속성을 수동 조합해야 해서 쿼리가 불가능하다. 메서드 내부는 속성, 메서드 간은 엣지 — 이게 확장성과 쿼리 성능의 균형점.

7. Impact Analysis 질의 시뮬레이션

질문: "OrderServiceImpl.place()의 로직을 바꾸려 한다. 영향 범위는?"

1타겟 메서드 확정

입력 qualified name으로 노드 확정: com.acme.order.OrderServiceImpl.place(OrderRequest).

2역방향 BFS — 누가 이걸 쓰는가

Cypher (개념, $max_hops 는 사용자 파라미터 — Q6 응답):

MATCH path = (src)-[:CALLS|AUTOWIRES|INTERCEPTS|MAPS_URL|PUBLISHES*1..$max_hops]->(t {qualified_name: $q})
RETURN DISTINCT src.kind, src.qualified_name, length(path) AS hops
ORDER BY hops

→ 결과 (이 예시):

  • METHOD OrderController.place (1 hop, via AUTOWIRES+CALLS)
  • HTTP_ENDPOINT POST /orders (2 hops, MAPS_URL)
  • ASPECT TransactionAspect (1 hop, INTERCEPTS)
3정방향 BFS — 이 메서드가 뭘 건드리는가
MATCH path = (t {qualified_name: $q})-[:CALLS|READS_TABLE|WRITES_TABLE|PUBLISHES|HAS_CONFIG|DERIVES_FROM|PROPAGATES_TO*1..$max_hops]->(dst)
RETURN DISTINCT dst.kind, dst.qualified_name, length(path) AS hops

정방향에 데이터 계보 엣지(DERIVES_FROM/PROPAGATES_TO) 포함 — §6-B 결과.

3-AHops 제어 — 사용자 파라미터 (Q6 응답)

고정값 대신 사용자 조정 가능. API 설계:

파라미터기본값의미
max_hops-1 (무제한)BFS 최대 깊이. 순환 방지는 visited-set으로 별도 처리되므로 무제한이 안전함. 사용자가 성능 이슈 있을 때만 제한 걸도록.
edge_kinds전체탐색할 엣지 kind 화이트리스트. 예: CALLS,AUTOWIRES만. "호출 그래프만 보고 싶다"는 요청용.
max_results500과도한 출력 방지. 결과 cutoff, 초과 시 "더 있음" 플래그.
include_lineagetrue데이터 계보 엣지 포함 여부.
기본값 정책. 당초 제안한 "기본 8"은 철회. 이유: 사용자 지적대로 영향 누락 >> 성능 이슈. 무제한 기본값으로 시작, 사용자가 UI 슬라이더로 낮출 수 있게. 단 프론트는 응답 시간 2초 초과 시 자동으로 hops 경고 배너 표시 + 추천 값 제안.

→ 결과 (이 예시):

  • METHOD InventoryClient.reserve (1 hop, CALLS)
  • METHOD OrderRepository.save (1 hop, CALLS)
  • DB_TABLE orders (2 hops, WRITES_TABLE)
  • EVENT_TYPE OrderPlacedEvent (2 hops — Controller에서 발행이지만 Impl 경유)
  • METHOD OrderEventsListener.onPlaced (3 hops, via PUBLISHES→HANDLES)
4리포트 생성

프론트에 테이블로:

방향kind이름hops경로
upstreamHTTP_ENDPOINTPOST /orders2endpoint → controller.place → impl.place
upstreamASPECTTransactionAspect1aspect INTERCEPTS impl.place
downstreamDB_TABLEorders2impl.place → repo.save → orders
downstreamEVENT_TYPEOrderPlacedEvent2impl.place → ... PUBLISHES → event
downstreamMETHODOrderEventsListener.onPlaced3event HANDLES → listener
이 전 과정에 LLM이 0회. term resolution(한국어 → qualified name) 단에서만 LLM이 붙고, 일단 qualified name이 잡힌 순간부터 끝까지 Cypher. 재현 가능 + 캐시 가능 + 감사 가능. 이것이 "Impact Analysis는 deterministic"의 구체적 의미.

7-A. 실행 배치 경로 — 임시 섹션 (Q10 응답)

3대 기능(Impact / Reverse / Test Generation)은 원래 정식 Section 3의 책임이다. 하지만 Section 3 공식 신설까지 기다리면 Section 2 모델링 툴의 쓸모를 검증할 방법이 없다.

→ 결정: Section 2 모델링이 완성되는 순간, 임시 섹션을 하나 띄워 3대 기능 + JVM Agent + 런타임 계측을 실험한다. 정식 Section 3는 그 이후에 이 임시 섹션의 결과를 바탕으로 설계.

세 섹션의 역할 구분 (재정리)

Section 2 (지금)

모델링 툴. 사용자가 레거시 코드를 불러와 직접 온톨로지를 빌드·수정·검증. 파서 초안 + 사람 주석 + 스키마 validation. 3대 기능은 이 툴의 소비자.

임시 섹션 (신규)

PoC 런타임. Section 2에서 완성된 온톨로지를 입력으로 받아 Impact / Reverse Lookup / Test Generation 3기능을 돌려보는 사용자 검증 환경. JVM Agent 런타임 계측도 이곳에서.

Section 3 (정식, 나중)

프로덕션 오퍼레이팅. 임시 섹션에서 확립된 패턴을 기반으로 여러 레거시에 적용 가능한 정식 플랫폼. 지금 범위 밖.

왜 임시 섹션인가. "Section 3 정식 신설"과 "Section 2 검증"이 맞물려 있으면 어느 쪽도 앞으로 못 간다. 임시 섹션은 throwaway 가능을 전제로 만들어 의사결정 속도를 올리는 장치. 설계 결정이 안정된 뒤 필요한 것만 Section 3로 승격.

임시 섹션 구성 (초안)

  • 폴더: toClaude/temp-runtime/ (세션 격리 대상 밖, 실험적 공간)
  • 백엔드: backend/temp_runtime/ — 3대 기능 API (/temp/impact, /temp/reverse, /temp/testgen) + JVM Agent 엔드포인트
  • 프론트: frontend/src/components/sections/temp-runtime/ — 간단한 질의 UI
  • 데이터 원천: Section 2의 Neo4j 그래프를 그대로 읽음. 읽기 전용.

8. Round 1 합의 체크리스트

Q1~Q11 답변 모두 반영 완료 (rev.3). Round 1 스키마 확정.

Q1 ✓노드 15종으로 충분한가? → 합의: 당장 충분, 완성 후 확장 용이하도록 설계. §3-A 플러그인 레지스트리 + Neo4j 자유 스키마로 대응.
