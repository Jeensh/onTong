배경 — B6-1/2/3 이 남긴 marker 요약

B6-4 가 소비할 3 가지 marker 의 현재 형식입니다. 이 형식은 이미 구현되어 있어 변경 비용이 있습니다.

B6-1 MapStruct implicit marker

METHOD.attributes["mapstruct_implicit_fields"] = [
    {
        "mapper_fqn": "com.x.mapper.OrderMapper",
        "method": "toDto",
        "src_type": "com.x.model.OrderReq",   # 미해소 시 simple name
        "dst_type": "com.x.dto.OrderDto",
        "line": 42,
    },
    ...
]

명시 @Mapping 이 없는 매퍼 메서드만 marker 를 받음. default / @Named 메서드 제외.

B6-2 BeanUtils call marker

METHOD/CONSTRUCTOR.attributes["beanutils_calls"] = [
    {
        "library": "spring" | "apache" | "modelmapper" | "unknown",
        "src_type": "com.x.model.OrderReq",   # 미해소 시 simple name
        "dst_type": "com.x.dto.OrderDto",
        "ignore": ["password"],               # Spring copyProperties 3rd+ arg
        "confidence": 0.7 | 0.5,              # import 해소 실패 시 0.5
        "line": 42,
    },
    ...
]

B6-3 NativeSQL relation (이미 엣지)

CodeRelation(
    kind="reads_table" | "writes_table",
    source="com.x.repo.OrderRepo.findByCustomer",
    target="orders",                           # lowercase table
    attributes={
        "columns": ["id", "customer_id"],      # [""] 가능
        "confidence": 1.0,                     # dynamic=0.3
        "raw_sql": "SELECT ...",
        "dialect": "sql" | "jpql",
        "multi_statement_warning"?: True,
    },
)

DB_TABLE 노드는 B6-3 에서 emit 하지 않음 (B6-4 가 dedup 해서 한 번만 emit). JPQL 의 경우 target 이 entity 이름 lowercase (예: order) 이므로 B6-4 가 table 로 해소해야 함.

§ 입출력 계약

Q1 입출력 계약

enrich_repo() 반환 방식 — in-place vs 새 리스트

B6-4 가 새 엣지 / 엔티티를 어디에 넣을지 정합니다. 100K 파일 규모에서 메모리 복사 비용이 차이가 큽니다.

A in-place 수정 — 기존 ParseResult.entities / relations 에 직접 append.
B 새 ParseResult 리스트 생성 (불변).
WHY 100K 규모에서 메모리 copy 회피, B9 JavaParser 통합 단순. 테스트는 before/after snapshot 으로 비교해 mutation 검증.
Q2 입출력 계약

JPA annotation (@Entity / @Table / @Column) 추출 주체

B6-4 는 JPA entity 정보를 알아야 SQL column 을 Java field 로 해소할 수 있습니다. 이 정보를 누가 AST 에서 뽑아줄지 결정합니다.

A JavaParser 본체 확장 — CLASS / FIELD entity 의 attributes 에 jpa_table / jpa_column 담아 배포.
B B6-4 내부에서 tree 재스캔.
C 별도 JpaAnnotationExtractor 모듈 — cross_file_enricher 만 소비.
WHY JavaParser / analyzer 계층을 건드리지 않고 B6-4 전용 헬퍼로 격리. B5-7 JpaAnalyzer 가 나중에 들어와도 책임 중복 없음.
Q3 입출력 계약

class_index / field_index 를 누가 빌드?

스펙 §6.1 은 이 두 dict 를 파라미터로 주입한다고만 명시. 실제로 빌드하는 주체를 정해야 합니다.

def enrich_repo(
    parse_results: list[ParseResult],
    class_index: dict[str, CodeEntity],        # FQN → CLASS/INTERFACE/ENUM
    field_index: dict[str, list[CodeEntity]],  # class_fqn → [FIELD, ...]
) -> list[ParseResult]
★ cross_file_enricher.build_indices(parse_results) -> (class_index, field_index) 헬퍼를 B6-4 모듈에 노출. 운영 통합 코드는 이 헬퍼 호출, 테스트는 합성 index 를 직접 주입. JPA info 는 JpaAnnotationExtractor 가 entity.attributes 에 merge 한 뒤 전달.

§ MapStruct implicit finalize

Q4 MapStruct

src ↔ dst FIELD 교집합 기준

예: OrderReq → OrderDto 매퍼 — 양쪽에 id (Long), total (BigDecimal) 이 있으면 어디까지 교집합으로 볼지?

A 이름만 같으면 교집합.
B 이름 + 타입 둘 다 같아야.
C 이름 같고 타입 호환 (Long ↔ long, BigDecimal ↔ double 등).
WHY MapStruct 실제 동작이 타입 mismatch 를 auto-generated 변환 메서드로 해결 — 이름 기반이면 실제 사용 패턴을 거의 다 커버. implicit: true 마커로 명시 엣지와 구분해 B7 런타임에서 정밀 검증 가능.
Q5 MapStruct

명시 @Mapping 과 implicit 의 중복 처리

B6-1 이 이미 @Mapping(target="id") 을 PROPAGATES_TO(confidence=1.0) 엣지로 emit. B6-4 가 같은 메서드의 implicit 을 돌릴 때, id 필드가 양쪽 DTO 에 존재하면 중복 엣지가 생깁니다.

★ B6-4 는 각 mapper method 단위로 B6-1 엣지의 target 필드셋 (<DstFqn>.<field>) 을 수집 → implicit 후보에서 제외.
WHY 같은 메서드 맥락에서 명시 > implicit 우선. 엣지 중복 방지로 Impact BFS 결과 깨끗.

§ BeanUtils field intersection

Q6 BeanUtils

미해소 타입 fallback

B6-2 가 src_type="OrderDto" (simple name, import 해소 실패) 만 남긴 경우. class_index 에서 simple name suffix 매칭 시 FQN 후보가 여러 개 나올 수 있습니다 (예: com.x.OrderDto, com.y.OrderDto).

★ 후보 1개 = 사용 (confidence 그대로). 후보 ≥2 = skip + METHOD marker 에 ambiguous_types=[candidates] 부착.
WHY 조기 emit 보다 명확한 실패 신호가 B9 회귀에서 유리. 모호 타입은 B7 런타임 / 사람 주석 레이어에서 확정.
Rename 정책: Round 1 은 same-name only (Spring / Apache / ModelMapper 공통 기본 동작).

§ NativeSQL column → field

Q7 NativeSQL

DB_TABLE / DB_COLUMN qn (qualified_name) 컨벤션

Round 1 은 single-schema 전제이나, qn 포맷을 미리 고정해야 dedup / Impact BFS 가 일관됩니다.

★
노드qn 포맷예
DB_TABLE<table> (lowercase)orders
DB_COLUMN<table>.<column> (lowercase)orders.customer_id
<dynamic> target / columns → 노드 생성 skip (엣지 marker 만 유지).
Q8 NativeSQL

JPA @Column(name=...) 미명시 필드 fallback

private Long customerId; 에 @Column 이 없는 경우 — 실제 컬럼은 Hibernate naming strategy (ImplicitNamingStrategyJpaCompliantImpl 등) 설정에 따라 customer_id 또는 customerid 또는 customerId 일 수 있습니다.

A camelCase → snake_case 추측 (customerId → customer_id), confidence 0.6 으로 emit.
B 명시된 컬럼만 매칭, 미명시 필드는 skip (Round 1 단순화).
WHY naming strategy 는 설정 의존이라 오탐 위험. Round 1 은 @Column(name=...) 명시만 신뢰 — B9 Slab 엔진 실 데이터 보고 fallback 필요성 재결정.
Q9 NativeSQL

READS_TABLE + READS 엣지 병존 여부

B6-3 이 이미 READS_TABLE (method → table, columns 속성 내장) 을 emit. B6-4 는 READS (method → column) 을 추가해야 합니다. 원래 엣지를 지울지 / 남길지?

A 교체 — READS_TABLE 삭제 후 READS 엣지만 남김.
B 병존 — READS_TABLE 유지 + READS 추가.
WHY Impact BFS 쿼리가 table-coarse (어느 테이블 건드리나) / column-fine (어느 컬럼) 둘 다 자주 필요. 컬럼 해소가 부분적 (JPA entity 가 아직 없거나 일부 컬럼만 명시) 이어도 table 레벨은 항상 유효 — <dynamic> SQL 도 table 엣지는 유의미.

§ DB_TABLE dedup & 저장

Q10 저장 위치

DB_TABLE / DB_COLUMN entity 를 어느 ParseResult 에 부착?

여러 파일이 같은 테이블 orders 를 참조 → DB_TABLE entity 는 한 번만 emit. 반환 타입은 list[ParseResult] 로 고정되어 있으니 저장 위치를 정해야 합니다.

A 첫 참조 ParseResult 에 부착.
B 새로운 synthetic ParseResult(file_path="<db_schema>", ...) 를 리스트 끝에 추가. PROPAGATES_TO / READS / WRITES 엣지는 각 caller ParseResult 에 부착 (source 가 그 파일의 METHOD 이므로).
C 공유 리스트 반환 튜플로 분리 — 스펙 §6.1 시그니처 변경 필요.
WHY (A) 는 "왜 이 파일이 DB_TABLE 을 emit 했지?" 역추적이 어려움. (C) 는 시그니처 변경 비용. (B) 는 file_path 가 <db_schema> 로 "cross-file 산출물" 을 명시 — graph_writer 가 그대로 처리 가능.

§ 보조 결정 (추천 그대로, 비평만)

개별 옵션이 없거나 자명한 결정들. 틀린 게 있으면 지적해 주세요.

테스트 픽스처 — 합성 ParseResult + 합성 class_index 로 직접 구성 (JavaParser 실제 호출 최소화). 통합 케이스 1~2개만 실제 JavaParser + JpaAnnotationExtractor 전체 경로 태우기.
중복 엣지 dedup — (kind, source, target) 튜플로 dedup, confidence = max(duplicates). attributes 는 first-wins 또는 merge 여부는 케이스별.
via_methods 컨벤션
  • BeanUtils : caller METHOD / CONSTRUCTOR FQN 1개 (호출 지점).
  • MapStruct implicit : <MapperFqn>.<method> (B6-1 명시 엣지와 동일 컨벤션).
JPQL entity → table 해소
  1. @Entity(name="Order") 명시 우선 (lowercase 비교).
  2. 없으면 클래스 simple name lowercase 매칭 (Order → order).
  3. 클래스에 @Table(name="orders") 있으면 table name 으로 최종 치환 — 없으면 entity name 그대로 사용.
confidence merge 정책 — 한 메서드가 BeanUtils 여러 번 호출하고 같은 (src, dst) 쌍이 중복되면 (kind, source, target) 로 dedup 후 confidence = max, library 는 첫 번째 기준.
