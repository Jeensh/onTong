§2. Authoring vs Recommend 직접 비교 (HrSpec 케이스)

Recommend (자동, ~1초)

label: 열연표준
fqn: term.scm.hr_spec
kind: composite
description: "자동 추천 —
   ...HrSpec"
confirmed: false
source: auto

(facets: 없음)
(composition: 없음)

→ "열연표준 (HrSpec)" 1 entity. Class 명 그대로. 도메인 의미 미파악.

Authoring (인터뷰, ~3분, ~$0.5)

root: HrPlant (열연공장)
  is_root_entity: true

child: HrPlantConstraint (열연공장제약)
  parent: HrPlant
  facets:
    - 폭 LOW/HIGH
    - 길이 LOW/HIGH
    - matchPattern: EXACT
  errorOnMiss: DG107

(2 entity composition)
(인터뷰 5건 archive)
(갭 4건 자동 검출)

→ "HrPlant + HrPlantConstraint" 분리. 도메인 정확. composition + facets + 갭.

§4. Authoring + Recommend Hybrid — 4 가지 전략

★ 전략 1 — "큰 그림 먼저, 세부는 깊게" (가장 자연)

  1. recommend 1회 → 큐에 29 term 채움 (1차 라벨링)
  2. 사용자가 큐에서 명확한 것 (검증결과, 에러코드 등) ✓ confirm — 빠름
  3. 중요한 entity (HrSpec, EdgingSpec, CastSpec) 는 ✗ reject → Authoring 으로 깊게 재작성
  4. Authoring 으로 만든 것은 새 fqn (HrPlant + HrPlantConstraint) 이라 충돌 X

시간: recommend 1초 + 큐 confirm 30분 + Authoring 3개 (HrPlant + 단중표 + Edging) ~30분

전략 2 — "Authoring 먼저, recommend 보충"

  1. 핵심 entity (HrPlant, slab, 주문) Authoring 으로 깊게 (현재 진행)
  2. 그 외 부속 entity (검증결과, 에러코드 등) recommend bulk + 큐 confirm

단점: 사용자가 Authoring 후 어떤 entity 가 부족한지 일일이 판단 필요

전략 3 — "동시 사용" (병렬)

  1. recommend 백그라운드 실행 (큐 채워둠)
  2. Authoring 으로 핵심 작업 (앞단)
  3. 큐는 시간 날 때 정리

전략 4 — "Authoring 단독" (현재 우리)

  1. 모든 entity 를 Authoring 으로

100+ entity 시 시간·비용 ↑↑. 현실적이지 않음.

내 추천: 전략 1 — recommend 의 빠른 1차 채우기 + Authoring 으로 핵심 깊이. 비용·시간 효율 최고.
  • 실제로 Round 5 의 8 표준 중 (HrSpec, CastSpec, HrMin/MaxWgt, EdgingGroup, EdgingSpec, CustomerStd, ProductivityStd) — 4~5 개는 recommend 의 1:1 매핑이면 충분 (CustomerStd, ProductivityStd 등)
  • HrSpec, CastSpec, EdgingSpec — composition 분리가 필요해서 Authoring 가 필요
  • 즉 50% 는 recommend, 50% 는 Authoring 같은 분포
