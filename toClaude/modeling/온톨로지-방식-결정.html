왜 Two-Layer 인가 (D1=C 의 가치)

  • Code Layer 가 Java 의 모든 사실 (extends/implements/abstract/private/helper) 을 잃지 않음 → 매핑 사각지대 0
  • Domain Layer 는 깨끗한 의미 모델 — BaseEntity 같은 코드 노이즈가 새어들지 않음 (D2=A 정합)
  • Mapping Layer 의 분리로 — code 변경 시 mapping 만 갱신, domain 변경 시 mapping 만 갱신, 양쪽 동시 cascade 회피
  • Anchor / Realization / TypeRealization 모두 명확한 양쪽 reference 를 가짐 → 양방향 traversal 쉬움

4.1 effective_parts resolver

# transitive closure — RushOrder 의 effective parts
def effective_parts(term_fqn: str) -> list[Composition]:
    own_parts = term.parts
    inherited_parts = []
    for parent in term.parents:
        if parent.kind == "extends" or parent.kind == "implements":
            inherited_parts += effective_parts(parent.parent_fqn)
    return inherited_parts + own_parts  # own 이 override 가능

6. CallSiteAnalyzer — D3 메모 응답

사용자 메모: "자바의 실행순서를 따라갈 수 있도록 하면, 어떤 게 들어가는지 알 수 있지 않아? 아닌 경우가 있나? 그런 경우가 있다면 그 경우에만 사람이 매핑할 수 있도록 하면 안되나?"

맞습니다. Java 정적 call-flow 분석으로 dispatch 의 상당 부분을 자동 추적할 수 있습니다. 추적 가능한 case 는 자동 confirmed Realization, 추적 불가능한 case 만 사용자 큐 (with 후보·컨텍스트). Q-C=C3 (혼합 anchor) 와 같은 패턴.

6.1 정적 분석 7 케이스

Case 1 — Single implementation (자동 ✓) interface Validator { ... } class StandardValidator implements Validator { ... } // 유일 impl → 호출 사이트 어디든 StandardValidator 로 dispatch 확정 Case 2 — Instanceof guard (자동 ✓) if (order instanceof RushOrder) { order.validate(); // → RushOrder.validate 확정 } Case 3 — Annotation 기반 DI (자동 ✓) @Service class OrderService { ... } // Spring 등록 1개 @Autowired OrderService svc; svc.process(); // OrderService.process 확정 Case 4 — Factory if-else / switch (자동 ✓ per branch) switch (orderType) { case "STANDARD": return new StandardOrder(); // branch 별 확정 case "RUSH": return new RushOrder(); } Case 5 — Generic with reified bound (자동 ✓ 부분) <T extends Order> void process(T o) → T 의 정적 upper bound 까지만 확정, 호출자에서 T 가 RushOrder 로 bound 되면 거기서 더 narrow Case 6 — Strategy Map (모호 ⚠ → 사용자 큐) Map<String, Validator> validators; validators.get(orderType).validate(); // key 가 동적이라 정적 추적 불가 → 사용자에게 "후보 = [StandardValidator, RushValidator, ...] / context = OrderService.line 42" 큐 Case 7 — Reflection / SPI (모호 ⚠ → 사용자 큐) Class.forName(...).newInstance(); ServiceLoader.load(Validator.class); → 정적 분석 불가, 사용자 큐 (분석 source = "static_unresolved")

6.2 사용자 큐 — 풍부한 context 제시

모호한 call site 마다 보여줄 정보

  • 호출 사이트: 파일 경로 + 라인 + 주변 코드 5 lines
  • 정적 추론 후보 list: 같은 인터페이스 implement 한 모든 class (정렬: usage 빈도)
  • Spring 등록 정보 (있다면): @Conditional / @Profile 같은 조건
  • 이전 사용자 confirm 패턴: 같은 type pattern 에서 사용자가 이전에 고른 답
  • 도메인 컨텍스트: 호출 메서드가 어느 BusinessProcess 에 PART_OF 인지

이 정도 context 면 "코드 한번도 안 본 도메인 전문가" 도 어느 impl 이 맞는지 판단 가능. LLM 보조까지 추가하면 — "이 호출 사이트는 OrderService 의 일부고, 입력 type 이 RushOrder 일 가능성 70% (라인 38 의 if 체크 기반)" 식으로 추천.

요약 — 우리가 만든 것

  1. Two-Layer 아키텍처 — Code(Java 사실) + Domain(비즈니스 의미) 분리, 노이즈 차단
  2. Action + Realization 다형성 모델 — Java OO 4가지 (extends/implements/abstract/override) 모두 표현
  3. CallSiteAnalyzer — Java 정적 분석으로 dispatch 자동 추적, 모호한 case 만 사용자 큐 (with 후보·컨텍스트)
  4. Composite BusinessTerm — kind 2종 + facets, parents/parts, dotted path syntax (subtype cast 포함)
  5. SimulationScenario + InputAdapter plugin — Form/Fixture 시작, 점진 확장 (사용자 메모 정합)
  6. VerificationLevel — 시뮬 신뢰도 calibration (우리 고유 개념, 팔란티어보다 우리 문제에 fit)
  7. fragment-level AnchorBinding — god-method/generic 사각지대 흡수
  8. Method.role / Class.role 자동 분류 — 매핑 사각지대 가시화
