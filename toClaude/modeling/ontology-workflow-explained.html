§1. ontology 의 4 layer 구조

onTong ontology 는 의도적으로 4개 layer 로 분리되어 있습니다 (project_decisions_v4_action.md 의 핵심 결정). 각 layer 는 다른 type 의 entity 를 다루고, 별도 작업이 필요합니다.
┌─────────────────────────────────────────────────────────────┐ │ Layer 4 — View / Simulation │ │ 시뮬레이션, 영향도 분석, 그래프 — 위 layer 들 위에 작동 │ └─────────────────────────────────────────────────────────────┘ ▲ ┌─────────────────────────────────────────────────────────────┐ │ Layer 3 — Mapping (anchor binding) │ │ method 의 fragment ↔ Action 의 parameter / variable │ │ "이 if 조건은 X 도메인 룰" / "이 변수는 Y 도메인 값" │ └─────────────────────────────────────────────────────────────┘ ▲ ┌──────────────────────────┐ │ ┌───────────────────────────┐ │ Layer 2 — Domain │ │ │ Layer 1 — Code │ │ BusinessTerm (명사) │ │ │ CodeType (Java class) │ │ Action (동사) │ │ │ CodeMethod (Java mtd) │ │ Inheritance / Compose │ │ │ CodeField │ └──────────────────────────┘ │ └───────────────────────────┘ ▲ (자동 import) ▲ repo source
Layer주요 entity현재 onTong 진행도
L1 Code CodeType (class), CodeMethod, CodeField ✅ 자동 import 작동 — slab-design-real 123 class 인덱스됨
L2 Domain - 명사 BusinessTerm (열연공장, 슬랩, 주문) 🟡 우리 Authoring 모드 가 작성 중 (현재 R2 진행)
L2 Domain - 동사 Action (slab 설계, validate, 폭 계산) 🔴 미작성 — Authoring 모드는 아직 Action 못 만듦
L3 Mapping AnchorBinding (code fragment ↔ Action 의 도메인 의미) 🔴 미작업 — Action 이 있어야 매핑 가능
L4 View 시뮬레이션 코드 생성, 영향도 분석 ⏳ 다음 phase

§2. 명사 (BusinessTerm) vs 동사 (Action) — 구분 이유

도메인 표현은 "무엇이 있나"(명사) 와 "무엇을 하나"(동사) 로 나뉩니다. 코드도 마찬가지로 data structure(class/field) 와 behavior(method) 로 분리됩니다.
BusinessTerm (명사) termAction (동사) action
예시 열연공장, 슬랩, 주문, HrPlantConstraint, 압연MAX단중기준 "slab 설계", "validate 우선도", "폭 LOW 산정", "EDGING_GROUP 룩업"
코드 매핑 CodeType (Java class) — 1:1 가깝게 매핑 CodeMethod (Java method) — 다형성 (1:N realization)
핵심 facet kind, key (PK), facets, composition params, output, preconditions, realizations, anchor_bindings
Round 5 예시 HrPlant (열연공장) SdSecondWgtHighAction.execute() → "2차 단중상한 산정"
Detail/Split mode 안 봄 (BusinessTerm 은 별도 view) ✅ 이 mode 의 입력 — Action 의 anchor binding 작업용

왜 분리했나

  • Action 다형성 — Java OO 의 추상메서드 + override 패턴. abstract Action 을 N 개 class 가 realize. ex. validate() 가 50 class 에서 override → Action 1개 + realization 50개.
  • Anchor binding 의 단위 — method body 안의 if/return/계산 fragment 마다 도메인 의미. method=Action 일 때만 자연스러움.
  • 시뮬레이션 — Action 단위로 generate (메서드별 Python 변환). BusinessTerm 은 data shape, Action 은 logic.

§3. 처음부터의 작업 순서 (이상적 흐름)

1
Repo Import — 코드 자동 분석
Java repo 를 onTong 에 import. tree-sitter 가 class/method/field 를 추출 → code_types, code_methods, code_fields 테이블에 저장. slab-design-real ✅ 완료 (123 CodeType)
2
BusinessTerm 작성 — 도메인 명사 entity
"열연공장", "슬랩", "주문" 같은 도메인 entity 를 만든다. 각 BusinessTerm 은 facets / composition / inheritance 를 가진다.
현재 진행 중 — 우리 ✏️ Authoring 모드 가 이 단계 자동화. round 5 인터뷰 패턴으로 코드 → 가설 → 옵션 → 명명 → confirm.
3
Action 작성 — 도메인 동사 entity
"validate 우선도", "폭 LOW 산정", "EDGING_GROUP 룩업" 같은 도메인 행위. 각 Action 의 params / output / preconditions / realizations 를 정의.
미구현 — Authoring 모드를 Action 모드로 확장하면 가능 (인터뷰: 이 method 는 도메인상 어떤 행위? 입력은 어떤 BusinessTerm? 출력은? 룰은?). round 5 형식 그대로 적용 가능.
4
AnchorBinding — 코드 ↔ 도메인 매핑
Step 3 의 Action 이 만들어진 후, 코드 method body 안의 fragment (if 조건, 변수, 호출) 를 Action 의 parameter / 도메인 룰과 매핑. 이 단계에서 Detail/Split 모드를 사용.
미구현 — Detail mode 는 이미 UI 가 있지만 Action 데이터가 없어서 빈 화면.
5
Verification + Simulation — 매핑 위에서 실행
매핑된 Action 을 Python 으로 generate, 도메인 룰 위에서 simulation 실행 + 영향도 분석. 미래 phase

§4. 사용자 질문에 대한 정확한 답

Q: Detail/Split 이 Action 만 받는 이유?

Detail/Split 은 Step 4 (AnchorBinding) 작업의 view 입니다. 이 단계는 "Action 이 이미 존재한다" 는 가정 위에서 method body 의 fragment 를 그 Action 의 parameter 등에 매핑하는 작업이라 Action FQN 이 입력.

좌측 트리에서 CodeType (class) 만 선택해도 Detail 은 빈 화면 — Class 자체는 method 들의 컨테이너이지 Action 이 아님. Class 의 method 하나하나가 execute(), validate() 같은 도메인 행위 후보.

Q: 처음부터 어떤 순서로?

위 5 step 그대로. Step 1 (코드 import) 은 자동 완료, Step 2 (BusinessTerm) 가 우리 Authoring 의 현재 작업. Step 3 (Action) 부터는 아직 인터뷰 capability 가 없으니 Authoring 모드를 확장해야 진행 가능.

§5. 우리가 갈 길 — 두 갈래

경로의미사용자 결과
A. 깊게 (BusinessTerm 만) 현재 R2 진행. BusinessTerm 인터뷰 + cascading + UI 폴리시. Action 은 별도 phase 에 둠. HrPlant + 산하 entity 다 만들고, 다른 entity (Customer, Productivity 등) 도 BusinessTerm 으로 만든 후, 별도 phase 에서 Action 작성.
B. 넓게 (BusinessTerm + Action 둘 다) R2 의 핵심 (P1-B humble, P2-B refresh, P4-1 markdown) 끝낸 후, Authoring capability 를 Action 까지 확장. 한 BusinessTerm 작성 후 그 BusinessTerm 과 관련된 Action 도 같은 인터뷰로. HrPlant + Action (validate, lookup 등) 같이. 하지만 작업 ↑↑.
현 시점 추천: 경로 A — BusinessTerm 인터뷰의 quality 를 R2 로 끌어올려 한 entity 를 정확히 만든 후, 그게 제대로 작동하면 Action 으로 확장. Round 5 의 만족감 5/5 에 도달 후 다음 단계로.
