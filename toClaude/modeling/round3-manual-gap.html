1. 왜 Round 3 는 '기준서 × 조직' 인가

Round 2 에서 확정한 3각 구도 (코드 ↔ BusinessTerm ↔ BusinessRule) 는 "이 메서드가 어떤 개념을 실현하는가" 질문에 답한다. 하지만 실제 팀에서 일어나는 일은 한 층 더 있다:

  1. 규칙의 진실(authoritative) 은 기준서에 산다. 공장 운영의 "룰" 은 PDF/PPT/Word/이미지 에 적혀있고, 코드는 그것을 구현한 사본이다. 기준서가 바뀌면 코드가 따라가야 하고, 코드가 먼저 바뀌면 기준서도 업데이트돼야 한다.
  2. 책임자는 코드 바깥에 산다. "이 프로세스는 재고관리팀 소관" 같은 정보는 Git blame 이 아니라 조직도/내규에 있다. 변경 알림을 보낼 대상이 누군지 모르면 Reverse Lookup 은 UI 상 버튼일 뿐이다.
  3. 드리프트 감지. 10년 운영된 레거시에서 가장 비싼 버그는 "아무도 모르는 사이 코드가 기준서와 어긋나 있었다" 류다. Round 3 은 이 어긋남을 그래프 위에서 검출 가능한 1급 시민으로 만든다.
3대 기능 관점
  • Impact Analysis : 코드 변경 → 영향 프로세스 → 책임자 + 업데이트해야 할 기준서 섹션 까지 한 번에.
  • Reverse Lookup : "안전재고" 용어 → 코드 위치 (Round 2) → 설명 섹션 (Round 3) → 담당자 (Round 3).
  • Test Generation : 기준서에서 입력 범위 / 경계값 / 금지 조건을 추출 해 테스트 케이스 시드. (Round 3 기준서 인제스트가 전제).

2. 노드 5종

Round 3 가 추가하는 5개 신규 노드는 두 층으로 나뉜다 — 조직 + 기준서.

2-1. BusinessProcess — 업무 프로세스

qualified_name{domain}.{process_name}. 예: inventory.safety_stock_management, order.payment_settlement
canonical_label사람이 읽는 한글 명칭. 예: "안전재고 관리", "주문 결제 정산"
description프로세스 요약 (1~3문장)
(계층 관계)노드 필드 아님. PARENT_PROCESS 엣지로 분리 (§3). Q1=C 결정 : graph 쿼리 유연성 우선 (자식 탐색 / 루트 집계 / 재부모화 모두 엣지 쿼리로).
domain도메인 태그. inventory / order / production 등
sourceenum: manual / extracted / llm_proposed
confirmedbool. 사람 승인 여부

2-2. Role — 책임자/조직 (team 단위)

qualified_nameteam.{slug}. 예: team.inventory_mgmt, team.production_ops, team.qa. Q2=A 결정 : team 단위 고정.
kind고정값 team (Q2=A). 컬럼은 유지해 Phase E+ 에서 title/person 으로 확장 여지 보존. 초기 데이터 는 모두 team.

contactOptional. 팀 메일링리스트 / 슬랙 채널. 변경 알림 디스패치 키. 예: inv-mgmt@example.com, #team-inv-mgmt.
sourceenum: manual / hr_import / llm_proposed
confirmedbool. 자동 제안된 Role 은 false (승인 대기)

2-3. ManualDocument — 기준서 문서 하나

qualified_name저장소 기준 상대 경로 + SHA-256 prefix. 예: manuals/inventory/SOP-안전재고-v3.pdf#sha256:a1b2c3...
title문서 제목 (메타데이터 or 파일명 기반)
formatenum: pdf / pptx / docx / md / image / html
last_modified파일시스템 mtime 또는 인제스트 시 기록

source_repoOptional. 기준서가 별도 git 레포일 때

2-4. ManualSection — 문서 내 섹션

qualified_name{doc_fqn}#{section_path}. 예: manuals/.../SOP-안전재고-v3.pdf#3.2, manuals/.../slides.pptx#slide-7

heading"3.2 안전재고 계산식" 같은 제목
ordinal문서 내 순번 (UI 정렬)
page_or_slidePDF 페이지 번호 / PPT 슬라이드 번호 / DOCX heading anchor

2-5. ManualFragment — 추출 조각

qualified_name{section_fqn}::{ordinal}
section_fqn부모 ManualSection.qualified_name
kindenum: text / image / table / formula / ocr_text
content추출된 텍스트 (이미지는 OCR 결과)
content_hashSHA-256. 중복 감지 + 재임베딩 스킵
ocr_confidenceOptional. image/ocr_text 에만. tesseract/easyocr confidence
embeddingchromadb collection manual_fragments. Round 2 임베딩 스택 재사용 (OpenAI text-embedding-3-small).
왜 Section + Fragment 2층 인가?
Section 은 사람이 참조하는 단위 ("SOP 섹션 3.2"). Fragment 는 알고리즘이 처리하는 단위 (임베딩 / gap 비교). UI 에서는 Section 을 보여주고, 내부 매칭은 Fragment 로 한다. Q3 에서 DESCRIBED_IN 이 어느 층에 걸리는지 결정.

3. 엣지 6종

Round 2 엣지 (REALIZES / VALIDATES / DERIVED_FROM) 는 유지. Round 3 가 추가하는 6개. PARENT_PROCESS 는 Q1=C 결정 에 따라 노드 필드 대신 엣지로 분리 — 계층은 그래프 쿼리로 풀어낸다.

엣지SourceTargetCardinality주요 속성
PART_OF BusinessTerm / BusinessRule BusinessProcess N:M confidence, source ∈ {manual, llm}, confirmed
RESPONSIBLE_FOR Role BusinessProcess N:M responsibility_kind ∈ {owner, approver, reviewer, notify}, confirmed
DESCRIBED_IN BusinessTerm / BusinessRule / BusinessProcess ManualSection (기본) 또는 ManualFragment (선택) Q3 N:M confidence, source ∈ {manual, name_match, embedding, llm}, confirmed, excerpt (첫 200자)
CONFLICTS_WITH BusinessTerm / BusinessRule (코드 측) 동일 타입 (기준서 측 extracted 사본) 또는 ManualFragment N:M severity ∈ {low, medium, high, critical}, detected_by ∈ {llm, rule_ast, embedding_drift}, summary, confirmed
MISSING_IN BusinessTerm / BusinessRule ManualDocument (code_only) 또는 가상 <no-code> sink (manual_only) N:1 direction ∈ {code_only, manual_only}, severity, confirmed
PARENT_PROCESS Q1=C BusinessProcess (자식) BusinessProcess (부모) N:1 source ∈ {manual, scor_template, llm}, confirmed. 자기 참조 금지, cycle 검출 필수.

3-1. 엣지 세부 규약

  • PART_OF : 개념 → 프로세스 소속. Term "안전재고" 가 Process "inventory.safety_stock_management" 에 속함. Rule 도 동일 관계.
  • RESPONSIBLE_FOR : Role → Process. 한 프로세스에 여러 책임자 (owner 1 + approver N + notify N). 직접 Term/Rule 로 걸지 않는다 — 책임 관리 단위는 Process.
  • DESCRIBED_IN : 개념 → 기준서. Round 2 의 REALIZES (개념 → 코드) 와 거울. 둘 다 있으면 그래프 상에서 "코드 ← Term → 기준서" 삼각 연결.
  • CONFLICTS_WITH : 같은 의미의 두 해석이 다름. 예: BusinessRule.statement "SS = μ × L" (코드) vs Fragment.content "SS = z × σ × √L" (기준서) 의 수식 차이. 방향 없는 대칭 엣지로 모델링하되 저장은 (a, b) 정규화 (a.fqn < b.fqn).
  • MISSING_IN : 한쪽에만 있음. code_only = REALIZES 는 있는데 DESCRIBED_IN 이 없다. manual_only = DESCRIBED_IN 은 있는데 REALIZES 도 없고 Term 등록도 없다 (신규 기준서에서 추출됐지만 Term 으로 승격 전).
  • PARENT_PROCESS : Process → Process 계층 (자식 → 부모). SCOR L1/L2/L3 같은 프로세스 트리. cardinality N:1 일방향. 자기 참조 금지, cycle 검출 필수 (쓰기 시 ancestors 검사). Q1=C : 노드 필드 대신 엣지로 분리해 재부모화 / depth 쿼리 / 루트 집계 모두 단일 패턴으로 처리.
DESCRIBED_IN 의 target 선택
기본은 ManualSection — 사람이 "섹션 3.2" 로 참조한다. 세밀한 매칭이 필요한 경우 (예: 섹션 내 여러 수식 중 특정 수식을 집어내야 할 때) ManualFragment 로 내려간다. Q3.

4. 4층 아키텍처

Round 1/2/3 를 합치면 4개 층이 된다. 각 층이 세로로 연결되고, 가로로도 연결(COFLICTS/MISSING) 된다.

세로 축 = 같은 의미의 4가지 표현 (실행 가능한 코드 / 개념 / 사람 읽는 문서 / 책임자). Impact Analysis 는 세로로 올라갔다가 내려온다. Gap Detection 은 가로 축에서 층 2 ↔ 층 3 어긋남을 찾는다. 책임 전파는 층 4 에서 수렴한다.

5. 워킹 예시 — "안전재고 공식 변경 시 누구에게 알리나"

1트리거

개발자가 SafetyStockService.calc() 메서드를 수정하는 PR 을 올린다. CI가 QueryEngine.impact(method_fqn, direction=outgoing, edge_kinds={REALIZES,PART_OF,RESPONSIBLE_FOR,DESCRIBED_IN}) 호출.

2REALIZES 역방향 → BusinessTerm

Method com.example.inv.SafetyStockService.calc → REALIZES 입방향으로 Term inventory.safety_stock 도달. Round 2 에서 이미 확정된 경로.

3PART_OF → BusinessProcess

Term → PART_OF → Process inventory.safety_stock_management. 동일 Term 이 여러 Process 에 속할 수 있음 (N:M).

4RESPONSIBLE_FOR 역방향 → Role

Process ← RESPONSIBLE_FOR ← Role(들). 예: team.inventory_mgmt (owner) + team.production_ops (approver) + team.qa (notify).

각 Role (team 단위) 의 contact 필드 → 팀 메일링리스트/슬랙 채널 dispatcher 로 전달. Q2=A 결정 : team 단위 고정 (title/person 은 Phase E+ 확장).

5DESCRIBED_IN → ManualSection

Term / Rule → DESCRIBED_IN → Section (들). 예: "SOP-안전재고-v3.pdf §3.2" 와 "계산기준서-2024.pptx slide-7". PR 설명에 "다음 기준서 섹션도 업데이트 필요" 체크리스트 자동 추가.

6CONFLICTS_WITH 스캔

Gap Detector (§7) 가 비동기로 (A) PR 변경 Term 의 Rule.statement 와 (B) 해당 Term 의 DESCRIBED_IN Fragment.content 를 비교. 차이가 크면 CONFLICTS_WITH{severity:high, detected_by:llm} 엣지 신규 생성 + 승인 큐로.

7자동 액션
  • Role 3명에게 변경 알림 발송 (이메일 템플릿 : "안전재고 계산 공식 변경 PR #1234 - 기준서 2건 업데이트 필요")
  • PR checklist 에 Section 2개 링크 삽입 + CONFLICTS_WITH 1건 경고 배너
  • 승인 큐에 "이 변경이 기준서와 충돌 — 둘 중 어느 쪽이 맞는가" 카드 생성

6. 기준서 인제스트 파이프라인

5 포맷 (PDF / PPT / Word / Image / MD) 을 마크다운 통합 중간표현 으로 변환 → 섹션 분할 → Fragment 추출 → 임베딩 → ManualDocument/Section/Fragment 노드 생성.

PPT — 이미 존재 ✅

backend/api/files.py::_parse_pptx_slides() (python-pptx 기반). 슬라이드별 텍스트 + 도형 + 이미지 추출. Section = 슬라이드 1장 단위.

Image / OCR — 이미 존재 ✅

PDF — 신규 의존성 필요 Q9

pypdf (구조 파싱) + pdfplumber (표 / 수식 / 이미지 추출). 페이지별 텍스트 + 임베디드 이미지 → 이미지면 OCREngine 재호출.

Word — 신규 의존성 필요 Q9

python-docx. heading 파싱으로 Section 분할 자연스럽게 가능. 표 / 이미지 / 수식 OMML 도 추출.

MD — 기본 파이썬 ✅

마크다운은 heading (`#`/`##`/`###`) 으로 섹션 분할. 그 외 코드펜스 / 표는 text Fragment.

6-1. 파이프라인 단계

# backend/modeling/manual_ingest/pipeline.py (D2 예정)
class ManualIngestor:
    def ingest(self, path: Path) -> IngestResult:
        # 1. checksum 체크 → 이미 동일 문서면 skip
        if self.registry.exists(checksum):
            return IngestResult.SKIP

        # 2. format 별 파서 디스패치
        parser = self._resolve_parser(path.suffix)
        doc, sections, fragments = parser.parse(path)

        # 3. 각 Fragment 임베딩 → chromadb "manual_fragments"
        for f in fragments:
            if f.kind in ("text", "ocr_text"):
                f.embedding = self.embed_fn(f.content)
                self.chroma.upsert(f)

        # 4. Neo4j 에 ManualDocument/Section/Fragment 노드 생성
        self.graph_writer.write_manual(doc, sections, fragments)

        # 5. DESCRIBED_IN 자동 제안 (optional):
        # 각 Fragment 에 대해 기존 BusinessTerm 과 임베딩 cosine 상위 K.
        # cutoff ≥ 0.78 이면 confirmed=False 로 DESCRIBED_IN 엣지 큐.
        return IngestResult.OK(doc_fqn=doc.qualified_name)

6-2. 트리거 옵션 Q7=E 결정

3가지 트리거 모두 구현. ManualDocument.source 에 진입 경로 기록 (ui_upload / watch_folder / git_hook). 동일 checksum 은 트리거 무관 skip (중복 방지).

  1. A : UI 업로드 — 관리자 endpoint POST /api/modeling/manuals/upload. 시연 / 1회성 주입. D2 1순위 (demo guide 작성 용).
  2. B : watch folder — /var/ontong/manuals/ (환경변수로 override) 5분 주기 스캔. 일상 운영 경로. D2 2순위.
  3. C : git push hook — 기준서가 별도 git 레포인 경우. webhook endpoint POST /api/modeling/manuals/git-hook (GitHub/GitLab payload 파싱). D2 에서 endpoint 만 구현, 실제 레포 연동은 Phase E 실증 에서 activate.

7. Gap Detection

3 가지 케이스. 각 케이스는 감지 알고리즘 + 저장 엣지 + UI 카드가 다르다.

7-1. Case A — code-only (코드에는 있는데 기준서에 없음)

  • 검출 : BusinessTerm 에 REALIZES 는 1개 이상인데 DESCRIBED_IN 은 0개.
  • Cypher 초안: 
    MATCH (t:OntNode {kind:'business_term'})<-[:REALIZES]-()
WHERE NOT (t)-[:DESCRIBED_IN]->(:OntNode {kind:'manual_section'})
RETURN t.qualified_name
  • 엣지 : MISSING_IN{direction:'manual_only', severity:'medium'} → 가상 <no-manual> sink 노드.
  • UI : "이 Term 은 문서화가 없습니다. 기준서 업로드 또는 해당 섹션 작성 필요."

7-2. Case B — manual-only (기준서에 있는데 코드에 없음)

  • 검출 : Fragment 에서 자동 추출된 용어가 있는데 대응 BusinessTerm 으로 등록되지 않음. Round 2 term_resolver 4단 MISS 가 일정 기간 반복되면 자동 트리거.
  • 엣지 : MISSING_IN{direction:'code_only', severity:'high'} — Rule 이 코드로 구현되지 않음 = 규정 위반 가능성.
  • UI : "다음 Rule 이 기준서에 있지만 구현 안 됨: ..."

7-3. Case C — conflict (양쪽 있지만 불일치)

  • 검출 우선순위 (Q4=C, 기본 모드) :
    1. Rule AST diff — BusinessRule.statement 가 Round 2 DSL 로 파싱되면 AST 비교 (가장 확실). Fragment.content 에서 동일 변수/연산 추출 가능하면 diff.
    2. Embedding drift — Term.embedding 과 Fragment.embedding cosine < 0.65 인 쌍은 conflict 의심.
    3. LLM semantic compare — 위 2단 후보를 LLM 에 전달 → "같은 의미인가 / 차이가 무엇인가 / severity 예측". 프롬프트 : "다음 코드 규칙과 기준서 문구가 같은 의미인지 판정. 다르면 차이 요약 + severity(low/medium/high/critical)".
  • 모드 전환 Q4=C + A 선택 옵션 : gap_mode 설정값 2종 —
    • hierarchical (기본) : 위 3단 우선순위 그대로. 비용 효율. 일상 사용 / 월간 전수 스캔.
    • llm_only : 최대 정확도 요구 시. Rule AST / Embedding 1차 스크리닝을 스킵하고 모든 (Term × Fragment) 쌍을 LLM 으로 직접 비교. 토큰 비용 약 10× 증가하지만 AST / embedding 이 놓치는 의미 차이까지 포착. 언제 쓰나 : 분기별 감사 / 신규 도메인 onboarding / 승인 직전 최종 검증.
    선택은 CLI / UI / API 파라미터 (?gap_mode=llm_only) 로 노출. D3 엔진은 두 모드 모두 지원하는 strategy 패턴.
  • 엣지 : CONFLICTS_WITH{severity, detected_by, summary, confirmed:false, gap_mode} — 항상 승인 큐로 (Q5). detected_by 에는 실제 검출 단계 기록 (rule_ast / embedding_drift / llm).
  • UI : "안전재고 공식이 코드는 SS = μ · L, 기준서는 SS = z · σ · √L. 차이 요약: ..."

7-4. 실행 주기

  • 인제스트 직후 : 신규 ManualDocument 의 모든 Fragment × 전체 BusinessTerm 스크리닝 (embedding 1차).
  • PR webhook : PR 로 변경된 Term/Rule 의 DESCRIBED_IN Fragment 만 재검증 (Round 2 Q7 재검증 정책 동일).
  • 월간 전수 : 배경 잡. 임베딩 드리프트 모델 업데이트 시 한 번.

8. 운영 — 책임 전파 + 변경 알림

8-1. 책임 전파 규칙

  1. Term/Rule 변경 → PART_OF 따라 Process 집합 도출
  2. Process 각각에서 RESPONSIBLE_FOR 역방향 → Role 집합. responsibility_kind 별 그룹화 :
    • owner — 승인권자. PR approval 필수 (optional).
    • approver — 승인권자 후보.
    • reviewer — 리뷰 코멘트 요청.
    • notify — 참조. 읽기만.
  3. Role.contact 가 있으면 dispatcher 로. 없으면 UI 만.

8-3. Dispatcher 후보

  • 1차 : 로그 + UI 카드만. 외부 알림 OFF (개발 단계).
  • 2차 : 이메일 (SMTP / SES). contact 필드 이메일만 처리.
  • 3차 : 슬랙 (incoming webhook). 채널 라우팅은 Role → channel 맵.
  • Phase E+ : PR comment bot (GitHub App).
