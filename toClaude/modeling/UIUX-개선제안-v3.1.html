1. Anchor 확장 — 클래스 instance field 까지

사용자 지적 (Q-U1) : "메서드에만 뭐가 있는게 아니라 클래스 변수도 로직에 영향을 많이 주잖아."

맞습니다. v3 에선 anchor 6 종 (field/param/local/return/branch/literal) 으로 정의했는데 field 가 클래스 정적 정의 (선언 위치) 만 가리키고 있어서, method body 안에서 그 instance field 를 읽고/쓸 때의 의미가 빠졌습니다.

Anchor 7 종 (field-access 추가) + 2 가지 scope

AnchorScope의미예시
fieldclass클래스 instance field 선언 자체private final EdgingRepository repo;
field_access 신규method bodymethod 안에서 instance field 의 read / write / callmethod 안의 this.castSpec.smCd 읽기, this.cache.put(...) 쓰기
parammethod body메서드 파라미터BigDecimal hrTgtWidth
localmethod body지역 변수List<EdgingSpec> specs = ...
returnmethod body반환식return s.getGroup();
branchmethod bodyif/else/switch 조건식if (widthLow ≤ x ≤ widthHigh)
literalmethod body매직넘버 / 상수 문자열"DG107", 0.95
결과 — 한 메서드 동작을 ontology 가 완전 표현 가능 : param (입력) → local (계산 단계) → field_access (외부 상태 사용) → branch (분기) → literal (상수) → return (출력). Python 동등 함수 생성 시 모든 anchor 가 채워야 할 슬롯.

field_access 의 sub-locator

MethodAnchor:
    method_fqn: str
    kind: AnchorKind         # field_access 등
    locator: str             # 'this.castSpec.smCd' 같은 path
    access_kind: str         # 'read' | 'write' | 'invoke' (field_access 만)
    target_field_fqn: str    # 'EdgingService.castSpec' (정적 field 와 link)
    line: int

이 access anchor 는 field anchor 와 자동으로 link됨 (target_field_fqn). 즉: EdgingService.castSpec field 의 binding 을 사용자가 변경하면, 그 field 가 read 되는 모든 method 의 anchor 도 자동으로 영향받음.

2. Ontology vs 매뉴얼 — 역할 명확화

사용자 의문 (Q-U4) : "메뉴얼은 참고인건가? 실제로는 온톨로지에 들어갈 내용이 중요한 것 같은데."

제가 v3 에서 매뉴얼 작성을 main input 으로 framing 한 게 모호함의 원인. 정확히 정리합니다.

역할 분리

Ontology매뉴얼
본질 구조화된 데이터 (term, rule, relation, anchor binding) 사람이 읽는 자유 텍스트 (markdown)
누가 직접 읽나 시뮬레이션 엔진 / 영향 propagator / Python generator 사람 (도메인 전문가, 신규 입사자)
입력 우선순위 primary (사용자가 직접 입력하는 main 작업) secondary (ontology 의 자연어 description, 또는 외부 reference)
모양 term.슬래브두께 = {label, aliases, def, unit, range, anchors[]} "슬래브 두께는 발주 시 결정되며 200~280mm 범위..."
변경 시 영향 시뮬레이션 결과 즉시 변경, 갭 큐 재계산 인간 가독성만, 시뮬레이션 무관

두 역할이 만나는 지점

모든 ontology entity (term / rule) 는 description 필드 (자연어) 를 갖습니다. 그리고 그 description 이 사용자가 보기에는 매뉴얼 단락처럼 보임. 즉:

  • 매뉴얼 = ontology description 들의 묶음 view. Ontology 입력 시 사용자가 자연어 설명도 같이 작성하면, 그게 "매뉴얼" 의 본문이 됨.
  • 외부 매뉴얼 (PDF/DOCX 등) 은 import 후 fragment 풀로 → 사용자가 ontology 입력 시 reference panel 에 보이게 → "이 내용을 ontology 의 어느 항목에 매핑할까?" 도와줌.
  • 매뉴얼 export 는 ontology 에서 자동 생성 (description 들을 markdown 으로 묶음, directive 자동 삽입). 사람이 회사 위키에 올릴 수 있게.
결론 — 사용자가 입력하는 것은 Ontology entity (term/rule + description). 매뉴얼은 (a) 외부 import 의 reference 또는 (b) ontology description 들의 export view. 별도의 "매뉴얼 작성기" 탭은 사라지고, ontology 입력 폼이 main input.

3. 정정된 Workbench — Ontology Editor 가 Main Input

3 가지 변경 :

  1. L 패널 — 메서드 트리 + 클래스 트리 토글 (instance field 도 노출).
  2. C-R 패널 = Ontology Editor (기존 카드 + 인라인 편집 폼). 사용자가 anchor 별로 term/rule 를 직접 입력/수정. description 자연어 필드 포함.
  3. R 패널 = "Reference" 패널 — 외부 매뉴얼 fragment + 영향 분석 + 시뮬레이션 trigger. 모두 보조. 매뉴얼 작성기는 제거.

Ontology Card 의 인라인 편집 모드 (확장)

각 카드는 5 가지 inline 필드 (term 의 경우):

  • label — canonical 한국어 이름. 예 슬래브두께
  • aliases — 영문/축약 변종 list. 예 [slabThickness, SLAB_THICKNESS, thickness]
  • description — 자연어 정의 (markdown OK). 이게 매뉴얼 본문이 됨
  • unit / range — 단위 (mm 등) + 값 범위 (input_domain 으로 쓰임)
  • relations — IS_A / PART_OF / RELATED 다른 term 과의 link

Rule 의 경우:

  • statement — DSL 또는 자연어 (양쪽 가능)
  • kind — guard / bound / formula / enum / regex / throw / lookup
  • scope — 적용 term FQN list
  • severity — hard / soft
  • description — 자연어 (매뉴얼 본문 됨)
  • relations — DERIVES_FROM / CONFLICTS_WITH 등 다른 rule 과의 link

5. 시뮬레이션 viewer — non-modal 패턴 (Q-U5)

사용자 의견 : "모달이든 뭐든 좀 답답하지 않게 좋은 방법을 찾아봤으면 해."

모달은 작업 흐름 끊고, 또 모달 안에서 코드/ontology 보고 비교하기 답답. 다음 3 단계 패턴 제안.

5-C. 풀 화면 — 「🔬 Sim」 mode rail 클릭

Drawer 가 좁다 싶으면 「▼ 풀 화면 보기」 → mode rail 의 🔬 Sim 으로 전환 → 화면 전체에 결과 viewer (Python diff, 매뉴얼 stale 리스트, chain effect 그래프 등). 이 mode 는 Workbench 와 별개의 화면.

3 단계 패턴 정리 :
  • Step 1 (drawer 작음) — ChangeSpec 입력. Workbench 보임.
  • Step 2 (drawer 확장) — 결과 요약. inputs × outputs table. Workbench 여전히 보임.
  • Step 3 (full mode) — 자세한 분석 필요할 때만 mode 전환. Workbench 가림.
모달이 아니라 점진적 확대 (progressive disclosure). 사용자가 결과 보면서도 코드/ontology 클릭 가능.

"사이즈 조정 / 모달 / 팝업" 어떻게 일관되게 쓸지 정리. 사용자 작업 흐름이 끊기지 않도록 "방해 정도 (intrusiveness)" 기준으로 패턴을 분류합니다.

6-B. 사이즈 조정 — Resizable / Collapsible / Maximize

모든 메인 패널은 3 가지 인터랙션 표준 :

인터랙션방법저장
Resize (드래그) 패널 사이 경계선 위에 hover 시 cursor 가 col-resize / row-resize. 드래그로 비율 조정. min/max 한계 있음 (예: tree 최소 160px). localStorage 에 저장 (사용자별, 화면별)
Collapse (접기) 패널 헤더 우상단 ◀ 또는 ▶ 클릭. 패널 width → 0 (얇은 spine 만 남음, 클릭 시 다시 펼침). 키보드: ⌘1~⌘4 로 패널 토글. localStorage
Maximize (집중) 패널 헤더 ⛶ 클릭. 다른 패널 모두 숨김 + 그 패널이 화면 전체. 다시 클릭 시 복원. ESC 도 복원. 일회성 (저장 안 함)
Detach (분리) 패널 헤더 ⤴ 클릭. 별도 창으로 popout. 본 화면은 빈자리에 placeholder. 다시 dock 가능. 창 위치 / 크기 저장

B) 일부 변경 — modal 을 더/덜 쓰자

Q-U11 — Detach (별도 창) 지원 여부
패널을 별도 창으로 떼어내는 detach 기능이 필요한가?

B) 보류 — collapse + maximize 만으로 충분
단순. 나중에 필요하면 추가.

이전 v3.1 질문 (그대로)

Q-U7 — Class field 입력 흐름 (v3.1 신규)
클래스 instance field 의 ontology 입력은 어디서?
A) Workbench L 패널 「클래스」 토글에서 클래스 선택 → C-R 패널이 "class 모드" 로 전환 → 그 클래스의 field 들이 카드로 보임
메서드 ↔ 클래스 작업 흐름 분리. 사용자가 명시적으로 토글.
B) 메서드 보고 있을 때도 그 메서드가 사용하는 instance field 카드를 위쪽에 표시 (현재 mockup §4 가 이 방식)
메서드 작업 시 자연. 다만 같은 field 를 여러 메서드에서 매번 마주침.
C) 둘 다 — 클래스 토글에서 정식 입력 + 메서드 보기 시 read-only summary
UX 좋음. 구현 복잡도 ↑.
Q-U8 — Ontology description 의 길이/형식
term/rule 의 description (자연어 설명) 은 얼마나 길게 허용?
A) markdown 자유 형식, 길이 제한 없음 → 매뉴얼 export 시 그대로 본문 됨
사용자가 풍부하게 작성 가능. 카드 펼치면 길어질 수 있음.
B) 짧은 한 줄 정의 (max 200 자) — 풍부한 본문은 별도 매뉴얼 작성
카드 컴팩트. 매뉴얼 작성기가 다시 필요해짐 (모순).
Q-U9 — 외부 매뉴얼 (PDF) 의 위치
📥 Import mode 에서 PDF/DOCX 업로드 → fragment 풀 → Workbench R 패널에 보임. 그 외 어떤 작업이 더 필요?
A) Import 후 fragment 가 LLM 으로 자동 분석 → 관련 메서드 자동 link → Workbench 에 reference 로 표시
사용자 작업 0. fragment ↔ method link 정확도가 LLM 성능에 의존.
B) Fragment 풀만 만들고 link 는 사용자가 ontology 입력 시 수동으로 ⊕ 클릭
사용자 통제 높음. 노가다.
