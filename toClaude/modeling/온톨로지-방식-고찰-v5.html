Action 모델 v5 — Java OO 표현 결함 재설계 v5 · OO RETHINK

사용자 지적 (C1 메모): "자바의 상속/인터페이스를 잘 표현 못 하면 레거시 자바를 다루는 우리에겐 더 큰 문제 아닌가?" 맞습니다. v1~v4 의 BusinessTerm 모델은 IS_A·implements·override·abstract 네 가지를 아예 다루지 않았고, 이건 SCM 레거시 코드에서 치명적입니다. 이전 결정에 매달리지 않고 처음부터 재검토합니다.

1. v4 모델의 진짜 결함 — Java OO 4 가지를 다루지 않음

아부 빼고 정직한 평가

v1 ~ v4 의 BusinessTerm + TermComposition 만으로는 다음 4 가지를 표현할 수 없습니다:

  1. 상속 (extends) — RushOrder extends Order
  2. 인터페이스 구현 (implements) — Order implements Trackable, Auditable
  3. 다형성 / 메서드 오버라이드 — RushOrder.validate() 가 Order.validate() 를 override
  4. 추상 (abstract) — abstract class Order, abstract validate() — 인스턴스화 불가, 선언만

BusinessTerm.kind=aggregate + TermComposition (HAS_A) 만으로는 "X 는 Y 의 일종이다" 라는 IS_A 의미를 못 표현하고, Action.realized_by 도 단일 메서드 매핑이라 polymorphism 이 안 됩니다. 이게 레거시 자바를 모델링하면서 가장 큰 갭입니다.

1.1 구체 사례 — SCM 도메인의 흔한 패턴

// 레거시 SCM 코드 (전형)
abstract class Order {
    String orderNo;
    Counterparty customer;
    OrderSpec spec;
    abstract ValidationResult validate();
}

class StandardOrder extends Order {
    @Override ValidationResult validate() {
        if (spec.diameter > 240.0) return fail("초과");   // ← anchor
        return ok();
    }
}

class RushOrder extends Order {
    int priorityLevel;                              // ← 추가 필드
    @Override ValidationResult validate() {
        if (priorityLevel < 1 || priorityLevel > 5)  // ← anchor
            return fail("우선도 범위 위반");
        if (spec.diameter > 200.0) return fail("긴급주문 직경 한도");  // ← 더 엄격
        return ok();
    }
}

interface Trackable {
    String getTrackingNo();
}
class Order implements Trackable, Auditable, Notifiable { ... }

1.2 v4 모델로 이걸 표현하면 무슨 일이 생기나

실제 사실v4 모델 한계결과
StandardOrder, RushOrder 둘 다 Order 다 BusinessTerm "주문" 만 있고 변형 표현 불가 둘이 별개 term 으로 등록되거나, 한쪽만 등록되어 다른 한쪽 무시
Action 주문_검증 = StandardOrder.validate OR RushOrder.validate (런타임 결정) Action.realized_by 가 단일 매핑 한 메서드만 시뮬, 다른 분기 무시 → 시뮬 결과 부정확
RushOrder.priorityLevel 만 RushOrder 에 있음 "주문" term 에 priorityLevel 부분 추가하면 StandardOrder 에도 잘못 노출 도메인 의미 오염
Order implements Trackable 인터페이스 = capability 를 표현할 노드 없음 "trackingNo 가져오기" 같은 공통 capability 가 도메인 모델에 안 들어감
abstract class Order — 직접 인스턴스 없음 BusinessTerm 에 abstract 플래그 없음 시뮬 input 으로 "Order" 인스턴스 만들기 시도 가능 (실제론 불가능)

1.3 왜 시뮬레이션에 치명적인가

다형성 무시 = 시뮬 결과 신뢰성 0

"긴급주문 의 직경 한도를 200→220 으로 완화하면?" 시뮬을 돌리는데, v4 모델은 RushOrder.validate 와 StandardOrder.validate 의 차이를 모르므로 엉뚱한 메서드 시뮬하거나 둘 중 하나만 돌림. 사용자에겐 "괜찮음" 으로 보이지만 실제 실행은 실패. 이게 SIM_VERIFIED 라는 verification level 의 신뢰를 통째로 무너뜨립니다.

2. 재설계 — 무엇이 진짜로 필요한가?

2.1 두 갈래 framing 비교

Framing X — 단일 레이어 BusinessTerm 에 OO 추가

BusinessTerm 이 IS_A·implements 까지 흡수. 즉 도메인 모델이 코드 구조를 부분적으로 mirror.

  • 장점: 모델 1 종, 학습 곡선 낮음
  • 단점: BaseEntity, AbstractAuditable 같은 코드-only 추상이 도메인에 새어들 위험

Framing Y — 두 레이어 (Code Type + BusinessTerm)

Java 클래스/인터페이스 트리는 별도 CodeType 레이어, 도메인 BusinessTerm 은 그것과 매핑.

  • 장점: 코드 노이즈 분리, 도메인 모델 깨끗
  • 단점: 두 트리 동기화·UI 복잡도 ↑

2.2 어느 쪽을 택할 것인가 — 정직한 분석

팔란티어는 사실상 Framing X 에 가깝습니다 (Object Type 자체가 데이터 + 의미). OWL/Semantic Web 도 X. UML→OWL 변환 연구도 X. (UML → OWL transformation) 하지만 그들은 "데이터 도메인 → 의미 모델" 매핑 (DB schema → ontology) 을 다루지, "레거시 OO 코드 → 의미 모델" 을 다루지 않습니다. 우리는 코드를 ground truth 로 받기 때문에, 코드의 구조적 사실 (extends/implements/abstract) 이 도메인 의미와 분리되어 있을 수 있습니다.

중도 — 단일 레이어, 단 OO 사실은 분리된 facet 으로

Framing X 채택. 단 BusinessTerm 안에 "이 term 이 어느 Java 클래스에서 왔는지" 와 "도메인 의미" 를 분리해서 저장. BaseEntity 같은 코드-only 추상은 BusinessTerm 으로 승격하지 않음 (Method.role=helper 와 같은 원리 — class.role 도 도입). 이렇게 하면 모델은 1 종 유지하면서 코드 노이즈 차단.

3. 새 모델 — 단일 BusinessTerm + Inheritance + 단순화

v4 의 4-kind (atomic/bundle/aggregate/reference) 를 다시 봅니다. 사용자 메모를 받아 정직하게: 4-kind 는 over-engineered 였습니다. bundle vs aggregate 는 UI/codegen hint 일 뿐 구조적으로는 같음. reference 도 standalone flag 면 충분. 깊이·다형성·추상 같은 진짜 구조 정보가 빠진 채로 4-kind 만 정밀했음.

3.1 BusinessTerm — 2-kind + facets + parents/parts

class BusinessTerm:
    fqn: str                          # "term.scm.order"
    label: str                        # "주문" (한국어, Q6=B)
    aliases: list[str]
    domain: str
    description: str

    kind: Literal["atomic", "composite"]     # 2 종 (was 4)

    # facets (조합 가능, 모두 boolean)
    is_abstract: bool = False         # 직접 인스턴스 불가 (Java abstract / interface)
    is_interface: bool = False        # 순수 capability 선언 (Java interface 정합)
    is_root_entity: bool = False      # 독립 lifecycle (was kind=reference)
    struct_like_hint: bool = False    # UI 렌더링 hint (was kind=bundle)

    # composite 일 때
    parents: list[Inheritance]        # extends + implements (NEW)
    parts:   list[Composition]        # HAS_A (v4 와 동일)

    # atomic 일 때
    value_type: ValueType | None
    unit, range, enum_values

class Inheritance:                    # NEW — IS_A
    child_fqn: str
    parent_fqn: str
    kind: Literal["extends", "implements"]
    # extends: 단일만, parts/parents 다 상속
    # implements: 다중 OK, parent 가 is_interface 여야 함

class Composition:                    # v4 와 동일
    parent_fqn: str
    child_fqn: str
    role_name: str
    cardinality: "1:1" | "0:1" | "1:N" | "0:N"
    required: bool

3.2 effective_parts — 상속 펼치기

# RushOrder 의 effective parts (resolver 가 transitive closure)
RushOrder.effective_parts = (
    Order.parts                       # extends 로 상속 (orderNo, customer, spec)
    + Order.implements_parts          # implements 한 인터페이스의 parts (trackingNo)
    + RushOrder.own_parts             # 자기 추가 (priorityLevel)
)

# 시뮬 codegen 시 dataclass 트리에 모두 평탄화

SCM 케이스 적용 — 표현 가능 여부 검증

BusinessTerm("Order",
  kind="composite", is_abstract=True,    # 추상 클래스
  parts=[orderNo, customer, spec],
  parents=[implements Trackable, implements Auditable]   # 인터페이스 다중
)
BusinessTerm("Trackable",
  kind="composite", is_abstract=True, is_interface=True, # 인터페이스
  parts=[trackingNo]
)
BusinessTerm("StandardOrder",
  kind="composite",
  parents=[extends Order]                # 단일 상속
)
BusinessTerm("RushOrder",
  kind="composite",
  parents=[extends Order],
  parts=[priorityLevel]                  # 추가 필드
)

3.3 Java OO 4 가지 표현력 점검

요구v4v5 (이 제안)
extends (단일 상속)✗✓ Inheritance(kind="extends")
implements (다중)✗✓ Inheritance(kind="implements")

interface (capability)✗✓ is_interface flag
composition (HAS_A)✓✓ Composition (변경 없음)
1:N collection✓✓ cardinality (변경 없음)
독립 엔티티 (reference)✓ kind=reference✓ is_root_entity flag
UI bundle hint✓ kind=bundle✓ struct_like_hint flag

4. Action realization with polymorphism

4.1 Action 모델 보강

class Action:
    fqn: str                          # "action.scm.주문_검증"
    label: str                        # "주문 검증"
    kind: Literal["pure_function", "effectful", "workflow"]
    is_abstract: bool = False         # NEW — Java abstract method 정합
    declared_on_term: str | None      # 어느 BusinessTerm 에 선언된 Action 인지

    params: list[ActionParam]
    output: ActionOutput | None
    preconditions, postconditions, effects

    realizations: list[Realization]   # NEW (was realized_by, 단일이었음)
    verification_level
    ...

class Realization:                    # NEW
    method_fqn: str                   # 코드 측 Java 메서드
    applies_to_term: str              # 어느 subtype 에 적용? (None = 모든 instance)
    is_override: bool                 # base 의 override 인가
    scope: Literal["primary", "partial"]

4.2 Dispatch — 시뮬 시 어느 메서드를 실행하나

# PythonGenerator 가 다음 모양으로 dispatch 코드 생성
class 주문_검증_Dispatcher:
    @staticmethod
    def execute(주문_instance):
        # 런타임 type tag 체크
        if isinstance(주문_instance, RushOrder_Term):
            return rush_order_validate(주문_instance)
        elif isinstance(주문_instance, StandardOrder_Term):
            return standard_order_validate(주문_instance)
        else:
            raise UnreachableAction(f"abstract Order can't be validated directly")

5. C3 후속 — input adapter 추상화

사용자 메모: "온톨로지 구조를 보고 직접 데이터를 만들 수도 있어야 하고, realData 도 잘 사용할 수 있도록 이 부분을 추상화해서 이런저런 포맷의 input 을 읽어서 사용할 수 있어야 해"

옳은 지적입니다. C3 답변 (A: 사용자 직접 입력) 을 그대로 두면 30+ 필드 Order fixture 만들기가 고통. Input source 를 plugin pattern 으로 추상화: 

class ScenarioInputAdapter(Protocol):
    """시뮬 input 을 다양한 출처에서 빌드하는 어댑터."""
    name: str
    def can_handle(self, source_spec: dict) -> bool: ...
    def materialize(self, term_fqn: str, spec: dict) -> Any:
        """주어진 BusinessTerm 구조에 맞는 객체 트리 반환."""

# 구현체들 (점진 추가)
class FormInputAdapter:        # C3=A — 사용자 form 직접 입력
    """사용자가 UI form 으로 채움. 깊이는 path picker 로."""

class GeneratedInputAdapter:   # 사용자 메모 — "온톨로지 보고 자동 생성"
    """BusinessTerm 의 range/enum 정보로 random valid 값 생성.
    조합: minimal / boundary / random / property-based."""

class FixtureInputAdapter:     # 미리 등록한 sample
    """SQLite 에 저장된 named fixture 로딩."""

class JsonInputAdapter:        # JSON 파일 / paste
    """임의 JSON → BusinessTerm 구조로 매핑 (best-effort + LLM 보강)."""

class CsvInputAdapter:         # CSV 1행 → input 1개
    """대량 시뮬 시 CSV row 를 input 으로."""

class DbQueryAdapter:          # realData
    """SQL query 결과 → input. 권한 분리 필요."""

class ApiAdapter:              # realData
    """REST/GraphQL endpoint → input."""

ScenarioStep 의 input 은 이제 출처 표시: 

ScenarioInput:
    adapter: str                # "form" | "generated" | "fixture" | "json" | "csv" | "db" | "api"
    spec: dict                  # adapter 별 자유 형식
    # form: {"values": {...}}
    # generated: {"strategy": "boundary", "seed": 42}
    # fixture: {"id": "order_42"}
    # json: {"path": "/path/to/sample.json"}
    # csv: {"path": "...", "row": 0}
    # db: {"query": "SELECT * FROM orders WHERE ..."}

장점

  • 1 단계: FormInputAdapter + FixtureInputAdapter 구현 (C3=A 답변 정합)
  • 2 단계: GeneratedInputAdapter 추가 — BusinessTerm.range 가 풍부해질수록 자동 생성 풍부 (사용자 메모 정합)
  • 3 단계: JsonInputAdapter + 외부 데이터 가져오기
  • 4 단계: DbQueryAdapter + ApiAdapter — realData 단계
  • 각 단계에서 ScenarioStep 변경 없이 새 adapter 만 추가

6. 시뮬레이션 정합성 재점검 — 다형성 환경

시나리오v4 결과v5 결과
"긴급주문 직경 한도 200→220 시뮬" 주문_검증 의 어느 메서드 실행할지 모름. 임의로 1 개 선택. RushOrder fixture 로 시뮬 → dispatcher 가 RushOrder.validate 정확히 호출
"표준주문 vs 긴급주문 비교 시뮬" 비교 자체 표현 불가 같은 Action 을 두 fixture 로 두 step 실행 → side-by-side diff
"인터페이스 Trackable 변경 영향 분석" 인터페이스 모델 자체가 없어 영향 분석 불가 Trackable.is_interface=True term 변경 → implements 한 모든 term 영향 traversal
"abstract Order 로 시뮬 시도" 가능 (잘못된 시뮬 결과 반환 가능) 거부 — abstract 라 인스턴스 안 만듦, 사용자에게 "subtype 골라달라" 안내

7. C1~C4 답변에 미치는 영향

이전 답변v5 영향
C1=A (4-kind) 변경 권장: 2-kind + facets 가 더 단순하고 OO 표현 통합. 아래 D1 으로 재질문.
C2=A (풍부 syntax) 유지 + 확장: params[0]<RushOrder> subtype cast 추가
C3=A (직접 입력) 유지하되 adapter 추상화: §5 의 plugin pattern 으로 점진 확장 (form 부터)
C4=A (Java 자동 추출 + confirm) 유지 + 확장: Java parser 가 extends/implements/abstract 도 함께 추출 + class.role 분류

8. 결정 질문 D1 ~ D3

D1 BusinessTerm kind 단순화 (2-kind + facets)

§3.1: 4-kind (atomic/bundle/aggregate/reference) → 2-kind (atomic/composite) + facets (is_abstract, is_interface, is_root_entity, struct_like_hint). 이전 C1=A (4-kind) 답변을 v5 에서 재검토.

D2 코드 노이즈 (BaseEntity / Helper) 처리

Java 레거시에는 BaseEntity, AbstractAuditable, AbstractDtoMapper 같은 코드-only 추상이 흔함. 이걸 BusinessTerm 으로 승격할지.
