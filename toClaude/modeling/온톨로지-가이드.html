onTong 온톨로지 모델 가이드

2026-04-27 · 사용자 onboarding · 모델 구조 + 워크플로우 + 5 가지 진입점

한 문장 요약 — onTong 의 온톨로지는 표준 (노드/관계/제약사항) + 우리만의 특이점 (코드/매뉴얼 source 추적). 모델링은 5 가지 진입점으로 시작 가능.

1. 표준 온톨로지 vs 우리 모델

표준 (OWL/RDF 등)우리 구현예시 (slab-design)
노드 (Class / Concept / Individual) BusinessTerm term.품종코드, term.열연공장코드
관계 (ObjectProperty / hasA / isA) OntologyRelation 7 종 is_a, part_of, governs, conflicts 등
제약사항 (Constraint / Axiom / Rule) BusinessRule "품종코드는 4자리 영문+숫자", severity=hard
외부 인스턴스 anchor ConceptBinding (term ↔ code), BusinessRule.source (provenance) term.품종코드 ↔ productTypeCd 필드
우리만의 특이점 — BusinessRule 도 그래프의 노드로 다룸 (제약사항이 일급 시민). Term-Rule 관계 (governs) 가 일반 OWL 보다 명시적. Code/Manual source provenance 가 필수.

2. 전체 데이터 흐름

┌────────────────────────────────┐ ┌────────────────────────────────┐ │ Code (Java) │ │ Manual (PDF / DOCX / MD) │ │ • Class / Method / Field │ │ • ManualDocument │ │ • MethodAnchor (param/local..) │ │ • ManualSection │ │ │ │ • ManualFragment │ └──────────┬─────────────────────┘ └─────────────┬──────────────────┘ │ 자동 추출 + 사용자 매핑 자동/LLM/수동 추출 ↓ ↓ ┌──────────────────────────────────────────────────────┐ │ 온톨로지 (정제된 도메인 모델) │ │ │ │ BusinessTerm ←─ governs ──→ BusinessRule │ │ ↑ ↑ │ │ │ ConceptBinding │ source │ │ │ (term ↔ code anchor) │ (manual:fqn 등) │ │ │ │ │ │ [Code position] [Manual fragment] │ │ │ │ OntologyRelation : term-term (is_a, part_of, ...) │ │ term-rule (governs) │ │ rule-rule (conflicts) │ └───────────────────────────────────────────────────────┘ ↓ 시뮬레이션 / 영향 분석 / 갭 탐지

3. 5 가지 모델링 진입점

온톨로지 자체에 노드/관계/제약사항을 채우는 진입점입니다. 어디서든 시작 가능.

1BusinessTerm 등록 (도메인 노드 추가)
  • 위치: Workbench Ontology 패널 「BusinessTerm 관리」 collapsible OR 「용어 매핑」 탭
  • 방법: 「+ 새 BusinessTerm」 (수동) OR 「AI 추천」 (LLM 이 매뉴얼/코드 보고 추천)
  • 필수 필드: qualified_name, canonical_label (한국어), aliases (token 매칭용)
2Code → Term 매핑 (ConceptBinding)
  • 위치: Workbench → 메서드 클릭 → C-R Ontology 패널 anchor 카드
  • 방법: alias 자동 매칭 또는 「LLM 보강」 → 추천된 term 옆 「확정」 버튼
  • 결과: term.품종코드 ↔ method@param.productTypeCd 같은 매핑이 ConceptBindingProposal 에 confirmed 로 저장
3Code → BusinessRule 추출 (자동)
  • 위치: backend startup 자동 — Workbench R 「⚖️ 룰」 탭에서 검토
  • kinds: guard / bound / formula / enum / regex / throw / lookup (P16 body extractor)
  • auto-confirm: formula / throw / regex (확정), 나머지는 사용자 검토
  • source: body:guard, body:throw 등
4Manual → BusinessRule 등록
  • 위치: 사이드바 「매뉴얼」 → 매뉴얼 행 expand → fragment 옆 「+ 룰로 등록」 (수동) OR 행 「💡 룰 추출」 (LLM 일괄)
  • 제공: statement (편집 가능), severity, terms_ref, source (provenance: manual:doc#frag:fqn)
  • 온톨로지에 들어감: BusinessRule 이 노드로 등록되고 source 가 어느 매뉴얼/섹션 출처인지 추적
5관계 (OntologyRelation) 추가
  • 위치: 사이드바 「온톨로지 그래프」 탭 → 노드 클릭 → 우측 「새 관계 추가」
  • kind 선택: term-term (is_a, part_of, synonym_of, related_to), term-rule (governs), rule-term (derives), rule-rule (conflicts)
  • 자동 inferred: rule.terms_ref 가 있으면 점선 엣지로 자동 추가 (DB 미저장)

4. Workbench R 「📝 노드」 탭 — 통합 모델링 view

L3 신규 — 메서드를 온톨로지 노드로 다루는 통합 view. 모델링 행위가 한 곳에 모임.

이전엔 모델링 행위가 여러 패널에 분산:

  • anchor 카드 → ConceptBinding (Ontology 패널)
  • BusinessRule 추출 결과 → 「⚖️ 룰」 탭
  • 호출 관계 → 「🧬 영향」 탭
  • 온톨로지 관계 → 별도 「온톨로지 그래프」 탭

「📝 노드」 탭에 모두 모임:

섹션표시편집
노드 개요method/class kind, fqn, file:line—
📝 비즈니스 description이 메서드의 비즈니스 의미 (자유 텍스트), tags, owner「편집」 → 저장 (CodeNodeMeta 영구화)
🔗 노드 내부 (anchor + term 매핑)anchor 수, kind 분포, 매핑된 BusinessTerm좌측 Ontology 패널에서 인라인
⚖️ 노드 제약사항 (BusinessRule)이 메서드의 룰 (kind / severity / 확정 여부)「⚖️ 룰」 탭에서 검토/편집/등록
🧬 다른 노드와의 관계호출 관계 (call graph), 온톨로지 관계 안내「🧬 영향」 / 「온톨로지 그래프」 탭

5. 모델링 시나리오 (slab-design demo)

시나리오 A — 코드부터 시작
  1. Workbench → SdFinalLengthRangeAction.execute() 메서드 클릭
  2. 「📝 노드」 탭 → description 작성: "슬라브 길이 범위 결정 — 슬라브 중량/두께/비중 기반"
  3. C-R Ontology 패널 → anchor 카드들 (slab.slabWgtInProgress, slab.slabThickness 등) → 「확정」 으로 BusinessTerm 매핑
  4. 「⚖️ 룰」 탭 → 자동 추출된 body:formula 룰들 검토 → 「확정」
  5. 「온톨로지 그래프」 탭 → 슬라브중량 ↔ 슬라브두께 「related_to」 관계 추가
시나리오 B — 매뉴얼부터 시작
  1. 「매뉴얼」 → 업로드 (PDF 또는 MD)
  2. 매뉴얼 행 클릭 → fragment 미리보기
  3. 「💡 룰 추출」 → LLM 이 17 개 BusinessRule 후보 추천 → 체크박스 multi-select → 「선택한 룰 등록」
  4. 등록된 룰들이 BusinessRule 노드로 추가됨 (source = manual:doc#frag:fqn)
  5. Workbench R 「📚 참고」 탭에서 메서드 룰 옆에 매뉴얼 본문 표시 (provenance lookup)
시나리오 C — 시뮬레이션
  1. Workbench → 메서드 선택 → 「🔬 시뮬」 탭 → 「+ 새 시뮬레이션」
  2. Step 1 정의: kind = method_body, payload = old/new snippet
  3. Step 2 실행: Java→한국어 Python LLM 변환 → RestrictedPython sandbox
  4. Step 3 결과: Before/After diff (Decimal 정밀 비교, exception/mock/perf)
  5. 「적용」 → unified diff patch + 「GitHub PR 만들기」 (gh CLI draft PR)

6. 자주 묻는 질문

Q. 매뉴얼이 온톨로지의 일부인가요?

아닙니다. 매뉴얼은 raw source layer 입니다. 온톨로지 노드 (BusinessTerm/Rule) 는 사용자/LLM 이 매뉴얼에서 추출해 만듭니다. BusinessRule.source 가 manual:doc#frag:fqn 으로 어느 매뉴얼에서 왔는지 provenance 추적.

Q. ConceptBinding 과 OntologyRelation 차이?

ConceptBindingOntologyRelation
역할코드 ↔ 도메인 매핑 (외부 anchor)도메인 내부 관계
예시term.품종코드 ↔ productTypeCd 필드품종코드 is_a 코드
위치anchor 카드 「확정」온톨로지 그래프 탭

Q. 노드/관계 100% 자동 생성 안 되나요?

핵심 부분은 자동:

  • MethodAnchor (param/local/branch/literal) — 100% 자동
  • BusinessRule from code body (P16) — 7 kinds 자동, 검토 필요
  • anchor → term 매핑 — alias + LLM 추천 (확정은 사용자)
  • BusinessRule from manual — LLM 추천 (확정은 사용자)

하지만 도메인 의미 결정은 사람이 해야 (LLM 환각 방지). 자세한 이유는 IA-개선제안-v1.html 참조.
