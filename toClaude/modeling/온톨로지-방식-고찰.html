1. TL;DR — 사용자 직관 검증 결과

요점 3 줄

  1. 사용자 직관은 정확합니다. 팔란티어는 진짜로 메서드/함수를 별도 계층(Action·Function)에 두며, Object Type(명사) 에 직접 묶지 않습니다.
  2. 지금 우리는 명사·동사를 한 통에 담고 있습니다. BusinessTerm(REALIZES) 하나가 명사("안전재고")와 동사("안전재고 계산하기") 둘 다를 받아내고 있어 의미가 흐려져 있습니다.
  3. 다만 "Action 노드 신설" 만이 답은 아닙니다. 우리가 이미 가진 Process(IO + formula + rules) 가 거의 Action 시그니처라서, 신설 vs 재활용 vs 하이브리드 3 갈래 의사결정이 필요합니다. 본 문서가 그 결정 자료입니다.

오해 정정

  • 팔란티어 Action 은 "메서드 = Action 1:1" 이 아닙니다. Action 은 사용자가 트리거하는 schema 정의된 변경이고, 실제 로직은 Function 이 담당하는 "function-backed Action" 패턴입니다.
  • 즉 Action ≈ 권한·검증·감사 wrapper, Function ≈ 순수 계산. 둘은 다른 역할입니다. 우리도 둘 다 필요할 가능성이 큽니다.

2. 현재 우리 온톨로지 정확히 보기

지금 모델 코드 (backend/modeling/ontology/schema.py + mapping/mapping_models.py) 기준 사실관계입니다. 주관 평가는 §5 부터.

2.1 노드 종류 (4 종)

노드역할의미코드 매핑
BusinessTerm 업무 용어 "안전재고", "발주수량", "리드타임"… 명사·동사 모두 등록 가능한 자유 양식 METHOD ←REALIZES→ BusinessTerm (ConceptBinding)
BusinessRule 비즈니스 규칙 "안전재고는 음수 불가", "리드타임 14일 초과 시 알림" 같은 제약 (HARD/SOFT) METHOD ←VALIDATES→ BusinessRule
BusinessProcess 업무 프로세스 허브 "발주관리", "재고보충" 같은 조직적 묶음. 실행 단위 아님, 책임/소속 hub METHOD ←PART_OF→ BusinessProcess
Role 팀 "team.scm", "team.purchasing"… 책임자/승인자/리뷰어/통지대상 Role ←RESPONSIBLE_FOR→ {Process|Code}

2.2 (Primary Layer) 매뉴얼 기반 Process 스키마

schema.py 의 Process 는 위의 BusinessProcess 와 다른 물건입니다 — 매뉴얼에서 추출한 SCOR 스타일 워크플로우 노드로, 이미 거의 Action 시그니처에 가까운 구조를 가지고 있습니다. 

class Process:
    id, name, parent_id          # 계층
    inputs:  list[IOPort]        # ⬅ 타입 있음 (int/float/string/bool, range, unit)
    outputs: list[IOPort]        # ⬅ 타입 있음
    formula: Formula | None      # ⬅ 산식
    rules:   list[Rule]          # ⬅ warning / assign / constraint
    depends_on, source_sections
핵심 관찰: Process 는 매뉴얼에서 도출된 동사적 단위인데, 현재 코드 매핑 대상으로는 쓰이지 않고 있습니다. 코드 매핑은 전부 BusinessTerm 으로 흡수되어 있습니다 → 여기가 의미 충돌의 진앙입니다.

2.3 매핑 (코드 ↔ 비즈니스)

엣지방향현재 적재량의미
REALIZESMETHOD/CLASS → BusinessTerm주된 매핑이 코드가 이 용어를 "구현"한다
VALIDATESMETHOD → BusinessRule일부이 메서드가 이 규칙을 검사/적용한다
PART_OFMETHOD/CLASS → BusinessProcess일부이 코드가 이 업무에 "소속" 된다
USES / PRODUCESProcess → Entity매뉴얼만매뉴얼-한정. 코드와 안 엮임.

2.4 시뮬레이션 측 (이미 결정된 것)

v3 결정 (2026-04-26) 에 따라 시뮬레이션은 온톨로지 → Python 코드 생성 → RestrictedPython 실행 파이프라인입니다. body AST visitor 가 anchor 7 종(field / field_access / param / local / return / branch / literal)을 추출합니다.

즉 코드 본체에서 입력·출력·분기·literal 을 자동 추출하는 인프라는 이미 있습니다. 다만 그 추출 결과가 현재는 BusinessTerm 옆에만 매달려 있고, 별도 "동사 노드" 가 없습니다.

3. 팔란티어 4-pillar — Object · Link · Action · Function

팔란티어 공식 문서 (core-concepts, action-types/overview) 기준 정리.

Object Type

명사 / 실세계 엔티티의 schema. Customer, Order, Airport.

  • Property (= 속성/필드)
  • Property type (string/number/timestamp…)
  • Primary key

데이터셋·테이블·모델이 "물리 backing" 되어 있고, ontology layer 가 의미를 부여.

Link Type

두 Object Type 사이 관계의 schema. Customer owns Order.

  • 방향성 / cardinality
  • 그래프 traversal 가능

우리의 Relation 과 동치.

Action Type

사용자가 트리거하는 변경 schema. createOrder, cancelShipment, approveLeave.

  • Parameter (타입 있음, 사용자 입력)
  • Validation rule (전제·권한·범위)
  • Effect (어떤 object/property/link 가 어떻게 변하나)
  • Side effect (notification, webhook)
  • Audit trail (누가 언제 무엇을)

"모든 쓰기는 Action 을 통해야 한다" — 권한·감사 boundary.

Function Type

입력 → 출력 순수 계산 블록. TypeScript/Python 으로 작성.

  • Object 의 derived property 계산
  • Action 의 logic 백킹 (function-backed Action)
  • Workflow 안에서 재사용

로직 자체. 쓰기 권한·감사 wrapper 는 없음 (Action 이 wrapping).

Action vs Function 의 결정적 차이

  • Action = "사용자가 호출할 수 있는 schema 정의된 안전한 mutation". UI 버튼이 이걸 쏨.
  • Function = "재사용 가능한 계산 단위". UI 가 직접 호출하지 않고 Action·View 에서 가져다 씀.
  • 한 Action 은 0~N 개 Function 을 합성해서 자기 effect 를 구현 ("function-backed Action").

다시 말해 Action 은 거버넌스 boundary, Function 은 로직 boundary.

3.1 팔란티어가 자기 표현하는 한 줄

"Ontology 는 semantic elements (objects, properties, links) 와 kinetic elements (actions, functions, dynamic security) 를 함께 담아 사용 케이스를 가능하게 하는 운영 레이어다."

→ semantic = 명사·관계 (정적), kinetic = 동사·계산·권한 (동적). 우리는 지금 semantic 만 두텁고 kinetic 이 약합니다.

4. 교차 매핑 매트릭스

팔란티어onTong 현재일치도코멘트
Object Type + Property BusinessTerm + Entity 부분 BusinessTerm 에 properties 타입 시스템이 없음. 그냥 string canonical_label + aliases.
Link Type Relation (part_of/uses/produces/responsible_for) 상당 방향·종류 다 있음. cardinality 개념만 좀 약함.
Action Type — 없음 현재 메서드는 BusinessTerm 에 흡수됨. 파라미터·effect·검증 schema 가 별도로 없음.
Function Type Process(formula+rules) + Java method 본체 분산 매뉴얼 측 Process 는 시그니처만, 코드 측 method 는 본체. 둘이 명시 매핑 안 됨.
Audit / 권한 boundary ResolutionAuditLog 만 있음 미흡 action 실행 감사·권한 정책 자체가 없음 (지금은 read-mostly 라 OK, 시뮬레이션 가면 필요).

5. 우리 모델의 비판적 진단

5.1 증상 — 지금 무엇이 어색한가

① 명사·동사 한 통(BusinessTerm)에 담김

"안전재고"(명사) 와 "안전재고 계산"(동사) 이 같은 BusinessTerm 으로 등록 가능. 실제로 사용자가 "안전재고 계산" 을 term 으로 입력하면 그것대로 받아들여짐.

결과: 검색·매칭 시 명사를 찾는 의도와 동사를 찾는 의도가 섞여 노이즈 ↑.

② 메서드 시그니처가 "온톨로지에 노출되지 않음"

코드 측 METHOD 노드는 이름 + body 만 가지고 있음. 매핑은 REALIZES → BusinessTerm 한 줄. 파라미터 타입·반환 타입·전제 조건이 온톨로지 모델에 1급 시민이 아님.

결과: 시뮬레이션 Python 코드 생성 시 LLM 이 메서드 본체를 다시 파싱해서 시그니처를 추론해야 함. Anchor visitor 가 있긴 하지만 그 결과가 별도 동사 노드에 묶이지 않고 매핑 옆에 floating.

③ Process(매뉴얼) ↔ Method(코드) 가 안 만남

schema.py 의 Process 는 매뉴얼 도출 동사 단위 (IO + formula + rules) 인데 코드 매핑 흐름과 끊겨 있음. 사용자는 매뉴얼에서 "안전재고 계산" Process 를 정의했는데, 그 Process 가 SafetyStockCalculator.compute() 메서드와 직접 묶이지 않음 — 둘 다 같은 BusinessTerm 옆에 매달려 있을 뿐.

결과: "이 매뉴얼 절차의 코드 구현체는?" 질의를 BusinessTerm 우회로 답해야 함. 체이닝이 한 단계 더 들어가서 정확도·설명력 ↓.

④ 시뮬레이션 input 계약이 모델에 없음

v3 결정대로 시뮬레이션은 Python 함수 생성 → 실행. 함수의 "이 input 으로 호출하면 된다"는 계약이 필요한데, 지금 모델에는 그게 IOPort 로 매뉴얼 Process 에만 있고 코드 매핑에는 없음.

결과: Anchor binding suggester 가 매번 코드를 재분석해서 "param x 는 lead_time" 식으로 추론해야 함. 한 번 확정해서 노드에 박아두면 끝날 일.

5.2 왜 지금까지는 괜찮아 보였나

  • 지금까지 user flow 는 주로 read(검색·정의 조회)였고 write/execute 가 적었음.
  • BusinessTerm 의 자유로움이 "일단 다 등록해보자" 단계에는 도움됐음 (low-friction onboarding).
  • Process 스키마가 워낙 풍부해서 "이미 동사를 다루고 있다" 는 착시.

하지만 시뮬레이션 (Python 생성·실행) + draft PR 자동 생성 단계로 가면 "메서드를 부른다" 가 핵심 동사가 됩니다. 거기서 의미 분리가 필요합니다.

6. Action(또는 동치 개념) 도입 시 무엇이 좋아지나

6.1 시뮬레이션 (현 결정 v3 와 정합성 ↑)

Python 코드 생성기가 LLM 에 넣을 프롬프트를 떠올려보면: 

# Action 노드가 있을 때 — 깨끗
Action: 안전재고_계산
  params:
    - item_id: string
    - lead_time_days: int (range 1..60)
    - demand_stdev: float (unit: ea/day)
  output: SafetyStock { value: float, computed_at: timestamp }
  preconditions:
    - lead_time_days > 0
    - demand_stdev >= 0
  realized_by: SafetyStockCalculator.compute()    # function-backed
  rules: [BR-001(severity=hard), BR-007(severity=soft)]

# 지금 — LLM 이 본체를 다시 파싱해야 함
Term: 안전재고
Method: SafetyStockCalculator.compute(...)        # 시그니처 따로 추출 필요
Rules : [BR-001, BR-007]                          # 어느 단계에서 적용할지 별도 추론

6.2 LLM agent (Round 2 의 4-stage resolution)

  • "발주서를 취소해" → Action 후보를 먼저 검색 (verb-aware retrieval) → 매칭 정확도 ↑.
  • 지금은 BusinessTerm 풀에서 "취소" 관련 명사/동사 다 섞여 검색됨.

6.3 거버넌스 / 감사

  • "이 코드 매핑이 시뮬레이션 PR draft 를 만들 권한이 있나?" 같은 질문이 나오면, Action 단위에 권한·승인 정책을 박을 수 있음.
  • 지금처럼 "모든 매핑은 평등" 모델로는 임팩트 큰 mutation 과 read-only 조회가 같은 면에 있음.

6.4 UI / Workbench (v3.1 §6 5-mode rail)

  • "Code"·"Ontology"·"Manual"·"Simulation" 모드 사이 자연스러운 1급 객체로 Action 이 들어감 → simulation drawer 가 "이 Action 을 실행해보기" 버튼으로 단순화.
  • Ontology editor cards 에서 Process 카드 vs Term 카드 가 분리된 채로 명사 카드만 비대해진 현 상태가 정리됨.

7. 옵션 4 가지

범례: 유지비 ↓ 중간 유지비 ↑   ·   의미 정합성: ★ 1~3 개

옵션 A — 현 상태 유지 (BusinessTerm 흡수)

변경 없음. 사용자가 동사 형태 term 도 자유롭게 등록.

  • 유지비: 유지비 ↓ (코드 0)
  • 의미 정합성: ★
  • 리스크: 시뮬레이션 단계 들어갈수록 LLM 이 본체 재파싱해서 시그니처 만들어야 함 → 정확도/속도 ↓

언제 옳은가: 시뮬레이션을 당분간 demo 수준만 유지할 때. 단, v3 에 "MVP 타협 금지" 결정이 있어서 사실상 배제.

옵션 B — Process 를 Action 으로 격상 (재활용)

이미 있는 schema.Process (IO + formula + rules) 를 코드 매핑 대상으로 1급 격상. 메서드는 METHOD ←IMPLEMENTS→ Process 엣지로 묶음. BusinessTerm 은 순수 명사 (entity / property) 로 정화.

장점

  • 새 노드 타입 0 (스키마 신설 비용 적음)
  • Process 의 IO/formula/rules 가 그대로 Action 시그니처 됨 (이미 충분히 풍부)
  • 매뉴얼 → Process → 메서드 chain 이 자연스러움

단점

  • "Process" 라는 단어가 두 의미로 쓰이게 됨: schema.Process(동사·실행단위) vs BusinessProcess(조직 허브). 사용자 멘탈 모델 헷갈림.
  • UI 라벨링 작업 필요 (둘 중 하나는 이름 변경 권장: 후자를 BusinessFunction/OrgUnit 으로 등).

유지비 중간 · 의미 정합성 ★★

옵션 C — BusinessAction 신설 (팔란티어 충실)

4 번째 1급 노드 BusinessAction 추가. 명사(Term)·관계(Relation)·조직(Process)·동사(Action) 4-pillar.

class BusinessAction:
    qualified_name: str
    canonical_label: str            # "안전재고 계산"
    params:  list[ActionParam]      # typed
    output:  ActionOutput | None
    preconditions: list[BusinessRule_fqn]
    effects: list[ActionEffect]     # creates/mutates/reads
    parent_process: BusinessProcess_fqn | None
    confirmed: bool

class ActionBinding:                # METHOD ←REALIZES→ Action
    code_fqn: str
    action_fqn: str
    scope: primary | partial
    confidence, source, ...

장점

  • 의미 분리가 가장 깨끗 (semantic vs kinetic)
  • 시뮬레이션 코드 생성기 입력으로 그대로 사용 가능 (§6.1 참고)
  • 팔란티어 사용 경험자가 들어와도 멘탈 모델 호환

단점

  • 스키마 신설 + Round 2 매핑 흐름 일부 재배선 필요 (BusinessTerm-only 매핑 → Term/Action 양립)
  • 매뉴얼 import 단계에서 "이건 명사? 동사?" LLM 분류 한 단계 추가
  • UI Workbench 에 Action 카드 종류 추가 (5-mode rail 안에서 가능)

유지비 유지비 ↑ · 의미 정합성 ★★★

옵션 D — 하이브리드 (Term 에 kind 필드 + 점진 migration)

일단 BusinessTerm 에 kind: "noun" | "action" 필드 추가 (저비용). kind=action 인 term 은 추가 스키마 (params/output/preconditions) 를 옵션으로 가짐. 나중에 충분히 모이면 옵션 C 로 정식 분리.

장점

  • 지금 데이터 안 깨짐 — 기존 term 은 모두 kind="noun" 으로 잡으면 됨
  • 매뉴얼 import LLM 에 "noun/action 분류" 한 줄만 추가하면 시작
  • 충분히 쌓이면 진짜 분리 결정을 데이터 기반으로

단점

  • 한동안은 여전히 한 통 (분리 미완성)
  • Workbench UI 에서 같은 term 카드인데 kind 별로 분기 그리는 작업 필요
  • 최종 옵션 C 로 갈 거면 결국 마이그레이션 두 번 하는 셈

8. 결정해야 할 질문 6 가지

Q1. "Action" 1급 시민화에 동의하는가?

= "메서드는 명사가 아니라 동사에 매핑되어야 한다" 라는 사용자 직관을 모델 레벨로 받아들이는가?
(받아들이지 않으면 옵션 A 유지, 받아들이면 B/C/D 중 선택)

Q2. 신설(C) vs 재활용(B) — 단어 충돌 감수?

옵션 B 는 schema.Process 를 코드 매핑의 동사 노드로 격상. 단점은 BusinessProcess(조직 허브) 와 단어 충돌. 둘 중 하나의 이름을 바꿀 의지가 있는가? (예: BusinessProcess → BusinessUnit 또는 schema.Process → BusinessAction)

Q3. Function-backed Action 패턴 채택?

팔란티어식으로 Action(거버넌스 wrapper) 와 Function(순수 계산) 을 따로 둘지, 아니면 "메서드 = Action 1:1" 단순 모델로 갈지. 현 모델은 후자에 가까움. v3 의 draft PR 자동 생성/시뮬레이션 권한 분리를 생각하면 전자가 유리.

Q4. Action 의 effect 표현 깊이?

팔란티어 Action 은 effect 를 schema 로 선언 ("이 Action 은 Order.status 를 modify, Order.cancelledAt 를 set"). 우리는 어디까지 갈 것인가?
(a) 표현 안 함 — 본체에서 추론 / (b) 자연어 description / (c) 정형 effect (target_term + op) 까지

Q5. 매뉴얼 import 시 noun/action 자동 분류?

매뉴얼에서 term 추출 단계에 LLM 이 "이건 명사인가 동사인가" 를 분류해서 자동으로 BusinessTerm vs BusinessAction 으로 라우팅할지. 안 하면 사용자 수작업 분류. v3 결정 Q-C("혼합 anchor") 와 같은 결의 — 명백한 패턴은 자동, 모호한 것만 큐.

Q6. 마이그레이션 — 기존 BusinessTerm 어떻게?

지금 등록된 term 을 어떻게 분류하나? (a) 전부 noun 으로 두고 새 등록만 분리 / (b) LLM 1회 일괄 재분류 / (c) 사용자 1회 검토 큐

9. 부록 — Action vs Function 의 미묘한 차이

"메서드 = Action" 으로 단순히 보지 말아야 하는 이유. 팔란티어 문서에서 두 개념이 분리된 정확한 이유:

예제로 보기 
# Function (순수 계산, 권한·감사 wrapper 없음)
function calculateSafetyStock(item: Item, leadTime: int, demandStdev: float): float {
  return demandStdev * sqrt(leadTime) * 1.65   // 95% service level
}

# Action (사용자 트리거, 권한·감사·effect 있음)
ActionType: UpdateSafetyStockTarget {
  parameters:
    - item_id: ItemRef        # 사용자가 UI 에서 고름
    - lead_time: int          # 사용자 입력
  validation:
    - actor.team == "team.scm" OR actor.team == "team.purchasing"
    - lead_time in [1, 60]
  effect:
    new_value = calculateSafetyStock(item_id, lead_time, item_id.demand_stdev)
    item_id.safety_stock_target = new_value
    item_id.last_updated_at = now()
  side_effect:
    notify(channel="#scm", "{actor} updated safety stock for {item_id} → {new_value}")
}

여기서 calculateSafetyStock 은 여러 Action 에서 재사용 가능한 Function이고, UpdateSafetyStockTarget 은 그 Function 을 안전하게 호출하는 거버넌스 wrapper.

우리 시뮬레이션 측면으로 보면:

  • Java SafetyStockCalculator.compute() = Function (순수 계산)
  • "PR draft 로 안전재고 산식 변경 제안" = Action (사용자 트리거 변경, 감사·승인 필요)

v3 의 "Java patch draft PR 자동 생성" 결정은 사실상 Action 의 설계 영역이고, 코드 본체 로직은 Function 영역입니다. 둘을 분리해두면 "어떤 변경이 PR 까지 가야 하나?" 같은 정책을 Action 레벨에 박을 수 있습니다.

마무리 — 사용자에게

사용자의 직관 ("메서드를 Action 으로 매핑해야 한다") 은 팔란티어와 같은 방향이며, 현 모델의 가장 큰 미흡 지점을 정확히 짚었습니다. 다만 단순히 "Action 노드 추가" 가 아니라 (a) 신설/재활용/하이브리드 셋 중 하나, (b) Action vs Function 구분 여부 두 결정이 핵심입니다.

위 §8 의 Q1~Q6 에 대한 답을 주시면, 그에 맞춘 스키마 변경안 + 마이그레이션 플랜 + UI 영향 분석을 별도 문서(온톨로지-방식-결정.html)로 내겠습니다.
