1. 결정 전제 — Action 도입이 시뮬레이션에 의미하는 것

확정 사항 (v1 § 7 옵션 중)

  • Action 을 1급 시민으로 추가한다 (옵션 C 또는 B 확장).
  • 메서드는 BusinessTerm (명사) 에 직접 매핑되지 않고, Action 을 거쳐 매핑된다.
  • 이 결정의 진짜 가치는 "온톨로지 깔끔함" 이 아니라, 시뮬레이션 정확도 다.

1.1 시뮬레이션이 지금 부정확한 4 가지 이유 (Action 부재로)

현 증상Action 부재로 인한 원인Action 도입 시 해소
같은 메서드에 매번 LLM 이 시그니처 재추론 → 비결정적 params/output 타입이 노드에 없음 — body 만 있음 Action.params/output 이 1급 → 캐시·재사용
"이 input 으로 호출하면 된다" 를 안 보장 BusinessTerm 매핑은 단방향 라벨일 뿐, 호출 계약 아님 Action 시그니처 = 호출 계약
`ChangeSpec.target_method_fqn` 가 "이 method body 어딘가" 를 가리킬 뿐 변경의 대상이 메서드 본체 텍스트라 anchor·rule 분리 약함 ChangeSpec 이 Action 의 어느 슬롯을 변경하는지 정확히 지목
여러 메서드 chain (workflow) 시뮬레이션 안 됨 — 단일 메서드만 chain 의 각 단계가 같은 평면에 묶일 수가 없음 Action chain 으로 multi-step 시뮬

→

→
PythonGenerator (LLM 매번 시그니처 추론)
→
SandboxRunner
→
Diff

약점: ① 메서드 단위라 chain 시뮬 불가 ② 시그니처 재추론 비결정적 ③ Term 매핑이 호출 계약 보장 안 함 ④ ChangeSpec.target = method, kind 별로 변경 단위가 method body 텍스트 또는 룰 — Action 슬롯이 없어 PR 단위가 명확하지 않음.

2.2 After (Action 도입)

User: Scenario 입력
→
Action 1개 또는 chain 식별
→
Action.params/output/effects (이미 typed, frozen)
→
PythonGenerator (시그니처는 Action 에서, body 만 변환)
→
SandboxRunner (input → Action → output)
→
Diff (Action 의 effect 단위)
→
PR draft (Action 의 어느 슬롯 변경)

강점: ① Action 시그니처가 lock 되면 LLM 호출 1회로 충분 ② chain 표현 가능 ③ ChangeSpec 이 "Action.precondition[2] 의 statement" 같은 슬롯을 정확히 가리킴 ④ PR 단위가 Action 슬롯 단위로 명확.

3. Action 데이터 모델 (시뮬레이션 입력 관점)

단순히 "메서드 1개 = Action 1개" 로 두면 의미가 부족하다. 시뮬레이션이 호출 계약으로 신뢰할 수 있을 만큼 무엇을 박아둘지가 모델 설계의 진짜 질문이다. 

class Action:
    # — 식별
    qualified_name: str            # "action.scm.calculate_safety_stock"
    canonical_label: str           # "안전재고 계산" (한국어)
    aliases: list[str]
    domain: str                    # "scm" / "purchasing" / ...

    # — 호출 계약 (시뮬레이션 핵심)
    kind: Literal["pure_function", "effectful", "workflow"]
    params: list[ActionParam]      # typed (name, type, range, unit, term_ref?)
    output: ActionOutput | None    # typed
    preconditions: list[BusinessRule_fqn]
    postconditions: list[BusinessRule_fqn]
    effects: list[ActionEffect]    # creates / mutates / reads, target term

    # — 매핑 (코드 측)
    realized_by: list[CodeBinding] # METHOD fqn + scope (primary/partial)
    anchors_locked: list[AnchorRef] # 확정된 anchor (param→term, return→term, branch literal)

    # — 매뉴얼 측 연계
    parent_process: BusinessProcess_fqn | None  # 조직 허브 소속
    sourced_from_manual: list[str]              # 매뉴얼 fragment ref

    # — 워크플로우 (선택)
    sub_actions: list[Action_fqn]  # workflow 일 때만

    # — 거버넌스
    confirmed: bool                # 시뮬레이션 가능 여부 게이트
    signature_locked_at: datetime | None  # signature 확정 시각
    confirmed_by: str | None
    created_at: datetime

핵심 invariant (시뮬레이션과 직결)

  1. signature_locked_at != None 이어야 시뮬레이션 가능. signature lock = params/output/preconditions 형식 확정.
  2. kind == "pure_function" 이면 effects 가 비어 있어야 함. 있으면 의미 충돌 → kind 자동 강등.
  3. kind == "workflow" 이면 realized_by 가 비어 있고 sub_actions 가 비지 않아야 함.
  4. 한 METHOD 는 realized_by 의 primary scope 로 최대 1 개 Action 에 묶인다 (현 ConceptBindingSet 의 invariant 계승).

3.1 ActionParam — anchor 와의 연결

class ActionParam:
    name: str                  # 한국어 또는 영어
    type: ValueType            # int/float/string/bool/object_ref
    object_ref_term: str | None  # type=object_ref 시 BusinessTerm fqn
    unit: str | None
    range: list[float] | None
    nullable: bool = False
    description: str = ""

    # — anchor 연결 (시뮬레이션이 신뢰하는 부분)
    anchor_locator: str        # method body 안의 어느 anchor 인지
    confirmed: bool            # Q-C=C3 혼합 큐 결정 결과

v3 결정 Q-C=C3 혼합: formula/literal 같은 명백 패턴은 자동 confirmed, branch/lookup 같은 모호한 것만 사용자 큐. 이 분류 결과가 ActionParam.confirmed 에 박힘.

3.2 ActionEffect — diff 의 단위

class ActionEffect:
    op: Literal["create", "mutate", "read", "delete"]
    target_term: str           # BusinessTerm fqn — 무엇이 변하나
    target_attr: str | None    # term 의 어느 속성
    description: str = ""
    # 시뮬레이션 diff 출력의 단위가 됨 (안전재고.value: 100 → 142)

4. Pure Function · Effectful Action · Workflow — 3분류

이 분류가 시뮬레이션 정확도를 결정한다. simulator 가 어떤 mocking 전략으로 돌릴지 직결.

kind예시 (Java 코드)simulator 전략diff 의미
pure_function SafetyStockCalculator.compute(item, leadTime, stdev) — 입력만으로 출력 결정 RestrictedPython 직접 실행, 외부 의존 mock 없음, 결과 신뢰 output.value 변화 — 가장 정확
effectful OrderService.place(order) — DB 쓰기, 알림 발송 등 부작용 외부 호출 mock_* stub (현 PythonGenerator 가 이미 함), state delta 추적 effects[*] 별 변화 — "이렇게 변할 것" (가설적)
workflow PurchasePlanner.run() — 여러 Action 순차 호출 sub_actions 를 순차 실행, state 누적 각 step 의 effect + 최종 상태

왜 분류가 시뮬레이션 정확도와 직결인가

pure function 시뮬은 결정적 (deterministic) 결과 — 사용자에게 "이 변경 시 안전재고가 정확히 100→142 됨" 으로 자신 있게 보여줄 수 있다. effectful 시뮬은 가설적 (hypothetical) 결과 — "외부 시스템이 mock 처럼 행동한다고 가정하면 이렇게 됨". UI 가 둘을 구분 표시해야 사용자가 신뢰 수준을 안다.

현재 모델은 이 구분이 없어서 모든 시뮬 결과가 같은 무게로 보여진다. 이것이 "시뮬레이션 결과를 얼마나 믿어야 하나?" 라는 사용자 의구심의 근원.

5. Action 라이프사이클 — Discovery → 시뮬 → PR

  1. Discovery
    • 코드 측: Java parser 가 메서드 추출 → Action 후보 (kind 자동 추정 — DB/IO 호출 있으면 effectful, 없으면 pure_function)
    • 매뉴얼 측: LLM 이 "동사 같은 표현" (-하기/-계산/-처리) 추출 → Action 후보 (parent_process 에 연결)
  2. Pairing (코드 ↔ 매뉴얼)
    • 4-stage resolution (현 term_resolver 와 동일 패턴): exact → alias → embedding → LLM
    • 매칭 결과 = realized_by 채워짐
  3. Anchor binding (혼합 큐, Q-C=C3)
    • params/output 자동 매칭: 명백한 alias / literal → 자동 confirmed
    • 모호한 것: 사용자 큐 → 확정 시 ActionParam.confirmed = True
  4. Signature lock
    • 모든 ActionParam 이 confirmed → signature_locked_at 세팅
    • 이때부터 시뮬레이션 가능 (locked 안 된 Action 은 simulate 시도 시 거부)
  5. Simulation
    • ChangeSpec → target_action_fqn (or workflow_fqn) → PythonGenerator 가 lock 된 시그니처 + 변환된 body 로 함수 빌드
    • RestrictedPython 실행, effects 별 diff
  6. PR draft (Q-E=E2)
    • ChangeSpec.kind 가 Action 의 어느 슬롯에 해당? 슬롯별 Java patch 템플릿
    • 예: kind=anchor_value + target_action.params[2] → 상수 변경 patch

6. 시뮬레이션 정확도를 위한 7 설계 원칙

P1. Signature lock 게이트

Action 시그니처 (params/output/preconditions) 가 confirmed 되기 전에는 시뮬레이션 호출 거부. UX 적으로 짜증날 수 있지만 결과 신뢰를 위해 필수. "lock 안 된 Action" 큐 카드를 Workbench 우측에 노출 → 사용자가 confirm 흐름으로 자연스럽게.

P2. Anchor 는 Action 의 1급 필드

현재 anchor 는 method 옆에 floating. Action 도입 시 ActionParam 에 직접 붙는다. anchor 가 Action 슬롯 하나하나에 박혀야 ChangeSpec 이 "params[0] 의 literal 변경" 처럼 슬롯 정확히 지목 가능.

P3. Pure / Effectful / Workflow 분류 = 신뢰 등급 표기

UI 에서 시뮬 결과는 kind 별 다르게 표시 — pure 는 "확정", effectful 은 "가정 하에", workflow 는 "체인 누적". 같은 톤으로 보여주지 않는다.

P4. Action signature 변경 ≠ Action body 변경 (다른 ChangeSpec kind)

리드타임의 max range 를 60→90 으로 확대 (시그니처 변경) vs 안전재고 산식의 1.65 계수 변경 (body 변경) — 영향 범위·리스크가 다르다. ChangeSpec.kind 가 이 둘을 구분해야 함.

P5. Workflow 는 Action chain, 별도 노드 아님

"Workflow Action" 도 그냥 kind=workflow 인 Action. sub_actions 필드만 있을 뿐 모델 한 종류로 통일. 시뮬 입장에서 일관된 trigger 단위.

P6. 한국어 canonical + 영문 fqn (D1 결정 정합)

qualified_name 은 영문/dotted (search·diff·PR 메시지용), canonical_label 은 한국어 (사용자 표시·Python 변수명용). 둘 다 1급.

P7. Signature 변경은 Action 의 새 버전을 만든다

이미 시뮬·PR 만들어진 Action 의 시그니처를 깨면 과거 시뮬레이션 reproducibility 가 깨진다. signature_locked 이후 변경은 새 version 으로 fork. 과거 시뮬은 옛 version 에 pinned. (audit & reproducibility)

7. 기존 ChangeSpec 5종이 Action 모델에서 어떻게 살아남나

현 ChangeSpec.kind지금 의미Action 도입 후 의미PR 단위
rule_statement "x ≥ 10" → "x ≥ 20" Action.preconditions[i] 또는 postconditions[i] 의 statement 변경 Java if 조건 patch
rule_severity hard ↔ soft 토글 해당 BusinessRule.severity 변경 — Action 영향 분석은 derived (보통 코드 patch 없음, 정책 변경)
anchor_value literal/branch 값 변경 ActionParam[i].range 또는 body 안 literal 변경 Java 상수 patch
method_body 메서드 body 텍스트 교체 Action.realized_by 의 method body 교체 — 시그니처 유지 Java method body patch
term_binding term ↔ code 매핑 추가/제거 ActionParam.object_ref_term 변경 또는 ActionEffect.target_term 변경 (코드 patch 없음, 매핑만)
ChangeSpec 모델은 그대로 유지해도 된다. 단 target_method_fqn → target_action_fqn 으로 바뀌고, payload 안에 "Action 의 어느 슬롯" (precondition[2], params[0].range, effects[1].target_term) 을 명시하면 됨. 마이그레이션은 method → action 1:1 매핑만 처리하면 무 손실.

Q1 Action vs Function 분리 채택?

팔란티어는 Action(거버넌스 wrapper) 과 Function(순수 계산) 을 분리한다. 우리 시뮬레이션 입장에서 pure function 은 결정적 시뮬이 가능해 정확도가 다르다. 분리할 것인가?

Q2 Action ↔ Method 카디널리티

하나의 Java 메서드는 하나의 Action 에 대응? 아니면 한 Action 이 여러 메서드 (오버로드/언어별 구현) 를 가질 수 있나?

Q3 Action ↔ Process(매뉴얼 동사) 관계

현 schema.Process(매뉴얼-도출, IO+formula+rules) 와 새 Action 의 관계. Process 가 거의 Action 시그니처라 자원 중복 가능성.

Q4 Anchor 부착 위치

7종 anchor (param/local/return/branch/literal/field/field_access) 를 Action 모델 어디에 박을 것인가? 시뮬레이션이 정확하려면 ChangeSpec 이 anchor 슬롯을 정확히 지목해야 함.

Q5 precondition/postcondition 출처

Action 의 pre/post condition 은 어디서 오나? 코드 본체의 가드 (early return / throw) 자동 추출? 매뉴얼 명시? 둘 다?

Q6 Action naming convention

한국어 변수 사용 결정 (D1) 정합. 사용자가 표시·검색에 무엇을 보나?

Q7 Workflow 표현

"발주 cycle 전체 시뮬" 같은 multi-step. 별도 Workflow 노드 신설? Action 자체에 sub_actions 필드?

Q8 Signature lock 게이트 적용 강도

P1 원칙: lock 안 된 Action 은 시뮬 거부? 사용자 UX 와 정확도 트레이드오프.

Q9 Action 의 effects 표현 깊이

diff 의 단위가 됨. "안전재고.value: 100→142" 정도까지 정형화? 자연어로?
