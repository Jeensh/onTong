1. v1 → v2 정정 — 사용자 지적 3 가지

합의 #1 — 샌드박스는 온톨로지 기반 Python 생성 + 실행
"샌드박스 시뮬레이션은 우리 설계하면서 영향 범위에 대한 온톨로지를 확인하고 소스를 직접 만들어서 실행까지 해보는 걸로 확인했던 것 같은데. 맞지?" / "시뮬레이션 코드는 꼭 자바가 아닌 파이썬이어도 괜찮지 않을까?"
v1 잘못
제안
Docker + mvn test (Java 빌드)
왜 틀림
합의는 ontology → Python 동등 함수 생성 → Python 실행. Java 빌드는 무겁고 LLM patch fragile. 사용자가 Python 으로 충분하다고 명시.
v2
Python equivalent 함수를 ontology 에서 LLM 생성 → subprocess 또는 RestrictedPython 으로 격리 실행 → output diff. §5 참고.
합의 #2 — 코드가 ground truth, Javadoc/매뉴얼이 아님
"자바doc같은걸 주요 지표로 왜 삼는거야 레거시 시스템은 그런게 제대로 안되어있는 것들 천지인데, 실제 소스 내용을 기반으로 가야지" / 이전 세션 summary: "integrate it properly with code as ground truth (not docs)"
v1 잘못
제안
BusinessRule 시드 = `seed_rules_from_repo` 가 Javadoc 텍스트 추출
왜 틀림
레거시 Javadoc 은 부재/거짓. slab-design-real 도 일부 Javadoc 만 있고 진짜 비즈니스 룰은 method body 의 if 조건/literal/throw 에 있음.
v2
Rule 추출은 method body AST 에서. if/else 조건 → guard rule, literal → constant rule, throw → exception rule, 비교 연산 → bound rule. Javadoc 은 부차 신호. §6 참고.
합의 #3 — 메서드 단위 매핑은 필드만 아니라 method body 변수/로직까지
"메서드 단위까지 일단 어떻게 메뉴얼과 매핑이 되는지 명확히 내가 이해를 못하겠고, 내가 생각하기에 샌드박스 시뮬레이션 까지 가려면 필드뿐만 아니라 메서드 내에 변수나 로직도 잘 매핑할 수 있는 방법이 필요할 것 같은데"
v1 잘못
제안
BusinessTerm ↔ field/column 만 매핑 (alias 매핑 위주)
왜 틀림
method body 안의 local variable, 분기 조건, literal, return value 매핑 없으면 Python 함수 재구성 불가. 시뮬레이션의 본질이 빠짐.
v2
매핑 anchor 6 종으로 확장 — field / param / local / return / branch / literal. §3 참고.

2. 잊지 않았던 기존 설계 — round1 메서드 노드 (§6)

이미 round1 합의 시점에 메서드 노드는 body-level 정보를 담을 자리를 미리 잡아뒀습니다. v1 제안에서 이걸 활용 안 했던 게 실수.

field-to-field 엣지 (round1-code-schema §6-B-1, 미구현):

  • DERIVES_FROM — FIELD → FIELD, "A 값이 B 로부터 계산됨" + via_methods 로 어느 메서드가 carry 했는지
  • PROPAGATES_TO — FIELD → FIELD, "A 가 B 로 그대로 복사" + via_methods
v2 의 핵심 출발점 — 위 6 개 미구현 자리 (precondition/postcondition/input_domain/value_flow/DERIVES_FROM/PROPAGATES_TO) 를 채워야 시뮬레이션 가능. 이게 P13~P15 의 backbone.

3. 메서드 단위 매핑이 무엇인지 — anchor 6 종

BusinessTerm / BusinessRule 이 method 의 어디에 붙는지 6 종 anchor 를 정의합니다. 한 메서드에 여러 anchor 가 동시에 붙을 수 있음.

field
기존 (alias 매핑)
클래스 필드 / DB 컬럼. 예: SlabDesignHistJpo.slabNo (col=SLAB_NO) ↔ term.슬래브번호
현재 ConceptBinding (REALIZES) 가 이 anchor 만 다룸. 70% 구현됨.
param 신규
메서드 파라미터. 예: findGroup(BigDecimal hrTgtWidth) 의 hrTgtWidth ↔ term.열연타겟폭
시뮬레이션 시 param 별로 입력값을 무엇으로 넣을지 결정 (input_domain).
local 신규
메서드 본문 안의 지역 변수. 예: BigDecimal slabLengthLow = max(slabWgt / (widthHigh * thickness * gravity), primaryLengthLow) 의 slabLengthLow ↔ term.슬래브길이하한
value_flow 로 추출. 이 변수가 어떤 도메인 개념을 들고 있는지 사람이 확정.
return 신규
메서드 반환값. 예: SdProductivityStdEntity 반환 ↔ term.생산성기준
시뮬레이션 output 의 의미 검증에 사용.
branch 신규
if / else / switch / when / case 조건. 예: if (hrTgtWidth.compareTo(HR_TGT_WIDTH_LOW) >= 0 && hrTgtWidth.compareTo(HR_TGT_WIDTH_HIGH) <= 0) ↔ rule.HR타겟폭_범위검증
조건식 자체가 BusinessRule 의 statement. AST sub-tree 가 rule body. 시뮬레이션 시 이 조건을 변경하면 영향 명확.
literal 신규
method body 안의 literal 상수. 예: 0.95 (안전계수) / "^[A-Z0-9]{4}$" (품종코드 정규식) / 240 (최대 두께)
매직 넘버가 도메인 의미를 가짐. literal ↔ rule.안전계수 / rule.품종코드포맷 매핑. ChangeSpec 의 가장 흔한 변경 단위.

매핑 데이터 모델 (신규)

class MethodAnchor:
    method_fqn: str          # com.example...EdgingService.findGroup
    kind: AnchorKind         # field | param | local | return | branch | literal
    locator: str             # "param[0]" | "local[slabLengthLow]" | "branch[if-line:42]" | "literal[0.95@line:78]"
    ast_path: str            # JSON path within method AST (precise pointer)
    source_snippet: str      # 추출된 텍스트 (사용자 검토용)

class TermBinding:           # 기존 ConceptBinding 확장
    term_fqn: str
    anchor: MethodAnchor     # 또는 기존 code_fqn (field 만)
    confidence: float
    source: BindingSource    # manual | name_match | embedding | llm | body_analysis
    confirmed: bool

class RuleBinding:
    rule_fqn: str
    anchor: MethodAnchor     # branch / literal / 메서드 전체
    statement_ast: dict      # AST sub-tree (시뮬레이션 시 patch 대상)
    extracted_constant: str  # literal 일 때 값
    confirmed: bool

4. 실제 예시 — slab demo 의 한 메서드 → 매뉴얼 → Python

slab-design-real 의 실제 메서드 하나를 가지고 anchor 매핑 → Python 생성 까지 보여줍니다.

4-A. 원본 Java 메서드

// 파일: SdFinalLengthRangeAction.java
public LengthRange computeFinalLength(
    BigDecimal slabWgt,
    BigDecimal widthLow, BigDecimal widthHigh,
    BigDecimal thickness, BigDecimal gravity,
    BigDecimal primaryLengthLow, BigDecimal primaryLengthHigh
) {
    // rule1 — 길이 하한
    BigDecimal slabLengthLow = max(
        slabWgt.divide(widthHigh.multiply(thickness).multiply(gravity), 4, HALF_UP),
        primaryLengthLow
    );
    // rule2 — 길이 상한
    BigDecimal slabLengthHigh = min(
        slabWgt.divide(widthLow.multiply(thickness).multiply(gravity), 4, HALF_UP),
        primaryLengthHigh
    );
    if (slabLengthLow.compareTo(slabLengthHigh) > 0) {
        throw new ValidationException("DG107");
    }
    return new LengthRange(slabLengthLow, slabLengthHigh);
}

4-C. 매뉴얼 fragment 와의 연결 — 메서드 ↔ 매뉴얼 매핑이 어떻게 성립하나

핵심은 전이적 (transitive) 링크 입니다 : method anchor → BusinessTerm/Rule → ManualFragment. 직접 메서드 ↔ 매뉴얼 link 는 없고, 중간에 ontology 가 다리.

매뉴얼 (사람이 작성, slab-design.md 일부)

# 슬래브 길이 산식

<!-- ontong: rule=rule.SlabFinalLengthRange.formula -->
슬래브 길이 하한은 슬래브 단중을 (슬래브 폭 상한 × 두께 × 비중) 으로 나눈 값과
1차 길이 하한 중 큰 값. 길이 상한은 그 반대.

<!-- ontong: rule=rule.슬래브길이_상하한일관성 -->
산출된 길이 하한이 상한보다 크면 입력 오류. 오류코드 DG107 으로 차단.

<!-- ontong: term=term.슬래브단중 -->
슬래브 1 본의 무게. kg 단위. 발주 단계에서 결정되며 변경 불가.

<!-- ontong: term=term.비중 -->
강종별 무게/부피 비. 슬래브 길이 산식에서 분모로 들어감.

매뉴얼 → ontology → method 연결 결과

매뉴얼 fragmentdirectivemethod anchor 까지 도달
"슬래브 길이 하한은 ..." 단락 rule=rule.SlabFinalLengthRange.formula → SdFinalLengthRangeAction.computeFinalLength 메서드 전체 (formula rule)
"산출된 길이 하한이 상한보다 크면..." 단락 rule=rule.슬래브길이_상하한일관성 → 같은 메서드의 branch[if@line:14] anchor
"슬래브 1본의 무게..." 단락 term=term.슬래브단중 → 같은 메서드의 param[slabWgt] anchor + SlabOrderJpo.slabWgt field anchor
"강종별 무게/부피 비..." 단락 term=term.비중 → param[gravity] + SpecificGravityProvider.get 메서드 return anchor

UI 에서의 사용 예 :

  • 역탐색 — "슬래브 단중" 검색 → ontology 에서 term.슬래브단중 → 4 개 anchor (param, field, manual fragment, ConceptBinding) 모두 표시.
  • 매뉴얼 작성 탭 — 「rule directive 삽입」 클릭 → 추출된 BusinessRule 리스트 (rule.SlabFinalLengthRange.formula 등) → 선택 시 매뉴얼에 directive 자동 삽입 + 사용자가 그 rule 의 한국어 설명 작성.
  • 갭 큐 → 매뉴얼이 가리키는 rule 이 method body 와 일관 안하면 (예: 매뉴얼이 "두께 ≥ 200" 인데 코드가 "≥ 250") conflict 자동 검출.
왜 directive 가 method body anchor 까지 가는가 — directive 자체는 rule=<rule_fqn> 만 가리킵니다. 하지만 그 rule 이 추출된 출처는 method body AST 의 특정 anchor (branch / literal / formula expression). ontology 가 두 개를 묶고 있으니, 매뉴얼 → rule → anchor → method 까지 자동으로 navigable. 사용자는 매뉴얼 한 단락에서 「코드 위치 보기」 버튼만 눌러도 method body 의 정확한 line 까지 점프 가능.

5. Python Sandbox 시뮬레이션 흐름 (Docker 아님)

1
ChangeSpec 입력
예시 — kind=literal_change, target=literal["DG107"@SlabRule.line:15] 변경 또는 kind=branch_condition, target=branch[if@SlabRule.line:14], after="lengthLow ≥ lengthHigh" (≥ 로 변경, edge case 허용).
↓
2
Multi-Layer ImpactPropagator (4 layer BFS)
영향받는 메서드/룰/터미/매뉴얼 식별 — 이전 v1 §3 와 동일 구조, 단 anchor 단위까지 정밀.
↓
3
PythonGenerator — ontology → Python 함수
영향받는 메서드 N개 의 anchor 매핑 + body AST + ChangeSpec patch 를 prompt 로 LLM 호출 → 영향받는 모든 메서드의 Python 동등 함수 생성. 변수명 한국어 (BusinessTerm). ChangeSpec 이 적용된 버전 + before 버전 둘 다 생성.
↓
4
SyntheticInputGenerator — input_domain 활용
각 param 의 input_domain 또는 BusinessTerm 의 typical value range 에서 N 개 input 샘플 생성. 예: 슬래브단중 = [10000, 20000, 50000, 100000], 슬래브두께 = [200, 230, 280]. edge case (min/max/0/null) 자동 추가.
↓
5
SandboxRunner — Python subprocess 격리 실행
data/simulations/{run_id}/before.py + after.py + inputs.json → subprocess (timeout 5s, no network, no fs write 외) 또는 RestrictedPython. 각 input 별로 before(input) 와 after(input) 의 output 캡처. 예외 발생 여부도 캡처.
↓
6
DiffReporter — 도메인어로 차이 보고
• 같은 input 에서 before/after output 차이 (예: 슬래브길이하한: 850 → 845)
• 새로 발생하는 예외 / 사라진 예외 (예: DG107 throw 사례 5건 → 3건)
• 매뉴얼 stale 항목 (해당 rule binding 이 가리키던 fragment 가 더 이상 정확하지 않음)
• 영향받는 다른 rule (rule graph BFS 결과) 의 시뮬레이션도 동시 실행 (chain effect)
↓
7
Apply / Discard — 사용자 결정
• Apply → ontology 갱신 (rule statement / literal 변경 commit) + 매뉴얼 stale 항목은 갭 큐로 자동 추가 + Java 코드 patch 제안 PR 옵션
• Discard → simulation_run audit log 만 보존
왜 Python 으로 충분한가 — 비즈니스 규칙은 본질적으로 "입력 → 조건 → 계산 → 출력". Java 로 표현된 것은 framework / DI / DB 같은 인프라 + 비즈니스 로직. 시뮬레이션이 알고 싶은 건 비즈니스 로직만 이라 인프라를 stripping 한 Python 함수면 충분. Java 빌드 비용 없이 100배 빠름.

6. BusinessRule 추출 — Javadoc 아님, body 분석

현재 seed_rules_from_repo 는 Javadoc 텍스트만 보고 있음. 정정:

Rule 종류추출 위치예시
guard rule method 시작부 if/throw 패턴, validate-prefix 메서드 호출 if (productCode == null) throw IllegalArgumentException("...") → rule.품종코드_null검증
bound rule 비교 연산 (<, >, ≤, ≥) + literal if (thickness < 200 || thickness > 280) → rule.두께범위_200_280
formula rule 대입문의 RHS (산술 expression) length = wgt / (width * thickness * gravity) → rule.슬래브길이산식
enum rule switch / equals / contains literal 집합 plantCd.equals("HR1") || plantCd.equals("HR2") → rule.유효열연공장_HR1_HR2
regex rule Pattern.compile / matches 호출 "^[A-Z0-9]{4}$" → rule.품종코드_4자리포맷
throw rule throw 문 + 에러코드 literal throw new ValidationException("DG107") → rule.오류_DG107
lookup rule JPA findBy / native query + 비교 식 findByThicknessLessThanEqual + WIDTH_LOW ≤ x AND WIDTH_HIGH ≥ x → rule.HR타겟폭_lookup
(부차) javadoc rule Javadoc 의 한국어 설명 + LLM 위 7 종을 사람이 검토할 때 보조 신호로만
Body 분석 방법 — tree-sitter 로 method body AST 추출 후 visitor 패턴. 각 visitor 는 위 7 종 중 하나를 찾아 RuleBinding 후보 생성. confidence 는 패턴 명확성에 따라. 사람이 「rule 검토」 탭에서 일괄 확정.

7. 정정된 4-Layer 아키텍처

v1 의 4 layer 구조는 유지하되, method anchor 를 1급 시민으로 추가.

Layer노드엣지 (intra)cross-layer 연결
Code Class / Method / Field / MethodAnchor (param/local/return/branch/literal) CALLS / READS / WRITES / DERIVES_FROM / PROPAGATES_TO (with via_methods) ↓ binds to Term/Rule
Term BusinessTerm + alias IS_A / PART_OF / EQUIVALENT / RELATED ↑ TermBinding(anchor) → Code anchor
Rule BusinessRule (with statement_ast) + 7 종 분류 DERIVES_FROM / CONFLICTS / REFERENCES / SUPERSEDES / APPLIES_TO_TERMS ↑ RuleBinding(anchor) → Code anchor (branch/literal/method)
Manual ManualDocument / Section / Fragment — ↑ DescribedInBinding → Term/Rule
