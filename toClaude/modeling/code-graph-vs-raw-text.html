Authoring vs Code Graph — 현재 한계 + 개선안

2026-05-05 · 사용자 우려: "레거시는 자바독·주석 부족인데 AST 그래프 활용 안 하면 quality 어떡함?"
사용자 질문 (정확):
"Authoring 에서 코드 추출하면, 우리가 기존에 AST 트리 만들어 놓은 것들, 즉 코드 그래프를 타고 연관관계를 잘 분석하는거야? 레거시 소스는 자바독이나 주석이 제대로 적혀있지 않은 것이 대부분이라 걱정."

§1. 솔직한 진단 — 현재 cap 1 은 raw Java text 만 봄

현재 상태 (코드 확인): 
// backend/application/authoring/capabilities/code_extractor.py
async def extract_jpo_from_file(
    path: str,
    content: str,                  # ← Java raw text 그대로
    ...
):
    user_prompt = (
        f"File: {path}\n\n"
        "```java\n"
        f"{content.rstrip()}\n"     # ← 이거 + system prompt 만 LLM 에 보냄
        "```\n"
    )

cap 1 은 Java 파일 텍스트 1개만 Sonnet 에 통째로 넣음. onTong 이 미리 추출해둔 CodeType / CodeMethod / CodeField / inheritance_edges / 호출 관계 등 AST 그래프 정보 모두 미활용.

onTong 이 이미 가지고 있지만 안 쓰는 정보

테이블내용현재 활용?
code_typesclass fqn / extends / implements / annotations / role❌
code_methodsmethod 시그니처 / return / params / body fragments / line range❌
code_fieldsfield name / type / annotations❌ (LLM 이 텍스트에서 직접 추출)
inheritance_edgesextends / implements 그래프❌

§2. 사용자 우려가 정확한 이유 — 실제 영향

현재 (raw text only)

예: HrSpecJpo 인터뷰 시 LLM 이 보는 것:

@Entity
@Table(name = "HR_SPEC")
public class HrSpecJpo {
  @Id @Column(...) String cmpCd;
  @Column(...) BigDecimal widthLow;
  ...
}

→ JPO 1개의 자체 정보만. "이걸 누가 사용하나? 어디서 호출되나? 다른 entity 와 어떻게 연결되나?" 모름.

레거시에서 주석마저 부족하면 LLM 은 정말 단순 column 명만 보고 추측.

개선 후 (graph context)

LLM 이 봐야 할 것:

// JPO 자체
HrSpecJpo + Java text + 한국어 주석

// + 그래프 컨텍스트
extends:    BaseJpo
PK class:   HrSpecPK (4 fields)
호출자:     HrSpecRepository.findById
            HrSpecService.lookup(cmpCd, orgCd, ...)
사용처:     SdWidthRangeAction.execute()
            SdLengthRangeAction.execute()
호출 패턴:  Service.lookup → Action 의 step 2/3
형제 JPO:   HrMaxWgtJpo (HR_CD 같은 의미)
            HrMinWgtJpo

→ 도메인 추론 가능: "HrSpec 이 폭/길이 step 의 룩업 표 — 즉 표준 데이터"

§3. 개선 옵션 (3 단계)

★ 옵션 G1 — 인접 metadata 자동 첨부 (작은 작업, 즉시 효과)

cap 1 backend 가 fqn 받을 때 자동으로 다음 정보를 추출해서 prompt 에 추가:

  • 이 class 의 extends / implements (parent class 의 fqn)
  • 이 class 를 사용하는 다른 class 의 fqn list (max ~10)
  • 이 class 의 method 시그니처 (전체 body 아닌 시그니처만)
  • 형제 class (같은 패키지의 비슷한 이름)
  • 관련된 PK class (HrSpecPK 같은) 의 field 정보

예상 비용 증가: token ~30% ↑ ($0.025/call → $0.033/call). quality ↑↑↑.

옵션 G2 — 호출 그래프 traversal (중간 작업)

G1 + 호출 관계까지 1-hop traverse:

  • HrSpecRepository.findById ← HrSpecService.lookup ← SdWidthRangeAction.execute
  • 각 hop 의 method 시그니처 + 핵심 fragment (if/return) 발췌

cap 1 이 entity 1개 추출해도 도메인 호출 패턴까지 함께 — Action 작성 시 큰 도움.

옵션 G3 — 다중 파일 인터뷰 (큰 작업)

단일 JPO 가 아닌 관련 파일들 묶어서 한 번에 인터뷰:

  • JPO + PK class + Service + Action 4-5 파일을 한 prompt 에
  • cap 1 이 entity 1개 + 관련 Action 후보까지 동시 추출
  • 도메인 인터뷰가 1 turn 으로 묶임

비용 ↑↑ (token large), 시간 ↑. 하지만 도메인 정확도 최고.

§4. 추천 — 옵션 G1 즉시 적용

이유:
  1. onTong 이 이미 모든 metadata 를 DB 에 가지고 있음 (extra import 없음)
  2. backend SQL 쿼리 1~2회 추가 + prompt 에 inject 만 하면 됨 — ~30분 작업
  3. token 비용 +30% 정도. quality 는 도메인 인터뷰의 시작점이 자체적으로 의미 있어짐
  4. 레거시 시 주석 부족 시 가장 강한 hint 가 "이 class 가 어디서 호출되나"

구체 변경 사항 (G1 구현 시)

변경위치

§5. Round 5 와의 비교 (사용자 협업 시 우리가 한 일)

Round 5 에서 우리는 어떻게 했나?
  • HrSpecJpo 한 개만 보지 않았음. 사용자가 SdWidthRangeAction, HrSpecService, HrSpecPK 등 호출 chain 을 같이 봐가며 인터뷰
  • "EDGING_SPEC.PK 에 HR_PLANT_CD 누락" 발견은 EDGING_SPEC + EDGING_GROUP + SdWidthRangeAction 다 봐서 가능했음 — 단일 JPO 만 봤다면 갭 못 발견
  • 즉 우리 협업의 quality 는 multi-file context 에서 나온 것

현재 cap 1 + cap 2 는 단일 JPO 만 봐서 Round 5 의 quality 를 재현하기 어려움 — 사용자 우려 정확.
