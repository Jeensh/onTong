1. 한 페이지 요약

핵심 발견
  • Foundry Ontology 는 우리에 가장 가까운 prior art. ObjectType/ActionType/LinkType/FunctionType 4-종 모델이 우리 BusinessTerm/Action/TypeRealization/Realization 과 직접 매핑.
  • 우리가 더 발전된 영역 3종: ① TypeRealization.scope=PARTIAL (1 entity ⊃ N sub-term), ② Realization.dispatch_source 9-enum + AnchorBinding fragment-level (Foundry 는 코드 layer 자체 없음), ③ VerificationLevel 6단계 (SemVer 와 직교).
  • 우리 약점 = "그래프 못 그린다" 가 아니라 "작업 환경으로서 graph 가 빈약". 알고리즘은 동등, lens/state/detail context/compound expand/hover preview 5 종 부재.
  • 차용 필수 top 3: ① Schema migration framework (Foundry 의 8-option 우리에 매핑), ② Action SemVer + 자동 호환성 검사, ③ Action description → LLM tool spec 자동 변환.
  • 차용 필수 UX 3 묶음: ① Bottom preview panel + right-click menu (Quiver/Lineage 패턴), ② Perspective (Bloom 의 named view, 우리도 backend 1급), ③ Compound expand-in-place (cytoscape + ELK).

2. 왜 Palantir 가 1순위 reference 인가

Foundry Ontology 는 onTong 비전과 가장 가까운 상용 product. 매핑이 직접:

Action TypeAction (kind=pure_function/effectful/workflow)Foundry 는 pure 만 Function 별도 type
Link TypeInheritance + Composition + TypeRealization + Realization (4종)우리 분해도 더 세분

다른 reference (Backstage, Sourcegraph, Atlas, Bloom, Linkurious, Cytoscape) 는 부분 prior art 로 Stage 3 의 graph viz 비교에서 추가로 활용. 그러나 schema 모델 비교는 Foundry 가 압도적으로 가까움.

3. Stage 1 — Sweep 결과 요약

40 sources 인덱싱 (24 직접 fetch + 12 검색 발췌 + 4 Medium 인증 차단). 7 영역별 raw 노트.

단단히 답해진 영역

  • Object Type 의 모든 facet (Reserved name 9개)
  • Base property type 21종 카탈로그
  • Property kind 8종 (regular/derived/edit-only/required/shared/title key/primary key/mandatory control)
  • Link cardinality × backing 매트릭스 (1-1/1-many/many-many × FK/Join/Backing Object)
  • Action 5 facet + scale 한계 (50 types, 10K objects, 32KB/3MB edits)
  • Function 의 3 edit decorator 패턴 (TS v1/v2/Python)
  • AIP Logic block 6종 + tool 4종, AIP Agent tool 6종
  • Branching 5 stage + Proposal=PR
  • OSv2 architecture (Funnel + OSS, "tens of billions of objects per type", 2000 props/type)

의외 발견 (우리 가정 흔드는 것)

발견우리 영향
Property mapping 에 confidence 없음 — Foundry 는 binary (mapped/unmapped)우리 PRIMARY/PARTIAL + confidence 가 더 발전 가능성. 차별 강점.
Submission Criteria 표현력 제한 — attachment / object set 은 validation 불가. 단순 conditions+operators tree우리 BusinessRule.statement free-text 더 유연 (단 trade-off: machine-checkable X)
LLM 보안 — invoking user permission우리 ACL 방향과 동일 — 안심
Many-many link table 이 linear cost우리 Action.realizations 다대다 모델링 비용 인지
Merge 가 transactional history 보존 안 함Git mental model 과 다름. 우리 ontology branching 설계 시 명심

4. Stage 2 — Schema 비교 결과

11 섹션 side-by-side 표 (~480 줄, palantir-schema-vs-ontong.md). 5 의문점 중 3 개 완전, 2 개 부분 답.

5 의문점 처리

#의문결과
1Interface property declaration 가능?완전 local + shared property, required/optional, multi-impl + chaining
2AIP Agent tool description mechanics부분 "system prompt 로 compile" 까지만 docs. 자동/수동 mechanics 미공개
3Action lifecycle / versioning부분 Function 만 SemVer + immutable + range pin 확인. Action 자체 versioning 미언급
4Schema evolution / migration완전 OSv2 의 8종 predefined migration option (drop/move/cast × property/struct + revert)
5Multi-source conflict 처리완전 column-wise MDO 만, property multiplicity 금지, Always-Apply / Timestamp 2 strategy

차용 필수 Top 3 (Schema)

  1. Schema migration framework — Foundry 의 8-option set 을 Java refactoring → ontology 맥락에 매핑. 가장 큰 빈 영역. 다음 phase 우선.
  2. Action SemVer + 자동 호환성 검사 — Function versioning 메커니즘을 Action 에. param 추가/output type 변경 자동 경고.
  3. Action description → LLM tool spec 자동 변환 — Pydantic Action schema → JSON Schema → Anthropic tool spec. 비용 낮고 효과 큼. A2 Simulation Agent 의 입력.

우리만의 강점 (Schema 차원)

차별 강점 ★
  • TypeRealization.scope = PARTIAL (1 클래스 → N sub-term 부분 매핑). slab-design SDOrderEntity ⊃ {OS, OM, Chemical, QD} 시나리오는 Foundry MDO 로 표현 불가 — multiplicity 금지가 정반대 방향.
  • Realization.dispatch_source 9-enum + AnchorBinding fragment-level path. Foundry 는 코드 layer 자체가 없어 비교 불가 영역.
  • VerificationLevel 6단계 신뢰도 axis. Foundry SemVer 는 release axis 라 직교. 양립 가능.
