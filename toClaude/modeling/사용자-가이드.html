onTong 모델링 — 사용자 워크플로우 가이드 v2 / 2026-04-25 (P1~P5 반영)

레거시 Spring/JPA 코드와 회사 업무처리기준서를 한 몸에 묶는 도구. 이 가이드는 "신선한 사용자"가 처음 onTong 모델링 섹션을 켰을 때 무엇부터 해야 하는지, 그리고 지금 어디까지 가능하고 어디서 막히는지를 정리합니다.

v2 변경 — 사용자 답변 (2026-04-25) 에 기반한 5 개 작업 (P1~P5) 모두 완료. cold-start → 데모 로드 → 코드 분석 → 코드 옆 매뉴얼 작성 → LLM 용어 추천 → 매핑 → 갭 큐 → 역탐색 까지 풀 사이클 가능.

1. 왜 이게 필요한가

문제 — 30년 운영된 SCM 시스템에서 다음이 매일 일어난다.

  • 도메인 전문가가 떠나고, 후임은 코드를 봐도 비즈니스 의미를 모름.
  • 업무처리기준서(PDF/DOCX)와 실제 코드 동작이 어긋나 있는데 아무도 모름.
  • a1, i 같은 의미 모를 필드가 핵심 비즈니스 로직에 박혀 있음.
  • "이 컬럼 바꾸면 어디 영향?" 질문에 답하려면 사람이 grep 노가다.

onTong 의 가설 — 코드 그래프 + 도메인 용어 + 기준서를 같은 그래프에 정렬해 두면, 위 네 가지가 모두 자동/반자동으로 풀린다.

2. 기준 시나리오 — 신선한 사용자

입력상태
레거시 Spring/JPA 코드이미 등록 완료 (예: slab-design-engine)
회사 업무처리기준서 PDF/DOCX아직 없음 (또는 곧 업로드 예정)
BusinessTerm 도메인 용어0 개 — 사람 머릿속에만 있음
매핑 / 갭0 개

이 상태에서 사용자가 첫 화면에서 보는 것은 사이드바 8 탭 — Repository · 기준서 · 매뉴얼 작성 · 용어 매핑 · 갭 큐 · 역탐색 · 영향 분석 · DI 그래프 — 그리고 사이드바 하단의 「데모 데이터 로드 / 전체 초기화」 버튼입니다. "여기서 뭐부터 하라는 건지 모르겠다"가 정직한 첫 반응이라, 본 가이드는 그 막막함을 단계별로 풉니다.

3. 정규 워크플로우 (지금 있는 기능 기준)

이 흐름은 사용자 답변에 기반합니다 — "코드 탐색 우선 → 분석된 코드를 보면서 매뉴얼을 작성 → LLM 이 후보를 추천 → 사용자가 확정".

필수Phase 0 — 시작 상태 결정 (cold start vs 데모 로드)
탭 사이드바 하단 소요 5초

backend 부팅 시 아무 시드도 깔리지 않습니다 (P1 완료, 2026-04-25). 매뉴얼 0건 / BusinessTerm 0건 / 매핑 0건의 cold start 가 default.

사이드바 하단 — 「데모 데이터 로드」 버튼 (cold-start 일 때만 활성): 클릭하면 slab demo 매뉴얼 2건 + BusinessTerm 2건 (품종코드 / 열연공장코드) + auto-link DescribedInBinding 이 한 번에 적재됩니다. 「전체 초기화」 버튼은 매뉴얼/용어/매핑/갭 모두 비웁니다 (사용자 입력 포함, confirm 다이얼로그).

실 사용자는 데모 로드 클릭 없이 Phase 1 로 진행. 시연 / QA 때만 데모 로드.

필수Phase 1 — Repository 등록 + 코드 분석
탭 Repository 소요 1~5 분 (코드 크기 따라)
  1. Repository 탭 → 「+ 등록」 → 로컬 경로 입력 (예: ~/workspace/sample-repos/slab-design-real).
  2. 등록되면 12 개 analyzer 가 SSE 스트림으로 진행률을 보냅니다 (Spring Bean / JPA / DI / Rule 등).
  3. 완료되면 사이드바에 "선택된 Repository" 가 채워지고, DI 그래프 / 영향분석 / 역탐색 등 모든 후속 기능이 활성화됩니다.

검증

  • DI 그래프 탭에 들어가 bean 노드가 보이면 파싱 성공.
  • 없으면 사이드바에서 다른 repo 를 선택하거나, 분석 로그를 확인.
필수Phase 2 — 코드 탐색 (매뉴얼이 0 개여도 가능)
탭 DI 그래프 · 영향 분석 · Repository 소요 30 분 ~ 며칠

이 단계의 목적은 사용자가 코드 구조를 머릿속에 그리는 것이며, 동시에 "여기는 매뉴얼이 필요하다" 는 직감을 모으는 것입니다.

  1. DI 그래프 — Spring bean 의존 그래프. 시스템 전체 구조 한눈에 본다. 클릭으로 노드 선택, 연결 관계 추적.
  2. 영향 분석 — 클래스/메서드 FQN 입력 → 호출자/피호출자 BFS. "이 메서드 바꾸면 누가 영향?" 답변용.
  3. Repository 검색 — Repository 탭 안의 검색 박스로 클래스/메서드명 키워드로 위치 찾기.

이 단계가 끝나면 사용자는 다음 두 가지를 결정해야 합니다.

  • (A) 어느 영역(패키지/클래스)에 매뉴얼을 먼저 쓸 것인가?
  • (B) 어떤 도메인 용어가 코드에 등장하는가? (예: productCode, shipDate, rolledMillCode)
권장Phase 3 — 매뉴얼 등록 / 작성
탭 기준서 · 매뉴얼 작성 소요 매뉴얼 1 건당 1~30 분

3-A. 외부 매뉴얼이 이미 있을 때 (PDF / DOCX / PPTX / 이미지)

  1. 「기준서」 탭 → 파일 드래그 → 파싱 → ManualDocument / Section / Fragment 자동 생성.
  2. 파싱 결과는 검색 가능. BusinessTerm 자동 추출은 Phase 4 (AI 추천) 에서 한 번에 처리.

3-B. 우리 앱 안에서 매뉴얼을 새로 작성 (P5 완료, 2026-04-25)

「매뉴얼 작성」 탭 — 3분할 split-view :

  • 좌측 — 코드 엔티티 검색 (메서드/필드/클래스 필터) + 등록된 BusinessTerm 검색. hover 시 「+」 버튼으로 ontong directive 가 에디터 끝에 자동 삽입.
  • 중앙 — Markdown textarea + 표/코드펜스 템플릿 삽입 버튼.
  • 우측 — react-markdown 미리보기 (GFM 표 / 코드 하이라이트).

헤더의 「저장 + 인제스트」 클릭 → backend 가 data/manual_writes/{repo_id}/{filename}.md 로 디스크 저장 + 매뉴얼 파이프라인 자동 실행 → ManualRegistry 에 즉시 등록. 같은 파일명을 다시 저장하면 force 모드로 재파싱 (편집 → 저장 → 편집 루프 가능).

3-C. Structured Manual directive 문법

「기준서」 탭 상단의 호박색 가이드 패널 (P2 완료) 에 문법 + 예시 + 「복사」 버튼이 노출됩니다. auto-linker 가 directive 를 만나면 임베딩 매칭을 우회하고 confidence = 1.0 binding 을 만듭니다.

# 슬라브 발주 규칙

<!-- ontong: term=term.품종코드 -->
품종코드는 4자리 영문+숫자 조합이며, 첫 글자가 'S'면 강재.

<!-- ontong: rule=engine.SlabRule.validateProductCode -->
품종코드 검증은 정규식 `^[A-Z0-9]{4}$` 로 수행.

지원 키 — term=<BusinessTerm.qualified_name> / rule=<BusinessRule.qualified_name>. 이 directive 가 등장한 다음 단락 / 코드펜스 / 표가 binding 의 타겟 fragment 가 됩니다. Markdown(.md) 만 인식. PDF/DOCX 는 인식하지 않습니다.

필수Phase 4 — BusinessTerm 등록 (직접 입력 + AI 추천)
탭 용어 매핑 소요 직접 입력 30초/건, AI 추천은 한 번에 30개

4-A. 직접 입력

  1. 「용어 매핑」 탭 → 좌측 「+ 새 용어」.
  2. 이름 / alias / 정의 입력. 예: 품종코드, alias productCode, prodCd, 정의 "강재의 품종을 4자리 영문숫자로 표기한 코드".
  3. 저장하면 즉시 자동 매핑 후보 (TermResolver 4-stage) 가 우측 패널에 뜸.

4-B. 「AI 추천」 — LLM 일괄 추출 (P3+P4 완료, 2026-04-25)

「용어 매핑」 탭 좌측 헤더의 「AI 추천」 버튼 → 모달 → 매뉴얼 / 코드 source 토글:

  • 매뉴얼 source — 등록된 매뉴얼 1건 또는 모든 매뉴얼의 fragment 를 LLM 에 넘겨 BusinessTerm 후보 N 개 추출. 한국어 시스템 프롬프트 + JSON 배열 응답 강제. 이미 등록된 fqn 은 「이미 등록됨」 뱃지 + disabled.
  • 코드 source — 매뉴얼 0건이어도 사용 가능 (cold-start 도구). JPA @Column + 필드명 + Javadoc 을 합성해서 LLM 에 넘김. ID/created/updated 같은 메타 컬럼은 자동 제외.

추천 결과는 체크박스 멀티 선택 → 「선택 항목 등록」 → bulk-add → 자동 새로고침. 사용자가 모든 용어를 직접 타이핑할 필요 없음.

LLM 호출 graceful degrade — Anthropic API key 가 없거나 SDK 가 설치 안 돼 있으면 「추천 받기」 버튼이 503 응답을 반환하고, 다른 기능은 정상 동작.

필수Phase 5 — 용어 ↔ 코드 매핑 확정
탭 용어 매핑
  1. 용어를 클릭하면 우측에 자동 후보 리스트 가 뜸. 각 후보는 source (exact / alias / embedding / llm) 와 confidence 표시.
  2. 각 후보의 「확정」 / 「거부」 버튼으로 사람이 검토.
  3. 자동 후보가 만족스럽지 않으면 「수동 매핑」 폼으로 source_fqn (BusinessTerm) + target_fqn (Java 클래스/필드) 직접 입력.
  4. 한 번 확정한 매핑도 「거부로 변경」 가능 (양방향 토글). 스캔 다시 돌려도 사람이 확정한 것은 유지됨.
선택Phase 6 — 갭 큐 (매뉴얼 + 용어 + 매핑이 어느 정도 쌓였을 때)
탭 갭 큐

코드와 매뉴얼이 같은 개념을 다르게 주장하는 지점, 한쪽에만 존재하는 개념을 자동 검출합니다.

  • missing_in_manual — 코드에는 있는데 기준서가 비어 있음. 매뉴얼 작성 todo.
  • missing_in_code — 기준서에는 있는데 코드 구현이 없음. 누락 기능 / 데드 룰 의심.
  • conflict — 양쪽 다 있는데 숫자/연산자/단위 등이 다름. AST diff 로 증거 표시.

각 갭을 클릭하면 우측에 증거 (코드 스니펫 + fragment 텍스트) 가 표시되고, 「매뉴얼 보기」 / 「코드로 점프」 / 「영향 분석으로 점프」 크로스-네비게이션 가능.

주의 — 매뉴얼이 0 개면 갭 큐는 거의 비어 있음. 이건 정상 동작.

선택Phase 7 — 역탐색 (BusinessTerm 이 등록된 후 가능)
탭 역탐색
  1. BusinessTerm 이름 또는 alias 를 입력 → BFS 로 binding → 코드 노드 → 호출자까지 한 번에 수집.
  2. 결과 노드를 클릭하면 「영향 분석」 탭으로 자동 이동, target_fqn 자동 prefill.

"사람이 도메인 단어 하나만 알 때 → 코드의 모든 관련 위치 즉시 확인" 에 필요.

역탐색 / 영향 분석 / DI 그래프 / 갭 큐 + AST diff / Term resolver 4-stage / 매뉴얼 업로드+파싱 완료 이전 phase 누적.

5. 다음 우선순위 — v2 시점

P1~P5 완료 (2026-04-25) — 사용자 답변에 기반한 5 개 작업 모두 종결. 53/53 회귀 PASS, TS clean, E2E (cold→load→reset, write→ingest→list) 검증 완료.

제안되는 다음 단계 (사용자 결정 필요) :

  1. 실제 데모 코드로 풀 사이클 검증 — 사용자가 만들고 있는 Slab 데모 코드가 도착하면, Repository 등록 → 코드 분석 → 매뉴얼 작성 → AI 추천 → 매핑 확정 → 갭 큐 5건 검증 → 역탐색 까지 한 번에 돌려보기. 이게 데모 시연의 골든패스.
  2. In-app 시작하기 가이드 (반나절) — 첫 방문 시 modal 또는 사이드바 onboarding tour 로 본 HTML 가이드 핵심 5단계를 안내. 사이드 HTML 문서를 보여줘야만 사용 가능한 현 상태에서 벗어남.
  3. 「AI 추천」 모달 폴리시 — 추천 받은 후 「수정 후 등록」 (필드 인라인 편집), 「추가 매뉴얼/repo 합산」 옵션 등. 단순 등록 뿐 아니라 사용자 검수 워크플로우 강화.
  4. 매뉴얼 작성 에디터 폴리시 — 커서 위치 삽입 (현재는 끝에 append 만), 자동완성 (term=/rule= 옆에서 ghost suggestion), Monaco 또는 CodeMirror 로 교체 (syntax highlight + line number).
  5. auto-link 자동 재실행 — 매뉴얼 작성 탭에서 「저장 + 인제스트」 후 gaps_api auto-link 를 자동 호출 (현재 demo_api 만 자동 갱신, 일반 ingest 는 사용자가 「갭 큐」 탭에서 「자동 링크 재계산」 수동 클릭 필요).

1번 (실데모 검증) 이 가장 가치 있고, 그 결과를 보고 2~5번 순서를 다시 정하는 게 합리적.
