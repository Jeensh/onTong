1. 왜 이 문제가 어려운가 — drama DNA

레거시 modernization 이 일반적인 코드 리팩토링과 다른 이유. 우리가 의도적으로 "victim 코드" 에 박아둔 6 종류 drama DNA.

① 같은 도메인의 4 alias chaos

품종 (= product kind) 이 4 컬럼명으로 흩어짐:

  • CustomerStd.PRODUCT_NAME_CD
  • SdProductivityStd.PROD_KIND_CD
  • HrSpec.PRODUCT_TYPE_CD
  • 그 외 PROD_TYPE_CD / KIND_CD 등

→ 같은 의미인데 검색·매핑 못 묶음. 사람이 일일이 매핑하면 5,000+ class × 평균 10 컬럼 = 50K 매핑.

② 자바독 / 매뉴얼 부재

운영 코드 주석은 // 2018-09-12 정XX: ... 같은 변경 이력만. 의미 설명은 없음.

매뉴얼이 있어도 stale (실제 코드 동작과 다름).

→ 코드 자체가 유일한 ground truth. 자바독 의존 도구는 0.4 이하 정확도.

③ 다형성 dispatch (factory / interface)

룰엔진 fallback 가 List<RuleAction> 에 다수 구현 + instanceof + cast + 메서드 호출. static 분석으로만 추적 가능 (runtime 데이터 없으면 답 없음).

→ 우리 차별: CallSiteAnalyzer 7-case 정적 분석 + 모호 case 만 사용자 큐.

④ Magic literal + 운영 history

예: DEFAULT_PRODUCTIVITY = 0.95 — 2017 0.90 → 2019 0.92 → 2021 0.95 변경 이력. 0.50 (안전 하한) / 1.0 (안전 상한) 같은 magic literal.

→ AnchorBinding 으로 literal 자체를 도메인 의미와 연결.

⑤ 8 공정 8자리 string

confirmedPlantCd 가 8자리 char string. 자리 i (0~7) ↔ 공정 (SM/HR/HRF/CR/ANL1/ANL2/GAL/CRF). ' ' = 비활성.

코드 한 줄: if (confirmedPlantCd.charAt(i) == ' ') continue;

→ 단순 string 이지만 도메인적으로 "8 공정 활성/비활성" 의 표현. ontology 가 이 의미를 잡아야 시뮬 가능.

⑥ 운영 이슈 누적 + 보류 패치

예: P-2018-0721 "실수율 과다 → 분할수 폭주" + P-2020-0834 "std 1.05 등록 → 누적값 비정상".

보류 패치는 코드 주석으로 남음 (// if (p.compareTo(MAX) > 0) ...).

→ ontology 의 BusinessRule 또는 Action.metadata 에 그대로 보존 → 시뮬 시 "보류 패치 적용 케이스" 분기 가능.

핵심 통찰
드라마 DNA 가 많은 코드일수록 우리 도구의 가치가 큼. "깔끔한 코드는 이미 modernization 됐다". 온톨로지 + 매핑은 "사람이 일일이 읽어 의미를 잡아주던 시간" 을 자동화하는 도구.

2. 도메인 — slab-design (철강 SCM)

"demo repo" 로 사용하는 slab-design 시스템의 핵심. 단어가 처음이라도 21-step 알고리즘 흐름은 이해 가능하도록.

도메인 한 줄

철강 제조 SCM 의 slab(슬랩) 설계 — 고객 주문 들어오면 어떤 크기 / 무게 / 화학 성분의 중간 제품 (slab) 을 몇 개 만들지 결정. 21-step 알고리즘으로 폭/길이/단중/공정 별 실수율 계산.

21-step 알고리즘 (간략)

SdDesigner.java 의 메인 흐름. step 별로 1~3 Action 호출.

Step 1 초기화 (confirmedPlantCd 8자리 검증) Step 2~4 주문 데이터 정리 (om/os/qd/chemical 합성) Step 5 단중하한 = max(EdgingMin, HrMinWgt, CustomerStd.pkgWgtLow, ...) ← Customer 룰엔진 Step 6 단중상한 = min(EdgingMax, HrMaxWgt, CustomerStd.pkgWgtHigh, ...) ← Customer 룰엔진 Step 7 maxSplit = ceil(secondWgtHigh / orderWgtHigh / productivity) Step 6/9/13 productivity = cumulativeProductivity(8 공정 활성 자리 lookup 결과의 곱) ← Productivity Step 14~21 분할수 / slab 개수 / 폭 / 길이 결정 + slab 결과 저장

Customer / Productivity 는 21-step 의 fallback 룩업 데이터. 8 표준 중 마지막 2 개 (다른 6: HrSpec, CastSpec, EdgingSpec, EdgingGroup, HrMinWgt, HrMaxWgt).

3. 솔루션 큰 그림 — 3 Section

onTong 은 한 화면에 3 Section 으로 나뉘어 있고, 같은 도메인 그래프를 공유합니다.

SECTION 1

Wiki — 도메인 가이드

사람이 읽는 자연어. AI 채팅 (RAG) + 위키 페이지 작성 / 편집.

우리 솔루션의 입구. 도메인 처음 보는 사람에게 가르쳐줌.

완성 상태. 진행 중 작업 없음.

SECTION 2 ★ 메인

Modeling — 코드 ↔ 도메인 매핑

Code Layer (자바 mirror) + Domain Layer (BusinessTerm) + Mapping Layer (TR / Action / AnchorBinding).

"이 컬럼은 도메인 의미상 무엇" 을 자동 추천 + 사용자 합의로 채움.

진행 중 (Round 6 — Customer/Productivity 풀 사이클).

SECTION 3

Simulation — 한국어 Python 시뮬

ChangeSpec 입력 → ontology 매핑 활용해 Python 함수 자동 생성 → RestrictedPython sandbox 실행 → output diff.

도메인 룰 변경 영향 측정. 통과 시 Java PR 자동.

설계 합의 완료. 구현 진행 중 (Section 2 self-validation 부터).

같은 그래프 공유 — 핵심 통합 포인트

3 Section 이 모두 같은 ontology graph 위에서 작동:

  • Wiki 의 한 페이지 = ontology 의 한 BusinessTerm 에 link
  • Modeling 의 한 매핑 = Wiki 페이지 + 코드 위치 + 시뮬 시나리오에 연결
  • Simulation 의 한 시나리오 = ontology Action + 입력 fixture + expected output
왜 한 그래프가 중요한가
별 시스템이면 매번 ontology 재구축. 한 그래프면 사용자가 한 곳 합의 → 다른 두 Section 자동 활용.

4. Section 1 — Wiki (도메인 가이드)

이미 완성된 영역. 깊이 들어가지 않고, 다른 두 Section 과 어떻게 연결되는지만.

5.2 — Code Layer (Java 충실 mirror)

Java 코드를 가능한 그대로 mirror. 도메인 노이즈 (framework / infra / 비즈니스 무관) 도 일단 다 잡고, 나중에 role 분류로 거름.

CodeFieldname, type, annotationsJpo 의 @Column 도 보존

★ CallSiteAnalyzer 7-case (D3=A+)

Java polymorphism 의 dispatch 를 정적 분석으로 추적:

  1. Case 1 SINGLE_IMPL — interface 의 구현체가 1 개 → 자동 결정
  2. Case 2 INSTANCEOF_GUARD — instanceof 분기로 cast → body AST 분석
  3. Case 3 ANNOTATION — @Service / @Component 의 단일 구현 → 자동
  4. Case 4 FACTORY_BRANCH — factory 메서드의 분기 → AST 분석
  5. Case 5 GENERIC — generic type 의 dispatch → 사용자 큐
  6. Case 6 STRATEGY_MAP — Map<Key, Action> 룩업 → 사용자 큐
  7. Case 7 REFLECTION — Class.forName / getMethod → 사용자 큐

Case 1~4 자동, Case 5~7 사용자 큐 + LLM 추천 보조.

5.3 — Domain Layer (BusinessTerm)

BusinessTerm — 2 kind + facets

BusinessTerm:
  fqn          str          # 예: term.scm.shared.customer
  label        str          # 한국어 — "고객사"
  description  markdown
  domain       str          # 예: scm.shared
  kind         "atomic" | "composite"
  parts        list[BusinessTerm.fqn]  ## composite 만
  facets       dict {
                 is_abstract:    bool
                 is_interface:   bool
                 is_root_entity: bool
                 struct_like_hint: bool
                 enum_values:    list[str]   ## atomic enum 일 때
                 ...
               }
  inheritance  parent_fqn?              ## extends
  composition  composed_of: list        ## composes (DAG)
  confirmed    bool                     ## 사용자 합의?

kind 의 의미

  • atomic — 더 분해 안 되는 도메인 의미 단위 (cmp, org, customer, productivity, ...). 코드의 한 컬럼 / 한 enum / 한 literal 에 직접 매핑.
  • composite — 여러 atomic + facets 의 묶음 (CustomerStd, Order, Slab, ...). 코드의 한 entity (= class) 와 PRIMARY 매핑.

Inheritance + Composition (DAG)

BusinessTerm 끼리 두 가지 관계:

  • extends — IS-A. 자식이 부모의 parts/facets 를 자동 inherit.
  • composes — HAS-A. 다른 term 을 부분으로 가짐.

둘 다 사이클 검출. Resolver.effective_parts 가 자식 우선 override.

미해결
extends 시 effective_parts 의 정확한 override 규칙은 design-gaps #3.

5.4 — Mapping Layer (TR + Action + Realization + AnchorBinding)

TypeRealization — 코드 ↔ 도메인 다리

TypeRealization:
  term_fqn       BusinessTerm.fqn
  code_type_fqn  CodeType.fqn
  scope          "PRIMARY" | "PARTIAL"
  partial_parts  list[atomic.fqn]?         ## PARTIAL 일 때, 어느 atomic 들이 매핑되는지
  confirmed      bool
scope의미예시
PRIMARYcomposite term 이 한 entity (class) 의 통째 mirror. 모든 entity field 가 composite 의 part / facet 으로 매핑.term.scm.std.customer_std → CustomerStdEntity
PARTIALatomic 또는 composite 가 entity 의 일부 field 만 매핑. 한 entity 는 여러 atomic 의 PARTIAL 매핑 동시 가능.term.scm.shared.customer → CustomerStdJpo.customerCd field
우리 차별 ★
PARTIAL 의 매핑 단위 = (atomic, codeType, codeField) 3-tuple. 같은 컬럼명도 entity 별 독립 매핑 가능 → drama DNA "4 alias chaos" 자동 처리. Foundry 의 MDO multiplicity 와 정반대 (그건 PARTIAL 금지).

Action — 동사 (도메인 행위)

Action:
  fqn              str       # 예: action.scm.product.cumulative_productivity
  label            str       # 한국어 — "누적 실수율 계산"
  description      markdown
  kind             "pure_function" | "workflow"
  params           list[{name, term_fqn, type}]
  return_term_fqn  str?
  effects          list[{op, target_term, target_attr}]   ## kind=workflow 만
  realizations     list[Realization]                       ## 다형성
  precondition     markdown
  postcondition    markdown
  metadata         dict {
                     known_issues: ["P-2018-0721 ...", "P-2020-0834 ..."]
                     default_value: 0.95
                     ...
                   }

Action.kind 의 invariant (Q9=C)

  • pure_function — 입력 → 출력. effects 비어있어야 함. 예: cumulativeProductivity.
  • workflow — 상태 변경. realizations 비어있어야 함. effects 정형 (op + target_term + target_attr).

Realization — Action 의 코드 구현 (다형성 ★)

Realization:
  action_fqn        Action.fqn
  code_method_fqn   CodeMethod.fqn          # 어느 메서드가 이 Action 을 구현
  dispatch_source   "single_impl" | "annotation" | "instanceof_guard"
                    | "factory_branch" | "generic" | "strategy_map"
                    | "reflection" | "user_confirmed" | "static_unresolved"

한 Action 의 realizations 가 여러 row → polymorphism 표현. 시뮬 시 dispatch table 자동 생성.

AnchorBinding — fragment-level 매핑 (Q4'=A)

method body 내부의 한 표현식 / 분기 / literal 자체를 도메인 의미와 연결. 메서드 단위 매핑 없이도 anchor binding 가능.

AnchorBinding:
  code_method_fqn  CodeMethod.fqn
  anchor_kind      "field" | "field_access" | "param" | "local"
                   | "return" | "branch" | "literal"
  fragment_path    str    # 예: "method body line 25 col 8-22, AST node BinaryOp"
  binding_target   {
                     kind: "term" | "action" | "rule"
                     fqn:  ...
                   }
  confidence       0.0 ~ 1.0
  confirmed        bool
구체 예시 — cumulativeProductivity body
// Java 코드
public BigDecimal cumulativeProductivity(...) {
    if (confirmedPlantCd == null || confirmedPlantCd.length() < 8) {
        return DEFAULT_PRODUCTIVITY;            // ← AnchorBinding(literal): 0.95 → term.scm.product.default_productivity
    }
    BigDecimal product = BigDecimal.ONE;
    for (int i = 0; i < 8; i++) {
        if (confirmedPlantCd.charAt(i) == ' ') continue;   // ← AnchorBinding(branch): 8 공정 활성 검증
        BigDecimal p = lookupOrDefault(
            cmpCd, orgCd, PROC_CODES[i], ...);          // ← AnchorBinding(literal): PROC_CODES → term.scm.shared.proc.enum_values
        product = product.multiply(p);          // ← AnchorBinding(local): product → 누적 실수율
    }
    return product;
}

5.5 — VerificationLevel (state machine 6 단계 ★ 우리 차별)

매핑의 신뢰도를 6 단계로 표현. 시뮬 가능성 / PR 자동 가능성의 게이트.

단계조건의미
1. UNMAPPEDTR 미존재코드만 있고 도메인 매핑 X
2. DRAFTTR 존재 (자동 또는 사용자)매핑 시도됨, 검증 X
3. SIGNATURE_LOCKEDsignature_hash 매칭 + Action.params 일치signature 안정
4. BODY_ANCHORED모든 anchor 등록 + body_hash 일치body 까지 매핑 OK
5. SIM_VERIFIEDSimulationScenario 통과시뮬 시 정확성 확인됨
6. PR_PROVENJava draft PR 통과 (CI 통과 + 사람 review)실제 코드 변경 검증됨

1~4 는 자동 계산. 5~6 은 외부 신호 (시뮬 / PR).

왜 이게 차별인가
Palantir Foundry 는 ontology 신뢰도 표현이 약함 (있다 / 없다). 우리는 6 단계 + 자동 진행 → "신뢰도 calibration" 을 시스템에 박아둠. 시뮬 + PR 자동 흐름의 게이트.
미해결
SIM_VERIFIED 의 자동 결정 기준은 design-gaps #1.

12. FAQ — 외부 관계자 예상 질문

Q1. 이 도구를 도입하려면 코드 변경이 필요한가?

아니. 코드는 그대로. import 시 정적 분석만. 단 Java 21 + Spring Boot 3.x 처럼 표준 스택이면 자동 분석 정확도 높음.

Q2. 5,000+ 클래스 / 100K entity 가정에서 graph viz 가 작동하나?

전체 노드 렌더 X. 검색 우선 + 1~N hop subgraph navigation. 노드 100+ 면 경고 + auto-collapse. ELK 풀 마이그 후 117 노드 = 13ms / 5K 노드 = 88ms (compound). React Flow + ELK Layered.

Q3. AI 비용은?

자동 recommend = 1 회 import 시 LLM 약간 (1 repo ~$1). Authoring AI 풀 사이클 = ~$5 / entity. 5K entity 풀 자동화 = 비현실 → Pareto 운영 (핵심 50~500 entity 만).

Q4. 시뮬 결과 정확도는?

VerificationLevel 6 단계로 calibration. SIM_VERIFIED = 사용자 정의 시나리오 통과. PR_PROVEN = 실제 코드 변경 검증. 단계 별 신뢰도 다름.

Q5. 한국어 변수 / 도메인어가 다른 언어에도 적용되나?

Python PEP-3131 unicode identifier 활용. 일본어 / 중국어도 가능. 단 시뮬 코드 가독성은 그 언어 운영자에게.

Q6. "도메인 룰 변경" 의 범위는?

현재 단계: literal 변경 (0.95 → 0.93) / branch 변경 (PRIORITY ASC → DESC). param 변경은 SIGNATURE_LOCKED 해제 → 재confirm 흐름.

Q7. Section 1 Wiki 와 Section 2 Modeling 이 분리된 이유?

역할 분리. Wiki = 사람이 읽는 가이드 (자연어 자유). Modeling = 기계가 다루는 ontology (정형 데이터). 같은 그래프 공유 (BusinessTerm fqn link).

Q8. Round 5/6 식 인터뷰가 필수인가? 자동 recommend 만으로 충분?

자동 recommend 는 ~ DRAFT 단계 (label + kind + 기본 매핑). BODY_ANCHORED + SIM_VERIFIED 까지 가려면 사용자 합의 필요. 핵심 entity 50~500 만 인터뷰, 나머지는 자동.

Q9. 다른 산업 (금융 / 의료 / ...) 에 적용 가능?

도메인 의존 부분 = atomic / composite 정의 + Action label. 그 외 (Java 분석 + ontology 모델 + 시뮬 sandbox + Authoring AI) 는 도메인 무관. 도메인 마다 새 인터뷰 필요 (혹은 기존 ontology base 차용).

Q10. 운영 비용 (서버 / DB / LLM API)?

SQLite 단일 파일 (Q1=A) + FastAPI + Next.js. 단일 노드에서 5K class 처리 가능. LLM API = Authoring AI 사용 시 발생. Workbench / Wiki / 시뮬 자체는 LLM 없이 작동.
