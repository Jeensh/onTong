1. 왜 Round 2 는 '개념 브릿지' 인가

Round 1 로 "OrderController.place() 를 바꾸면 어디에 영향 가는가?" 는 답할 수 있게 됐다. 하지만 팀 리더의 실제 질문은 이쪽에 더 가깝다:

  • "안전재고 로직을 이번 스프린트에 수정해야 하는데, 손대야 할 모든 코드 위치를 알고 싶다."
  • "기준서에 'MOQ 제약' 이 있는데, 이게 실제로 어느 메서드/테이블에서 강제되는지?"
  • "'공정별 납기 계산' 프로세스를 누가 담당하고, 어떤 서비스가 그 책임을 구현하는가?"

이 질문들의 공통점 : 출발은 한국어 비즈니스 용어, 도착은 코드 위치. Round 1 스키마만으로는 "안전재고" 라는 한국어 검색어가 SafetyStockCalculator.compute() 또는 safety_stock 컬럼으로 연결되지 않는다. 브릿지 레이어가 필요하다.

Round 1 vs Round 2 역할 분리

Round 1 — 코드 그래프

사용자 : 개발자, 아키텍트

질문 : "X.method 를 바꾸면 뭐가 깨지나?"

해소 : 결정적 BFS (QueryEngine.impact)

LLM 개입 : 없음

Round 2 — 개념 브릿지

사용자 : 팀 리더, PM, 도메인 전문가

질문 : "'안전재고' 는 어디에 구현돼 있나?"

해소 : term → 개념 노드 → 다수 코드 위치 (QueryEngine.reverse_lookup)

LLM 개입 : term resolver 최후 fallback + 매핑 초안 제안 (사람 승인 전제)

핵심 설계 원칙 — Round 2 의 브릿지는 데이터 계층 이지 LLM 응답 이 아니다. 임베딩/LLM 은 매핑 등록·갱신 시점에만 호출돼서 BusinessTerm / ConceptBinding 에 고정된다. 사용자 쿼리 시점에는 결정적 그래프 조회로 답한다 (Round 1 동작 철학 계승).

2. 노드 — 1차 2종 + 이월 2종

BusinessTerm BusinessRule BusinessProcess (Phase D 이월) Role (Phase D 이월)
1차 범위 축소 — Q4 D + Q7 경계 B 반영 — Round 2 에서는 BusinessTerm + BusinessRule 만 구현한다. BusinessProcess 와 Role 은 PoC 과잉으로 판단, Phase D 에 이월. 실제 Slab sample 에서 다단계 프로세스 또는 Spring Security role 이 Reverse Lookup 맥락에 필요하다고 드러날 때 재도입.

2-1. BusinessTerm — 비즈니스 용어 · 도메인 개념

한국어/영어 용어 단위. "안전재고", "BOM", "MOQ", "LeadTime" 같은 것. 팀 리더가 일상 대화에서 쓰는 단어들.

@dataclass(frozen=True)
class BusinessTerm:
    qualified_name: str         # e.g. "inventory.safety_stock"
    canonical_label: str        # "안전재고" (권장 표기)
    aliases: list[str]           # ["Safety Stock", "안전 재고", "SS"]
    domain: str                 # "inventory" / "order" / "bom"
    description: str            # 1~3 줄 정의
    embedding: list[float] | None  # canonical_label + description 임베딩
    source: str                 # manual / extracted / llm_proposed
    confirmed: bool             # 사람이 승인했는가

2-2. BusinessRule — 비즈니스 규칙 · 제약

"안전재고 이하로 떨어지면 발주", "MOQ 미만 주문 거부", "납기일은 공휴일을 건너뛴다" 등 검증 가능한 명제. Round 1 의 메서드 precondition / postcondition 와 연결된다.

@dataclass(frozen=True)
class BusinessRule:
    qualified_name: str         # e.g. "inventory.rule.below_safety_stock_triggers_order"
    statement: str              # "현재 재고 < 안전재고 이면 자동 발주"
    terms_ref: list[str]         # 사용된 BusinessTerm FQN 들
    severity: str               # "hard" | "soft"
    source: str                 # 기준서 조항 / 담당자 인터뷰 / 코드 추론
    confirmed: bool

2-3. BusinessProcess — Phase D 이월

"주문 접수 → 신용 체크 → 재고 할당 → 배송 지시" 같은 다단계 절차는 Round 2 에서 제외. 단어·명사 단위 (BusinessTerm) 로 Reverse Lookup 요구 대부분 충족된다는 판단. Slab sample 에서 시퀀스 맥락이 필요하다고 확인되면 Phase D 에서 노드+PART_OF/NEXT_STEP 엣지로 재도입.

2-4. Role — Phase D 이월

역할/권한/페르소나 축도 PoC 범위에서 과잉. Spring Security @PreAuthorize 가 실제 코드에서 Reverse Lookup 질의 패턴으로 나올 때 재도입 (1차 스코프 : 권한 = Spring Security role 1:1, 조직/페르소나는 그 이후).

3. 브릿지 엣지

엣지 kind방향의미대표 속성
REALIZES Method/Class → BusinessTerm 이 코드가 해당 비즈니스 개념을 실현 한다 confidence, source ∈ {manual, name_match, embedding, llm}, scope ∈ {primary, partial}
VALIDATES Method → BusinessRule 이 메서드가 해당 규칙을 검증 한다 (runtime assertion 또는 branch condition) confidence, source, rule_position ∈ {guard, assert, throw}
DERIVED_FROMRound 3 예약 BusinessTerm → ManualDocument 이 용어가 어느 기준서 조항에서 나왔나 doc_ref, section, quote
1차 엣지 2종 (+1 예약) — Q4 D + Q7 경계 B 반영으로 PART_OF / RESPONSIBLE_FOR 후보 엣지는 삭제 (대상 노드 Process/Role 이 Phase D 이월). DERIVED_FROM 은 Round 3 (기준서 인제스트) 연결 지점으로 스키마에만 예약.

3-1. REALIZES 엣지의 3대 축

Reverse Lookup 정확도의 핵심이 이 엣지. 세 속성을 묶어서 본다:

source

  • manual — 사람이 직접 승인
  • name_match — 메서드/클래스 이름 정규식 매칭
  • embedding — 임베딩 유사도 ≥ cutoff
  • llm — LLM 초안 (승인 전)

confidence

  • manual → 1.0
  • name_match → 0.85~0.95
  • embedding → 코사인 유사도 값
  • llm → 0.4 (승인 필요 강제)

scope Q3 B 결정

  • primary — 해당 개념의 주 구현. 메서드당 최대 1 개 (유일성 제약).
  • partial — 일부 관여 (보조/검증/로깅). 개수 제한 없음.

동일 메서드가 여러 개념에 걸리면 : 1 개 primary + N 개 partial. QueryEngine edge_kinds={REALIZES} + scope=primary 필터로 "주 구현만" 결정적 질의 가능.

3-2. VALIDATES — Q5 A→B 단계적 확장

1단계 (A, 즉시) : @AssertTrue / @Valid / @NotNull 류 Bean Validation 어노테이션 + Javadoc @precondition / @postcondition 주석 → BusinessRule 로 자동 VALIDATES 엣지. 보수적, 오탐 거의 0.

2단계 (B, A 안정화 후) : validateXxx(...) / checkYyy(...) / ensureZzz(...) 메서드 이름 패턴 → source=name_match, confidence=0.85 로 자동 제안 (사람 승인 큐).

3단계 (C, Phase D+) : if (x < min) throw ... branch 패턴 LLM 해석. 비용·품질 편차로 일단 제외.

4. 1:N 구조 + method-level 1급 시민

Rewrite 대상 — 기존 backend/modeling/mapping/mapping_models.py 는 Mapping.code 가 단일 qualified name. 이 구조로는 "안전재고" → 5개 메서드 + 3개 엔드포인트 + 2개 테이블 매핑을 표현할 수 없다.

4-1. 재설계 원칙

  1. BusinessTerm 은 노드 — `Mapping` 이 값 컨테이너가 아님. 이게 핵심 전환.
  2. ConceptBinding 은 엣지 — BusinessTerm ↔ Code entity (method / class / field / table / endpoint) 각각 별도 REALIZES 엣지.
  3. method-level 이 기본 granularity — class-level 바인딩은 옵션. 대부분의 "안전재고 로직" 은 메서드 단위에 떨어져 있음.
  4. 한 메서드 → 여러 BusinessTerm 에 REALIZES 허용 (Q3 B) — primary 는 메서드당 1 개, partial 은 제한 없음. 예: OrderService.place() 가 "주문" primary + "신용 체크" partial + "재고 할당" partial.

4-2. 신/구 비교

# 현재 (단일 매핑)
class Mapping:
    term: str
    code: str  # 단일 FQN
    granularity: str

# Round 2 (N:N 브릿지)
class BusinessTerm:           # 노드 (위 §2-1)
    ...

class ConceptBinding:          # 엣지 DTO (REALIZES)
    term_fqn: str           # BusinessTerm 참조
    code_fqn: str           # Method/Class/Field FQN (Round 1)
    confidence: float
    source: str             # manual / name_match / embedding / llm
    scope: str              # primary / partial
    created_at: datetime
    confirmed_by: str | None  # 승인자 (사람만 저장, llm=None)

5. 워킹 예시 — "안전재고" Reverse Lookup

5-1입력 — 사용자 질문

팀 리더 (한국어 입력):

reverse_lookup("안전재고")
5-2Term Resolution (§6 체인)
  1. exact : BusinessTerm.canonical_label 에 "안전재고" 직접 매칭 → inventory.safety_stock 노드 찾음. 종료.
  2. (미스 시) alias 조회 → 임베딩 유사도 → LLM fallback.
5-3BusinessTerm → Code (REALIZES outgoing)

result = engine.reverse_lookup("inventory.safety_stock", edge_kinds={"REALIZES"})
# BusinessTerm 노드에서 outgoing REALIZES 만 따라감

기대 결과:

  • com.acme.inventory.InventoryService.checkAndOrder() — scope=partial, conf=0.92 (embedding)

  • db_schema.table.safety_stock — scope=primary, conf=1.0 (manual)

사용자가 "이 중 SafetyStockCalculator.compute() 를 바꾸면 뭐가 영향?" 이라고 follow-up:

result2 = engine.impact(ImpactQuery(
    target_fqn="com.acme.inventory.SafetyStockCalculator.compute",

# Round 1 incoming BFS 로 callers 추적 (B8-1)

→ Round 1 + Round 2 체인 : 비즈니스 용어로 들어와서 코드 그래프로 파고 들어감.

6. Term Resolution Chain

Rewrite 대상 — 기존 backend/modeling/query/term_resolver.py 는 한국어 alias 가 하드코딩. 이걸 데이터 드리븐 으로 바꾼다.

6-1. 체인 4단계

  1. exact — canonical_label 직접 매칭. 테이블 룩업 O(1).
  2. alias — BusinessTerm.aliases 에 포함 여부. 대소문자/공백 정규화. 여전히 O(1) (역인덱스).
  3. embedding — 쿼리 임베딩 vs 전체 BusinessTerm.embedding cosine. top-K (기본 3) + cutoff (기본 0.78).
  4. LLM fallback — 위 3단에서 매칭 없거나 모두 cutoff 미만 → LLM 에 "이 용어가 어느 BusinessTerm 과 가장 가까운가? 또는 신규 제안?" 요청. 결과는 반드시 사람 승인 대상으로 큐잉 (자동 바인딩 X).

6-2. 데이터 드리븐 원칙

# AS-IS (한국어 하드코딩)
ALIASES = {
    "안전재고": "safety_stock",
    "안전 재고": "safety_stock",
    ...  # 파일 하나에 쌓임 — drift
}

# TO-BE (BusinessTerm.aliases 에서 끌어옴)
def build_alias_index(terms: list[BusinessTerm]) -> dict[str, str]:
    index = {}
    for t in terms:
        for a in [t.canonical_label, *t.aliases]:
            index[_normalize(a)] = t.qualified_name
    return index

6-3. 임베딩 스택

  • 대상 임베딩 텍스트 — canonical_label + "\n" + description
  • 모델 — §9 Q6 에서 결정 (OpenAI text-embedding-3-small 기본 제안 vs 로컬)
  • 저장 — chromadb 재활용 (Wiki 에서 이미 검증됨) 또는 Neo4j vector index
  • 갱신 시점 — BusinessTerm 신규 등록 / aliases 변경 시 비동기 재계산
Q6 A 결정 — 임베딩 스택 = OpenAI text-embedding-3-small + chromadb (Wiki 와 통일). 저장소 전환 대비해 C3 에서 EmbeddingProvider Protocol 로 추상화 (구현체 OpenAIChromaProvider).

7. 코드↔개념 매핑 운영 — 자동 제안 + 사람 승인

매핑 품질이 Reverse Lookup 정확도를 정한다. 자동화와 수동 관리의 경계선이 제일 민감.

7-1. 파이프라인 Q1 A 결정

  1. 수동 seed (Q1 A 확정) — 팀 리더가 핵심 용어 20~50 개 먼저 등록 (canonical_label + aliases + 대표 코드 위치 1~2 개). CLI 또는 YAML 배치 제공.
  2. 자동 제안 엔진 — Seed 이후 :
    • 메서드/클래스 이름 ↔ canonical_label / aliases 정규식 매칭 → source=name_match 제안
    • 메서드 docstring + Java doc ↔ term.description 임베딩 유사도 ≥ cutoff → source=embedding 제안
    • LLM 에 "이 메서드는 어떤 BusinessTerm 을 실현하나?" 질의 → source=llm 제안
  3. 제안 큐 — 제안된 모든 매핑은 confirmed=False 로 저장. Reverse Lookup 결과에 기본 포함 안 함.
  4. 사람 승인 UI — 팀 리더가 제안 큐를 주기적으로 검토, Approve / Reject / Edit (scope 조정). 승인 시 confirmed=True + confidence=1.0.
  5. 활성 룩업 — Reverse Lookup 은 confirmed=True 만 기본. include_unconfirmed=True 옵션으로 자동 제안도 같이 볼 수 있음 (개발 모드).

7-2. 제안 트리거 시점

시점트리거범위
BusinessTerm 신규 등록자동 — 전 코드 인덱스에서 매칭 제안 생성name_match + embedding
코드 변경 (B9 E2E 이후)자동 — 변경 파일의 엔티티 대상으로 재제안name_match + embedding
사람 요청"이 용어 매핑 후보 더 제안해줘" UI 버튼LLM
Q7 (d) 재검증 결정 — PR 영향 범위만 재검증. GitHub webhook / PR 이벤트에서 변경 파일의 엔티티를 추출 → 그 엔티티 대상 REALIZES 엣지만 재검증 + 사라진 엔티티 참조 엣지는 stale=True 마킹. 야간 배치·매 커밋 훅은 비용·노이즈로 제외.

8. Reverse Lookup 질의 시뮬레이션

8-1. 시나리오 A — 단일 용어

# 입력
from backend.modeling.query import term_resolver, query_engine
