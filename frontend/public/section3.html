CHAPTER 01 · 왜

정적 도구는 답을 주지 못합니다.

"이 BR 이 정말 발동하나?" "이 anchor 가 진짜 실행 경로에 있나?" — 코드 정적 분석이나 LLM 요약은 이 질문에 답하지 못합니다. 실행해 봐야 합니다.

Section 1 에서 위키와 페르소나로 도메인 지식을 정리했고, Section 2 에서 온톨로지 모델링으로 코드를 1급 노드 (Action / Realization / AnchorBinding / BusinessTerm) 로 끌어올렸습니다.

Section 3 의 임무 — 모델링 결과를 실 코드 수준 시뮬에서 검증합니다. ChangeSpec 한 번 보내면, 1,514 actions 의 ontology 가 어느 method 가 dispatch 되고, 어느 BR 이 enforce 되며, 어느 anchor 가 hit 되는지 — 그래프로 따라갑니다.

정적 도구의 한계 3가지
왜 시뮬이 필요한지 — 구체적으로

1. 다형성 dispatch 무지 — 정적 분석은 interface.method()가 어느 구현체로 dispatch 되는지 런타임에 결정되는 것을 알 수 없습니다. Section 2 의 Realization 매핑이 이를 1:1 명세화하고, Section 3 가 실제 input runtime type 으로 dispatch 정합성을 확인합니다.

2. BR 발동 시점 불명 — 코드에서 if (x < 1200) throw...가 어떤 시나리오에서 발동하는지 정적으로는 모릅니다. ChangeSpec 의 atomic_overrides 로 경계값을 던져 BR enforcer 가 실행되는지 시뮬에서 직접 확인합니다.

3. Anchor stale 위험 — 코드 line 이 바뀌면 anchor 의 line 정보가 stale 될 수 있습니다. POST /anchor-invalidate로 일괄 무효화 + 영향 받는 action 목록 자동 식별합니다.

"코드를 읽지 말고, 실행하세요." — Section 3 의 1줄 정의.
CHAPTER 02 · 무엇을

ChangeSpec 한 번 → SimResult 의 verdict.

코드 변경 / 시나리오 입력 / Customer fixture — 어떤 입력이든 ChangeSpec 한 객체로 압축됩니다. 결과는 SimResult — verdict, BR 증거, anchor 증거, dispatch trace. 

# spec 03 §1.1 — 한 번의 호출
POST /api/simulation/runs
{
  "change_spec": {
    "action_fqn": "action.scm.std.match_customer_limit_for_order",
    "atomic_overrides": { "...inputs[0]<Order>.width": 1180 },
    "scenario_fixture": { "metadata": { "scenario_kind": "regression" } }
  }
}

# 응답
{
  "run_id": "run-...",
  "status": "completed",
  "verdict": "sim_verified",
  "br_evidence": [{ "br_fqn": "rule.scm...customer_find_first_match", "outcome": "passed" }],
  "anchor_evidence": [{ "anchor_id": "anchor_customer_first_match", "outcome": "hit" }],
  "suggested_promotion": "BODY_ANCHORED → SIM_VERIFIED"
}
verdict 3가지 — sim_verified / sim_violation / inconclusive
각 verdict 가 의미하는 것

sim_verified — 모든 직접 BR passed + 모든 expected anchor hit + 모든 frame dispatch_consistent=True. scenario_kind 가 regression / boundary / integration 이면 BODY_ANCHORED → SIM_VERIFIED 진급 권장.

sim_violation — BR 위반 (severity=error) 1건 이상. 기존 verification level 이 SIM_VERIFIED 였으면 SIM_VERIFIED → BODY_ANCHORED 다운그레이드 권장.

inconclusive — anchor miss / dispatch_consistent=False / sandbox 실패 등. design-gap 영향. verification level 변동 없음.

    { "evidence_kind": "anchor", "ontology_source": "AnchorBinding", ... }

}
4 evidence kind — action / realized_method / br / anchor
각 trace 가 보여주는 것

action — root ChangeSpec.action_fqn 이 ontology 에 등록된 Action 인지. fqn / kind / declared_on_term / sub_actions count / realizations count.

realized_method — dispatch 된 Java method 가 어느 Realization 에서 왔는지. confirmed / confidence / applies_to_code_type_fqn.

br — BREvidence 의 br_fqn 이 Action.preconditions / postconditions / (transitive) 중 어느 쪽인지.

anchor — AnchorEvidence 의 anchor_id 가 어느 AnchorBinding 인지. anchor_locator (예: "matches.isEmpty() → null") / target_slot.

CHAPTER 05 · Java ↔ Python

두 응답을 5 카테고리로 분류해 비교합니다.

raw payload 를 그대로 보여주지 않습니다. matched / mismatched / java_only / python_only / both_null 5 카테고리로 분류해 어느 필드가 일치하고 어느 필드가 한쪽에만 있는지 한 눈에 보입니다. 

# spec 03 §3.1 — POST /api/simulation/differential/run 의 새 응답
{
  "summary": "38 matched / 2 mismatched / 1 java_only / 0 python_only",
  "matched_count": 38,
  "mismatched_count": 2,
  "java_only_count": 1,
  "python_only_count": 0,
  "both_null_count": 5,        // noise 자동 제거

    { "path": "weight", "java": 13000, "python": 13500, "category": "mismatched" },
    { "path": "java_only_field", "java": "X", "python": null, "category": "java_only" }
  ],
  "java_payload_normalized": { ... },     // null/empty 제거
  "python_payload_normalized": { ... }
}
왜 Python 응답에 null 이 많았는가? 그리고 어떻게 해결했는가
2026-05-10 STEP 3f-1 변경사항

원인 — Python pipeline_full 이 일부 step 만 구현해 결과 dict 에 None 필드 다수. Java SdDesigner 는 BigDecimal 결과를 풍부하게 채움. 두 schema 가 다른 추상화 레벨이라 같은 path 에서 한쪽이 None.

해결 — _normalize_payload() helper 가 두 raw 응답에서 null / 빈 문자열 / 빈 dict / 빈 list 를 재귀 제거. _classify_diff()가 5 카테고리로 분류. UI 가 카테고리별로 필터링 가능.

both_null은 noise 라 field_diffs 리스트에서 자동 제외 (count 만 보고). 사용자가 의미있는 차이만 본다.
