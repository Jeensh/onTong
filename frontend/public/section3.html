CHAPTER 01 · 왜

정적 도구 4가지 한계.
그리고 그걸 해결하는 4가지 무기.

룰 변경의 영향을 코드만 보고 알 수는 없습니다. "이 규칙을 0.95 → 0.92 로 바꾸면 결과가 뭐가 깨지나?" — 정적 분석은 답하지 못합니다. Section 3 는 실행 + 차이 비교 + 온톨로지 근거 로 답합니다.

① 정적 분석은 "실수율 0.95 → 0.92" 의 영향을 못 본다

코드 검사기 / lint / type checker 는 룰의 의미 를 모릅니다. 값을 바꿨을 때 어떤 주문이 다른 결과를 받는지, 어느 분기가 안 도달하는지 알 수 없습니다.

해결: Hypothesis 자동 케이스 100건 → 격리 샌드박스 실행 → 라인 커버리지 + 실패 케이스 자동 보고.

② 코드와 도메인 용어가 따로 산다

"실수율" 이라는 도메인 용어가 자바의 어느 메서드에 매핑되는지, 실수율 변경 시 어떤 단계가 영향받는지 — 비개발자는 추적 불가능.

해결: OntologyBridge + Section 2 의 Action/Realization 그래프 → 용어 → 단계 → 코드 위치까지 한 번에 뽑아냄.

③ Java↔Python 결과를 비교하기가 어렵다 (필드 다름 + null 많음)

Java SdDesigner.design() 와 Python pipeline_full 은 같은 입력에도 다른 schema 로 응답 → raw payload 비교가 어렵고 한쪽 None 인 필드가 많음.

해결 (STEP 3f): 5 카테고리 분류 (matched / mismatched / java_only / python_only / both_null) + payload normalize (null/빈값 재귀 제거) + summary 한 줄 요약.

④ "이 결과가 ontology 의 어디에서 나왔지?" 추적 불가

시뮬 결과가 신뢰할 만한지 — 어떤 Action / Realization / BR / Anchor 에서 derive 됐는지 명시되지 않으면 결과를 못 믿음. 사용자가 "이게 진짜 ontology 기반이야?" 의심.

해결 (STEP 3f): /ontology-evidence endpoint + UI 토글 — 모든 SimResult / 모든 패널 결과 옆에 4 evidence kind trace 표시. 근거 섹션 ↓

CHAPTER 03 · 근거

모든 결과는 4 evidence kind 로 추적됩니다.

각 SimResult 항목을 Section 2 ontology 의 어느 entity 에서 derive 했는지 명시. UI 의 "📚 온톨로지 근거 보기" 토글이 이 4 카드를 보여줍니다.

① Action 노드

Action

시뮬레이션의 root entity. action_fqn 으로 식별.

source: mapping_layer.schema.Action
facade: get_action(fqn)
data: kind / label / declared_on_term / sub_actions / realizations
② Realization → Java

Realization

Action 을 실제 Java 메서드로 매핑. confirmed + confidence 메타 포함.

source: mapping_layer.schema.Realization
facade: action.realizations
data: code_method_fqn / applies_to / confirmed / confidence / scope
③ BusinessRule

BR (pre / post-condition)

Action 이 만족해야 할 비즈니스 룰. precondition / postcondition 으로 구분.

source: Action.preconditions / postconditions
facade: get_action(fqn).preconditions
data: br_fqn / kind (pre|post) / action_fqn
④ AnchorBinding

AnchorBinding

Java 코드 라인에 anchor 된 실 측정점. anchor invalidation 으로 재시뮬 트리거.

source: mapping_layer.schema.AnchorBinding
facade: get_anchor_bindings_for_action(fqn)
data: anchor_locator / code_method_fqn / target_action / target_slot

CHAPTER 05 · 비교

Java ↔ Python 5 카테고리 분류 (STEP 3f).

이전엔 raw payload 만 dump → 한쪽 None 인 필드 가득. 이제 5 카테고리 + summary 한 줄로 즉시 파악.

카테고리의미UI 표시
matched 두 값이 같음 (numeric tolerance 1e-9 / 1e-12 적용) summary count + 색상 emerald
mismatched 양쪽 값 있는데 다름 — 진짜 차이 diff 테이블에 우선 노출
java_only Java 만 값 있음 — Python schema 누락 또는 None schema gap 표시
python_only Python 만 값 있음 — Java schema 누락 또는 None schema gap 표시
both_null 양쪽 None — diff list 에서 자동 제외 (count 만) noise 제거
응답 신규 필드 — DifferentialResult
  • summary 한 줄 — "38 matched / 2 mismatched / 1 java_only / 0 python_only"
  • matched_count / mismatched_count / java_only_count / python_only_count / both_null_count
  • java_payload_normalized / python_payload_normalized — null/빈 문자열/빈 dict/빈 list 재귀 제거. UI 가 원본 vs 정리본 둘 다 노출 가능.
